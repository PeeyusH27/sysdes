<TLDR>
Start from the **access pattern**, not the product: how is data written and read, and what must never go wrong? Postgres for anything transactional; specialised stores only where it's the wrong shape, fed from **one source of truth** by CDC or the outbox.
</TLDR>

## Why one database isn't enough

A B-tree database with transactions is superb at "move money correctly" and hopeless at "store a 2 GB video" or "rank 50M products by relevance to a typo". So at scale you run several stores (**polyglot**), and keeping them consistent is the hard part.

Ask of each kind of data:

- **Writes:** how many per second, single- or multi-row, atomic?
- **Reads:** by key, range, text, or aggregated over millions of rows?
- **Correctness:** is a lost or stale value an annoyance (a view count) or a bug (a balance)?

## One shop, many stores

A typical shop runs six stores, each owning different facts. Step through a page view, a price change and a checkout.

<FlowDiagram spec={polyglotShop} />

Postgres, MongoDB, Redis and S3 are written directly (S3 by the browser, via a presigned URL). Elasticsearch and ClickHouse are **derived** from the change stream: lose either, and you rebuild it by replaying Kafka or re-snapshotting the source.

## Stores compared

| Store | Strong at | Weak at | How it scales |
|---|---|---|---|
| Relational (PostgreSQL, MySQL) | Transactions, constraints, joins, ad-hoc queries | Horizontal write scale | Replicas, then sharding (Citus, Vitess) |
| Document (MongoDB) | Flexible entities read together | Cross-document transactions and joins | Built-in sharding |
| Key-value (Redis, DynamoDB) | Single-key lookups at huge scale | Queries other than by key | Partition by key |
| Wide-column (Cassandra, ScyllaDB) | Write-heavy, time-ordered partitions | Ad-hoc queries, joins | Partition key + clustering |
| Object storage (S3, GCS) | Large blobs, cheap and durable | Low-latency small reads | Effectively unlimited |
| Search (Elasticsearch, OpenSearch) | Full text, relevance, facets | Being the source of truth | Shards + replicas |
| Time-series / columnar (ClickHouse, TimescaleDB) | Aggregations over time and events | Point updates | Partition by time |
| Graph (Neo4j) | Multi-hop relationship queries | Bulk analytics | Hard to shard well |

## Principles

<Steps>
  <Step title="Model by access pattern first">
    List queries before tables: "latest 20 orders for a user" and "revenue per day" want different stores, keys and indexes. In key-value and wide-column stores the key **is** the query: a new access pattern needs a new table or index.
  </Step>
  <Step title="One source of truth per fact">
    Write each fact to one store; derived stores (search, analytics, caches) are fed by CDC or the outbox and can be rebuilt. Never write the database and the search index in one request: one write will eventually fail.
  </Step>
  <Step title="OLTP and OLAP don't share a database">
    A dashboard scanning 100M rows starves checkout on the same primary; stream changes into a columnar store for analytics.
  </Step>
  <Step title="Boring by default">
    Every store is one more thing to back up, monitor, secure and wake up for; add one only when an access pattern demands it.
  </Step>
</Steps>

### Wide-column (Cassandra)

One table per query. The partition key picks the node; the clustering key sorts rows inside it.

```sql
-- Wide-column (Cassandra CQL): partition by (sensor, day) so no partition grows without bound;
-- rows inside a partition are sorted by time
CREATE TABLE readings (
  sensor_id text, day date, ts timestamp, value double,
  PRIMARY KEY ((sensor_id, day), ts)
) WITH CLUSTERING ORDER BY (ts DESC);
```

### Search and time-series

Elasticsearch (search) and ClickHouse or Timescale (metrics, events) are fed from the main DB through events.

<CodeBlock src="snippets/search-events.js" />

On the analytics side, the table is append-only and columnar:

```sql
-- ClickHouse: append-only events, partitioned by month, sorted for the common filter
CREATE TABLE events (
  ts DateTime, user_id UInt64, type LowCardinality(String), sku String, price Decimal(10, 2)
) ENGINE = MergeTree
PARTITION BY toYYYYMM(ts)
ORDER BY (type, ts);

-- Orders per hour over the last day: scans two columns, not whole rows
SELECT toStartOfHour(ts) AS hour, count() AS orders
FROM events
WHERE type = 'order_placed' AND ts > now() - INTERVAL 1 DAY
GROUP BY hour ORDER BY hour;
```

## Interview questions

<FollowUps>
  <FollowUp q="Where do chat messages live?">
    Wide-column (Cassandra or Scylla), partitioned by conversation and sorted by sequence: write-heavy, read by recency. At moderate scale, MongoDB with a `{conversationId, seq}` index.
  </FollowUp>
  <FollowUp q="Why not store images in Postgres?">
    Blobs bloat the database, backups and replication, and a CDN can't serve them; keep them in object storage, with the key and metadata in Postgres.
  </FollowUp>
  <FollowUp q="How do you keep Elasticsearch in sync?">
    CDC (Debezium) or the outbox feeds an idempotent indexer, and periodic full reindexes rebuild it from the source of truth.
  </FollowUp>
  <FollowUp q="SQL or NoSQL?">
    Let the access patterns decide: cross-row transactions, constraints or ad-hoc queries mean SQL; known-key access beyond one primary, or a per-record shape, means NoSQL.
  </FollowUp>
  <FollowUp q="When would you pick DynamoDB over Postgres?">
    When access patterns are few, known and key-based at large or spiky scale (carts, sessions, device state) and you want no servers to run; not for joins, ad-hoc reporting or multi-entity invariants.
  </FollowUp>
</FollowUps>
