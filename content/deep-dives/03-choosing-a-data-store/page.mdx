<TLDR>
Start from the **access pattern**, not the product: how is this data written, how is it read, and what must never go wrong? Default to Postgres for anything transactional, then add specialised stores (object storage, key-value, search, analytics) where Postgres is the wrong shape. Keep **one source of truth per fact** and feed every derived store from it with CDC or the outbox.
</TLDR>

## Why one database isn't enough

Every store is a bundle of trade-offs. A B-tree database with transactions is excellent at "move money correctly" and poor at "store a 2 GB video" or "rank 50M products by relevance to a typo". At scale you end up with several stores, a **polyglot** architecture, and the hard part becomes keeping them consistent.

Ask three questions about each kind of data:

- **Writes:** how many per second, single-row or multi-row, must they be atomic?
- **Reads:** by key, by range, by text, or aggregated over millions of rows?
- **Correctness:** is a lost or stale value an annoyance (a view count) or a bug (a balance)?

## One shop, many stores

A typical e-commerce site uses six stores, each owning different facts. Step through a page view, a price change and a checkout.

<FlowDiagram spec={polyglotShop} />

Postgres, MongoDB, Redis and S3 are written directly (S3 by the browser, through a presigned URL). Elasticsearch and ClickHouse are **derived**: they are filled from the change stream, so if either is lost or corrupted you rebuild it by replaying Kafka or re-snapshotting the source.

## Stores compared

| Store | Strong at | Weak at | Examples | How it scales |
|---|---|---|---|---|
| Relational | Transactions, constraints, joins, ad-hoc queries | Horizontal write scale | PostgreSQL, MySQL | Replicas, then sharding (Citus, Vitess) |
| Document | Flexible entities read together | Cross-document transactions and joins | MongoDB | Built-in sharding |
| Key-value | Single-key lookups at huge scale | Queries other than by key | Redis, DynamoDB | Partition by key |
| Wide-column | Write-heavy, time-ordered partitions | Ad-hoc queries, joins | Cassandra, ScyllaDB | Partition key + clustering |
| Object storage | Large blobs, cheap and durable | Low-latency small reads | S3, GCS | Effectively unlimited |
| Search | Full text, relevance, facets | Being the source of truth | Elasticsearch, OpenSearch | Shards + replicas |
| Time-series / columnar | Aggregations over time and events | Point updates | ClickHouse, TimescaleDB | Partition by time |
| Graph | Multi-hop relationship queries | Bulk analytics | Neo4j | Hard to shard well |

## Principles

<Steps>
  <Step title="Model by access pattern first">
    List the queries before the tables. "Latest 20 orders for a user" and "revenue per day" want different stores, keys and indexes. In key-value and wide-column stores, the key **is** the query: you can't add a new access pattern later without a new table or index.
  </Step>
  <Step title="One source of truth per fact">
    Each fact is written to exactly one store. Derived stores (search, analytics, caches) are fed by CDC or the outbox and can always be rebuilt. Never write to the database and the search index from the same request: one of the two writes will eventually fail.
  </Step>
  <Step title="OLTP and OLAP don't share a database">
    A dashboard query that scans 100M rows will starve the checkout queries on the same primary. Stream changes into a columnar store and run analytics there.
  </Step>
  <Step title="Boring by default">
    Every extra store is another thing to back up, monitor, secure and wake up for. Add one only when the access pattern clearly needs it.
  </Step>
</Steps>

### Key-value (Redis, DynamoDB)

Use for sessions, counters, and single-key lookups at very high speed. Model around access patterns because there are no joins. In DynamoDB, a composite key (`pk = USER#42`, `sk = ORDER#2025-06-01…`) turns "latest orders for a user" into one sorted range read.

### Wide-column (Cassandra)

Design one table per query. The partition key decides which node holds the rows; the clustering key sorts them inside the partition. Adding the day to the partition key keeps any one partition from growing without bound.

```sql
-- Wide-column (Cassandra CQL): partition by (sensor, day) so no partition grows without bound;
-- rows inside a partition are sorted by time
CREATE TABLE readings (
  sensor_id text, day date, ts timestamp, value double,
  PRIMARY KEY ((sensor_id, day), ts)
) WITH CLUSTERING ORDER BY (ts DESC);
```

Keep files and media here, never in the database. Store only the key in your DB and let clients upload directly with presigned URLs.

### Search and time-series

Elasticsearch gives full-text search; ClickHouse or Timescale handle metrics and events. Feed them from the main DB through events and never treat them as the source of truth.

<CodeBlock src="snippets/search-events.js" />

On the analytics side, a columnar table is append-only, partitioned by time and sorted by what you filter on:

```sql
-- ClickHouse: append-only events, partitioned by month, sorted for the common filter
CREATE TABLE events (
  ts DateTime, user_id UInt64, type LowCardinality(String), sku String, price Decimal(10, 2)
) ENGINE = MergeTree
PARTITION BY toYYYYMM(ts)
ORDER BY (type, ts);

-- Orders per hour over the last day: scans two columns, not whole rows
SELECT toStartOfHour(ts) AS hour, count() AS orders
FROM events
WHERE type = 'order_placed' AND ts > now() - INTERVAL 1 DAY
GROUP BY hour ORDER BY hour;
```

<Callout kind="warning" title="Common mistakes">
- Choosing a NoSQL store "for scale" before you know the access patterns.
- Storing images or PDFs as database blobs.
- Writing to the database and the search index from the same request (dual writes).
- Running dashboards on the primary that serves checkout.
- Treating Elasticsearch or a cache as the source of truth.
</Callout>

## Interview questions

<FollowUps>
  <FollowUp q="Where do chat messages live?">
    In a wide-column store (Cassandra or Scylla) partitioned by conversation and sorted by sequence: write-heavy and read by recency. Or MongoDB with a `{conversationId, seq}` index at moderate scale.
  </FollowUp>
  <FollowUp q="Why not store images in Postgres?">
    Large blobs bloat the database, backups and replication, and you can't serve them from a CDN. Store them in object storage and keep only the key and metadata in Postgres.
  </FollowUp>
  <FollowUp q="How do you keep Elasticsearch in sync?">
    CDC (Debezium) or the outbox publishes changes, and an indexer consumes them idempotently. Rebuild with periodic full reindexes, and never treat the index as the source of truth.
  </FollowUp>
  <FollowUp q="SQL or NoSQL?">
    Start from the access patterns. If you need transactions across rows, constraints or ad-hoc queries, use SQL. If every access is by a known key at a scale one primary can't handle, or the shape varies per record, a NoSQL store fits. Many systems use both, each for the data it suits.
  </FollowUp>
  <FollowUp q="When would you pick DynamoDB over Postgres?">
    When the access patterns are few, known and key-based, the scale is large or spiky, and you want no servers to operate: carts, sessions, user settings, device state. Not when you need joins, ad-hoc reporting or multi-entity invariants.
  </FollowUp>
</FollowUps>
