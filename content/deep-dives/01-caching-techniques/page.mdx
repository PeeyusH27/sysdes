<TLDR>
Pick a caching pattern by what you can live with when the cache is **stale, cold or down**. Default to cache-aside with delete-on-write and a TTL; write-through trades slower writes for fresh reads, write-behind risks data loss for fast writes.
</TLDR>

## Why the technique matters

A cache is a copy, and copies drift. Each pattern decides **who re-syncs it, and when**, and that fixes three things:

- **Staleness:** how long readers see the old value.
- **Cold start:** what an empty cache does after a deploy or restart.
- **Cache loss:** slower, wrong, or lost data?

TTLs, eviction and stampedes: see the [Caching lesson](/learn/caching). Add an L1, refresh-ahead or a Bloom filter only for a measured problem.

## The read path: cache-aside

Cache first, database on a miss. Pick **cache hit** or **cache miss** in the diagram.

<SequenceDiagram spec={cacheAsideSequence} />

A hit is one Redis round trip, about 1 ms. A miss pays the check, the query **and** the `SET`, so a cold cache is slower than none. TTL jitter stops keys written together from expiring together.

## The write path: update, then delete

Update the database, then **delete** the key; the next read loads the truth.

<SequenceDiagram spec={writeInvalidate} />

Why not `SET` the new value? Two concurrent writers can land cache writes in the opposite order to their database writes, pinning the old value until the TTL; a delete can't be out of order. The last race, a slow reader refilling an old value, is bounded by the TTL.

## Six patterns compared

| Pattern | Write path | Staleness | If the cache dies |
|---|---|---|---|
| Cache-aside | App writes DB, deletes key | Until delete or TTL | Slower, still correct |
| Read-through | — | Same as cache-aside | Depends on the library |
| Write-through | DB + cache, synchronously | Minimal | Correct |
| Write-behind | Cache now, DB later in batches | The DB lags | **Unflushed writes are lost** |
| Write-around | DB only | None (next read loads) | Correct |
| Refresh-ahead | — | Up to the refresh interval | Correct |

**Start with cache-aside**: simple, any store, and losing Redis only costs latency. Switch only when:

- users must see their own write: write-through, or delete and read from the primary;
- the DB can't keep up with writes and a few seconds' loss is fine (counters, metrics): write-behind;
- data is written once, rarely read (audit logs, old orders): write-around keeps it out of the cache;
- a few hot, predictable keys hurt on a miss: refresh-ahead stops them expiring under load.

### Bloom filter against penetration

Ids that don't exist always miss the cache and hit the database: a cheap attack. A Bloom filter of real ids rejects them in memory first.

<CodeBlock src="snippets/bloom-filter.js" />

Two independently seeded hashes with a murmur-style finaliser spread the 7 bit positions evenly. With 100K keys in 1M bits, the test sees about 0.65% false positives, as `(1 − e^(−kn/m))^k` predicts, and zero false negatives.

### Eviction policy

When memory fills, Redis evicts by `maxmemory-policy`. A pure cache can evict any key.

```ini
# redis.conf for a pure cache: evict any key by recency (or allkeys-lfu by frequency).
# Use volatile-lru when some keys have no TTL and must never be evicted.
maxmemory 2gb
maxmemory-policy allkeys-lru
```

<Callout kind="warning" title="Common mistakes">
- Adding a cache without measuring the hit ratio before and after: a low ratio adds a hop and saves nothing.
</Callout>

## Interview questions

<FollowUps>
  <FollowUp q="Cache-aside or write-through?">
    Cache-aside by default: losing the cache only costs latency. Write-through when users must read their own writes and can afford slower writes.
  </FollowUp>
  <FollowUp q="How do you keep in-process caches consistent across 50 instances?">
    Pub/sub invalidations **plus** short L1 TTLs, because a missed fire-and-forget message leaves a stale copy until the TTL. Use L1 only where seconds of staleness are fine.
  </FollowUp>
  <FollowUp q="When is write-behind acceptable?">
    When losing seconds of updates is fine (view counters, analytics), never for money or orders. A shutdown flush shrinks the window; a crash still loses the buffer.
  </FollowUp>
  <FollowUp q="What's the difference between cache-aside and read-through?">
    Who runs the miss path: your code in cache-aside, the cache's own loader (a library, a CDN, DAX) in read-through.
  </FollowUp>
  <FollowUp q="Requests for non-existent ids are hammering your database. What do you do?">
    Cache "not found" briefly, put a Bloom filter of real ids in front, and rate-limit callers if it looks like an attack.
  </FollowUp>
</FollowUps>
