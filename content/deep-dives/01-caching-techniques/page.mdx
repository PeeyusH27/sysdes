<TLDR>
Choose a caching pattern by what you can live with when the cache is **stale, cold or down**. Cache-aside with delete-on-write and a TTL is the default; write-through buys fresh reads with slower writes; write-behind buys fast writes by risking data loss. Reach for an in-process L1, refresh-ahead or a Bloom filter only when you've measured the problem each one solves.
</TLDR>

## Why the technique matters

Every cache answers the same question differently: **who keeps the copy in sync with the database, and when?** That one decision fixes three behaviours you'll be asked about in an interview:

- **Staleness:** how long a reader can see the old value after a write.
- **Cold start:** what happens when the cache is empty after a deploy or a restart.
- **Cache loss:** whether losing the cache makes you slower, wrong, or loses data.

The [Caching lesson](/learn/caching) covers where caches live, TTLs, eviction and stampedes. This page compares the patterns side by side and gives you code for each.

## The read path: cache-aside

The app talks to the cache and the database itself. Pick **cache hit** or **cache miss** to step through each branch.

<SequenceDiagram spec={cacheAsideSequence} />

A hit costs one Redis round trip (about 1 ms). A miss costs the Redis check **plus** the database query **plus** the `SET`, so a cold cache is slower than no cache at all. The jittered TTL stops keys written together from expiring together.

## The write path: update, then delete

On a write, change the database first, then **delete** the key. The next read misses and loads the truth.

<SequenceDiagram spec={writeInvalidate} />

Why delete rather than `SET` the new value? With two concurrent writers, the cache writes can land in the opposite order to the database writes, leaving the older value cached until the TTL. A delete can't be "out of order": whichever happens last, the next read reloads from the database. The one remaining race (a slow reader refilling an old value) is bounded by the TTL; the Caching lesson shows it step by step.

## Six patterns compared

| Pattern | Read path | Write path | Staleness | If the cache dies | Use for |
|---|---|---|---|---|---|
| Cache-aside | App checks the cache, loads the DB on a miss, fills the cache | App writes the DB, deletes the key | Until the delete or TTL | Slower, still correct | The default |
| Read-through | The cache loader fetches from the DB | — | Same as cache-aside | Depends on the library | CDN, caching libraries |
| Write-through | Always fresh | Write DB + cache synchronously | Minimal | Correct | Read-after-write heavy data |
| Write-behind | From the cache | Cache now, DB later in batches | The DB lags | **Unflushed writes are lost** | Counters, metrics |
| Write-around | The first read after a write misses | DB only | None (next read loads) | Correct | Write-once, rarely-read data |
| Refresh-ahead | Hot keys always hit | — | Bounded by the refresh interval | Correct | Hot, predictable keys |

How to pick in practice:

- **Start with cache-aside.** It is simple, works with any store, and losing Redis only costs latency.
- **Users must see their own write immediately?** Write-through, or delete the key and read your own write from the primary.
- **The database can't keep up with writes, and losing a few seconds is fine?** Write-behind (view counters, analytics).
- **Written once, rarely read** (audit logs, old orders)? Write-around, so it never pollutes the cache.
- **A handful of very hot keys whose misses hurt?** Refresh-ahead, so they never expire under load.

### Write-behind (write-back)

Write to the cache now and flush to the database later in batches. Very fast writes, but a crash can lose unflushed data.

<CodeBlock src="snippets/write-behind.js" />

The naive version clears the buffer **before** the database call, so a failed flush silently drops the batch, and a slow flush can overlap the next one. This version puts the batch back on failure without overwriting newer values, and the `flushing` flag keeps flushes from running in parallel.

Single flight collapses concurrent misses **inside one process**. With 50 app instances, up to 50 rebuilds can still reach the database at once. Across instances, combine it with the Redis `SET lock NX` pattern from the [Caching lesson](/learn/caching).

### Two-level cache (L1 + L2)

An in-process map answers in microseconds and absorbs hot keys before they reach Redis. Every instance holds its own copy, so invalidations fan out over pub/sub, and a short L1 TTL covers the messages pub/sub drops.

### Refresh-ahead

Once 80% of a key's TTL has passed, the next read triggers a background refresh. Readers keep getting the cached value and the key never actually expires while it's hot.

<CodeBlock src="snippets/refresh-ahead.js" />

### Bloom filter against penetration

Lookups for ids that don't exist always miss the cache and always hit the database: a cheap attack. A Bloom filter of every real id answers "definitely not present" in memory, so those requests stop before the cache.

<CodeBlock src="snippets/bloom-filter.js" />

The two hash functions use independent seeds and a murmur-style finaliser, so the 7 bit positions are spread evenly. The test adds 100K keys to 1M bits and measures about 0.65% false positives, matching the formula `(1 − e^(−kn/m))^k`, with zero false negatives.

### Eviction policy

When memory is full, Redis evicts according to `maxmemory-policy`. For a pure cache, let it evict any key.

```ini
# redis.conf for a pure cache: evict any key by recency (or allkeys-lfu by frequency).
# Use volatile-lru when some keys have no TTL and must never be evicted.
maxmemory 2gb
maxmemory-policy allkeys-lru
```

<Callout kind="warning" title="Common mistakes">
- Write-behind for data you can't afford to lose (orders, payments).
- Updating the cache on write instead of deleting the key.
- An in-process cache with no TTL, trusting pub/sub alone.
- Treating single flight as cluster-wide protection.
- Caching without measuring the hit ratio first and after.
</Callout>

## Interview questions

<FollowUps>
  <FollowUp q="Cache-aside or write-through?">
    Cache-aside is the default: simple, and resilient to cache loss because the database is always the source of truth. Use write-through when reads right after writes dominate and you can afford slower writes.
  </FollowUp>
  <FollowUp q="How do you keep in-process caches consistent across 50 instances?">
    Publish invalidations over pub/sub **and** keep L1 TTLs short, because pub/sub is fire-and-forget: an instance that misses a message keeps its stale copy until the TTL. Or only use L1 for data that tolerates seconds of staleness.
  </FollowUp>
  <FollowUp q="When is write-behind acceptable?">
    When losing a few seconds of updates is fine (view counters, analytics) and the store benefits a lot from batching. Never for money or orders. Flush on graceful shutdown to shrink the loss window, and accept that a crash still loses the buffer.
  </FollowUp>
  <FollowUp q="What's the difference between cache-aside and read-through?">
    The behaviour is the same; the difference is who runs the miss path. In cache-aside your code loads the database and fills the cache. In read-through the cache (a library, a CDN, DAX) has a loader and does it for you, so app code only talks to the cache.
  </FollowUp>
  <FollowUp q="Requests for non-existent ids are hammering your database. What do you do?">
    Cache the "not found" result briefly (negative caching) and put a Bloom filter of real ids in front of the cache, so ids that are definitely absent are rejected in memory. Rate-limit the callers if it looks like an attack.
  </FollowUp>
</FollowUps>
