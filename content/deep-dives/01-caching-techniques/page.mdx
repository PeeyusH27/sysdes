<TLDR>
Pick a caching pattern by what you can live with when the cache is **stale, cold or down**. Start with cache-aside.
</TLDR>

## Why the technique matters

A cache is a copy, and copies drift. Each pattern decides **who updates the copy, and when**. That sets how stale readers can be, what an empty cache does after a restart, and what you lose if it dies. More in the [Caching lesson](/learn/caching).

## The read path: cache-aside

Before walking to the archive room, glance at the notepad on your desk. A **cache** is that notepad: fast memory next to your app that holds the answers you ask for most.

With **cache-aside**, the app checks the cache first. A **hit** answers in about 1 ms. A **miss** goes to the database (about 50 ms), then saves the answer for next time. Pick hit or miss in the diagram.

<SequenceDiagram spec={cacheAsideSequence} />

Each saved answer gets a **TTL**, a timer that expires it. Add a little random jitter. Without it, a hot key that expires at noon sends all 5,000 reads a second to the database at once. That pile-up is a **stampede**.

**Do the sum first.** The **hit ratio** is the share of reads the cache answers. Take 10,000 reads a second:

| Hit ratio | Average read | Database sees |
|---|---|---|
| 50% | about 25 ms | 5,000 a second |
| 90% | about 6 ms | 1,000 a second |
| 99% | about 1.5 ms | 100 a second |

At 50% you added a hop and saved little. Aim for 90% or more.

**Skip the cache** when the database already answers in a few ms and holds up. Skip it for data read once, data that changes every second, and values that must never be stale (a balance). Fix the slow query or add an index first.

## The write path: update, then delete

When data changes, the notepad is wrong. Update the database, then **delete** the cached copy. The next read misses and loads the truth.

<SequenceDiagram spec={writeInvalidate} />

Why not overwrite it? Two writers at once can reach the cache in the opposite order to the database and pin the old value until the TTL. A delete can't be out of order.

Even a delete has a rare race. A slow reader loads the old price, the admin sets 12 and deletes the key, then the reader saves the old price. Shoppers see it until the TTL ends, so always set one.

## Six patterns compared

Each pattern answers one question: who keeps the copy fresh?

| Pattern | How it writes | If the cache dies |
|---|---|---|
| Cache-aside | App updates the DB, deletes the key | Slower, still correct |
| Write-through | App writes the DB and cache together | Still correct |
| Write-behind | Writes the cache now, the DB later | **Unflushed writes are lost** |
| Write-around | Writes the DB only | Still correct |

Two more: **read-through** is cache-aside where the cache itself loads misses. **Refresh-ahead** reloads hot keys before they expire.

In a flash sale, 20,000 order writes a second land in the cache. If it dies before it flushes, those orders are gone. Fine for view counts, never for orders.

**Start with cache-aside.** Losing the cache only costs speed. Switch only when:

- users must see their own write: write-through;
- the database can't keep up and losing a few seconds is fine (counters): write-behind;
- data is written once and rarely read (audit logs): write-around;
- a few hot keys hurt when they expire: refresh-ahead.

## Interview questions

<FollowUps>
  <FollowUp q="Cache-aside or write-through?">
    Cache-aside by default. Write-through when users must read their own writes.
  </FollowUp>
  <FollowUp q="How do you keep in-process caches consistent across 50 instances?">
    Pub/sub invalidations **plus** short L1 TTLs, since a missed message leaves a stale copy until the TTL.
  </FollowUp>
  <FollowUp q="When is write-behind acceptable?">
    When losing a few seconds is fine (view counters), never for money or orders.
  </FollowUp>
  <FollowUp q="What's the difference between cache-aside and read-through?">
    Who runs the miss path: your code in cache-aside, the cache's own loader in read-through.
  </FollowUp>
  <FollowUp q="Requests for non-existent ids are hammering your database. What do you do?">
    Cache "not found" briefly, add a Bloom filter of real ids, and rate-limit callers.
  </FollowUp>
</FollowUps>
