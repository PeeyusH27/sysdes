<TLDR>
Every new connection costs handshakes, auth and server memory, so **reuse** them: pool database connections, keep HTTP alive. Keep the pool **total** under `max_connections` (PgBouncer when instances multiply), put a **timeout** on every call, bound concurrency, shut down gracefully.
</TLDR>

## Why it matters

A connection isn't free: at a 50 ms round trip, DNS, TCP and TLS 1.3 burn **150 ms** before you've asked anything, PostgreSQL's SCRAM login adds more, and the server caps you (`max_connections` defaults to 100 in PostgreSQL).

Most load-related outages look alike: a pool runs dry, a call with no timeout hangs, or an unbounded `Promise.all` floods a dependency. The diagram plays a healthy pool, a pool running dry, and PgBouncer squeezing many app connections onto a few database ones.

## What each connection costs

| Connection | Setup | Server holds | Reuse with |
|---|---|---|---|
| TCP | 1 round trip | A socket and a file descriptor | Keep-alive |
| TLS 1.3 / 1.2 | +1 / +2 round trips, plus crypto | Session keys | Keep-alive, session resumption |
| HTTP/2 | One TCP + TLS for many requests | Streams on one connection | Multiplexing |
| HTTP/3 (QUIC) | 1 round trip for transport and TLS together | QUIC connection state | Multiplexing, 0-RTT resumption |
| PostgreSQL | TCP + TLS + auth: up to tens of ms | A whole process (a few MB) | A pool, then PgBouncer |
| MySQL | TCP + TLS + auth | A thread | A pool, ProxySQL |
| Redis | TCP + `AUTH`: under 1 ms nearby | A few KB | One shared, pipelined client |

## Pool sizing

Each instance opens its own pool, so the rule is about the **total**:

> instances × pool size ≤ `max_connections` − headroom (admin tools, migrations, cron jobs)

<StatTiles items={[{ label: "max_connections", value: "200" }, { label: "Reserved", value: "20", sub: "admin, migrations" }, { label: "App instances", value: "12" }, { label: "Pool per instance", value: "15", sub: "(200 − 20) ÷ 12" }]} />

Two more checks:

- **Big enough?** Little's law: busy connections = queries per second × time each holds a connection. 1,000 queries/s × 5 ms = **5**, so a pool of 15 has room for bursts.
- **Too big?** The PostgreSQL wiki heuristic for useful concurrent connections is `(cores × 2) + effective spindles`: about **17** on 8 cores. Past that you add context switching and lock contention, not throughput; many pools summing far beyond it call for PgBouncer.

Give every pool three timeouts: `connectionTimeoutMillis` (about 2 s, then fail fast), `idleTimeoutMillis`, and a server-side `statement_timeout` so a runaway query can't hold a connection forever.

## PgBouncer

A lightweight proxy speaking the PostgreSQL protocol: apps open hundreds of cheap connections to it, and it runs their work over a few real server connections.

| Mode | A server connection is held for | Good for | Breaks |
|---|---|---|---|
| Session | The whole client connection | Anything | Almost no multiplexing |
| Transaction | One transaction | Most web apps | Session state between transactions |
| Statement | One statement | Autocommit-only workloads | Multi-statement transactions |

Transaction mode is the usual pick. The catch: session-bound things (`SET`, session advisory locks, `LISTEN`, temporary tables) don't survive into the next transaction, so use `SET LOCAL` inside it. Named prepared statements need `max_prepared_statements` (PgBouncer 1.21 and later).

## Keep-alive

Node's `fetch` (undici) keeps connections alive by default, and so does the default HTTP agent since Node 19. Two problems still bite:

- **Ephemeral ports.** Without keep-alive, each closed outgoing connection sits in `TIME_WAIT` for 60 s on Linux. With 28,232 default ports, that's only about **470 new connections per second** to one destination before `connect` fails.
- **The idle-timeout race.** If the server closes idle sockets before the load balancer does, the LB sometimes sends a request down a closing socket: a 502. Keep the server's keep-alive timeout **longer** than the LB's (Node's default is 5 s; AWS ALB's is 60 s).

## Timeouts and deadlines

Without a timeout, one slow dependency ties up your sockets, pool slots and memory, and its outage becomes yours.

| Timeout | What it bounds | Typical setting |
|---|---|---|
| Connect | Opening TCP + TLS | 1–3 s |
| Pool acquire | Waiting for a pooled connection | 1–2 s, then fail fast |
| Request or statement | One call or query | A few times its p99 |
| Idle | An unused connection's lifetime | Shorter than the server's or LB's |
| Deadline | The whole request, across every hop | From the SLO, e.g. 2 s |

Fixed per-call timeouts don't add up across a chain. With **deadline propagation**, the edge sets one budget and every hop passes the remainder downstream (gRPC does this for you), so nobody works on a request whose caller already gave up.

## Concurrency limits

`Promise.all(ids.map(fetchUser))` over 10,000 ids fires 10,000 requests at once: it drains your pool, trips the downstream rate limit, or flattens the dependency. Use a fixed number of workers (the `mapLimit` snippet, or `p-limit`) and **bounded** queues, so overload becomes fast rejections, not unbounded memory and latency.

## File descriptors and ulimit

Every socket, file and pipe is a file descriptor: one per inbound connection, pooled outbound connection and open file. The default soft limit is often 1,024; past it, `accept` and `connect` fail with `EMFILE: too many open files`.

```bash
ulimit -n                                  # the current soft limit, often 1024
ls /proc/$(pgrep -n node)/fd | wc -l       # descriptors in use right now
# Raise it: LimitNOFILE=1048576 in the systemd unit, or --ulimit nofile=1048576 for Docker
```

## Graceful shutdown

Deploys restart every instance, many times a day; done badly, each drops in-flight requests and WebSockets.

<Steps>
  <Step title="Fail readiness">
    On `SIGTERM`, answer the readiness probe with 503 so the load balancer stops sending requests. In Kubernetes, a short `preStop` sleep lets the endpoint change spread.
  </Step>
  <Step title="Stop accepting and close idle sockets">
    `server.close()` stops new connections; `server.closeIdleConnections()` drops idle keep-alive sockets at once. WebSocket clients get close code 1001 and reconnect elsewhere, with jitter.
  </Step>
  <Step title="Finish in-flight work">
    Let running requests complete, then close database pools and flush logs and metrics.
  </Step>
  <Step title="Exit before the kill">
    Set a hard deadline a little under the orchestrator's grace period (30 s by default in Kubernetes), then exit.
  </Step>
</Steps>

## HTTP/2 multiplexing and HTTP/3

HTTP/1.1 runs one request at a time per connection, so browsers open about 6 per origin. **HTTP/2** multiplexes streams over one connection with compressed headers, but one lost TCP packet stalls them all (head-of-line blocking). **HTTP/3** runs over QUIC on UDP: independent streams, combined transport and TLS handshakes (0-RTT on resumption), and it survives a switch from Wi-Fi to mobile data.

The service-to-service trap: gRPC holds one long-lived HTTP/2 connection, so behind a layer-4 load balancer a client's traffic all hits one backend. Use a layer-7 (HTTP/2-aware) or client-side balancer.

## Interview questions

<FollowUps>
  <FollowUp q="We scaled from 10 to 30 app instances and Postgres started refusing connections. Why?">
    Each instance opens its own pool: 30 × 20 = 600 connections, far past `max_connections`. Size pools as `(max_connections − headroom) ÷ instances` and add PgBouncer in transaction mode.
  </FollowUp>
  <FollowUp q="Why can a bigger pool make things slower?">
    Past roughly the database's core count, extra connections only add context switching and lock contention; a small pool with a short queue serves more.
  </FollowUp>
  <FollowUp q="How do you deploy WebSocket servers without dropping users?">
    Fail readiness, send close 1001 (going away), and let clients reconnect elsewhere with jitter and resume from their last message id.
  </FollowUp>
  <FollowUp q="How would you size the connection pool?">
    Top down: the total at maximum autoscale fits under `max_connections` minus headroom. Bottom up: Little's law plus burst room, then a load test.
  </FollowUp>
  <FollowUp q="A downstream service got slow, and now our service is down too. What happened?">
    Calls without timeouts held sockets and pool slots until healthy traffic starved. Add timeouts inside a propagated deadline, a circuit breaker, a bulkhead pool per dependency and a fallback.
  </FollowUp>
</FollowUps>
