<TLDR>
Shard only when one primary can no longer hold the data or absorb the writes. The **shard key** matters more than the algorithm: pick one with high cardinality that matches your main query. Hash for an even spread, ranges for scans, a directory for multi-tenant "whales", and consistent hashing so that adding a node moves about 1/N of the keys instead of nearly all of them.
</TLDR>

## When to shard

Sharding is the last scaling step, not the first. It makes joins, transactions, unique constraints and schema changes harder forever. Before you shard, use up the cheaper options in roughly this order:

1. **Vertical scaling:** a bigger machine buys a lot (hundreds of GB of RAM, tens of thousands of writes per second).
2. **Indexes and query fixes:** most "the database is slow" problems are a missing index.
3. **Caching:** take reads off the database entirely.
4. **Read replicas:** scale reads, if you can tolerate replication lag.
5. **Archiving:** move cold rows (old orders, logs) to cheaper storage.

Shard when **writes** or **data size** outgrow one primary. Read load alone is rarely a reason.

## Choosing the shard key

The shard key decides which queries stay on one shard and whether the load spreads evenly. A good key:

- **Has high cardinality.** `country` has about 200 values, so you can never have more than 200 useful shards, and one country will dominate.
- **Spreads evenly.** No single value should own a large share of rows or traffic.
- **Matches the dominant query.** If most queries are "this user's orders", shard by `user_id` so they hit one shard.
- **Avoids hot ranges.** Timestamps and auto-increment ids put every new write on the same shard.

`user_id` (or `tenant_id` in SaaS) is the usual answer. When one key can't serve two big access patterns, store the data twice, keyed differently (orders by buyer **and** by seller).

## Strategies compared

| Strategy | Even spread | Range scans | Rebalancing cost | Extra hop | Typical use |
|---|---|---|---|---|---|
| Hash mod N | ✓ | ✗ | Moves ~all keys | No | Fixed shard count |
| Range | Risk of hot ranges | ✓ | Split or merge ranges | No | Time-series, ordered ids |
| Directory | Manual control | Depends | Move one tenant at a time | Cached lookup | Multi-tenant SaaS with "whales" |
| Consistent hashing (+ vnodes) | ✓ | ✗ | ~1/N of the keys | No | Caches, Dynamo-style stores |
| Rendezvous (HRW) | ✓ | ✗ | ~1/N of the keys | No | Small node sets, no ring to maintain |

Many real systems sidestep the rebalancing problem with **fixed logical partitions**: create far more partitions than machines (say 1,024), map keys to partitions with `hash % 1024` (which never changes), and move whole partitions between machines. Kafka, Elasticsearch, Redis Cluster (16,384 slots) and Cassandra's vnodes all work this way.

The difference grows with cluster size. With `hash % N`, a key stays put only when `hash mod N` equals `hash mod (N+1)`, so **N/(N+1)** of all keys move. With consistent hashing, only the new node's share, **1/(N+1)**, moves.

## Cross-shard queries and transactions

Queries that don't include the shard key must ask every shard. Three ways to live with that:

- **Scatter-gather** for admin and reporting: query all shards in parallel, merge, re-sort, cut. Latency is the slowest shard's.
- **Global secondary index:** a separate table keyed by the other attribute (`email → user_id`) that points at the right shard.
- **Denormalized or precomputed tables** fed by events, e.g. a "top products" table updated by a consumer.

Transactions across shards are worse: two-phase commit is slow and blocks when the coordinator fails. **Design them away** by keeping data that changes together on one shard (shard orders and their line items by the same key). When a workflow must span shards, use a **saga**: a sequence of local transactions, each with a compensating action (reserve stock, charge card, and on failure release the stock).

## Hot keys

A good shard key can still have one hot value: a celebrity's post, a flash-sale product. The fix is **salting**: split the key into N sub-keys (`likes:42:0` … `likes:42:15`) that hash to different shards, write to a random one, and sum them on read. Reads get N times more expensive, so salt only the keys you've measured as hot. Pair it with an in-process cache for hot reads.

## Resharding without downtime

<Steps>
  <Step title="Add the new shards">
    Provision them empty, with replicas, monitoring and backups, before any traffic moves.
  </Step>
  <Step title="Dual-write">
    Every write for a moving key goes to the old and the new location. The old shard stays the source of truth.
  </Step>
  <Step title="Backfill">
    Copy historical rows in batches with idempotent upserts, throttled so the old shard isn't overloaded.
  </Step>
  <Step title="Verify">
    Compare row counts and checksums per key range, and shadow-read from the new shard to diff the results.
  </Step>
  <Step title="Flip reads">
    Behind a feature flag, a few percent at a time. Flip back instantly if errors rise.
  </Step>
  <Step title="Stop old writes and clean up">
    Stop dual-writing, then delete the moved rows from the old shard. Every step before this one can be reversed.
  </Step>
</Steps>

## Ids across shards

Auto-increment ids break once there are several primaries: two shards hand out the same id. The options are UUIDs (random v4 fragments indexes; time-ordered **UUIDv7** is fine), a central ticket server (simple, but one more service to keep up), or **Snowflake** ids: 64 bits that pack a timestamp, a worker id and a per-millisecond sequence. They need no coordination per id, sort roughly by time, and fit in a `BIGINT`.

### Consistent hashing

Nodes sit on a ring with many virtual points each. Adding a node moves only about 1/N of the keys and virtual nodes even out the load. The lookup is a binary search over the sorted points, `O(log n)` instead of scanning the whole ring on every request.

The tests add a 5th node to 20K keys: 19% move, every one of them to the new node, and removing a node only moves that node's keys.

### Rendezvous hashing

Each key scores every node and picks the highest. No ring and no virtual nodes, at the cost of hashing against every node per lookup, which is fine for tens of nodes.

<Callout kind="warning" title="Common mistakes">
- Sharding before trying indexes, caching and replicas.
- A low-cardinality or monotonically increasing shard key.
- Hot-path queries that need every shard.
- `hash % N` for a cluster that will grow.
- Sending 64-bit ids to JavaScript as numbers (they lose precision above 2^53).
</Callout>

## Interview questions

<FollowUps>
  <FollowUp q="What's the shard key for a multi-tenant SaaS?">
    `tenant_id`, so a tenant's queries hit one shard. Use a directory so the few huge tenants can get their own shards, and keep a global table for cross-tenant admin queries.
  </FollowUp>
  <FollowUp q="How do you run queries that span shards?">
    Avoid them on hot paths. Use scatter-gather for admin and reporting, a global secondary index, or precomputed or denormalized tables fed by events.
  </FollowUp>
  <FollowUp q="How do you reshard without downtime?">
    Add the new shards, dual-write, backfill historical data, verify counts and checksums, flip reads behind a flag, stop the old writes, and clean up. Every step can be reversed until the last one.
  </FollowUp>
  <FollowUp q="Why do you need virtual nodes?">
    With one point per node, the arcs between points differ a lot, so one node can own twice its fair share. Many points per node average that out, and when a node fails its keys spread across many survivors instead of doubling one neighbour's load.
  </FollowUp>
  <FollowUp q="Hash or range sharding for time-series data?">
    Pure range-by-time makes the newest shard take every write. Shard by the series (sensor or user) with a hash, and keep time as the sort key inside each shard; or use a compound key such as `(sensor_id, day)` so each partition is bounded and recent data still spreads.
  </FollowUp>
</FollowUps>
