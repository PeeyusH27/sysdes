<TLDR>
Shard only when one primary can't hold the data or the writes. The **shard key** (high cardinality, matches your main query) matters more than the scheme; consistent hashing moves only ~1/N of keys when a node joins.
</TLDR>

## When to shard

Sharding is the last resort: joins, transactions, unique constraints and schema changes get harder forever. Spend the cheap options first:

1. **Vertical scaling:** hundreds of GB of RAM, tens of thousands of writes per second.
2. **Indexes:** most "slow database" problems are a missing one.
3. **Caching** and **read replicas** (if you can stand replication lag) for reads.
4. **Archiving** cold rows (old orders, logs) to cheaper storage.

Shard when **writes** or **data size** outgrow one primary, rarely for reads alone.

## Choosing the shard key

The key decides which queries stay on one shard, and whether load spreads. A good key:

- **Has high cardinality.** `country` has about 200 values: at most 200 useful shards, and one country dominates.
- **Spreads evenly.** No value owns a big share of rows or traffic.
- **Matches the dominant query.** Mostly "this user's orders"? Shard by `user_id`.
- **Avoids hot ranges.** Timestamps and auto-increment ids pile new writes onto one shard.

Usual answer: `user_id` (`tenant_id` in SaaS). Two big access patterns? Store the data twice (orders by buyer **and** by seller).

## Strategies compared

| Strategy | Spread and scans | Rebalancing cost | Typical use |
|---|---|---|---|
| Hash mod N | Even; no range scans | Moves ~all keys | Fixed shard count |
| Range | Range scans; hot-range risk | Split or merge ranges | Time-series, ordered ids |
| Directory | Manual; scans depend | Move one tenant at a time | Multi-tenant SaaS with "whales" |
| Consistent hashing (+ vnodes) | Even; no range scans | ~1/N of the keys | Caches, Dynamo-style stores |
| Rendezvous (HRW) | Even; no range scans | ~1/N of the keys | Small node sets, no ring to maintain |

Kafka, Elasticsearch, Redis Cluster (16,384 slots) and Cassandra's vnodes dodge rebalancing with **fixed logical partitions**: far more than machines (say 1,024), keys mapped by `hash % 1024` (which never changes), whole partitions moved between machines.

## Consistent hashing, interactively

Nodes and keys hash onto one circle; a key belongs to the first node clockwise. Add or remove a node in the ring: only neighbouring keys move. Then drag virtual nodes down to 1 and watch the bars drift from the ideal share (the readout shows max ÷ min).

<HashRing />

With `hash % N`, a key stays only if `hash mod N` equals `hash mod (N+1)`, so **N/(N+1)** of keys move. Consistent hashing moves only the new node's share, **1/(N+1)**.

## Cross-shard queries and transactions

No shard key in the query? Every shard gets asked. Cope with:

- **Scatter-gather** for admin and reporting: ask all shards in parallel, merge, re-sort, cut. The slowest shard sets the latency.
- **A global secondary index** (`email → user_id`) that points at the shard.
- **Denormalized or precomputed tables** fed by events, e.g. "top products".

Cross-shard transactions are worse: two-phase commit is slow and blocks if the coordinator dies. **Design them away** by keeping data that changes together on one shard (orders and their line items). Must span shards? A **saga** chains local transactions, each with an undo (reserve stock, charge card; on failure, release the stock).

## Hot keys

A good key can still have one scorching value: a celebrity's post, a flash-sale product. **Salt** it into N sub-keys (`likes:42:0` … `likes:42:15`) on different shards, write to a random one, sum on read. Reads cost N times more, so salt only measured hot keys, and cache hot reads in-process.

## Resharding without downtime

Never stop the world: move the data while it serves traffic.

<Steps>
  <Step title="Add the new shards">
    Empty, with replicas, monitoring and backups, before any traffic moves.
  </Step>
  <Step title="Dual-write">
    Writes for moving keys go to both; the old shard stays the source of truth.
  </Step>
  <Step title="Backfill">
    Copy old rows in batches with idempotent upserts, throttled to spare the old shard.
  </Step>
  <Step title="Verify">
    Compare row counts and checksums per key range; shadow-read the new shard and diff.
  </Step>
  <Step title="Flip reads">
    Behind a feature flag, a few percent at a time. Flip back instantly if errors rise.
  </Step>
  <Step title="Stop old writes and clean up">
    Stop dual-writing, delete the moved rows. Only this step is irreversible.
  </Step>
</Steps>

## Ids across shards

Two auto-increment primaries hand out the same id. Options:

- **UUIDs:** random v4 fragments indexes; time-ordered UUIDv7 is fine.
- **A central ticket server:** simple, but one more service to run.
- **Snowflake ids:** 64 bits of timestamp, worker id and per-millisecond sequence. No coordination per id, roughly time-sorted, fits a `BIGINT`.

## Interview questions

<FollowUps>
  <FollowUp q="What's the shard key for a multi-tenant SaaS?">
    `tenant_id`, with a directory so the few huge tenants get their own shards and a global table for cross-tenant admin queries.
  </FollowUp>
  <FollowUp q="How do you run queries that span shards?">
    Keep them off hot paths: scatter-gather for admin and reporting, otherwise a global secondary index or precomputed tables fed by events.
  </FollowUp>
  <FollowUp q="How do you reshard without downtime?">
    Add shards, dual-write, backfill, verify, flip reads behind a flag, then stop old writes; only the cleanup is irreversible.
  </FollowUp>
  <FollowUp q="Why do you need virtual nodes?">
    With one point per node, a node can own twice its fair share; many points even out the arcs and spread a dead node's keys over many survivors.
  </FollowUp>
  <FollowUp q="Hash or range sharding for time-series data?">
    Hash by series (sensor or user) and sort by time inside each shard, or key by `(sensor_id, day)` so partitions stay bounded; pure range-by-time sends every write to the newest shard.
  </FollowUp>
</FollowUps>
