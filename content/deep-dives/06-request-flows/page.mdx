<TLDR>
Know five flows cold: **read**, **write**, **async**, **failure** and **idempotent retry**. Give every request a latency budget and enforce it with timeouts.
</TLDR>

## Why it matters

"Walk me through what happens when…" is the most common follow-up in a design interview. It tests whether every box on your diagram has a job. Five flows cover almost every system.

Pick a flow in the diagram. In **Read**, try a CDN miss, then a Redis miss.

## The flows side by side

| Flow | Responds with | Protected by |
|---|---|---|
| Read | 200 from CDN, cache or DB | CDN, cache, TTLs |
| Write | 201 after the commit | Validation, the outbox |
| Async | 202 + `Location` | A queue, retries |
| Failure | 200 degraded, or a fast 503 | Timeouts, breaker, fallback |

Idempotent retries get their own section below.

## Latency budgets

Split the user-facing p99 target across the hops, and keep headroom. A 200 ms budget:

| Hop | p99 budget | Enforced by |
|---|---|---|
| TLS + CDN edge | 30 ms | Keep-alive, a nearby edge |
| Load balancer + gateway | 10 ms | Local JWT checks |
| Service logic | 20 ms | No blocking work |
| Redis | 5 ms | A command timeout |
| Database | 50 ms | Indexes, `statement_timeout` |
| Downstream service | 45 ms | A per-call timeout |
| Headroom | 40 ms | Retries, GC pauses |
| **Total** | **200 ms** | |

Slow calls add up: make 10 parallel calls, each 1% likely to be slow, and about **10%** of page loads hit a slow one. So per-hop budgets must be tighter than the page's.

## Watch the budget

Each span runs against a 200 ms budget line. Turn off the CDN and cache hits, slow the database, or time out a dependency: which hop blows the budget?

## Read path

CDN, cache, database: each layer soaks up traffic. At 80% CDN hits and 90% Redis hits, only 0.2 × 0.1 = **2%** of reads reach the database. See the [caching lesson](/learn/caching).

## Write path

Save the truth in **one transaction**, answer, and let the rest catch up:

1. Validate input first.
2. In one transaction, insert the order **and** an outbox row for the event.
3. Respond `201 Created`.
4. A relay publishes `order.created` from the outbox.
5. Consumers update caches, search and email, ignoring duplicates.

Save, then publish separately, and a crash in between leaves an order with no confirmation email, ever. The outbox makes the event part of the commit. For a page-view counter, losing one event is fine: skip it.

## Async path

Slow work (reports, video) leaves the request: enqueue a job and answer `202 Accepted` with a status URL. The client finds out by polling, a webhook, or SSE.

Workers retry with backoff. Repeat failures land in a **dead letter queue** for a human. A job can run twice, so make it idempotent.

## Failure path

<Doodle name="circuit-breaker" size={150} caption />

A dependency's outage shouldn't become yours. In a flash sale the recommendations service slows to 5 s. With no timeout, every checkout waits on it, threads pile up and the whole site goes down. With a 45 ms timeout and a fallback of popular items, checkout loads without recommendations.

- **Timeouts** on every call.
- **Retries** only for safe-to-repeat calls, with jitter and a small budget.
- A **circuit breaker**: after repeated failures, fail fast for a cooldown, then let one trial through.
- A **fallback**: cached data or a smaller page. Slightly worse beats an error page.

## Idempotent retries

<Doodle name="idempotency" size={150} caption />

A phone on weak signal taps Pay. The charge succeeds, the reply is lost, the app times out, and the user taps again. Without a key, that is two charges. Reads are safe to repeat, but every payment or order write needs an **idempotency key**: an id made once per operation and reused on every retry.

The server claims the key atomically (`SET key pending NX`), stores the result, and replays it for repeats. A duplicate arriving mid-flight gets `409 Conflict`, not a second charge.

## Trace context propagation

One id must tie five services' logs together. That is the `traceparent` header.

```http
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
```

OpenTelemetry handles it for HTTP, gRPC and database clients. You put the trace id in every log line and copy the header into queue messages.

## Interview questions

<FollowUps>
  <FollowUp q="Walk me through what happens when a user clicks 'Buy'.">
    CDN, gateway (auth, rate limit), then the order service. It checks the idempotency key, writes the order plus an outbox row in one transaction, and answers 201. A relay fans the event out to email and analytics.
  </FollowUp>
  <FollowUp q="How do you set a latency budget?">
    Split the user-facing p99 across the hops, with headroom. Enforce it with timeouts and a deadline.
  </FollowUp>
  <FollowUp q="The client timed out, but the charge went through. What now?">
    It retries with the same idempotency key and gets the stored result.
  </FollowUp>
  <FollowUp q="Why not just publish the event right after the database commit?">
    A crash between the two loses the event. The outbox commits it with the data.
  </FollowUp>
  <FollowUp q="Some requests are slow, but only sometimes. How do you find the hop responsible?">
    Distributed tracing: the widest span in a slow trace is the culprit.
  </FollowUp>
</FollowUps>
