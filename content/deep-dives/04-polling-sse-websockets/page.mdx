<TLDR>
Pick by direction and frequency: **polling** for dashboards that can be seconds stale, **SSE** for one-way live updates, **WebSockets** when the client talks back often, **webhooks** server to server. Connections always drop, so reconnect with jittered backoff and design for resume.
</TLDR>

## Why it matters

HTTP waits to be asked. Live scores, chat, notifications and progress bars need the server to speak first. Each workaround trades **simplicity** against **latency** and **server cost**. Get it wrong and you show stale screens, or run a fleet holding millions of idle sockets.

<PollingRace />

A browser request with cookies often carries 500 bytes to 2 KB of headers; a WebSocket frame header is 2 to 14 bytes. And 100K clients polling every 5 s make **20,000 requests per second**, mostly empty.

## Short and long polling

**Short polling** is a timer and a `fetch`: schedule the next poll *after* the reply (`setInterval` stacks requests on a slow server), pause in hidden tabs, and answer unchanged data with `ETag` and `304 Not Modified`. Fine for a 30 s dashboard.

**Long polling** holds the request until there's news or about 30 s pass (under proxy idle timeouts, often 60 s); the client re-asks with a cursor (`?since=41`). Two classic bugs:

- **The gap:** subscribe *after* reading the backlog and an event in between is lost. Subscribe first, then read and merge.
- **The tight loop:** instant re-polls after an error hit a down server with thousands of requests per second from every client. Back off with jitter.

Each waiting request holds a connection and memory, so use an async server (Node, Go, Netty), not a thread per request.

## Server-Sent Events

Plain HTTP: one long `Content-Type: text/event-stream` response, each event a few `field: value` lines and a blank line. `EventSource` parses it, reconnects by itself and sends the last `id:` it saw as `Last-Event-ID`, so the server replays what was missed.

```http
id: 42
event: score
data: {"home":2,"away":1}

: ping
```

- **Connection limits.** HTTP/1.1 browsers allow about 6 connections per origin, one per stream, so a seventh tab hangs; HTTP/2 multiplexes them on one connection.
- **Proxies.** Some buffer, so events arrive in bursts or never: send `X-Accel-Buffering: no` (nginx) and a `: ping` comment every 15 s, and check idle timeouts.
- **Limits.** Text only (send JSON), one direction (the client sends plain `POST`s), and `EventSource` can't set custom headers, so authenticate with a cookie.

## WebSockets

An HTTP `GET` with `Upgrade: websocket` gets `101 Switching Protocols`, and the TCP connection becomes a two-way channel of small frames. Use it when the client sends often too: chat, multiplayer games, collaborative editing. The price is **state**: each socket lives on one server, and reconnect, resume, heartbeats and backpressure are yours to write.

### Scaling WebSockets

Play the diagram's three stories: **Message across nodes**, **Dead peer** and **Deploy drain**.

<FlowDiagram spec={wsScaling} />

- **Pub/sub backplane.** Alice is on node 1, Bob on node 2: node 1 publishes to `user:bob` (Redis pub/sub, NATS, Kafka) and Bob's node delivers.
- **No sticky sessions:** any node reaches any user, so reconnects land anywhere.
- **File descriptors.** One per socket; many Linux systems default to a soft limit of 1,024. Raise `ulimit -n` (`LimitNOFILE` in systemd); then memory caps you at tens of thousands of idle sockets per Node process.
- **Heartbeats.** Dead TCP peers are silent. Ping every ~30 s, kill sockets that miss a pong, stay under load balancer idle timeouts (AWS ALB default: 60 s).
- **Drain on deploy.** Fail readiness, send close code `1001` (going away) and let clients reconnect elsewhere with **full jitter**, or 50K reconnects in one second flatten the other nodes.

### Authenticating sockets

Browsers can't set an `Authorization` header on a WebSocket (or `EventSource`), so authenticate the **connect**:

- A session **cookie** rides the upgrade; check `Origin` too, or any site can open a socket as your user (cross-site WebSocket hijacking).
- Or a short-lived **token** in the first message (Socket.IO's `auth` payload), never in the query string, which lands in access logs.
- **Re-auth on expiry.** Sockets outlive tokens: the client sends a fresh one before expiry, or the server closes with an app code (e.g. 4001). Re-check permissions on every room join.

## Webhooks

Don't poll Stripe or GitHub: they `POST` to your public endpoint when something happens, sometimes twice or out of order, and retry until you answer `2xx`. Try all three branches in the diagram.

<SequenceDiagram spec={webhookDelivery} />

- **HMAC signatures.** Recompute over the **raw** body (JSON parsing changes the bytes); compare with `timingSafeEqual`, in constant time.
- **Timestamps against replay.** The provider signs one too; reject anything older than about 5 minutes.
- **Acknowledge fast.** Enqueue durably, return `200` within a second or two. Providers time out (GitHub allows 10 s) and count slow as failed.
- **Process idempotently.** A unique constraint on the event id makes a duplicate a no-op.
- **Expect retries**, and gaps: providers eventually give up, so reconcile through their API now and then.

## Interview questions

<FollowUps>
  <FollowUp q="Live sports scores: which technique?">
    SSE: one-way, plain HTTP that CDNs and proxies understand, resuming with `Last-Event-ID`. Fan out through pub/sub so every SSE server gets every score.
  </FollowUp>
  <FollowUp q="Why does SSE hang behind some proxies?">
    The proxy buffers the stream; disable buffering (`X-Accel-Buffering: no` on nginx) and send `: ping` heartbeats so it never looks idle.
  </FollowUp>
  <FollowUp q="How do you serve 1M concurrent WebSockets?">
    At ~50K sockets per gateway node (memory and file descriptors decide), 20 nodes plus headroom. Route over pub/sub, and drain on deploy while clients reconnect with jitter.
  </FollowUp>
  <FollowUp q="SSE or WebSocket for a chat app?">
    Usually WebSocket, since typing, receipts and messages flow both ways often; SSE plus `POST` suits low-volume chat. Either way, give messages ids so clients resume after a reconnect.
  </FollowUp>
  <FollowUp q="How do you notify a mobile user whose app is in the background?">
    Push through APNs (iOS) or FCM (Android), because the OS kills a backgrounded app's sockets; on open, reconnect and sync from the last message id seen.
  </FollowUp>
</FollowUps>
