<TLDR>
Pick by direction and frequency: **polling** for slightly stale dashboards, **SSE** for one-way live updates, **WebSockets** when the client talks back often. Connections drop, so reconnect with jitter.
</TLDR>

## Why it matters

HTTP waits to be asked. Live scores and chat need the server to speak first. It is like checking your mailbox every five minutes versus a doorbell. Each workaround trades **simplicity** against **delay** and **server cost**.

## Side by side

| | Short polling | SSE | WebSocket |
|---|---|---|---|
| Direction | Client asks | Server to client | Both ways |
| Delay | Up to the interval | Real time | Real time |
| Cost | Many empty requests | One open stream | One stateful socket |
| Best for | Dashboards | Feeds, scores | Chat, games |

**Long polling** holds each request open until there is news. **Webhooks** are server to server and have their own section.

Start with plain polling. Move only when users notice the delay, or the request count hurts. Pick by product:

| Product | Pick | Why |
|---|---|---|
| Sales dashboard | Poll every 30 s | Seconds of delay are fine |
| Order or score alerts | SSE | Server talks, client listens |
| Chat | WebSocket | Both sides send often |
| Live cursors | WebSocket | Many tiny messages both ways |

## Race them

Four techniques race on one event stream. Raise the poll interval: short polling's delay climbs (about **half the interval**) as its requests fall.

<PollingRace />

Do the sum. 1,000 dashboards polling every 30 s is about 33 requests per second: trivial, so keep polling. 100K clients polling every 5 s make **20,000 requests per second**, mostly empty, so switch to SSE. The cost moves to memory: each open stream holds a socket, and one node holds roughly 50K.

## Short and long polling

**Short polling** is a timer and a `fetch`. Schedule the next poll *after* the reply, and answer unchanged data with `304 Not Modified`. Fine for a 30 s dashboard.

**Long polling** holds the request until there is news or about 30 s pass; the client re-asks with a cursor (`?since=41`). Two classic bugs:

- **The gap:** subscribe *after* reading the backlog and an event in between is lost. Subscribe first, then read.
- **The tight loop:** instant re-polls after an error flood a down server. Back off with jitter.

Use an async server (Node, Go), not a thread per request.

## Server-Sent Events

**SSE** is plain HTTP: one long response that streams events. The browser's `EventSource` parses it, reconnects by itself and sends the last `id:` it saw as `Last-Event-ID`, so the server replays what was missed.

```http
id: 42
event: score
data: {"home":2,"away":1}

: ping
```

- **Connection limits.** HTTP/1.1 allows about 6 connections per origin, so a seventh tab hangs. HTTP/2 shares one.
- **Proxies.** Some buffer the stream. Send `X-Accel-Buffering: no` (nginx) and a `: ping` every 15 s.

## WebSockets

A **WebSocket** starts as an HTTP request, then upgrades the same connection into a two-way channel of small messages. Use it when the client sends often too, like chat. The price is **state**: each socket lives on one server, and reconnect and resume are yours to write.

Picture a chat app on a train. The tunnel kills the connection silently, and without a heartbeat the server keeps writing to nobody. Messages with ids let the client resume where it stopped.

### Scaling WebSockets

Play the diagram's three stories: **Message across nodes**, **Dead peer** and **Deploy drain**.

<FlowDiagram spec={wsScaling} />

- **Pub/sub backplane.** Alice is on node 1, Bob on node 2. Node 1 publishes to `user:bob` and Bob's node delivers. Any node reaches any user.
- **Heartbeats.** Dead peers are silent. Ping every ~30 s and close sockets that miss a pong.
- **Drain on deploy.** Let clients reconnect elsewhere with **full jitter**, or 50K reconnects in one second flatten the other nodes.

### Authenticating sockets

Browsers can't set an `Authorization` header on a WebSocket, so authenticate the **connect**:

- A session **cookie** rides the upgrade. Check `Origin` too.
- Or a short-lived **token** in the first message, never in the URL, which lands in logs.
- Sockets outlive tokens, so re-authenticate before expiry.

## Webhooks

Stripe and GitHub `POST` to your endpoint when something happens, sometimes twice, and retry until you answer `2xx`. Try all three branches.

<SequenceDiagram spec={webhookDelivery} />

- **Check the signature.** Recompute the HMAC over the **raw** body and compare in constant time.
- **Reject old timestamps.** Anything older than about 5 minutes is a replay.
- **Acknowledge fast.** Enqueue, then return `200` quickly.
- **Process idempotently.** A unique constraint on the event id makes a duplicate a no-op.

## Interview questions

<FollowUps>
  <FollowUp q="Live sports scores: which technique?">
    SSE: one-way, plain HTTP, and it resumes with `Last-Event-ID`. Fan out through pub/sub.
  </FollowUp>
  <FollowUp q="Why does SSE hang behind some proxies?">
    The proxy buffers the stream. Disable buffering and send `: ping` heartbeats.
  </FollowUp>
  <FollowUp q="How do you serve 1M concurrent WebSockets?">
    At ~50K sockets per node, about 20 nodes plus headroom. Route over pub/sub, and drain on deploy.
  </FollowUp>
  <FollowUp q="SSE or WebSocket for a chat app?">
    Usually WebSocket, since messages flow both ways. Give messages ids so clients can resume.
  </FollowUp>
  <FollowUp q="How do you notify a mobile user whose app is in the background?">
    Use push (APNs or FCM), since the OS kills background sockets. On open, reconnect and sync.
  </FollowUp>
</FollowUps>
