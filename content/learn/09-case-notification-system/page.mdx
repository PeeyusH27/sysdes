<TLDR>
Accept with `202`, check preferences, publish one message per channel onto **queues split by channel and priority**, so an OTP never waits behind a marketing blast. Dedupe on `eventId:channel`, send via providers behind **circuit breakers with failover**; quiet hours, caps and suppression lists protect users.
</TLDR>

## Why it matters

Unlike the URL shortener, this system is **write-heavy and asynchronous**: almost nothing happens in the request. The hard parts are isolation (one slow channel or huge campaign mustn't hurt the rest), exactly-once *behaviour* on at-least-once queues, and providers you don't control.

Play all four scenarios: **Normal fan-out**, **SMS provider down**, **Duplicate event dropped** and **Quiet hours**.

## Estimation

- 50M users × 10 a day = 500M a day ≈ **5.8K/s** average.
- Campaigns burst to **50K+/s**, far above provider limits: queues absorb it; campaign fan-out is throttled.
- Delivery log: 500M rows × ~200 B ≈ **100 GB a day**, partitioned by day, kept 30–90 days.
- Most volume is push; SMS is smallest, since each message costs money.

## API

| Method | Path | Body / result |
|---|---|---|
| POST | `/v1/notifications` | `{ idempotencyKey, userIds \| segment, template, data, channels?, priority, sendAt? }` → `202 { notificationId }` |
| PUT | `/v1/users/:id/notification-preferences` | `{ channels: { push, email, sms }, types: {…}, quietHours: { start, end }, tz }` |
| POST | `/webhooks/:provider` | Delivery status callbacks (delivered, bounced, complained) |

**`202 Accepted`** means "queued", not "sent". A retry with the same `idempotencyKey` returns the same `notificationId`.

## Data model

```sql
CREATE TABLE notification_prefs (user_id bigint, channel text, type text, enabled boolean NOT NULL,
                                 PRIMARY KEY (user_id, channel, type));
CREATE TABLE device_tokens (token text PRIMARY KEY, user_id bigint NOT NULL, platform text, last_seen timestamptz);
CREATE TABLE deliveries (id text PRIMARY KEY,                       -- `${eventId}:${channel}`: the dedupe key
                         user_id bigint, channel text, provider text, provider_msg_id text,
                         status text, updated_at timestamptz);
CREATE INDEX deliveries_provider_msg ON deliveries (provider_msg_id);  -- webhook lookups
```

Preferences are read for **every** notification (5.8K/s) and rarely change: cache them. `device_tokens` is keyed by token (one per app install). `deliveries` is the busiest table: append-mostly, partitioned by day, looked up by `provider_msg_id` when webhooks arrive.

## Fan-out with queues

A queue per channel lets workers scale and fail independently: slow SMS never blocks push. Better: split by **channel and priority**.

| Queue | Typical messages | Workers |
|---|---|---|
| `notif.sms.critical` | OTPs, security alerts | Dedicated, always with spare capacity |
| `notif.push.high` | Order updates, messages | Scaled on queue depth |
| `notif.email.normal` | Receipts, comment replies | Scaled on queue depth |
| `notif.push.low` | Marketing, digests | Throttled, paused first under load |

Each queue has its own consumer group, so no backlog steals another's workers. A message that keeps failing lands in a **dead-letter queue** with an alert.

## Priorities: the OTP never waits

08:00: a 1M-message campaign hits one shared queue, drained at 2,000/s: about **8 minutes**. 08:01: a login code joins the back of the line and expires before arriving.

With lanes, the campaign fills only `notif.push.low`; the OTP takes `notif.sms.critical`, where dedicated workers sit idle, and leaves in milliseconds. Reserve provider capacity too (a separate account or sender, or a slice of the rate limit), or a campaign can exhaust the provider's limit anyway.

## Templates and localisation

Copy changes weekly; deploys shouldn't have to.

- Reference a **template id + version + locale**, never raw text, so product teams edit without a deploy.
- **Render in the worker**, late: fresh data, current language, locale fallback (`pt-BR` → `pt` → `en`).
- One variant per channel: push title, HTML email, one-segment SMS (160 GSM-7 characters, or 70 with any other character, like an emoji or Devanagari).
- Escape user data in HTML; store the template version in the delivery row to debug what a user got.

## Scheduling and quiet hours

A scheduled `sendAt` and a 3 a.m. marketing push get the same fix: a **`notBefore`** timestamp.

- Store an **IANA time zone** per user (`Asia/Kolkata`, not `+05:30`, which breaks with daylight saving).
- Check quiet hours **at send time, in the user's zone**. Low priority gets `notBefore` = end of the window; **critical ignores quiet hours**.
- Waiting messages sit in a **delayed queue**: a Redis sorted set scored by `notBefore`, which a scheduler polls every second, moving due messages to the channel queue. (Broker delays are often capped: SQS allows 15 minutes.)
- Workers re-check quiet hours and caps right before sending; preferences change.

## Reliability: providers fail

Every provider will be slow, throttle you, or go down. Wrap them in a **provider abstraction** (`send(msg)` returns a provider message id), with a **circuit breaker** each and a **failover order** per channel (for SMS, often per country).

| Error | Examples | What to do |
|---|---|---|
| Transient | Timeout, `429`, `5xx` | Next provider; the queue retries with exponential backoff and jitter |
| Permanent | Invalid number, unregistered device token, hard bounce, user unsubscribed | Don't retry: mark failed, delete the token or suppress the address |

An open breaker sends workers straight to the backup; after a cool-down, one half-open trial decides whether it closes. Track **delivery rate per provider**: accepting but silently not delivering is worse than erroring. More in the [reliability lesson](/learn/reliability-observability).

## Dedupe and idempotency

Duplicates come from client retries, re-emitted events and redelivery after a crash. Defend in layers:

1. **API idempotency key.** Store `key → notificationId` (`SET NX` with a TTL); a retry gets the same id.
2. **Deterministic message ids.** `eventId:channel`: reprocessing yields the same ids.
3. **Check before sending.** Skip ids with a `sent:<id>` key; set it only **after** the provider accepts, so failed sends can retry.

The gap: a crash between provider acceptance and writing `sent:<id>` resends. Narrow it with the id as the provider's idempotency key, plus a short `SET processing:<id> NX PX` claim if two workers can get one message ([async messaging lesson](/learn/async-messaging)). Exactly-once to a phone is impossible; aim for **effectively once**.

## Protecting users

Every extra ping risks an uninstall.

- **Daily caps per type**: say 3 marketing pushes a day. `daily-cap.js` resets on the UTC date; key by local date if needed.
- **Digests**: 20 likes become one push ("Priya and 19 others liked your photo").
- **One-click unsubscribe** (`List-Unsubscribe` header) in every marketing email: large mailbox providers now require it of bulk senders.
- **Suppression lists**: never email addresses that hard-bounced or flagged you as spam. Your whole domain's reputation rides on it.

## Device token lifecycle

Tokens rot: phones get wiped, apps get uninstalled.

- Register or refresh the token on every app start; update `last_seen`.
- Invalid or unregistered? **Delete it** now: a permanent error.
- Expire tokens unseen for months.
- Three devices, three pushes: render once, send to each token.

## Delivery tracking

Providers report back by **webhook** (delivered, bounced, complained, opened), updating the delivery row by `provider_msg_id` and feeding **sent → delivered → opened → clicked** per template and channel.

- Verify the signature over the **raw** body before parsing.
- Webhooks retry too: updates must be idempotent.
- They arrive out of order: rank statuses and never go backwards (a late `delivered` mustn't overwrite `opened`).

## Large campaigns

A 10M-user campaign is a batch job, not 10M API calls:

- **Resolve the segment in pages** (keyset pagination by user id).
- **Enqueue in batches** of ~1,000 onto low-priority lanes, on **separate workers**, so critical traffic keeps capacity.
- **Throttle to provider limits**: at 5,000 sends/s, 10M take about 33 minutes.
- **Dedupe per user** (`campaignId:userId:channel`) across overlapping segments.
- **Pause and cancel**: workers check campaign status before sending, so a typo can be stopped mid-send.

## Code

`notify.js` routes by priority with deterministic ids. `quiet-hours.js` handles windows that cross midnight, in the user's zone. `deliver.js` skips open breakers, fails over in order, never retries permanent errors, and writes `sent:<id>` only after acceptance. `email-webhook.js` verifies the raw-body signature and feeds the suppression list.

## Interview questions

<FollowUps>
  <FollowUp q="How do you make sure a notification isn't sent twice?">
    Queues deliver at least once, so dedupe on deterministic `eventId:channel` ids, marked sent only after the provider accepts. An API idempotency key covers client retries.
  </FollowUp>
  <FollowUp q="A 10M-user campaign is running. How do OTPs still arrive in seconds?">
    Priority lanes with dedicated workers and reserved provider capacity: the campaign can only fill the low lane.
  </FollowUp>
  <FollowUp q="The SMS provider goes down. What happens?">
    The breaker opens and traffic fails over to the backup provider. Per-provider delivery rate catches one that accepts but doesn't deliver.
  </FollowUp>
  <FollowUp q="How do quiet hours work across time zones?">
    Store an IANA zone per user and evaluate at send time; low priority waits in a delayed queue, critical never does.
  </FollowUp>
  <FollowUp q="How do you send 10M campaign notifications without hurting the system?">
    As a throttled batch job on separate workers: paged segment, batched enqueue, per-user dedupe, pause and cancel.
  </FollowUp>
