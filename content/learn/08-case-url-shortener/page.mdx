<TLDR>
A URL shortener is a read-heavy key-value lookup: about **40 writes/s and 4,000 redirects/s**. Generate 7-character base62 codes from **range-allocated counters** (scrambled so they aren't guessable), serve redirects from the CDN and Redis with Postgres behind them, and send click events through a **queue** so analytics never slow the redirect down.
</TLDR>

## Why it matters

A classic that exercises every earlier idea: estimation, ID generation, read-heavy caching, and storage. It's small enough to finish in 45 minutes, which is exactly why interviewers use it: they're watching **how** you work through the loop, and whether you can go deep on the two or three decisions that matter (code generation, 301 vs 302, and keeping the redirect fast).

Say the asymmetry out loud: **redirects matter more than creation**. If creating links is down for a minute, people retry. If redirects are down, every link ever shared (in emails, PDFs, printed posters) is broken at once.

## Estimation

- 100M new URLs a month ≈ **40 writes/s**.
- At 100 reads per write, that's **≈ 4,000 redirects/s**, and about **12K/s** at a 3× peak.
- Storage: 100M a month for 5 years is 6B URLs × ~500 B ≈ **3 TB** (≈ 9 TB with 3 replicas).
- 7 base62 characters give 62⁷ ≈ **3.5 trillion** codes, which is plenty.

Two conclusions fall out of these numbers. The write path is tiny (one Postgres primary handles 40 inserts/s while barely noticing), so **all the interesting work is on the read path**. And the data is small enough that the hot set fits in memory: 10M hot codes × ~600 B is about 6 GB, one Redis node.

## API

| Method | Path | Body / result |
|---|---|---|
| POST | `/api/urls` | `{ longUrl, alias?, expiresAt? }` → `201 { code, shortUrl }` · `409` alias taken · `429` rate limited |
| GET | `/:code` | `302` (or `301`) to `long_url` · `404` · `410` expired |
| GET | `/api/urls/:code/stats` | `{ clicks, byDay[], topReferrers[] }` |

The redirect lives at the root (`short.example/oqxem9y`) because short is the whole point. That means the root namespace is shared with every other route, so words like `api`, `admin` and `login` must be reserved and can never become aliases.

## Data model

```sql
CREATE TABLE urls (
  code        varchar(16) PRIMARY KEY,                -- generated (7 chars) or custom alias
  long_url    text        NOT NULL,
  user_id     bigint,
  created_at  timestamptz NOT NULL DEFAULT now(),
  expires_at  timestamptz
);
CREATE INDEX urls_expiry ON urls (expires_at) WHERE expires_at IS NOT NULL;   -- for the cleanup job
```

Every read is a primary-key lookup by `code`, and there are no joins. At larger scale this becomes a key-value table keyed by `code` (DynamoDB or Cassandra), sharded by the hash of the code. Clicks do **not** go in this table: a counter column updated 4,000 times a second would turn a read-only table into a write-hot one.

## Generating short codes

The code must be unique, short, and cheap to produce. There are four common ways to get one:

| Option | Unique? | Length | Coordination | Guessable? |
|---|---|---|---|---|
| Counter + base62 | Yes | Shortest | Counter (use range allocation) | **Yes**, unless scrambled |
| Hash (MD5/SHA) + truncate | Collisions possible | 7+ | None | No |
| Random + uniqueness check | Retry on a rare collision (~0.17% when 6B of 3.5T codes are used) | 7 | None | No |
| Snowflake-style 64-bit id | Yes | 11 in base62 | Worker ids | Partly (time-ordered) |

**Base62** uses `0-9`, `a-z` and `A-Z`: every character is safe in a URL, unlike base64's `+` and `/`. Each character holds 62 values, so 7 characters cover 62⁷ ≈ 3.5 trillion ids.

**Hashing** the long URL needs no coordination, but truncating a hash to 7 characters means collisions: with 6B links you'd expect millions of them over five years, so you still need a check-and-retry. It also gives every user the same code for the same URL, which breaks per-user analytics and expiry.

**A single counter** is simple but becomes a hot spot and a single point of failure. The fix is **range allocation**: each app server reserves a block of 1,000 ids with one atomic `INCRBY` and hands them out from memory. At 40 writes/s, the whole cluster calls the counter about **once every 25 seconds**. A crashed server wastes the rest of its block, which doesn't matter: ids must be unique, not contiguous.

## Making sequential ids unguessable

You'll often read that base62 of a counter gives unpredictable-looking codes. It doesn't. Ids 1000, 1001, 1002 become `g8`, `g9`, `ga`. Anyone can walk the whole keyspace and read every private link (shared documents, password-reset pages, invoices).

The fix is to scramble the id before encoding it. Multiply by a large constant `P` modulo 62⁷. Because `P` shares no factor with 62⁷ = 2⁷ · 31⁷, the map is a **bijection**: every id gets a different code, codes stay exactly 7 characters, and you can reverse it with the modular inverse. Consecutive ids now land far apart: `shortCode(1)` is `CjIO2GV`, `shortCode(2)` is `eDrC5nQ`.

<Callout kind="warning" title="Obfuscation, not security">
The scramble is linear, so anyone holding two consecutive codes can work out the step and enumerate the rest. It stops casual guessing, not a determined attacker. If enumeration must be impossible (private documents), use **random** codes with a uniqueness check, or make the codes longer and add access control on the destination.
</Callout>

## 301 vs 302

Both send the browser to the long URL. The difference is who remembers the answer.

| | 301 Moved Permanently | 302 Found |
|---|---|---|
| Browser caches it | Yes, often for a very long time | No (unless `Cache-Control` allows it) |
| CDN caches it | Yes | Only with an explicit `max-age` |
| Every click reaches you | No: only the first per browser | Yes |
| Can change the destination later | Hard: old browsers keep the old one | Easy |
| Server load | Lowest | Every click |

A **301** is the fastest option, but clicks become invisible and a mistake is cached in browsers you can't reach. A **302** always comes back to you, so you can count every click, expire the link, or disable it for abuse. Default to **302**, and pick 301 only when analytics don't matter. A middle ground for very hot links: a 302 with `Cache-Control: max-age=60` lets the CDN absorb the load while you still see roughly one request per edge per minute.

## Scaling the reads

Hot links follow a power law: a small fraction of codes gets most of the clicks. Each layer absorbs a share of the traffic before it reaches Postgres:

1. **CDN.** Caches 301s (and short-max-age 302s) at the edge, close to the user.
2. **Redis.** Cache-aside on `u:<code>` with a TTL of one day, capped at the link's expiry. At 4,000 redirects/s and a 95% hit ratio, Postgres sees only 200 reads/s.
3. **In-process L1.** When one link goes viral (50K redirects/s on a single key), one Redis node becomes the hot spot. A tiny LRU with a few seconds of TTL in every app server absorbs it.
4. **The database.** A key-value table keyed by `code`, with read replicas, sharded by hash of the code when storage outgrows one machine.

Redirects never write to the main table, so they can be served from replicas in every region. Creation (40/s) can go to a single primary region without anyone noticing the extra latency. And if Postgres is briefly down, redirects for cached codes keep working, which is how you get to 99.99%.

## Click analytics

The redirect fires a click event and **never awaits it**:

1. The app publishes `{ code, ts, referrer }` to a queue and sends the 302 in the same breath.
2. A worker consumes events in batches of a few thousand.
3. It bulk-inserts them into a columnar store such as ClickHouse, partitioned by day.
4. The stats API reads pre-aggregated rollups (clicks per day, top referrers) instead of scanning raw events.

Switch the diagram to **Click analytics** to watch it. If the queue or the analytics store is down, the redirect still works: you lose (or delay) a few counts, never a redirect. Two details interviewers like: filter bot traffic and link-preview fetchers (chat apps unfurl every link they see) out of the counts, and store a country instead of the raw IP address.

## Expiry and cleanup

- **Lazy check on read.** The lookup query filters on `expires_at > now()`, and the cache TTL is capped at the link's expiry, so an expired link stops working on time even if it was hot.
- **Nightly cleanup.** A job deletes expired rows in small batches using the partial index on `expires_at`, so it never locks the table for long.
- **Status code.** Return `410 Gone` if you keep a tombstone for expired links, or `404` if the row is deleted.
- **Don't reuse codes.** Old links live forever in emails, PDFs and printed QR codes. Reusing a code silently sends those clicks to someone else's destination, which is a phishing vector. With 3.5 trillion codes, there's no reason to.

## Abuse and safety

Shorteners are a favourite tool for hiding malicious links, so safety is part of the design:

- **Rate-limit creation** per user and per IP (see the [rate limiter question](/questions/rate-limiter)). That's where the `429` in the API comes from.
- **Scan destinations** against malware and phishing lists when the link is created, and rescan periodically, because a destination can turn bad later.
- **Block `javascript:` and `data:` URLs.** Allow only `http` and `https`, as the route below does.
- **Reserve words** for custom aliases: `api`, `admin`, `login`, `static`, brand names.
- **Keep aliases in their own namespace.** If aliases can be any 7 characters, a user can claim a code the counter will generate later, and that insert fails. Require aliases to be longer (8+ characters) or to contain a character generated codes never use, such as `-`.
- **Disable, don't delete.** Flag abusive links so they show a warning page, and purge them from Redis and the CDN.

## Interview questions

<FollowUps>
  <FollowUp q="Counter-based vs hash-based short codes?">
    Counters guarantee uniqueness and give the shortest codes, but they need coordination and are guessable unless scrambled. Hashes need no coordination but need collision handling and longer codes, and they give everyone the same code for the same URL. Range allocation scales counters well: each server reserves a block of ids per call, so the counter is never a hot spot.
  </FollowUp>
  <FollowUp q="301 or 302?">
    302 if analytics matter or the link may change. 301 for pure performance, because browsers and CDNs cache it and you stop seeing clicks. A 302 with a short `max-age` is a useful middle ground for very hot links.
  </FollowUp>
  <FollowUp q="How do custom aliases work?">
    Validate the charset and length, check reserved words, and rely on the primary-key unique constraint (409 on conflict). Keep aliases out of the generated namespace, for example by making them longer than 7 characters, so a user can never claim a code the counter will produce later.
  </FollowUp>
  <FollowUp q="How do you expire links?">
    Store `expires_at`, check it on read (return 410 or 404), cap cache TTLs at the expiry, and run a nightly cleanup. Don't reuse codes: old links live on in emails and printed material.
  </FollowUp>
  <FollowUp q="A link goes viral (50K redirects/s). Now what?">
    Serve it from the CDN with a 301 or a short-max-age 302, add an in-process L1 cache on every app server so one Redis node isn't the hot spot, and make sure analytics are async with batched writes.
  </FollowUp>
</FollowUps>
