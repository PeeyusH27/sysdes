<TLDR>
A URL shortener is a read-heavy key-value lookup: about **40 writes/s and 4,000 redirects/s**. Use 7-character base62 codes from scrambled **range-allocated counters**, serve redirects from CDN and Redis over Postgres, and send clicks through a **queue** so analytics never slow a redirect.
</TLDR>

Say it out loud: **redirects matter more than creation**. Creation down? People retry. Redirects down? Every link ever shared, in emails, PDFs and posters, breaks at once.

## Estimation

- 100M new URLs a month ≈ **40 writes/s**.
- 100 reads per write ≈ **4,000 redirects/s**; **12K/s** at a 3× peak.
- 6B URLs over 5 years × ~500 B ≈ **3 TB** (9 TB with 3 replicas).
- 62⁷ ≈ **3.5 trillion** 7-character base62 codes: plenty.

One Postgres primary barely notices 40 inserts/s: **the read path is the whole game**. And the hot set fits in memory: 10M codes × ~600 B ≈ 6 GB, one Redis node.

## API

| Method | Path | Body / result |
|---|---|---|
| POST | `/api/urls` | `{ longUrl, alias?, expiresAt? }` → `201 { code, shortUrl }` · `409` alias taken · `429` rate limited |
| GET | `/:code` | `302` (or `301`) to `long_url` · `404` · `410` expired |
| GET | `/api/urls/:code/stats` | `{ clicks, byDay[], topReferrers[] }` |

The redirect lives at the root (`short.example/oqxem9y`) to stay short, so reserve `api`, `admin`, `login` and the like: they can never be aliases.

## Data model

```sql
CREATE TABLE urls (
  code        varchar(16) PRIMARY KEY,                -- generated (7 chars) or custom alias
  long_url    text        NOT NULL,
  user_id     bigint,
  created_at  timestamptz NOT NULL DEFAULT now(),
  expires_at  timestamptz
);
CREATE INDEX urls_expiry ON urls (expires_at) WHERE expires_at IS NOT NULL;   -- for the cleanup job
```

Every read is a primary-key lookup on `code`, no joins; at scale, a key-value table (DynamoDB, Cassandra) sharded by hash of the code. Never count clicks here: 4,000 updates a second would make a read-only table write-hot.

## Generating short codes

Unique, short, cheap. Four candidates:

| Option | Unique? | Needs | Guessable? |
|---|---|---|---|
| Counter + base62 (shortest) | Yes | A counter (range allocation) | **Yes**, unless scrambled |
| Hash (MD5/SHA), truncated (7+) | Collisions possible | Nothing | No |
| Random + uniqueness check (7) | Rare retry (~0.17% at 6B of 3.5T used) | Nothing | No |
| Snowflake 64-bit id (11 in base62) | Yes | Worker ids | Partly (time-ordered) |

**Base62** (`0-9`, `a-z`, `A-Z`) is URL-safe, unlike base64's `+` and `/`.

**Hashing** needs no coordination, but 7 truncated characters collide (millions over five years at 6B links), so you still check and retry. And identical URLs share one code, breaking per-user analytics and expiry.

**One counter** is a hot spot and a single point of failure. Use **range allocation**: each app server grabs 1,000 ids with one atomic `INCRBY` and serves them from memory, so at 40 writes/s the counter sees a call about **every 25 seconds**. A crash wastes a block. Fine: ids must be unique, not contiguous.

## Making sequential ids unguessable

Base62 of a counter only *looks* random: 1000, 1001, 1002 become `g8`, `g9`, `ga`. Anyone can walk the keyspace and read private links (shared documents, password resets, invoices).

Scramble first: multiply by a large constant `P` modulo 62⁷. `P` shares no factor with 62⁷ = 2⁷ · 31⁷, so the map is a **bijection**: every id gets its own code, always 7 characters, reversible with the modular inverse. `shortCode(1)` is `CjIO2GV`; `shortCode(2)` is `eDrC5nQ`.

<Callout kind="warning" title="Obfuscation, not security">
The scramble is linear: two consecutive codes reveal the step. It stops casual guessing, not a determined attacker. If enumeration must be impossible (private documents), use **random** codes with a uniqueness check, or longer codes plus access control on the destination.
</Callout>

## 301 vs 302

Both redirect. The difference is who remembers the answer.

| | 301 Moved Permanently | 302 Found |
|---|---|---|
| Browser caches it | Yes, often for a long time | No (unless `Cache-Control` allows it) |
| CDN caches it | Yes | Only with an explicit `max-age` |
| Every click reaches you | No: only the first per browser | Yes |
| Change the destination later | Hard: old browsers keep the old one | Easy |

A **301** is fastest, but clicks vanish and mistakes stay cached in browsers you can't reach. A **302** always comes back, so you can count, expire or disable. Default to 302. For the hottest links, `Cache-Control: max-age=60` on a 302 lets the CDN absorb load while you still see about one request per edge per minute.

## Scaling the reads

A few codes get most clicks (a power law). Each layer catches traffic before Postgres:

1. **CDN.** Caches 301s and short-max-age 302s at the edge.
2. **Redis.** Cache-aside on `u:<code>`, TTL one day capped at expiry. At 4,000 redirects/s and a 95% hit ratio, Postgres sees 200 reads/s.
3. **In-process L1.** A viral link (50K redirects/s on one key) overloads one Redis node; a tiny few-second LRU in each app server absorbs it.
4. **The database.** Key-value by `code`, read replicas, hash-sharded once it outgrows one machine.

Redirects never write to `urls`, so replicas in every region serve them; creation (40/s) stays in one primary region. Cached codes survive a Postgres blip: that's your 99.99%.

## Click analytics

The redirect fires a click event and **never awaits it**:

1. Publish `{ code, ts, referrer }` to a queue while sending the 302.
2. A worker consumes batches of a few thousand.
3. It bulk-inserts them into a columnar store (ClickHouse), partitioned by day.
4. The stats API reads rollups (clicks per day, top referrers), not raw events.

Queue or analytics store down? You lose or delay a few counts, never a redirect. Two details interviewers like: filter out bots and link-preview fetchers (chat apps unfurl every link), and store a country, not the IP.

## Expiry and cleanup

Expired means expired, even when hot in cache.

- **Lazy check on read.** Lookups filter on `expires_at > now()`; cache TTLs are capped at expiry.
- **Nightly cleanup.** Small batches via the partial index on `expires_at`, never a long table lock.
- **Status code.** `410 Gone` with a tombstone, `404` once the row is deleted.
- **Never reuse codes.** Old links live on in emails, PDFs and printed QR codes; reuse sends their clicks to a stranger's destination (phishing). With 3.5 trillion codes, there's no need.

## Abuse and safety

Shorteners are a favourite disguise for malicious links:

- **Rate-limit creation** per user and IP: the API's `429` (see the [rate limiter question](/questions/rate-limiter)).
- **Scan destinations** against malware and phishing lists at creation, and rescan: destinations turn bad later.
- **Block `javascript:` and `data:` URLs.** Allow only `http` and `https`, as `routes.js` does.
- **Keep aliases apart.** Reserve `api`, `admin`, `login`, `static` and brand names. Require 8+ characters or a character codes never use (like `-`), or a user can claim a code the counter will generate later, and that insert fails.
- **Disable, don't delete.** Show a warning page; purge from Redis and the CDN.

## Code

`range-allocator.js` shares one in-flight refill, so a burst on an empty block makes **one** Redis call, not hundreds. `routes.js` validates the scheme, maps a unique violation to `409`, never caches past expiry, and fires the click event unawaited.

## Interview questions

<FollowUps>
  <FollowUp q="Counter-based vs hash-based short codes?">
    Counters: unique and shortest, but need coordination (range allocation removes the hot spot) and are guessable unless scrambled. Hashes: no coordination, but collisions, longer codes, and one shared code per URL.
  </FollowUp>
  <FollowUp q="301 or 302?">
    302 if analytics matter or the link may change; 301 for pure speed, since browsers and CDNs answer and you stop seeing clicks. Very hot links: a 302 with a short `max-age`.
  </FollowUp>
  <FollowUp q="How do custom aliases work?">
    Validate charset and length, check reserved words, let the primary key reject duplicates (409). Keep aliases out of the generated namespace, say longer than 7 characters.
  </FollowUp>
  <FollowUp q="How do you expire links?">
    Store `expires_at`, check it on read (410 or 404), cap cache TTLs at expiry, clean up nightly, and never reuse codes.
  </FollowUp>
  <FollowUp q="A link goes viral (50K redirects/s). Now what?">
    CDN (a 301 or a short-max-age 302), an in-process L1 on every app server so one Redis node isn't the hot spot, and async, batched analytics.
  </FollowUp>
</FollowUps>
