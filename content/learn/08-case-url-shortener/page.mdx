**Redirects matter more than creation.** If creation is down, people retry. If redirects are down, every link ever shared breaks at once.

## Estimation

100M new links a month is **40 writes a second**. At 100 reads per write, that is **4,000 redirects a second**. Six billion links in 5 years is about 3 TB.

One database barely notices 40 writes a second. **The read path is the whole game.** The popular links fit in about 6 GB: one Redis node.

Do the sum first:

| Reads per write | Redirects/s | Plan |
|---|---|---|
| 1 | 40 | One database, no cache |
| 100 | 4,000 | Add Redis; the database would sweat |
| 1,000 | 40,000 | CDN and Redis, no choice |

A private link tool with 1,000 redirects a day needs none of this.

## API

| Method | Path | Result |
|---|---|---|
| POST | `/api/urls` | `201 { code, shortUrl }` · `409` alias taken · `429` rate limited |
| GET | `/:code` | `302` (or `301`) to the long URL · `404` · `410` expired |
| GET | `/api/urls/:code/stats` | `{ clicks, byDay[], topReferrers[] }` |

The redirect lives at the root to stay short, so reserve `api`, `admin` and `login`: they can never be aliases.

## Data model

```sql
CREATE TABLE urls (
  code        varchar(16) PRIMARY KEY,                -- generated (7 chars) or custom alias
  long_url    text        NOT NULL,
  user_id     bigint,
  created_at  timestamptz NOT NULL DEFAULT now(),
  expires_at  timestamptz
);
CREATE INDEX urls_expiry ON urls (expires_at) WHERE expires_at IS NOT NULL;   -- for the cleanup job
```

Every read is a lookup by `code`, with no joins. At scale, use a key-value table sharded by hash of the code. Never count clicks here: 4,000 updates a second would make a read-only table write-hot.

## Generating short codes

<Doodle name="hash-map" size={150} caption />

A short code is a number written with 62 symbols (**base62**: 0-9, a-z, A-Z). Seven symbols give 3.5 trillion codes. Six billion links fill only 0.2% of that, so a random code collides about 1 time in 600.

Where does the number come from?

| Option | Unique? | The catch |
|---|---|---|
| Counter | Yes | Guessable unless scrambled |
| Hash, cut to 7 | Collisions | Check and retry |
| Random + check | Rare retry | Check on every insert |

Use a counter. One counter is a bottleneck, so each app server grabs 1,000 ids at once and hands them out from memory. A crash wastes a block. That is fine: ids must be unique, not contiguous.

## Making sequential ids unguessable

Base62 of a counter only looks random: 1000, 1001, 1002 become `g8`, `g9`, `ga`. Anyone can walk the codes and read private links.

Scramble first: multiply the id by a large constant modulo 62⁷. Every id still gets its own 7-character code, and you can reverse it. `shortCode(1)` is `CjIO2GV`; `shortCode(2)` is `eDrC5nQ`.

<Callout kind="warning" title="Obfuscation, not security">
Two consecutive codes reveal the step. This stops casual guessing, not a determined attacker. If guessing must be impossible, use **random** codes with a uniqueness check.
</Callout>

## 301 vs 302

Both redirect. The difference is who remembers the answer.

A **301** says "moved for good": browsers and CDNs remember it, and repeat clicks never reach you. A **302** says "try here for now": every click comes back, so you can count it.

With a 301, a campaign link whose destination you fix later keeps sending returning visitors to the old page.

| | 301 | 302 |
|---|---|---|
| Every click reaches you | No | Yes |
| Change the destination later | Hard | Easy |
| Speed | Fastest | One extra trip |

Default to 302. For the hottest links, add `Cache-Control: max-age=60`: the CDN absorbs the load, and you still see some requests.

## Scaling the reads

A few links get most of the clicks. Stack caches so most reads never reach the database:

1. **CDN.** Answers at the edge.
2. **Redis.** Remembers recent codes. At 4,000 a second and 95% hits, Postgres sees only 200 reads a second.
3. **A tiny cache in each app server**, so a viral link (50K a second) does not overload one Redis node.
4. **Read replicas** behind it all.

Cached links survive a database blip.

## Click analytics

<Doodle name="queue" size={150} caption />

A redirect never waits for counting. It drops a click note on a **queue** and moves on.

A worker saves notes in batches to an analytics store. The stats page reads daily totals.

If the queue is down, you lose a few counts, never a redirect.

## Expiry and cleanup

Expired means expired, even when the link is hot in cache.

- **Check on read**, and cap cache lifetimes at expiry.
- **Clean up nightly**, in small batches.
- **Answer `410 Gone`**, then `404` once the row is gone.
- **Never reuse codes.** Old links live on in emails and printed QR codes.

## Abuse and safety

Shorteners are a favourite disguise for malicious links.

- **Rate-limit creation** (see the [rate limiter question](/questions/rate-limiter)).
- **Scan destinations** for malware and phishing, and again later.
- **Allow only `http` and `https`.**
- **Keep aliases apart** from generated codes (say 8 or more characters).
- **Disable, don't delete.** Show a warning page and purge the caches.

    302 if you count clicks or may change the link. 301 only for pure speed.

    Check length and reserved words, and let the primary key reject duplicates with a 409.
  </FollowUp>
  <FollowUp q="How do you expire links?">
    Check `expires_at` on read, cap cache lifetimes, clean up nightly, never reuse codes.
  </FollowUp>

    Let the CDN answer, add a tiny cache in every app server, and batch the analytics.
