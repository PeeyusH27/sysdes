<TLDR>
Spend the first 10 minutes on **what** to build and **how big** it is: 3–5 core features, concrete targets for latency, availability and consistency, then round-number estimates (average QPS = `DAU × actions ÷ 86,400`, peak ≈ 3×). Every number should justify a design choice later.
</TLDR>

## Why it matters

One server or fifty? A cache or a shard? The numbers decide: "add a cache" is a guess until you know reads outnumber writes 100 to 1. Without requirements you solve the wrong problem, and interviewers grade this process as much as the final picture.

Written scope also protects you: when "and it should support video" arrives at minute 30, you reply "that changes the storage estimate".

## The interview flow

45 minutes goes fast. Announce the plan up front ("five minutes on requirements, a quick estimate, then the design") so the interviewer sees you managing the clock.

## Functional requirements

"Design Twitter" is vague on purpose: the interviewer wants to watch you narrow it to **what users can do**. Ask three questions:

- **Who are the users?** Readers, writers, admins? Internal teams? Mobile, web or both? On most social products a few write and almost everyone reads.
- **What are the 3 core actions?** Name the verbs: post, follow, read the timeline.
- **What can be cut?** "I'll leave out DMs, search and ads unless you'd like one of them." Cutting signals seniority.

Sort features into must (no product without them), should (likes, a user's own profile timeline) and won't today (each is a whole interview). The board for Twitter-lite:

/>

## Non-functional requirements

"Fast" isn't a requirement; "p99 under 200 ms" is. Non-functional requirements say **how well** the system works, each with a number. No number given? Propose one: "I'll assume 100M daily users; tell me if that's off."

| Requirement | Example target | What it forces |
|---|---|---|
| Latency | p99 under 200 ms for reads | Caches, CDN, precomputation |
| Availability | 99.99% | Multi-zone redundancy, no single point of failure, graceful degradation |
| Consistency | Strong for payments, eventual for likes | Different stores per feature |
| Durability | Never lose an order | Replication, write-ahead log, backups |
| Scale | 100M DAU | Sharding, queues, horizontal scale |

Quote **p99**, not averages: the slowest 1% are the requests users complain about. Translate nines into downtime: 99.9% allows about 8.8 hours a year, 99.99% about 53 minutes. And set targets **per feature**: the timeline can be eventually consistent while the follow button must be read-your-writes.

## Back-of-envelope math

You want the right order of magnitude in under five minutes. Round hard (86,400 becomes 100,000; say "about") and fill in five quantities plus the server count:

| Quantity | How | 10M DAU × 10 actions, 10:1 reads |
|---|---|---|
| Average QPS | `DAU × actions ÷ 86,400` | ~1,160/s (1,050 reads, 105 writes) |
| Peak QPS | average × 3 (2–5×; 10× for events) | ~3,500/s |
| Storage | write QPS × 86,400 × days × bytes × replicas | ~50 TB over 5 years at 1 KB, 3 replicas |
| Bandwidth | QPS × bytes per request | in ~0.1 MB/s; out ~2 MB/s at 2 KB per read |
| Cache memory | 20% of a day's reads × item size | ~18 GB: fits on one Redis node |
| Servers | `peak ÷ (per-server QPS × 0.6)` | 6 at 1,000 req/s each, 60% busy |

Peak QPS grows linearly with users (10 actions a day, 3× peak), and roughly every 10× changes the architecture:

## Read vs write ratio

Same QPS, different architecture: reads scale with caches and replicas, writes with sharding and queues. Always split them.

| Ratio (reads:writes) | Typical products | Consequence |
|---|---|---|
| 100:1 or more | URL redirects, news feeds, product pages | Cache aggressively, CDN, read replicas, precompute results |
| ~10:1 | Typical web apps, e-commerce | Cache hot entities, a couple of replicas; one primary usually suffices |
| ~1:1 | Chat, collaborative editing | Writes are the hot path: partition by conversation, append-only storage |
| Write-heavy | Metrics, logs, IoT, click streams | Queues for bursts, LSM stores (Cassandra), batched writes, downsampling |

## Worked example: Instagram-lite

Whiteboard style: **100M DAU**, 10% upload 2 photos a day, everyone opens the feed 10 times a day, peak is 3× average.

<Steps>
  <Step title="Uploads per second">
    100M × 10% × 2 = **20M uploads a day** ≈ **230/s**, ~**700/s** at peak. One primary handles the metadata writes.
  </Step>
  <Step title="Media storage">
    20M × 500 KB = **10 TB a day**, ~**3.65 PB a year** before replication. Bytes go to **object storage** (S3); the database keeps metadata (~20 GB a day at 1 KB a row).
  </Step>
  <Step title="Feed reads">
    100M × 10 views = **1B feed loads a day** ≈ **11.6K/s**, ~**35K/s** at peak: 50× the uploads, so cache and precompute this path.
  </Step>
  <Step title="Egress bandwidth">
    10 thumbnails × 50 KB = 500 KB per view. 11.6K/s × 500 KB ≈ **5.8 GB/s** ≈ **46 Gbps** (bytes × 8). Serving that yourself is expensive and slow far from your region: a **CDN is non-negotiable**.
  </Step>
  <Step title="Say what it means">
    "Writes are small and steady, so one Postgres primary with replicas handles metadata. Photos go to object storage behind a CDN. The feed is the hot path at 35K reads/s, so I'll precompute feeds into a cache and spend the deep dive there."
  </Step>
</Steps>

## Numbers to remember

Memory is about 1,000× faster than an SSD read, and one cross-continent round trip costs as much as 10 to 100 indexed database reads. Approximate values; the [cheatsheet](/cheatsheet) repeats them.

| Quantity | Value |
|---|---|
| Seconds per day | 86,400 ≈ 10⁵, so 1M requests/day ≈ 12/s |
| Seconds per month / year | ≈ 2.6M (100M/month ≈ 40/s) / ≈ 31.5M |
| 2¹⁰ / 2²⁰ / 2³⁰ / 2⁴⁰ | ≈ thousand / million / billion / trillion: KB, MB, GB, TB |
| Main memory / SSD random read | ~100 ns / ~100 µs |
| Datacenter round trip / Redis GET | ~0.5 ms / ~0.5–1 ms over the network |
| Indexed database read / HDD seek | ~1–10 ms / ~10 ms |
| Cross-continent round trip | ~100–150 ms |
| Typical web API instance | hundreds to a few thousand req/s (assume, then say "I'd measure") |
| One Redis instance | ~100K simple ops/s |
| One Postgres primary | thousands to tens of thousands of simple queries/s, depending heavily on the query |

## Interview questions

<FollowUps>
  <FollowUp q="How do you estimate QPS?">
    DAU × actions ÷ 86,400 for the average, 2–5× for peak, reads and writes split: 10M DAU × 10 actions ≈ 1,160/s, about 3,500/s at peak.
  </FollowUp>
  <FollowUp q="Estimate storage for 5 years of tweets.">
    200M DAU × 2 tweets × ~1 KB = 400 GB a day, 146 TB a year, 730 TB over 5 years, ≈ 2.2 PB with 3 replicas. Estimate media separately: it lives in object storage.
  </FollowUp>
  <FollowUp q="Why split read and write QPS?">
    They scale with different tools (caches and replicas vs sharding and queues), so a 100:1 and a 1:1 system at the same QPS get different architectures.
  </FollowUp>
  <FollowUp q="What peak factor do you use?">
    2–5× average for daily traffic, 10× or more for events like sales and launches. Size for peak at 60–70% utilisation and autoscale the rest.
  </FollowUp>
  <FollowUp q="How many app servers for 3,500 peak QPS?">
    At ~1,000 req/s each and 60% busy, 3,500 ÷ 600 → 6. Run 3 per zone in three zones (9 total) so losing a zone still leaves 6.
  </FollowUp>
</FollowUps>
