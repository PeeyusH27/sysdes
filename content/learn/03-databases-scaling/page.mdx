<TLDR>
Pick a store by **access pattern**, index the queries you run, and scale reads with replicas. Shard last, on a key that matches your main query.
</TLDR>

## Why it matters

Lost orders and double bookings happen in the database. Copies of data must agree, so it is the hardest part to scale.

Take the cheapest move first: **indexes → a bigger machine → a cache → read replicas → sharding**.

| You see | Try first |
|---|---|
| A page takes 2 s at 300 queries/s | An index: `EXPLAIN` shows a `Seq Scan` |
| 10,000 reads/s, 95% of them reads | A cache, then replicas |
| Several TB, or writes one primary can't take | Shard |

## How storage engines work

Two designs, opposite bets. A **B-tree** updates sorted pages in place, so reads stay fast and predictable. An **LSM tree** only appends, so writes are fast; background **compaction** merges its files.

| | B-tree | LSM tree |
|---|---|---|
| Best at | Read-heavy and mixed workloads, range scans | Write-heavy ingest: events, messages, time series |
| Costs | Random writes, page splits | Compaction work; slower, less predictable reads |
| Used by | Postgres, MySQL InnoDB, SQL Server | Cassandra, RocksDB, ScyllaDB, HBase |

## Transactions and isolation levels

Two doctors on call each check "is anyone else on call?", see yes, and both go off call. That is an isolation bug.

**Isolation** decides what concurrent transactions see of each other. Weaker levels allow:

- **Dirty read**: seeing an uncommitted change.
- **Non-repeatable read**: a row changes between two reads.
- **Phantom**: a range query finds new rows on the second run.
- **Write skew**: two transactions write *different* rows and together break a rule (the doctors).

| Level | Prevents | Still possible |
|---|---|---|
| Read committed (Postgres default) | Dirty reads | Non-repeatable reads, phantoms, write skew |
| Repeatable read (MySQL InnoDB default) | Dirty and non-repeatable reads | Phantoms (per the SQL standard; Postgres's snapshot prevents them), write skew |
| Serializable | All four | Nothing |

For rules across rows, use **SERIALIZABLE** or `SELECT … FOR UPDATE`, and retry failures. Often a constraint is simpler: `UNIQUE (room_id, slot)`.

## Indexes

An index buys fast reads with slower writes. Index the queries you run, not the columns you have:

- **Leftmost prefix.** `(user_id, created_at)` serves `WHERE user_id = ?` but not `created_at` alone. Equality columns first, then range or sort.
- **Covering and partial.** `INCLUDE (total)` lets the index alone answer the query; `WHERE status = 'pending'` indexes only some rows.
- **Every index costs writes.** Drop unused ones.
- **Read `EXPLAIN ANALYZE`.** Watch for a `Seq Scan` on a big table.
- **Build online** with `CREATE INDEX CONCURRENTLY`, which doesn't block writes.

## Modeling: normalize, then denormalize

Store each fact once, then copy the hot ones on purpose.

**Normalize first**, so copies can't disagree. **Denormalize for hot reads**: a `comment_count` on posts, the author's name in feed items. Update every copy together.

## SQL vs NoSQL

Pick by access pattern. SQL gives joins and transactions. NoSQL gives flexible schemas and easier horizontal scale.

| Store | Pick it for | Examples |
|---|---|---|
| Relational | Orders, payments, anything with rules | Postgres, MySQL |
| Key-value | Sessions, carts, counters | Redis, DynamoDB |
| Wide-column | Huge append-heavy data: feeds, messages | Cassandra, Bigtable |
| Document | Nested records read whole: profiles | MongoDB |

Bad fits: a money transfer on a store with no multi-row transactions, or a sensor firehose of 100K writes/s on one Postgres primary. Real systems mix them: Postgres for orders, Redis for sessions, a search index for the catalog.

## Replication

A **replica** is a copy that only answers reads. It adds read capacity and a standby. The catch is lag: it trails the primary, and **how long a commit waits** decides what you can lose.

| Mode | A commit waits for | If the primary dies |
|---|---|---|
| Async | Only the primary's disk | The last few writes can be lost |
| Semi-sync | One replica to receive it | Nothing lost, if that replica survives |
| Sync | All replicas to confirm | Nothing lost, but one slow replica stalls every write |

Replicas scale reads only. If writes are the bottleneck, more replicas make it worse, since each one replays every write.

Most setups have one leader that takes all writes. Multi-leader and leaderless setups add conflicts to resolve; see [Consistency and CAP](/learn/consistency-cap).

Lag breaks two promises:

- **Read-your-writes**: you save, read a lagging replica, and your change seems lost. Read from the primary for a few seconds after a write.
- **Monotonic reads**: data goes back in time between replicas. Pin each user to one replica.

## Failover

The primary dies. Play **Failover** to watch a replica take over:

1. **Detect**: several missed heartbeats, so a blip doesn't trigger it.
2. **Promote** the replica with the newest log.
3. **Reconfigure**: point DNS or a proxy at the new primary.
4. **Fence the old primary.** If it returns believing it is primary, two nodes take writes: **split brain**. Cut its access.

**RPO** (recovery point objective) is the data you lose: with async replication, writes that hadn't shipped. **RTO** (recovery time objective) is time down: tens of seconds with automated failover.

## Sharding

<Doodle name="shard" size={150} caption />

Split the data over several databases, each owning a slice (a **shard**). It is a one-way door: every query must now know its shard. Shard last, when one primary can't keep up with **writes** or **data size**: several terabytes, or tens of thousands of writes a second.

| Strategy | Good | Bad |
|---|---|---|
| Hash: `hash(key) % N` | Even spread | Range scans hit every shard |
| Range: each shard owns a key range | Range scans, easy splits | Sequential keys make one hot shard |
| Directory: a lookup table | Full control | The directory is a dependency |

A good shard key has **high cardinality** (`user_id`, not `country`) and matches your main query. Shard by `country` and one shard holds most users while the rest sit idle. Never range-shard on a rising key like time: every new write hits the last shard.

Harder afterwards: cross-shard joins and transactions, hot keys, resharding. From 4 to 5 shards, `hash % N` moves about 80% of users. See the [sharding deep dive](/deep-dives/sharding-strategies).

## Backups and point-in-time recovery

**Replicas are not backups**: a `DROP TABLE` reaches every replica within milliseconds.

- **Base backups plus WAL archiving**: full backups plus every write-ahead log segment. Replay to any moment: "restore to 14:31:59, before the bad deploy".
- **Restore drills**: an untested backup is a hope. Restore on a schedule and time it.
- Keep copies in another region and account.

## Place the read replica

One node is hidden: the one the app reads from.

## Interview questions

<FollowUps>
  <FollowUp q="How would you shard a users table, and what can go wrong?">
    Hash `user_id`. Watch hot keys, cross-shard lookups like "find by email", and resharding cost.
  </FollowUp>
  <FollowUp q="How do you handle replication lag?">
    Read your own writes from the primary for a few seconds. Pin a session to one replica.
  </FollowUp>
  <FollowUp q="SQL or NoSQL for orders vs an activity feed?">
    Orders need transactions: SQL. A feed is huge, append-heavy and read by key and time: wide-column or key-value.
  </FollowUp>
  <FollowUp q="How do you stop two people booking the same slot?">
    A unique constraint, or SERIALIZABLE with retry. Check-then-insert races.
  </FollowUp>
  <FollowUp q="How do you add an index to a 500M-row table without downtime?">
    `CREATE INDEX CONCURRENTLY`. If it fails, drop the invalid index and retry.
  </FollowUp>
</FollowUps>
