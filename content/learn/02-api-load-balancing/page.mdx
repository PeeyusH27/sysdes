<TLDR>
Make services **stateless** and put a **load balancer** in front: capacity becomes "add a machine", and a crash loses nothing. Then give the API correct status codes, cursor pagination and idempotency keys.
</TLDR>

## Why it matters

One server is a ceiling and a single point of failure. Stateless servers behind a balancer make crashes and spikes routine: the balancer routes around a dead instance.

The API on top is every client's contract, so status codes and safe retries are design, not polish.

This page follows the order you would say it in an interview: where state lives, how requests are spread, what goes wrong when one server misbehaves, and how the API survives retries.

## The request path

Do you need a balancer yet? At 200 req/s one server has room, but a second behind a balancer means deploys and crashes cost nothing. At 5,000 req/s peak you need it for capacity too.

Each hop before your code adds one thing:

| Hop | What it adds |
|---|---|
| **DNS and CDN** | The nearest region; static files from the edge |
| **Load balancer** | Spreads requests over healthy instances |
| **API gateway** | Auth, rate limits, routing to the right service |
| **Services and data** | Stateless logic; state lives in databases, caches and queues |

## Stateless services

Stateless doesn't mean no state. It means **no instance owns any**, so any instance can serve any request, and any can die.

| State | Where it goes instead |
|---|---|
| Sessions, login | Redis with a TTL, or a signed token |
| Uploaded files | Object storage (S3) behind the CDN |
| Counters, locks | Redis |
| Business data | The database |

Long jobs go to a queue. The hardest piece to move is the login session. Play **Sticky-session pitfall** to see why it matters, then pick one of three places for it.

<FlowDiagram spec={requestPath} scenario="sticky" />

### Sticky sessions: pin the user

**Sticky sessions** make the balancer send a user to the same instance every time, so that instance can keep the session in its own memory. It is the quickest fix and the weakest one.

<FlowDiagram spec={stickyPin} />

Play **Pinned**, then **B restarts**. Use it only as a stopgap, or when an instance really holds a connection (a WebSocket, see below). It costs you every deploy, every crash and every scale-in: each one logs out everyone pinned to that instance. A hot user group also cannot be rebalanced, because the pin overrides the algorithm.

### Shared session store: the default

A **shared session store** moves the session out of the instance and into Redis, keyed by a random id in a cookie. Any instance can serve any user, and this is the default answer.

Play **Fix: shared session store**: Service B writes the session to Redis and Service A reads it.

<FlowDiagram spec={requestPath} scenario="fix" />

Use it for logged-in web apps. The session lookup is about 1 ms per request, and 1 million active sessions at about 1 KB each is about 1 GB of Redis. The cost is one more dependency on the hot path: if Redis is down, nobody can log in, so run it replicated.

### Signed tokens: store nothing

A **signed token** puts the session inside the token the client carries, so the server stores nothing and verifies the signature with a shared key. Any instance can check it in microseconds, with no network call.

<SequenceDiagram spec={tokenAuth} />

Use it for APIs called by apps and other services, where a lookup per request is unwelcome. The catch is revocation: a signed token stays valid until it expires. Keep lifetimes short (15 minutes) with a refresh token, or keep a small deny list in Redis for forced logouts.

## L4 vs L7 load balancing

L4 sees connections; L7 reads requests.

| | L4 (TCP/UDP) | L7 (HTTP) |
|---|---|---|
| Sees | IP and port | URL, headers, cookies |
| Can do | Fast forwarding, any protocol | Path routing, TLS termination, retries, canaries |
| Cost | Very low | More CPU per request |
| Examples | AWS NLB, IPVS, Maglev | AWS ALB, NGINX, Envoy, HAProxy (HTTP mode) |

Most stacks use both: L4 spreads connections over L7 proxies. Pick by what you need to see.

<DecisionTree spec={pickLayer} />

### L4: forward connections

An **L4 balancer** picks a server once per TCP connection and forwards bytes without reading them. That makes it very fast, and it works for any protocol, not just HTTP.

<FlowDiagram spec={l4Route} />

Use it for raw TCP or UDP, databases, game traffic, or as the outer tier in front of a proxy fleet. Play **The long-connection trap**: because it chooses per connection, one gRPC or HTTP/2 connection that carries 1,000 requests a second sends all 1,000 to one server.

### L7: route by request

An **L7 balancer** terminates TLS, reads the HTTP request and decides per request. That unlocks everything an API needs: path routing, header rules, retries on another instance and gradual rollouts.

<FlowDiagram spec={l7Route} />

Use it as the default for HTTP services. A canary at 5% means 1 request in 20 reaches the new version, so a bad release hurts 5% of users for ten minutes instead of all of them. The cost is CPU: it parses every request, and it holds the TLS keys.

### Both together

Use both when you outgrow one proxy: a pair of L4 balancers gives clients one stable IP and spreads connections over a fleet of L7 proxies. Clients never notice when you add or remove a proxy.

<FlowDiagram spec={bothLayers} />

On a managed cloud, a single L7 balancer (an ALB, for example) is enough until traffic or protocol needs say otherwise. Start with one box and name the reason before adding a second tier.

## Balancing algorithms

Which healthy instance gets the next request? Round robin is simple, until one server is slow: it stays on the rotation, its queue grows, timeouts trigger retries, and the retries bury it.

| Algorithm | Wins when | Weakness |
|---|---|---|
| Round robin | Same servers, uniform calls (5 ms lookups) | Keeps feeding a slow server |
| Least connections | Mixed calls (exports beside lookups) | Needs an accurate count |
| Power of two choices | Many balancers, large fleets | Slightly less precise |
| IP or consistent hash | Per-key affinity, like cache servers | A celebrity key overloads one server |

Not sure which fits? Walk the tree.

Try them in the simulator: make server C slow under **round robin** and watch its queue grow, then switch to **P2C**.

<LoadBalancerSim />

### Round robin: the default

**Round robin** hands out requests in turn: A, B, C, A, B, C. It is the default, because it needs no state and gives a perfectly even split when servers and requests are alike.

<FlowDiagram spec={rrSlow} />

Use it for stateless services with uniform calls, such as 5 ms lookups on identical machines. Play **C turns slow**: it ignores load, so a slow server keeps a third of the traffic.

<CodeTabs files={['snippets/round-robin.js']} />

### Weighted round robin

**Weighted round robin** gives each server a share in proportion to its weight, which suits a fleet of mixed sizes. A 16-core machine with weight 5 sits beside two 4-core machines with weight 1.

Weights 5, 1, 1 give `a a b a c a a` and not five `a` in a row, because the smooth variant spreads the turns. Use it during a migration between instance types, or when a few machines are much bigger. It still ignores live load, so it only fixes a size mismatch.

<CodeTabs files={['snippets/smooth-weighted-rr.js']} />

### Least connections

**Least connections** sends each request to the server with the fewest requests in flight. A server that holds requests longer gets fewer, so slow servers and long requests balance themselves.

<FlowDiagram spec={leastConn} />

Use it when request costs vary: a 5-second CSV export beside 5 ms lookups, or WebSocket-like long calls. The cost is an accurate count, which one balancer has but a fleet of balancers does not share. A brand new instance also starts at zero, which causes the flood in the failure section below.

<CodeTabs files={['snippets/least-connections.js']} />

### Power of two choices

**Power of two choices (P2C)** picks two servers at random and takes the less loaded. It balances almost as well as least connections, with no shared state and no scan of the fleet.

<FlowDiagram spec={p2cFlow} />

Use it when many proxies or balancers each see only part of the traffic, as in Envoy or a service mesh. Random assignment alone leaves the busiest server far above average; comparing just two random picks removes most of that gap, which is why the idea is famous. Its weakness is only a slightly coarser balance than a global count.

<CodeTabs files={['snippets/p2c.js']} />

### Hashing: same key, same server

**Hashing** picks the server from a key such as the user id or client IP, so the same key always reaches the same server. That keeps per-key state warm: local caches, shards, WebSocket sessions.

<FlowDiagram spec={hashRoute} />

Use **consistent hashing** rather than hash mod N. Going from 4 nodes to 3 with plain mod moves 75% of keys, because only keys where `k mod 4` equals `k mod 3` stay put. Consistent hashing moves only the 25% that lived on the removed node. The weakness is a hot key: one celebrity user overloads their server while the others idle. See the [sharding strategies deep dive](/deep-dives/sharding-strategies).

## Health checks

The balancer can only route around failures it can see. Four mechanisms cover it, and each answers a different question. Play **Instance failure** first for the whole story.

<FlowDiagram spec={requestPath} scenario="failure" />

### Active checks

**Active checks** have the balancer probe each instance on a schedule, usually `/readyz` every few seconds. **3 failures mark it down, 2 successes mark it up**, so a blip cannot flap an instance in and out.

<SequenceDiagram spec={healthSeq} />

Use it everywhere; it is the baseline. The cost is detection time. With a 5 s interval and 3 failures, a dead instance takes about 15 s to be noticed. At 900 req/s over three instances, that is 300 req/s sent to a corpse for 15 s: about 4,500 failed requests, unless the proxy retries them.

### Passive checks

**Passive checks** watch real traffic: an instance that returns 5 consecutive 5xx is ejected for 30 seconds. They catch what a probe misses, such as an instance that passes `/readyz` but fails real requests.

<FlowDiagram spec={passiveEject} />

Use them next to active checks, never instead. They react at request speed, but they only learn from real users failing, so pair them with a retry on another instance for idempotent requests.

### Liveness vs readiness

**Liveness** asks "is it alive?" (fail: restart the process). **Readiness** asks "should it get traffic?" (fail: stop routing, but leave it running). Keep readiness narrow: check only what this instance cannot work without, such as its own database connection.

<FlowDiagram spec={readinessTrap} />

Play **Wrong: depend on it**. If `/readyz` also calls an optional recommendations service, then when recommendations goes down every instance fails at once, and the whole site returns 503 over a carousel. Play **Right: degrade** for the fix: stay ready, drop the feature, and put a short timeout and a circuit breaker on the call.

### Connection draining

**Connection draining** lets an instance finish what it started before it leaves. On `SIGTERM` it fails readiness, the balancer stops sending new requests, and in-flight ones complete.

<SequenceDiagram spec={drainSeq} />

Without it, every deploy cuts requests in half. Set the grace period above your slowest normal request, for example 30 s. Cloud balancers call this deregistration delay; AWS target groups default to 300 s.

## When load balancing goes wrong

Most load balancer outages are not the balancer dying, they are a small fault that the balancer spreads. Four stories repeat, and each has a fix you can name.

### The slow-server spiral

A slow server turns into a fleet-wide outage through timeouts and retries. Play **The spiral**.

<FlowDiagram spec={spiral} />

Scene: 13:00, a sale starts at 900 req/s, and server C exhausts its database pool. Its calls go from 20 ms to 2 s. Round robin still sends C 300 req/s, and by Little's law (in flight = rate times latency) that is about 600 requests in flight on C instead of about 6. Clients time out at 1 s and retry, which pushes more load onto A and B.

Fix it in three layers: least connections or P2C so a slow server gets less, outlier ejection so a failing one gets none, and timeouts plus a retry budget so clients do not multiply the load. Play **The fix**.

### Retry storm

A **retry storm** is retries adding load to something already failing. Three retries per failed call can turn 1,000 req/s into 4,000 req/s on a server that could not handle 1,000.

Try the simulator: compare no retries, fixed retries and exponential backoff with full jitter.

<RetryStorm />

Fix it with exponential backoff and jitter, a **retry budget** (retries may add at most about 10% extra requests), and a circuit breaker. Retry only idempotent requests, and retry on a different instance than the one that just failed.

### A new instance gets flooded

Least connections can flood a brand-new instance. The autoscaler adds one during a spike, it reports ready with 0 open requests, and the balancer sends it nearly everything while its caches, connection pools and runtime are still cold.

<FlowDiagram spec={herd} />

Play **Flooded**, then **Slow start**. The fix is slow start: ramp the instance from 10% to full weight over 30 to 60 s, and only report ready after a warm-up call. Round robin and P2C hit this far less.

### The balancer is a single point of failure

One balancer is one more machine that can fail, and everything sits behind it. Run at least two, in different zones, and steer clients away from a dead one.

<FlowDiagram spec={lbPair} />

Play **One dies**. DNS with health checks can drop a dead address, but clients that cached it keep trying until the TTL (60 s here) runs out. Managed balancers (ALB, NLB) are already spread across zones and handle this for you. On your own hardware, use a floating IP shared by a pair, or anycast.

## Sizing the fleet

Size for the peak, not the average, and run well below full. A server at 90% busy has almost no room for a spike and answers slowly even before it fails.

In the simplest queueing model (random arrivals, one queue), average response time is the service time divided by one minus utilisation. So the cost of running hot is steep.

<LineChart title="Average response time by utilisation" x={[0.3, 0.5, 0.6, 0.7, 0.8, 0.9, 0.95]} series={[{ id: "latency", name: "Response time", values: [1.43, 2, 2.5, 3.33, 5, 10, 20] }]} xLabel="Utilisation" yUnit="x service time" xFormat="percent" />

Worked example: peak 5,000 req/s, and one instance does 500 req/s flat out.

| Step | Arithmetic | Result |
|---|---|---|
| Plan for 60% busy | 500 x 0.6 = 300 req/s each | 5,000 / 300 = 17 instances |
| Lose one of 3 zones | 2 zones must carry the peak | 7 per zone, 21 total |
| Check the survivors | 5,000 / 14 = 357 req/s | 71% busy, still fine |
| In flight per instance | 300 req/s x 20 ms | 6 requests |

Keep headroom instead of trusting autoscaling for the first spike: a new instance needs a minute or two to boot and warm up. Use autoscaling for the slow growth, and headroom for the sudden jump.

## REST API design

Be predictable: plural nouns for resources, HTTP for verbs, one level of nesting. Clients guess your API correctly when it follows the rules they already know.

### Resources and verbs

Model **nouns as resources** and use the HTTP method as the verb. `GET /orders` lists, `GET /orders/123` reads one, `POST` creates, `PUT` replaces, `PATCH` changes some fields, and `DELETE` deletes.

Other actions are sub-resources: `POST /orders/123/cancel`. Do not put verbs in paths like `/getOrders`. Keep nesting to one level (`/users/7/orders`); deeper trees force clients to know every parent id.

### Status codes

**Status codes** tell clients and proxies what happened, so pick them by asking the questions in order. Walk the tree, then use the table as a reference.

<DecisionTree spec={statusTree} />

| Code | Use it for |
|---|---|
| 200 OK | Success with a body: reads, updates returning the resource |
| 201 Created | Created by a POST; add a `Location` header |
| 202 Accepted | Queued, not done: return a job id or status URL |
| 204 No Content | Success, no body: DELETE, or PUT with nothing to return |
| 301 / 302 | Moved permanently / temporarily; browsers cache 301 |
| 304 Not Modified | Client's copy still valid (conditional GET, `If-None-Match`) |
| 400 Bad Request | Malformed: invalid JSON, a missing field |
| 401 Unauthorized | Not authenticated: missing or expired token |
| 403 Forbidden | Authenticated, not allowed: Alice reading Bob's orders |
| 404 Not Found | No such resource (or hiding that one exists) |
| 409 Conflict | Clashes with current state: duplicate, version mismatch, key in progress |
| 422 Unprocessable Content | Well-formed but invalid: end date before start date |
| 429 Too Many Requests | Rate limited; always add `Retry-After` |
| 500 Internal Server Error | Bug or unexpected failure, never a client mistake |
| 503 Service Unavailable | Overloaded, shedding load or failing readiness; add `Retry-After` |

The worst mistake is returning 200 with an error in the body: clients, proxies and monitoring all count it as a success.

### Long jobs: accept, then poll

A job that takes a minute should not hold a connection open. Return **202 Accepted** with a status URL, run the work on a queue, and let the client poll.

<SequenceDiagram spec={asyncJob} />

Use it for exports, video processing and bulk imports: anything over about 1 to 2 seconds. The cost is a second endpoint and a job record. Play **Still running** and **Done**.

### Versioning and errors

Put the **major version in the path** (`/v1/orders`). Adding an optional field needs no new version; removing or renaming one does.

Scene: you rename `total` to `totalCents` on Friday. Mobile app 4.2, which users update slowly, reads `undefined` and shows a blank price until you roll back. Keep changes additive, and run `/v1` and `/v2` side by side until old clients fade.

**Errors** should be machine-readable. RFC 9457 "problem details" is the standard shape:

```json
{ "type": "https://example.com/problems/out-of-stock", "title": "Out of stock",
  "status": 409, "detail": "SKU a1 has 0 units left", "instance": "/orders/123" }
```

## Pagination and safe retries

Page 50 of a feed, and the same POST sent twice: every busy API meets both. Offsets suit admin tables; feeds need cursors; and any POST that moves money needs an idempotency key.

| | Offset: `?page=3&limit=20` | Cursor: `?cursor=…&limit=20` |
|---|---|---|
| Query | `LIMIT 20 OFFSET 40` | `WHERE id < $1 ORDER BY id DESC LIMIT 21` |
| Deep pages | Slow: reads and discards every skipped row | Fast: seeks straight into the index |
| New items arrive | Rows shift: duplicates and skips | Stable |
| Jump to page 50 | Yes | No, only next (and previous) |
| Good for | Admin tables, numbered search results | Feeds, timelines, infinite scroll, sync APIs |

### Offset pagination

**Offset pagination** says "skip N rows, then give me 20". It is simple and lets users jump to page 50, but the database must read every skipped row.

<FlowDiagram spec={offsetScan} />

Play **Page 50,000**: `OFFSET 999980` reads about a million rows to return 20. The chart shows rows read as the page number grows; a cursor stays flat at 21.

<BarChart title="Rows read per request, 20 per page" unit="rows" scale="log" data={[{ label: "Offset, page 1", value: 20 }, { label: "Offset, page 50", value: 1000 }, { label: "Offset, page 5,000", value: 100000, display: "100,000" }, { label: "Offset, page 50,000", value: 1000000, display: "1,000,000" }, { label: "Cursor, any page", value: 21 }]} />

Use it for admin tables and numbered search results with a few hundred pages at most, where users really jump around. The cost is slow deep pages, and duplicates or gaps while data changes under the reader. Play **A new post arrives**.

### Cursor pagination

**Cursor pagination** says "give me 20 rows after the last one I saw". The cursor encodes that last row, and the database seeks straight to it through an index, so every page costs the same.

<FlowDiagram spec={cursorSeek} />

Use it for feeds, timelines, infinite scroll and sync APIs. It is the default for anything that grows. The cost: no jump to page 50, only next and previous, and the sort key must be unique and indexed, so sort on `(created_at, id)` when timestamps can tie.

<CodeBlock src="snippets/cursor-pagination.js" />

Cursor on `(created_at, id)`? Send the timestamp as text (`created_at::text`), or rows get skipped: Postgres keeps microseconds, JavaScript only milliseconds.

### Idempotency keys

Networks fail after the server did the work, so clients retry. A retried `POST /payments` must not charge twice. The client sends one UUID as an **`Idempotency-Key`**; the server claims it with `SET NX`, stores the response and replays it for repeats.

<SequenceDiagram spec={idemSeq} />

Scene: Black Friday, 20:02. A shopper's phone loses signal just after sending a 49.00 payment. The charge succeeded, the response was lost, the app retries. Without a key the card is charged twice; with one, the retry replays the first response. Play **Retry after a timeout**.

A duplicate that arrives while the first is still running gets **409**. Keep keys for about 24 hours (86,400 s in the snippet), and scope them to the user so one customer cannot replay another's.

<CodeBlock src="snippets/idempotency.js" />

GET, PUT and DELETE are safe to retry; PATCH isn't necessarily. Never auto-retry a POST without a key.

## API styles compared

Pick the style by who is calling. REST is the default; each other style earns its place by solving one specific problem.

| Style | Best fit | Strengths | Costs |
|---|---|---|---|
| REST | Public APIs, CRUD on resources | Simple, HTTP caching, tooling everywhere | Over- or under-fetching; several round trips per screen |
| GraphQL | Many clients wanting different shapes of the same data | Client picks fields; one round trip; typed schema | N+1 resolvers, harder HTTP caching, needs query cost limits |
| gRPC | Internal service-to-service calls | Compact typed Protobuf; HTTP/2 streaming; generated clients | Browsers need gRPC-Web; binary is harder to debug |
| WebSocket | Chat, multiplayer, collaborative editing | Full duplex, low latency | Stateful connections: harder to balance, scale and deploy |
| SSE | Notifications, live scores, progress, streamed LLM tokens | Plain HTTP, automatic reconnect | Server to client only; text only |

Answer these questions in order to choose.

<DecisionTree spec={apiPick} />

### REST: the default

**REST** is resources over HTTP, and it is the default answer. Every proxy, CDN, browser and tool understands it, and responses cache by URL.

<FlowDiagram spec={restScreen} />

Use it for public APIs and most CRUD, as described above. Play **One screen, three calls**: it costs extra round trips and extra fields on screens that combine resources. Reach for another style only when you can name that cost as the problem.

### GraphQL: the client picks fields

**GraphQL** lets the client describe exactly the fields it wants in one request, against a typed schema. One round trip replaces several, and each client gets its own shape.

<FlowDiagram spec={graphqlFlow} />

Use it when several client types (web, iOS, Android, partners) need different slices of the same data, and screens combine many resources. Play **One query**: about 80 ms of network instead of 240. The costs: the N+1 trap (play it; batch with a loader), HTTP caching by URL is gone because everything is a POST, and you must limit query depth and cost, or one query can ask for the whole database.

### gRPC: typed calls between services

**gRPC** calls remote methods defined in a shared `.proto` file, with compact binary Protobuf messages over a long-lived HTTP/2 connection. Clients and servers are generated, so a wrong field is a compile error.

<FlowDiagram spec={grpcFlow} />

Use it for internal service-to-service traffic with tight latency or streaming. The costs: browsers need a gRPC-Web proxy (play **From a browser**), binary payloads are harder to debug, and its long connections need L7 or client-side balancing, as the L4 section showed.

### WebSocket: a two-way channel

A **WebSocket** keeps one connection open so either side can send at any time. It is the right tool for chat, multiplayer games and collaborative editing.

<FlowDiagram spec={wsFlow} />

Use it only when both directions are frequent, because it makes the servers stateful. Play **A message across servers**: Alice and Bob sit on different servers, so the servers need pub/sub between them. If one machine holds about 100,000 sockets (an assumption; measure yours), 1 million users need 10 machines plus headroom. A deploy drops every socket, so clients reconnect with jitter. Play **A deploy drops sockets**.

### Server-sent events: one-way push

**Server-sent events (SSE)** keep one plain HTTP response open while the server writes events. The browser reconnects on its own and resumes from the last event id it saw.

<SequenceDiagram spec={sseSeq} />

Use it when only the server speaks: notifications, live scores, progress bars, streamed LLM tokens. It is far cheaper to run than WebSockets, because it is ordinary HTTP. The costs: server to client only, and text only. The [polling, SSE and WebSockets deep dive](/deep-dives/polling-sse-websockets) compares the real-time options.

## API gateway and BFF

An **API gateway** handles auth, rate limiting and routing, so services stick to business logic. A **backend for frontend (BFF)** shapes responses per client type.

### API gateway

An **API gateway** is the single front door: it checks the token, enforces rate limits and routes each path to a service. Requests that fail never reach your services.

<FlowDiagram spec={gatewayFlow} />

Use it as soon as you have several services, or any public API. Play **Rejected early**: a caller sending 300 req/s against a limit of 100 is stopped at the door with a 429. The cost is an extra hop and a possible single point of failure: run several gateways behind a balancer, and keep business logic out of it.

### Backend for frontend

Web and mobile need different payloads? Add a **BFF**: a thin layer per client type that calls the services and shapes the response for its own screens.

<FlowDiagram spec={bffFlow} />

Use it when one generic API forces a client to make many calls or download fields it never shows, for example a phone on a slow network. Each client team owns its BFF. The cost is more services to run, and logic can drift between BFFs. GraphQL is the alternative when you would rather let clients pick their own fields.

## API and load balancing in the interview

Bring this up the moment you draw more than one server, then say five decisions in order. The order shows you have done it before.

<Steps>
  <Step title="Make the services stateless">
    Sessions in Redis or a signed token, files in object storage, work on queues. Say it first: it is what makes the next steps possible.
  </Step>
  <Step title="Put a balancer in front">
    One managed L7 balancer by default, with an L4 tier in front only for raw TCP or very large scale. Round robin to start.
  </Step>
  <Step title="Pick the algorithm by the workload">
    Round robin for uniform calls, least connections or P2C for mixed or slow ones, consistent hashing only when a key needs the same server.
  </Step>
  <Step title="Say how it fails">
    Active plus passive health checks, narrow readiness, draining on deploy, a retry budget, and enough headroom to lose a zone.
  </Step>
  <Step title="Define the API contract">
    REST with correct status codes, cursor pagination for feeds, and an idempotency key on every POST that moves money.
  </Step>
</Steps>

| If the interviewer says | You raise |
|---|---|
| "Traffic is 10x on sale day" | Stateless instances, headroom, autoscaling with slow start |
| "One server gets slow" | Least connections or P2C, outlier ejection, a retry budget |
| "Users get logged out at random" | Sticky or in-memory sessions; move to Redis or a signed token |
| "A client retries the payment" | Idempotency key, 409 for in-flight duplicates |
| "Infinite scroll feed" | Cursor pagination, never offset |
| "Web and mobile need different data" | A BFF, or GraphQL if clients vary a lot |

<Callout kind="interview" title="Say it out loud">
"I'd make the services stateless, with sessions in Redis, and put a managed L7 load balancer in front, round robin to start. If request costs vary I'd switch to least connections or power of two choices. Health checks need three failures to mark an instance down, readiness checks only its own database, and I'd keep enough headroom to lose a zone. On the API, cursor pagination for the feed and an idempotency key on payments."
</Callout>

<Callout kind="warning">
Do not build every layer. Start with one balancer and stateless services, and add a piece only when you can name the problem it solves.
</Callout>

  <FollowUp q="How does the LB know an instance is unhealthy?">
    Active `/readyz` checks (3 failures down, 2 up) plus passive ejection on error spikes.
  </FollowUp>
  <FollowUp q="One server gets slow under round robin. What happens?">
    Its queue grows, clients time out and retry, and the retries load the rest. Use least connections or P2C, eject outliers, and cap retries with a budget.
  </FollowUp>
  <FollowUp q="REST, GraphQL or gRPC?">
    REST for public resources; GraphQL when clients need different shapes; gRPC for internal calls.
  </FollowUp>
  <FollowUp q="How do you make POST retries safe?">
    An `Idempotency-Key` the server claims with `SET NX`, replaying the stored response for repeats.
  </FollowUp>
