<TLDR>
Make services **stateless** and put a **load balancer** in front: capacity becomes "add a machine", and a crash loses nothing. Use least-connections or power-of-two-choices when servers can be slow, health-check with up/down thresholds, and give the API correct status codes, cursor pagination and idempotency keys.
</TLDR>

## Why it matters

One server is a ceiling and a single point of failure. Stateless servers behind a balancer, the first scaling move in almost every design, make deploys, crashes and spikes routine: the balancer routes around a dead instance, autoscaling adds new ones, nobody gets logged out.

The API on top is every client's contract, so status codes, pagination and safe retries are design, not polish.

## The request path

Each hop before your code adds one thing:

| Hop | What it adds |
|---|---|
| **DNS** (GeoDNS / Anycast) | The IP of the nearest healthy region |
| **CDN** | Static files and cacheable responses from the edge; absorbs DDoS |
| **Load balancer** | Spreads requests over healthy instances; terminates TLS |
| **API gateway** | Auth, rate limits, routing to the right service, request logs |
| **Services** | Business logic: stateless, scaled horizontally |
| **Data** | Databases, caches, queues, object storage: where state lives |

## Stateless services

Stateless doesn't mean no state. It means **no instance owns any**, so any instance can serve any request, and any can die.

| State | Where it goes instead |
|---|---|
| Sessions, login state | Redis with a TTL, or a signed token (JWT, signed cookie) |
| Uploaded files | Object storage (S3), served through the CDN |
| Rate-limit counters, locks | Redis |
| Business data | The database |
| Long-running work | A queue plus a jobs table |
| In-process caches | Fine, if losing one only makes things slower |

Play **Sticky-session pitfall** in the diagram, then **Fix: shared session store**. Sticky sessions (a cookie pins a user to one instance) can help warm caches or WebSockets, but never as the only home for state: deploys, crashes and autoscaling break the pin.

## L4 vs L7 load balancing

L4 sees connections; L7 reads requests.

| | L4 (TCP/UDP) | L7 (HTTP) |
|---|---|---|
| Sees | IP and port | URL, headers, cookies |
| Can do | Fast forwarding, any protocol | Path routing, TLS termination, retries, header rewrites, canaries |
| Cost | Very low | More CPU per request |
| Examples | AWS NLB, IPVS, Maglev | AWS ALB, NGINX, Envoy, HAProxy (HTTP mode) |

Most web stacks use both: an L4 network balancer spreads connections over a fleet of L7 proxies, which decide per request.

## Balancing algorithms

Which healthy instance gets the next request? It depends on whether servers and requests are uniform.

| Algorithm | How it picks | Wins when | Weakness |
|---|---|---|---|
| Round robin | Next in order | Identical servers, similar requests | Ignores load: keeps feeding a slow server |
| Weighted (smooth WRR) | By weight, spread out | Mixed instance sizes; 5% canary | Static weights ignore slowness |
| Least connections | Fewest in-flight requests | Long or variable requests (uploads, streaming) | Needs an accurate count per server |
| Power of two choices | 2 at random, take the less loaded | Many balancers, large fleets | Slightly less precise than a full scan |
| IP or consistent hash | Hash of the client or a key | Affinity: per-key caches, shards | Hot keys overload one server |

**Power of two choices (P2C)** is the surprise: two random samples balance almost as well as least-connections, with no global scan and no state shared between balancers. Envoy's least-request policy and NGINX's `random two least_conn` work this way.

In the simulator, make server C slow under **round robin**: its queue grows, because it still gets one request in four. Switch to **least connections** or **P2C** and C gets less work until it recovers.

## Health checks

The balancer can only route around failures it can see.

- **Active checks** call `/readyz` every few seconds (say every 5 s, 2 s timeout), with thresholds so a blip can't flap an instance: **3 failures to mark it down, 2 successes to mark it up**. Play **Instance failure** in the diagram.
- **Passive checks** (outlier detection) eject an instance whose real-traffic errors or timeouts spike (say 5 consecutive 5xx) for 30 seconds. Faster than probes.
- **Liveness** asks "is the process alive?" (fail: restart it); **readiness** asks "should it get traffic now?" (fail: stop routing). Failing liveness because the database is down causes restart loops; failing readiness on an optional dependency (recommendations, analytics) takes the whole fleet out at once.
- **Connection draining**: on `SIGTERM`, readiness fails, new requests stop, in-flight ones finish, then the process exits. Without it, every deploy drops requests.

## REST API design

Clients hard-code whatever you ship, so make it predictable: plural nouns for resources, HTTP for verbs, one level of nesting.

- `GET /orders?cursor=…` lists, `GET /orders/123` reads one, `GET /users/7/orders` gets one user's orders.
- `POST /orders` creates; `PUT /orders/123` replaces the whole order; `PATCH /orders/123` changes some fields; `DELETE /orders/123` deletes.
- Non-CRUD actions can be sub-resources: `POST /orders/123/cancel`.

**Status codes** tell clients and proxies what happened without parsing the body:

| Code | Use it for |
|---|---|
| 200 OK | Success with a body: reads, updates returning the resource |
| 201 Created | Created by a POST; add a `Location` header |
| 202 Accepted | Queued, not done: return a job id or status URL |
| 204 No Content | Success, no body: DELETE, or PUT with nothing to return |
| 301 / 302 | Moved permanently / temporarily; browsers cache 301 |
| 304 Not Modified | Client's copy still valid (conditional GET, `If-None-Match`) |
| 400 Bad Request | Malformed: invalid JSON, a missing field |
| 401 Unauthorized | Not authenticated: missing or expired token |
| 403 Forbidden | Authenticated, not allowed: Alice reading Bob's orders |
| 404 Not Found | No such resource (or hiding that one exists) |
| 409 Conflict | Clashes with current state: duplicate, version mismatch, key in progress |
| 422 Unprocessable Content | Well-formed but invalid: end date before start date |
| 429 Too Many Requests | Rate limited; always add `Retry-After` |
| 500 Internal Server Error | Bug or unexpected failure, never a client mistake |
| 503 Service Unavailable | Overloaded, shedding load or failing readiness; add `Retry-After` |

**Versioning.** Put the major version in the path (`/v1/orders`): visible, easy to route, cache-friendly. A header (`Accept: application/vnd.example.v2+json`, or a dated version) keeps URLs stable but is easy to forget. Adding optional fields needs no new version; removing or renaming one does.

**Errors** should be machine-readable. RFC 9457 "problem details" is the standard shape, sent as `application/problem+json`:

```json
{ "type": "https://example.com/problems/out-of-stock", "title": "Out of stock",
  "status": 409, "detail": "SKU a1 has 0 units left", "instance": "/orders/123" }
```

## Pagination and safe retries

Page 50 of a feed, and the same POST sent twice: every busy API meets both.

**Offset vs cursor.** Offsets suit admin tables; feeds need cursors.

| | Offset: `?page=3&limit=20` | Cursor: `?cursor=…&limit=20` |
|---|---|---|
| Query | `LIMIT 20 OFFSET 40` | `WHERE id < $1 ORDER BY id DESC LIMIT 21` |
| Deep pages | Slow: reads and discards every skipped row | Fast: seeks straight into the index |
| New items arrive | Rows shift: duplicates and skips | Stable |
| Jump to page 50 | Yes | No, only next (and previous) |
| Good for | Admin tables, numbered search results | Feeds, timelines, infinite scroll, sync APIs |

Cursor on `(created_at, id)` instead? Postgres stores microseconds but a JavaScript `Date` keeps milliseconds, so serialise the timestamp as text (`created_at::text`) or rows get skipped.

**Idempotency keys.** Networks fail after the server did the work, so clients retry, and a retried `POST /payments` must not charge twice. The client sends one UUID per logical operation as `Idempotency-Key`; the server claims it atomically (`SET NX`), stores the response and replays it for repeats. A duplicate arriving mid-flight gets **409**; a 5xx releases the key so the client can retry.

GET, PUT and DELETE are idempotent by definition, so they're safe to retry; PATCH isn't necessarily. Never auto-retry a POST without a key.

## API styles compared

Pick the style by who's calling.

| Style | Best fit | Strengths | Costs |
|---|---|---|---|
| REST | Public APIs, CRUD on resources | Simple, HTTP caching, tooling everywhere | Over- or under-fetching; several round trips per screen |
| GraphQL | Many clients wanting different shapes of the same data | Client picks fields; one round trip; typed schema | N+1 resolvers, harder HTTP caching, needs query cost limits |
| gRPC | Internal service-to-service calls | Compact typed Protobuf; HTTP/2 streaming; generated clients | Browsers need gRPC-Web; binary is harder to debug |
| WebSocket | Chat, multiplayer, collaborative editing | Full duplex, low latency | Stateful connections: harder to balance, scale and deploy |
| SSE | Notifications, live scores, progress, streamed LLM tokens | Plain HTTP, automatic reconnect | Server to client only; text only |

The [polling, SSE and WebSockets deep dive](/deep-dives/polling-sse-websockets) compares the real-time options in depth.

## API gateway and BFF

One front door, many services. An **API gateway** handles auth, rate limiting, routing and request logging, so services stick to business logic. It's also an extra hop (a few ms) and a possible single point of failure: run several instances behind a balancer, and keep business logic out.

Web and mobile need different payloads? Add a **backend for frontend (BFF)**, a thin layer per client type owned by that client's team: the mobile BFF calls three services and returns one compact response for a slow network, while the web BFF returns richer data.

## Interview questions

<FollowUps>
  <FollowUp q="Why must services be stateless to scale horizontally?">
    So the balancer can send any request to any instance. State in Redis or a database means a crash loses only in-flight requests.
  </FollowUp>
  <FollowUp q="L4 or L7?">
    L4 for fast TCP forwarding (databases, custom protocols); L7 for path routing, TLS termination, retries and canaries, usually behind an L4 balancer.
  </FollowUp>
  <FollowUp q="How does the LB know an instance is unhealthy?">
    Active `/readyz` checks with thresholds (3 failures down, 2 successes up) plus passive ejection on error spikes. On deploy, readiness fails first so connections drain.
  </FollowUp>
  <FollowUp q="REST, GraphQL or gRPC?">
    REST for public, cacheable resources; GraphQL when clients need different shapes of the same data (watch N+1 queries); gRPC for typed, fast internal calls.
  </FollowUp>
  <FollowUp q="How do you make POST retries safe?">
    An `Idempotency-Key` the server claims with `SET NX`, replaying the stored response for repeats. In-flight duplicates get 409; a 5xx releases the key.
  </FollowUp>
</FollowUps>
