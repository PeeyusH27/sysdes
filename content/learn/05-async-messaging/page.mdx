<TLDR>
Move slow, flaky or spiky work onto a queue. Delivery is **at-least-once**, so make consumers **idempotent**, retry with backoff, and use a **transactional outbox** instead of "write the database, then publish".
</TLDR>

## Why it matters

Send the welcome email inline and signup is as slow as the email provider (say 800 ms). Queue it instead: the API answers in tens of milliseconds and a worker sends the email, retrying if it fails. If the provider is down for an hour, inline signups fail; queued ones just wait.

The price: work happens **later**, maybe **twice**, maybe **out of order**. Skip the queue for fast work the user needs in the response: it adds a broker to run. Play **Burst absorbed**.

## Sync or async?

If the user needs the answer to carry on ("was my card accepted?"), keep it sync. Go async when work is **slow**, **unreliable**, **spiky** or **fans out** to many reactions. Most flows split in two:

| Request | Sync part (user waits) | Async part (worker) |
|---|---|---|
| Sign up | Create the user row | Welcome email, CRM sync |
| Upload a video | Store the file, return an id | Transcode renditions, thumbnails |
| Place an order | Reserve stock, authorise the card | Confirmation email, invoice PDF, analytics |
| Publish a post | Save the post | Fan out to followers' feeds |

Long jobs return `202 Accepted` and a job id to poll.

## Why queues

With a queue in between, the consumer can be slow, mid-deploy or briefly down and nothing is lost. That is **decoupling**: each side scales and fails on its own. "Queue" covers three tools:

| Tool | Each message goes to | Best for |
|---|---|---|
| Work queue (SQS, RabbitMQ) | One consumer | Jobs, emails, image processing |
| Pub/Sub (SNS) | Every subscriber, right now | Fire-and-forget fan-out |
| Log (Kafka) | Every consumer group, replayable | Event streams, analytics |

## Kafka basics

Kafka is a log, not a mailbox: reading doesn't delete. A topic splits into **partitions**; a key always lands in the same partition, and order holds only within it. In a **consumer group** each partition has one consumer. Other groups read the same topic independently.

- **Replay.** Consumers commit their position, so a group can rewind after a bug fix.
- **Retention.** Messages stay for a set time (7 days by default), read or not.
- **The parallelism cap.** 6 partitions and 8 consumers leave 2 idle.

## Delivery semantics

<Doodle name="idempotency" size={150} caption />

Your consumer will see the same message twice. Brokers redeliver after crashes: that is **at-least-once**, the default. "Exactly once" really means at-least-once plus **idempotent** work: doing it twice has the effect of doing it once.

| Semantics | How | What goes wrong |
|---|---|---|
| At-most-once | Ack before processing | A crash loses the message |
| At-least-once | Ack after processing | A crash before the ack delivers it again |
| Effectively once | At-least-once + idempotent work | Nothing |

At-most-once is fine for a metrics ping, where one lost point costs nothing. An email or a card charge needs its own idempotency. Two ways. **A dedupe table**: record the message id under a unique constraint, in the same transaction.

```sql
BEGIN;
INSERT INTO processed_messages (message_id) VALUES ($1)
  ON CONFLICT (message_id) DO NOTHING;
-- 0 rows inserted means a duplicate: ROLLBACK and ack the message
UPDATE accounts SET balance = balance + $2 WHERE id = $3;
COMMIT;
```

**Idempotent writes**: `SET status = 'shipped'` is safe twice; `balance = balance + 10` isn't.

## Ordering

"Order shipped" before "order paid" is a bug, and Kafka orders only within a partition. So:

- **Key by the entity** that needs order (`userId`, `orderId`): one partition, one consumer.
- **Retries can reorder.** Where order matters, retry in place.
- **Sequence numbers.** A per-key `seq` lets the consumer drop duplicates and spot gaps.
- **Global order is rarely needed.** One user's events, not two strangers'.

## Retries and dead letter queues

<Doodle name="backoff" size={150} caption />

Some failures heal; some never will. Retry the first, waiting longer each time (**backoff**). Park the second in a **dead letter queue (DLQ)**.

- **Transient errors** (timeouts, 503s): backoff with jitter, 1 s, 2 s, 4 s, 8 s.
- **Permanent errors** (bad payloads) go straight to the DLQ.
- **Poison messages** always fail. Without a DLQ, one bad message retries forever and blocks the ones behind it.
- **Alert** when the DLQ is not empty. Fix the bug, then redrive it.

## Backpressure and Little's law

1,000 messages arrive each second and workers handle 800. The backlog grows to **720,000 after an hour**, and a new arrival waits 15 minutes.

**Little's law**: items in a system = arrival rate × time in it. It sizes fleets: 1,000 jobs/s × 200 ms = 200 jobs in progress, so at least 200 worker slots.

<StatTiles items={[{ label: "Arriving", value: "1,000/s" }, { label: "Processed", value: "800/s" }, { label: "Backlog growth", value: "+200/s" }, { label: "After 1 hour", value: "720K", sub: "messages waiting" }]} />

**Backpressure** is your answer when consumers can't keep up:

- **Bound the queue**: slow producers when it is full.
- **Push back** on callers: `429` or `503` with `Retry-After`.
- **Autoscale consumers on queue depth**, not CPU.
- **Drop low-value work** first.

## The dual-write problem and the transactional outbox

"Save the order, then publish `order.created`" can't be atomic: the database and the broker share no transaction.

- **Crash in between**: the order exists, the event is lost.
- **Publish first**: if the transaction rolls back, consumers act on an order that doesn't exist.

The **transactional outbox** writes the order and an `outbox` row in one local transaction. A **relay** then publishes unpublished rows. A crash can send a row twice, so consumers dedupe by event id.

<SequenceDiagram spec={outboxSequence} />

```sql
CREATE TABLE outbox (
  id           bigserial PRIMARY KEY,
  topic        text NOT NULL,
  payload      jsonb NOT NULL,
  published_at timestamptz
);
CREATE INDEX outbox_pending ON outbox (id) WHERE published_at IS NULL;

BEGIN;
INSERT INTO orders (id, user_id, total_cents) VALUES ($1, $2, $3);
INSERT INTO outbox (topic, payload) VALUES ('order.created', $4);
COMMIT;
```

**CDC** (Debezium) is the alternative: it tails the write-ahead log instead of polling.

## Sagas: transactions across services

A purchase spans orders, inventory, payments and shipping, each with its own database. A **saga** chains local transactions, each with a **compensating action** that undoes it:

<Steps>
  <Step title="Orders: create the order as PENDING">
    Compensation: mark it cancelled.
  </Step>
  <Step title="Inventory: reserve the stock">
    Compensation: release the reservation.
  </Step>
  <Step title="Payments: charge the card">
    Compensation: refund. If the charge fails, undo in reverse.
  </Step>
  <Step title="Shipping: create the shipment">
    If this fails, refund, release and cancel. If it works, mark the order CONFIRMED.
  </Step>
</Steps>

| | Choreography | Orchestration |
|---|---|---|
| How it works | Each service reacts to the previous one's event | A coordinator tells each service what to do next |
| Strength | Loose coupling, no central component | Flow in one place: easy to read, time out, monitor |
| Weakness | Flow is scattered and hard to follow | One more service to run |
| Fits | 2–3 steps | Longer flows (Temporal, AWS Step Functions) |

Compensations must be idempotent: a business undo (a refund), not a delete.

## Delayed and scheduled jobs

Cancel unpaid orders after 15 minutes.

- **Short delays**: SQS `DelaySeconds` (up to 15 minutes), BullMQ's `delay`.
- **Long delays**: a `run_at` column polled with `FOR UPDATE SKIP LOCKED`, or a Redis sorted set.
- **Cron-style schedules**: make the job idempotent, since it will sometimes run twice.

## Interview questions

<FollowUps>
  <FollowUp q="How do you avoid processing a message twice?">
    Make the consumer idempotent: record the message id under a unique constraint, in the same transaction.
  </FollowUp>
  <FollowUp q="How do you keep events for one user in order?">
    Key by userId, so one partition and one consumer hold them in order.
  </FollowUp>
  <FollowUp q="Kafka or RabbitMQ/SQS?">
    Kafka for streams that many groups read and replay; RabbitMQ or SQS for task queues.
  </FollowUp>
  <FollowUp q="What is backpressure?">
    Slowing producers when consumers can't keep up: bounded queues, `429`/`503`.
  </FollowUp>
  <FollowUp q="Why an outbox instead of “write the DB, then publish”?">
    A crash in between loses the event. The outbox commits it with the data.
  </FollowUp>
