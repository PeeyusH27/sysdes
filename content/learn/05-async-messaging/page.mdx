<TLDR>
Move slow, unreliable, spiky or fan-out work off the request path and onto a queue. Delivery is **at-least-once**, so make consumers **idempotent**, retry with backoff, park poison messages in a **dead letter queue**, and use a **transactional outbox** instead of "write the database, then publish".
</TLDR>

## Why it matters

Send the welcome email inline and signup is as slow as the email provider, and fails when it fails. Queue it instead: the API records the intent and answers in milliseconds, a worker retries until the email goes out, and spikes wait their turn.

The price: work happens **later**, maybe **twice**, maybe **out of order**. Play **Normal consumption**, then **Burst absorbed**.

## Sync or async?

If the user needs the answer to carry on (logging in, loading a page, "was my card accepted?"), keep it sync. Go async when work is **slow** (transcoding, PDFs, a 2 s third-party API), **unreliable** (email, SMS, push, webhooks), **spiky** (flash sales, month-end batches, a viral post) or **fans out** (one event: receipt, search index, analytics). Most flows split in two:

| Request | Sync part (user waits) | Async part (worker) |
|---|---|---|
| Sign up | Create the user row | Welcome email, CRM sync |
| Upload a video | Store the file, return an id | Transcode renditions, thumbnails |
| Place an order | Reserve stock, authorise the card | Confirmation email, invoice PDF, analytics |
| Publish a post | Save the post | Fan out to followers' feeds |

Long jobs return `202 Accepted` and a job id; the client polls `GET /jobs/:id` or gets a push or webhook when it's done.

## Why queues

With a queue in between, the consumer can be slow, mid-deploy or briefly down and nothing is lost. That's **decoupling**: bursts smooth out, and each side scales and fails on its own. "Queue" covers three tools:

| | Work queue (SQS, RabbitMQ, BullMQ) | Pub/Sub (SNS, Redis Pub/Sub) | Log (Kafka, Redis Streams) |
|---|---|---|---|
| Each message goes to | One consumer | Every subscriber, right now | Every consumer group, replayable |
| Retention | Until acked | None | Days, configurable |
| Ordering | Best effort, or FIFO queues | None | Per partition |
| Best for | Jobs, emails, image processing | Fire-and-forget fan-out | Event streams, analytics, CDC |

A common pairing: SNS fans out to one SQS queue per subscriber, each a durable copy with retries.

## Kafka basics

Kafka is a log, not a mailbox: reading doesn't delete. Topics split into **partitions**, append-only logs; the key's hash picks one, so a key always lands in the same partition, and order holds only within it. In a **consumer group** each partition has exactly one consumer, while other groups (billing, search, analytics) read the same topic independently.

- **Offsets and replay.** Consumers commit their position (offset), so a group can rewind (say to "yesterday 09:00") after a bug fix, and a new service can read from the start.
- **Retention.** A set time or size (7 days by default), read or not. Compacted topics keep the latest value per key indefinitely, for changelogs.
- **Rebalancing.** A consumer joins, leaves or misses heartbeats, and partitions move: they pause briefly, and processed-but-uncommitted messages are redelivered. Cooperative rebalancing moves only what must move; static membership skips it on a quick restart.
- **The parallelism cap.** 6 partitions and 8 consumers leave 2 idle. Size partitions for peak: adding them later remaps keys.

## Delivery semantics

Your consumer will see the same message twice. **At-least-once** is the practical default; "exactly once" really means at-least-once plus deduplication.

| Semantics | How | What goes wrong |
|---|---|---|
| At-most-once | Ack (commit the offset) before processing | A crash mid-work loses the message |
| At-least-once | Ack after processing | A crash after the work, before the ack, delivers it again |
| Effectively once | At-least-once + idempotent processing | Nothing, if every effect is deduplicated |

Kafka transactions give exactly-once only for Kafka-to-Kafka pipelines; an email, a card charge or a Postgres row needs its own idempotency. Two ways:

**A dedupe table with a unique constraint**, in the same transaction as the business change:

```sql
BEGIN;
INSERT INTO processed_messages (message_id) VALUES ($1)
  ON CONFLICT (message_id) DO NOTHING;
-- 0 rows inserted means a duplicate: ROLLBACK and ack the message
UPDATE accounts SET balance = balance + $2 WHERE id = $3;
COMMIT;
```

**Idempotent writes**: `SET status = 'shipped'` is safe twice; `balance = balance + 10` isn't. Upsert by natural key, and pass the message id to external APIs as an idempotency key (most payment and email providers take one).

`idempotent-consumer.js` (in [Code](#code)) fixes a classic bug: marking a message "done" **before** sending, so a failed email was skipped as a duplicate on every retry. The fix: short lock, do the work, mark done on success, release the lock in `finally`.

## Ordering

"Order shipped" before "order paid" is a bug, and Kafka orders only within a partition. So:

- **Key by the entity** that needs order (`userId`, `orderId`, `conversationId`): one partition, one consumer, in order.
- **Retries can reorder**: message 1 goes to a retry queue, message 2 lands first. Where order matters, retry in place (pause that key) or queue the key's later messages behind it.
- **Sequence numbers.** The producer stamps a per-key `seq`; the consumer drops anything older than the last one applied (a duplicate) and spots gaps (buffer, or fetch the missing event).
- **Global order is rarely needed**: one partition, one consumer, no parallelism. You need one user's events in order, not two strangers'.

## Retries and dead letter queues

Some failures heal; some never will. Retry the first with backoff; park the second in a **dead letter queue (DLQ)**.

- **Classify errors.** Transient ones (timeouts, 503s, deadlocks) get exponential backoff with jitter: 1 s, 2 s, 4 s, 8 s. Permanent ones (validation errors, malformed payloads, a 404 for a deleted user) go straight to the DLQ.
- **Poison messages** always fail; without a DLQ they loop forever, burning worker time and, in Kafka, blocking the whole partition.
- **Redrive after the fix**: SQS's redrive API, or replay the DLQ topic in Kafka. Idempotent consumers make it safe.
- **Alert** on DLQ depth above zero and on the **age of the oldest message** (SQS's `ApproximateAgeOfOldestMessage`, Kafka consumer lag), which catches a stuck consumer even when depth looks normal.

## Backpressure and Little's law

1,000 messages arrive each second and workers handle 800, so the backlog grows to **720,000 after an hour**; a new arrival then waits 720,000 ÷ 800 = 900 s, a full 15 minutes.

**Little's law** links it all: items in a system = arrival rate × time in it, `L = λ·W`. It sizes fleets too: 1,000 jobs/s × 200 ms = 200 jobs in progress, so at least 200 worker slots (about 286 at a healthy 70% utilisation).

<StatTiles items={[{ label: "Arriving", value: "1,000/s" }, { label: "Processed", value: "800/s" }, { label: "Backlog growth", value: "+200/s" }, { label: "After 1 hour", value: "720K", sub: "messages waiting" }]} />

**Backpressure** is your answer when consumers can't keep up:

- **Bound the queue**: reject or slow producers when full, instead of buffering until memory runs out.
- **Push back** on callers: `429` or `503` with `Retry-After`.
- **Autoscale consumers on queue depth or age** (KEDA, for example), not CPU.
- **Drop or sample low-value work** (analytics events, previews) first.

## The dual-write problem and the transactional outbox

"Save the order, then publish `order.created`" can't be atomic: the database and the broker share no transaction.

- **Crash in between**: the order exists, the event is lost. Nobody sends the confirmation or ships the parcel.
- **Publish first**: if the transaction then rolls back, consumers act on an order that doesn't exist.

The **transactional outbox** writes the order and an `outbox` row in one local transaction; a **relay** publishes unpublished rows and marks them. A crash in between sends a row twice, so consumers dedupe by event id. Pick **crash before publish** in the sequence diagram: nothing is lost.

<SequenceDiagram spec={outboxSequence} />

```sql
CREATE TABLE outbox (
  id           bigserial PRIMARY KEY,
  topic        text NOT NULL,
  payload      jsonb NOT NULL,
  published_at timestamptz
);
CREATE INDEX outbox_pending ON outbox (id) WHERE published_at IS NULL;

BEGIN;
INSERT INTO orders (id, user_id, total_cents) VALUES ($1, $2, $3);
INSERT INTO outbox (topic, payload) VALUES ('order.created', $4);
COMMIT;
```

**CDC is the alternative**: a tool like Debezium tails the write-ahead log and publishes every committed change, no polling. It's more infrastructure, and raw row changes leak your schema, so many teams point CDC at the outbox table itself.

## Sagas: transactions across services

A purchase spans orders, inventory, payments and shipping, each with its own database. A **saga** chains their local transactions, each paired with a **compensating action** that semantically undoes it:

<Steps>
  <Step title="Orders: create the order as PENDING">
    Compensation: mark it cancelled.
  </Step>
  <Step title="Inventory: reserve the stock">
    Compensation: release the reservation.
  </Step>
  <Step title="Payments: charge the card">
    Compensation: refund. If the charge fails, compensate in reverse: release the stock, cancel the order.
  </Step>
  <Step title="Shipping: create the shipment">
    If this fails, refund, release the stock and cancel. If it succeeds, mark the order CONFIRMED.
  </Step>
</Steps>

| | Choreography | Orchestration |
|---|---|---|
| How it works | Each service reacts to the previous one's event | A coordinator tells each service what to do next |
| Strength | Loose coupling, no central component | Flow in one place: easy to read, time out, monitor |
| Weakness | Flow is scattered and hard to follow | One more service to run |
| Fits | 2–3 steps | Longer flows (Temporal, AWS Step Functions) |

Compensations must be idempotent and retryable: a business undo (a refund), not a delete. Others can see intermediate states such as PENDING, so design the UI for them.

## Delayed and scheduled jobs

Cancel unpaid orders after 15 minutes. Remind a user 24 hours before an event. Retry after a backoff.

- **Per-message delay**: SQS `DelaySeconds` (up to 15 minutes), BullMQ's `delay`, RabbitMQ's delayed-message plugin. Retry backoff works the same way.
- **Long delays**: a `run_at` column polled with `WHERE run_at <= now() … FOR UPDATE SKIP LOCKED`, or a Redis sorted set scored by due time feeding the work queue.
- **Cron-style schedules**: one node runs them (a lock or leader election); make the job idempotent (it will occasionally run twice) and record the last success so a missed run can catch up.

## Interview questions

<FollowUps>
  <FollowUp q="How do you avoid processing a message twice?">
    Make the consumer idempotent: record the message id under a unique constraint in the same transaction as the effect, and mark it done only after success.
  </FollowUp>
  <FollowUp q="How do you keep events for one user in order?">
    Key by userId so one partition, and one consumer, holds them in order. A per-user sequence number catches duplicates and gaps, even after retries.
  </FollowUp>
  <FollowUp q="Kafka or RabbitMQ/SQS?">
    Kafka for high-throughput streams that many consumer groups read and replay; RabbitMQ or SQS for task queues with per-message acks, delays and dead-lettering.
  </FollowUp>
  <FollowUp q="What is backpressure?">
    Slowing producers when consumers can't keep up: bounded queues, `429`/`503` with `Retry-After`, autoscaling on queue depth. Little's law tells you how fast the backlog grows.
  </FollowUp>
  <FollowUp q="Why an outbox instead of “write the DB, then publish”?">
    A crash in between loses the event, because the broker can't join the database transaction. The outbox commits the event with the data; a relay publishes it at least once.
  </FollowUp>
</FollowUps>
