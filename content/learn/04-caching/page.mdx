<TLDR>
Cache what you read far more than you change. Going from a 90% to a 99% hit ratio cuts database load 10×.
</TLDR>

## Why it matters

Your database is slow and far away. A **cache** keeps the answers you need most in fast memory, about **50× faster**. The price: each cached value is a copy, and copies go stale.

Play **Cache hit**, then **Cache miss**: ~1 ms against ~50 ms.

Skip the cache when the page already loads fast and the database sees 100 reads/s. Skip it for write-heavy or per-user data too: the hit ratio stays under 50%, and you pay for the copies.

## Where caches live

The fastest query never reaches the database. Play **A cold request** to watch a miss fall through all six layers.

<FlowDiagram spec={cacheLayers} />

| Layer | What to cache there |
|---|---|
| Browser | Static assets, `GET` responses with `Cache-Control` |
| CDN edge | Public pages, images, API responses identical for everyone |
| Reverse proxy | Rendered pages, rate-limit counters |
| In-process memory | Tiny, hot, read-only data (feature flags, config) |
| Redis / Memcached | Shared per-entity data: products, sessions, counters |
| Database buffer pool | Hot pages, automatically |

## What to cache and how to name it

Cache what is **read often and changes rarely**.

- The key holds everything the value depends on: `product:42:v3:en-IN` (id, version, locale).
- Per-user data never goes in a shared CDN cache.
- Keep values small: a 2 MB value turns a 1 ms hit into 20 ms.

## Caching patterns

Six ways to fill a cache. One is the default.

<Steps>
  <Step title="Cache-aside (lazy loading)">
    Check the cache. On a miss, read the database and fill the cache. If the cache dies, you only get slower. **The default.**
  </Step>
  <Step title="Read-through">
    The same, but the cache loads from the origin itself.
  </Step>
  <Step title="Write-through">
    Write the database and cache together. Always fresh, but writes cost double.
  </Step>
  <Step title="Write-behind (write-back)">
    Write the cache now, the database later. Fast, but a crash loses data: fine for view counts, never for payments.
  </Step>
  <Step title="Write-around">
    Writes skip the cache. For data written once and rarely read.
  </Step>
  <Step title="Refresh-ahead">
    Reload hot keys before they expire.
  </Step>
</Steps>

## Eviction and TTL

Memory is full; something has to go. **LRU** drops the least recently used key; **LFU**, the least often used.

A TTL bounds staleness. Set it by the cost of a stale read: seconds for prices, hours for config. Add jitter so keys written together don't expire together.

## Invalidation and the classic race

The safe default is **delete on write**: update the database, delete the cache key, and let the next read reload it. Updating the cache can leave the older value last when two writers race.

One race remains. Play **Write race**: a slow reader loads the old row, the writer updates and deletes, then the reader puts the old value back. Fixes:

- A **short TTL** as a safety net.
- A **second delete** about 1 s later.
- **Versioned keys** (`user:42:v7`), so old entries are never read.

## Failure modes

Four classic failures, all landing on your database. A Monday 9:00 stampede: the homepage key expires and 5,000 requests hit the database at once.

| Failure | What happens | Fix |
|---|---|---|
| **Stampede** | A hot key expires; thousands of requests hit the database | One request rebuilds, the rest wait (single flight) |
| **Penetration** | Lookups for ids that don't exist always miss | Cache "not found" briefly; a Bloom filter |
| **Avalanche** | Many keys expire together | Jittered TTLs |
| **Hot key** | One key gets 100K+ reads/s | In-process cache; copies `key#1…#N` |

## The numbers: hit ratio vs latency

A hit costs the lookup. A miss costs the lookup **plus** the database. Say hits take 1 ms, misses 51 ms, and 4,000 reads/s arrive:

| Hit ratio | Average read | Database reads/s |
|---|---|---|
| 50% | 26 ms | 2,000 |
| 90% | 6 ms | 400 |
| 99% | 1.5 ms | 40 |

## HTTP caching for frontend developers

Browsers and CDNs are caches too, and they are free.

- `Cache-Control: public, max-age=60` reuses a response for 60 s; `private` keeps it out of shared caches; `no-store` disables caching.
- `ETag` + `If-None-Match` returns `304 Not Modified` (no body) while the copy is valid.
- Fingerprinted assets (`app.3f9a1c.js`) can be cached for a year with `immutable`.
- `stale-while-revalidate=300` serves a stale copy while fetching a fresh one.

## Sizing and monitoring

Size for the **working set**: often 20% of keys serve 80% of reads. A falling hit ratio with rising evictions means the cache is too small.

<Callout kind="warning">
- Caching without a TTL.
- Caching per-user responses at the CDN.
- Treating the cache as the source of truth.
</Callout>

## Interview questions

<FollowUps>
  <FollowUp q="How do you prevent a cache stampede?">
    A per-key lock, so one request rebuilds while the rest wait. Add jittered TTLs.
  </FollowUp>
  <FollowUp q="Do you delete or update the cache on write?">
    Delete. Updating can leave the older value last.
  </FollowUp>
  <FollowUp q="How do you choose a TTL?">
    By the cost of a stale read: seconds for prices, hours for config.
  </FollowUp>
  <FollowUp q="Would you cache a write-heavy key?">
    Rarely: the hit ratio collapses. Cache the aggregate instead (the like **count**, not each like).
  </FollowUp>
  <FollowUp q="A single key gets 200K reads/s. What do you do?">
    An in-process cache with a short TTL on every app server, or N copies read at random.
  </FollowUp>
</FollowUps>
