This is the Strategy pattern with the smallest possible shape: one tiny interface (`allow(key, now)`), three classes that implement it, and a limiter that only holds one of them.

1. **Give the algorithms one interface.** `FixedWindow`, `SlidingWindowLog` and `TokenBucket` each take their own config in the constructor, keep their own per-key state, and expose `allow(key, now)`. The caller cannot tell which one it is talking to, which is exactly what removes the `if/else` ladder.
2. **Choose by name, in one place.** A `STRATEGIES` map from name to class is the only place that knows the names. `useStrategy` looks the name up, builds a new object and stores it. A fourth algorithm is one new class and one new map entry, so the three existing classes are never edited (open for extension, closed for modification).
3. **Let a new object mean fresh state.** Because every strategy object owns its own maps, replacing the object in `useStrategy` resets every key for free. An unknown name returns `false` before anything is replaced, so a failed switch cannot lose state.
4. **Fixed window: count per aligned window.** Compute `floor(now / windowSec)` and store it next to the count. When the index changes, reset the count. That is why 2 allowed requests at `t = 8, 9` and 2 more at `t = 10, 11` all pass with `limit = 2, windowSec = 10`: they fall in different windows, so about `2 × limit` get through in a few seconds.
5. **Sliding log: remember when, drop what expired, then count.** Keep the timestamps of allowed requests, drop those `<= now - windowSec` (the window start is exclusive), and allow only if fewer than `limit` remain. Push the timestamp **only on success**: logging rejected requests would make a client who keeps retrying block itself forever.
6. **Token bucket: refill lazily.** Do not run a timer. Store `tokens` and the time of the last look; on each call add `(now - last) × refillPerSec`, cap at `capacity`, then take one token if `tokens >= 1`. A fresh key is full, so a burst of up to `capacity` goes through at once and after that the rate settles at `refillPerSec`.

Where it bends: the limiter does not care what a strategy remembers, so a strategy could keep its state in Redis behind the same `allow`. Where it does not bend is the shared state. This version is single-process; with several servers each one would enforce its own budget, so at scale the check and update must be one atomic step in a shared store (a Lua script in Redis).

Cost per request: fixed window O(1) time and O(1) space per key; token bucket the same; sliding log O(limit) space per key and amortised O(1) time, which is the price of its exact answer. Old keys are never evicted here; a real limiter expires idle keys. A decorator on the limiter (logging, metrics) would be the next layer and still needs no change to the algorithms.
