This is the State pattern. The behaviour of the machine depends on its phase, so each phase becomes an object, and the machine forwards every event to whichever object is current.

1. **Write the table before the code.** Three states and four events (`insert`, `select`, `cancel`, `service`) give a dozen cells, and every cell needs one answer. Deciding the awkward ones up front (selecting while idle, a coin while out of service, `service(false)` with money inside) is the real design work.
2. **One class per state, one method per event.** `IdleState`, `HasMoneyState` and `OutOfServiceState` each implement `insert`, `select`, `cancel` and `service`. An illegal event is not an `if` that someone forgot, it is a method that returns `"REJECTED"`, `"NO_MONEY"` or `0`. The three flags `isIdle`, `hasMoney` and `outOfService` that a naive version needs, and the combinations that must never happen, disappear.
3. **The machine is a thin context.** It owns the data (slots, credit, last change) and one `current` state, and each public method is a single line that delegates. A state changes the phase by calling `machine.go(nextState)`, so transitions live next to the rule that causes them.
4. **Keep the money in one place.** Only `HasMoneyState` ever holds credit, and it leaves through exactly two doors: a sale (`credit - price` becomes change) or a refund (`cancel`, or the first half of `service(true)`). Both set the credit to 0 on the way out, which is what makes the sum of inserts equal purchases plus change plus refunds.
5. **Order the checks in `select`.** Slot exists, then stock, then price. The order is part of the contract: a sold-out slot answers `"SOLD_OUT"` even when the credit is short, and each failure leaves the machine untouched so the customer can try again.
6. **Share what is not phase-specific.** `restock` and the queries behave the same everywhere, so they live on the machine. Putting a method in every state class only to repeat the same line would be the over-engineering version of this pattern.

The design bends in the right place. A new state (say `MAINTENANCE`, which allows restocking only) is one new class plus the lines that switch to it, and no existing state's logic changes. A new event is one new method per state class, which forces you to decide what it means in every phase, and that is a feature. A new payment method (notes, cards) would add an `insert` variant, and the observer half of the lesson would let a display or telemetry listener watch `go(...)` without the states knowing about it.

Cost: every call is O(1) and each transition allocates one small state object. Because the state objects hold no data they could be shared singletons, which is what you would do in a hot path. At scale the interesting problems move elsewhere: persisting `current`, the credit and the last sale across a power cut, and giving change from a finite coin box, which turns `select` into a bounded change-making problem.
