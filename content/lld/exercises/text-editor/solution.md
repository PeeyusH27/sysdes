This is the Command pattern with a Composite on top. The editor stores no snapshots of the text. It stores actions, and each action knows how to reverse itself.

1. **Make each action an object with `do` and `undo`.** `TypeCommand` appends its text and undoes by cutting that many characters off the end. `DeleteCommand` is the interesting one: when it runs it records **what it actually removed**, not what it was asked to remove. That is what makes a clamped `delete(5)` on `"ab"` undo to `"ab"`, and it is the reason the command must remember state instead of the editor guessing.
2. **Keep two stacks, and let the editor stay ignorant.** `undo` pops the undo stack, calls `undo` on the command and pushes it onto the redo stack. `redo` does the mirror image. The editor never asks what kind of command it holds, so a new edit (say, `replace`) is a new class and no change to `undo`, `redo` or the stacks.
3. **Decide what counts as an action.** `type("")` and a `delete` that removes nothing would be commands that do nothing, and recording them would give the user an undo step that visibly does nothing and would wipe the redo history for no reason. Filtering them out at the entry point keeps the history honest.
4. **Clear the redo stack when a new action is recorded.** After an undo and a fresh edit, the old future no longer applies to the current text. Doing the clearing in one `commit` method means no path can forget it.
5. **Make a group a command too.** `MacroCommand` holds children, `do` runs them in order and `undo` runs them in reverse, because the last edit has to be reversed first. Since a macro is a command, the history does not know that groups exist, and a group can in principle hold groups.
6. **Collapse nesting with a depth counter.** `beginGroup` opens a macro only when the depth goes from 0 to 1, and `endGroup` commits it only when the depth returns to 0. Inner begin and end calls just move the counter. While the depth is above 0 the editor sends commands into the macro instead of into history, and it refuses undo and redo, because the history would otherwise change under a half-built step. An empty macro is dropped at commit time.

The design bends in the right places. A new edit type is a new command class. A new kind of history (limited depth, a timeline) changes only the stacks. A command that can merge with the previous one, so that typing letter by letter undoes word by word, is a method on the command plus one check in `commit`.

Cost: each command stores only the text it touched, so memory is proportional to the history and not to the document size times the history length. A real editor on a large document would also cap the history, coalesce typing and store edits as positions and spans (an operation log), which is also the starting point for collaborative editing.
