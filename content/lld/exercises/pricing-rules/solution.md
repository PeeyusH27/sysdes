This is the Decorator pattern in its simplest working form: a base price, plus rules that each take "the fee so far" and return a new fee. The engine stays tiny because it knows nothing about what any rule does.

1. **Give every rule the same shape.** A rule is `(feeSoFar, minutes) → newFee`. Some rules ignore `minutes` (a discount), some need it (the grace period, the daily cap), but the engine can call them all the same way. That uniform signature is what makes them stackable.
2. **Build rules from a registry, not an if/else.** `RULES` maps a name to a function that takes the params and returns the rule. A new kind of rule, say a weekend surcharge, is one new entry. `addRule`, `removeRule` and `fee` are never edited, which is the whole point of the pattern (open for extension, closed for modification). Unknown names are rejected by the lookup alone.
3. **Keep the chain as an ordered list and fold it.** `addRule` appends, and `fee` starts from the base fee and applies each rule to the previous result. Each rule really does wrap everything before it, so order is part of the answer: with a rate of 300, discount 50 percent then minimum 400 gives 400 for one hour, but minimum 400 then discount 50 percent gives 200.
4. **Be precise about the details.** The base fee uses `ceil(minutes / 60)`, so 61 minutes is 2 hours. The cap multiplies by `ceil(minutes / 1440)` started days, so a 1441 minute stay gets two days of cap. The discount rounds the result down, and `minimum` leaves 0 alone so a free stay cannot become a paid one.
5. **Removing is just deleting from the list.** Because `fee` recomputes the fold from scratch every time, removing a rule needs no undo logic: the remaining rules produce exactly what they would have produced alone. If you cached the running fee inside each rule, this would be where it breaks.

Where it bends: a rule that needs more than the fee and the minutes (the day of the week, member tier) means passing a small context object instead of `minutes`, which touches every rule once but nothing else. Where it breaks: rules that need to see each other's results in a more complex way than a straight chain, such as "apply the better of two discounts", need a composite rule rather than another link.

Cost: `fee` is O(R) for R rules, and the chain is rebuilt from the list with no state, so it is easy to test and safe to call repeatedly. In a real system the chain would be built from configuration and each rule would be priced in integer cents, as here, to avoid floating point drift.
