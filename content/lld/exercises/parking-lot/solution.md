The lot has three jobs that change for different reasons: remembering spots and tickets, choosing a spot, and pricing a stay. The design keeps those three apart, which is the Single Responsibility, Open/Closed and Dependency Inversion ideas in one small class.

1. **Model the physical lot as plain data.** Flatten `floors` into spots, each with its floor, its index, its type and whether it is taken. A fit table (`bike` to three spot types, `car` to two, `truck` to one) answers "can this vehicle use this spot" in one lookup, so no part of the code asks "is this a car and is that large" with a chain of `if`s.
2. **Turn spot choice into a policy.** A spot policy is only an ordering over the free spots that fit. `smallest-first` sorts by `[size, floor, index]` and `lowest-floor-first` by `[floor, size, index]`. `park` filters by the fit table, takes the minimum under the current key, and does not know which policy it is. A new policy ("closest to the exit", "spread across floors") is one new entry in the map, and `park` is not edited: that is open/closed.
3. **Turn pricing into a policy too.** A pricing policy is a function `(vehicle, minutes) => cents`. `hourly` is `0` up to 10 minutes and `ceil(minutes / 60) * rate` beyond that; `flat` ignores the minutes. The grace boundary is a `<=`, and the started-hour rule is a ceiling: 10 is free, 11 is one hour, 60 is one hour, 61 is two. `leave` asks the current policy and never sees a rate, so changing a rate or adding a weekend rule touches the pricing code only.
4. **Let the lot depend on the policies, not the reverse.** The lot holds one "current spot policy" and one "current pricing" reference and swaps them in `useSpotPolicy` and `usePricing`. The lot never imports a concrete rule inside `park` or `leave`; the map from names to rules is the only place that knows them (dependency inversion). Because only the reference changes, spots already issued stay where they are, and a fee uses whichever pricing is active at `leave`.
5. **Make tickets the single source of truth.** A ticket id maps to `{ plate, vehicle, spot }` while the vehicle is inside. `leave` deletes it, so an unknown and an already used ticket are the same lookup failure (`-1`), double-leave cannot refund or double-charge, and `spotOf` answers `""` for both. Ids come from a counter that only moves on success, so a failed `park` leaves no gap. A set of parked plates rejects duplicates in O(1).

Where the design bends: a new vehicle type is a new row in the fit table and in each pricing table, with no edits to the lot. A new spot type is a new size rank and a new entry in the fit rows. Pricing that depends on when the vehicle arrived (peak hours) would need `leave` to pass a timestamp into the policy rather than only minutes, and the lot would still only hold the reference.

Where you would stop: do not build a `SpotManagerFactory` and a class per rule when a function does the job. Two policies as map entries is the right size, and the class hierarchy only pays off when a policy needs its own state, such as a rolling daily cap.

Cost: `park` scans all spots, O(S), which is fine for hundreds. For a large garage keep one heap or sorted set of free spots per type, keyed by the current policy, so that `park` is O(log S). `leave`, `spotOf` and the plate check are O(1). Switching the policy would then rebuild those structures, which is the cost you accept for a policy that can change at runtime.
