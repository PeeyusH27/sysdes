<TLDR>
SOLID is five questions to ask a design when a requirement changes. Each one below is code that hurts, then code that does not.
</TLDR>

## What the five letters ask

Look at a class and say which change would hurt it.

| Principle | The question | The smell |
|---|---|---|
| **S**ingle responsibility | How many reasons to change? | Tax, layout, storage in one class |
| **O**pen/closed | Can I add without editing? | An `if/else` ladder on a type |
| **L**iskov substitution | Can a subtype stand in? | A subclass that throws |
| **I**nterface segregation | Does a client need methods it never calls? | Stubs that throw |
| **D**ependency inversion | Does policy depend on detail? | `new SmtpMailer()` in business code |

## Single responsibility: one reason to change

A swiss army knife is handy until one broken tool ruins the lot. In `srp-before.js` an `Order` computes tax, formats the receipt, and saves itself. Three teams edit one file.

In `srp-after.js` each concern has a home: `Order` holds items, `withTax` is a rule, `receiptText` is layout, and `OrderStore` is storage.

## Open/closed: add, don't edit

Think of a power strip: plug in a new device, never rewire the wall. In `ocp-before.js` every customer kind is a branch in `price`.

In `ocp-after.js` a `Pricing` object holds registered rules. A student rule is one `register` call. Old code is closed to edits and open to additions.

## Liskov substitution: keep the parent's promise

A subclass must work everywhere its parent does. `lsp-before.js` makes `Square` a `Rectangle`. But `areaAt4By5` sets width 4 and height 5 and expects 20. A `Square` returns 25, because setting one side moves the other.

Three signs of a violation: the subclass **throws** where the parent did not, **demands more** of its inputs, or **returns less** than promised. In `lsp-after.js` the shapes stop pretending: each offers `area()`.

## Interface segregation: small contracts

`isp-before.js` has one wide contract for paying: charge, refund and save a card. `Cash` can only charge, so it stubs the rest with throws. Then `refundAll` meets one cash entry and the whole batch crashes.

In `isp-after.js` the contracts are **roles named by what a client needs**. `checkout` needs something that can `charge`, so a one-method fake is enough to test it.

## Dependency inversion: policy should not know the detail

A lamp does not care which power station feeds the socket. In `dip-before.js`, `OrderService` creates its own `SmtpMailer`, so every test needs a mail server.

Step through: the service names a `Mailer`, and SMTP or a fake plugs into it. The **inversion**: the arrow now points from the detail to the interface the policy owns.

In `dip-after.js` the service takes a `Mailer`, so a test needs only a `FakeMailer`.

## SOLID as interview vocabulary, and when to stop

Say it as one concrete sentence: "I keep tax in its own rule so `Order` has one reason to change."

<Callout kind="interview" title="What interviewers listen for">
A named change and where it lands. Answer "why an interface here?" with a test fake or a second variant, not "because SOLID".
</Callout>

Stop when the pain is not real. Extract an interface when a **second variant** appears or a **test needs a fake**. An `if` with two branches is fine. Three is the cue.

<Callout kind="warning" title="Interface for every class">
Pay for an abstraction only where you can name the requirement that varies.
</Callout>

Practise on the [parking lot exercise](/lld/exercises/parking-lot).

## Follow-up questions

<FollowUps>
  <FollowUp q="Which SOLID principle matters most in an LLD round?">
    Open/closed and dependency inversion, because every question asks "how do I add a new X?" and "how do I test this?".
  </FollowUp>
  <FollowUp q="What is the difference between dependency injection and dependency inversion?">
    Injection passes a collaborator in. Inversion means the high-level code defines the interface the detail implements.
  </FollowUp>
</FollowUps>
