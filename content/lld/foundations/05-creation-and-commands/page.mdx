<TLDR>
Decide which class to create in one place. Skip the Builder when an options object will do, and pass one instance in instead of using a Singleton. Model undo as **commands** with `do` and `undo`.
</TLDR>

## Create it by name

<Doodle name="factory" size={150} caption />

Think of a vending machine: press B4 and the right snack drops. That is a **factory**.

A string like `"sms"` arrives from config. Something must turn it into an object. How many places know how?

Add push, and you must find **every** switch on the channel. Miss one and push users fail in production. Put the choice in **one place** instead.

Callers say `channels.create(kind)`. A new kind is one `register` call, with no edit to old code.

| Tool | Use it when | Example |
|---|---|---|
| Constructor | You know the type | `new Sms()` |
| Static factory | Creation needs a name or check | `Duration.ofMinutes(5)` |
| Registry | New kinds arrive as data | `channels.create(kind)` |

## Builder, and when it is overkill

A constructor with seven parameters, four optional, gives `new Email(a, b, null, null, true)`. Nobody can read that.

A **Builder** collects the parts one at a time and creates the object at the end, checking the whole combination once.

<CodeTabs files={['snippets/email-builder.js', 'snippets/email-builder.test.js']} python={['snippets/python/email_builder.py', 'snippets/python/test_email_builder.py']} />

Reach for it when:

- **Many parts are optional.**
- **A rule spans several fields** and must hold before any object exists.
- **The result is immutable**, but the parts arrive over time.

In JavaScript and Python you need one less often. An options object does the job in one line:

```js
new Email({ to: ['ann@x.com'], subject: 'Lunch', cc: ['bob@x.com'] })
```

```python
Email(to=("ann@x.com",), subject="Lunch", cc=("bob@x.com",))
```

Add a validity check to the constructor and you have most of a builder. Do not write one for a class with three fields.

## Singleton: one instance, no global

<Doodle name="singleton" size={150} caption />

One town clock that everyone checks sounds neat, until a test needs its own. That is a **Singleton**: `TicketNumbers.get().next()` is a global with a nicer name.

<CodeTabs files={['snippets/singleton-before.js', 'snippets/singleton-after.js', 'snippets/singleton.test.js']} python={['snippets/python/singleton_before.py', 'snippets/python/singleton_after.py', 'snippets/python/test_singleton.py']} titles={['Singleton (before)', 'Passed in (after)', 'Tests']} />

- **Hidden dependency.** `issueTicket(vehicle)` does not say it uses shared state.
- **Tests leak.** A test passes alone and fails in a suite.
- **You cannot have two.**

Instead, create it once near `main` and hand it in (**dependency injection**). Production still has one. A test builds a fresh one.

## Command: an action as an object

Saving a full copy before every edit is simple, but 1,000 edits of a 10,000-character text store 10 million characters. The **Command** pattern stores the action instead. Each command can `do` and `undo` itself.

<CodeTabs files={['snippets/command.js', 'snippets/command.test.js']} python={['snippets/python/command.py', 'snippets/python/test_command.py']} />

- **`Erase` remembers what it removed**, so undo restores exactly that.
- **`History` has two stacks.** `undo` moves a command from `done` to `undone`; `redo` moves it back.
- **A new edit clears the redo stack.**

A new `Paste` is a new class; `History` does not change.

## Which one, when

Each pattern answers one question. If you are not asking it, skip the pattern.

| Pattern | Reach for it when | Skip it when |
|---|---|---|
| Factory or registry | The class depends on data | The type is known at the call |
| Builder | Many optional parts | An options object will do |
| Singleton | Never as a global | Always, for state |
| Command | Undo, queues, logs | Nothing reverses or records it |

<Callout kind="interview" title="What interviewers listen for">
You say the choice of class lives in one place, and decline the Singleton on purpose. For undo, you name commands and two stacks unprompted.
</Callout>

## The over-engineering trap

<Callout kind="warning" title="A pattern needs a pain">
A factory for one constructor, a builder for three fields, or a command nobody undoes is cost with no benefit.
</Callout>

## Follow-up questions

<FollowUps>
  <FollowUp q="Is a Singleton ever the right answer?">
    One instance is often right. A global way to reach it rarely is. Create it at startup and pass it in.
  </FollowUp>
  <FollowUp q="What about an action that cannot be undone, such as sending an email?">
    Keep it off the undo stack. For a reversal, add a new compensating action, like a correction email.
  </FollowUp>
</FollowUps>
