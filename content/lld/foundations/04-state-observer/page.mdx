## The flags that rot

A door can be open, closed or locked. The first version uses one flag per fact.

<CodeTabs files={['snippets/door-flags.js', 'snippets/door-flags.test.js']} python={['snippets/python/door_flags.py', 'snippets/python/test_door_flags.py']} />

Two booleans describe four doors, but only three exist. Nothing stops `open()` then `lock()`: open and locked at once. A phase is one **state**: a single variable that holds only listed values.

## Write the table first

List every state and event, and give each pair one outcome. The door has 3 states and 4 events:

| State | Event | Next state | Action |
|---|---|---|---|
| closed | open | open | swing open |
| closed | lock | locked | throw bolt |
| open | close | closed | latch |
| locked | unlock | closed | retract bolt |

That is 4 of the 12 pairs. The other 8 are **rejected**: nothing changes. The gaps (what does lock do on an open door?) are the questions to ask. The [vending machine](/questions/vending-machine) is the same exercise with more rows.

## Make illegal moves impossible

Shape the code to refuse bad states:

- **One variable holds the state.** No flags to combine.
- **One door in:** every change goes through `send(event)`.
- **Decide before you mutate.** A rejected event changes nothing.
- **Test every pair.** Loop over all 12 and count the 4 that succeed.

## Observer: subscribe, unsubscribe, notify

<Doodle name="observer" size={150} caption />

Think of a bell that everyone in the building hears. The ringer does not know who is listening. That is **Observer**.

A log wants every change, an alarm wants locks. If `send` calls each, `Door` grows with every listener. Instead the door keeps a list of callbacks and calls whoever signed up.

<CodeTabs files={['snippets/emitter.js', 'snippets/emitter.test.js']} python={['snippets/python/emitter.py', 'snippets/python/test_emitter.py']} />

`subscribe` **returns the way to unsubscribe**. `emit` loops over a **copy** and catches each error. Why is next.

## Let the door announce itself

Combine the table door with the emitter. The door changes state first, then announces, and only for legal moves.

<CodeTabs files={['snippets/observable-door.js', 'snippets/observable-door.test.js']} python={['snippets/python/observable_door.py', 'snippets/python/test_observable_door.py']} />

The event is **pushed**: it carries `from`, `event` and `to`, so a listener needs no reference to the door. **Pull** only says "something changed" and loses changes that pile up. Push is the safer default.

Step through: the door comes first, and each stage adds classes without editing earlier ones.

## Where Observer bites

Play the sequence, then switch branches: one listener throws, or one unsubscribes itself mid-loop.

<SequenceDiagram spec={notifyFlow} />

- **Unsubscribing mid-notification.** Removing while looping skips entries, so loop over a copy. A listener removed mid-way still hears that one event.
- **A throwing listener.** One bad listener must not stop the rest. Catch per listener.
- **Memory leaks.** A short-lived listener on a long-lived door leaks unless it calls the function `subscribe` returned.

<Callout kind="warning" title="Do not observe what you could just call">
If one thing always reacts, just call it.
</Callout>

## Observer or an event bus

An observer is attached to **one object**: you subscribe to this door. An **event bus** sits in the middle: publishers announce a topic such as `door.locked`, subscribers ask for topics, and neither knows the other.

| | Observer | Event bus |
|---|---|---|
| You subscribe to | One object | A topic or pattern |
| Typical reach | One process | Many objects, maybe many processes |

Use Observer for a few listeners on one object. Use a bus when many parts need the same events, and accept no direct call to follow. The [event bus exercise](/lld/exercises/event-bus) builds one.

<Callout kind="interview" title="What interviewers listen for">
You draw the state table before the classes, name the rejected cells, and say illegal moves leave the state unchanged. For Observer, you raise the pitfalls before being asked.
</Callout>
