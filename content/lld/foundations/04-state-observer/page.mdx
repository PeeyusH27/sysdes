## The flags that rot

A door can be open, closed or locked. The first version uses what is at hand: a flag for each thing you can say about it.

<CodeTabs files={['snippets/door-flags.js', 'snippets/door-flags.test.js']} python={['snippets/python/door_flags.py', 'snippets/python/test_door_flags.py']} />

Two booleans describe four doors, and only three exist. Nothing stops `open()` then `lock()`, which gives a door that is open and locked at once, as the second test shows. Add an "ajar" state and you have three flags and eight combinations to defend by hand, with an `if` in every method. Flags describe **facts**. A phase is one **state**, and a state is a single variable that can hold only the values you listed.

## Write the table first

Before any code, list every state and every event, and give each pair one outcome. For a door with three states and four events (open, close, lock, unlock) the legal moves are:

| State | Event | Next state | Action |
|---|---|---|---|
| closed | open | open | swing open |
| closed | lock | locked | throw bolt |
| open | close | closed | latch |
| locked | unlock | closed | retract bolt |

That is 4 of the 12 pairs. The other 8 are **rejected**: nothing changes and the caller is told. The table is the specification. If you can fill it in during the interview, you can write the code, and the gaps (what happens when you press lock on an open door?) are exactly the questions an interviewer wants you to ask. The [vending machine](/questions/vending-machine) and the [elevator](/questions/elevator) are the same exercise with more rows.

## Make illegal moves impossible

You cannot test your way out of a state machine that allows bad states, so shape the code to refuse them:

- **One variable holds the state**, and only values you named can go in it. No flags to combine.
- **One door in**: every change goes through `send(event)`. Nothing else assigns `state`.
- **Decide before you mutate.** A rejected event returns a result and changes nothing, so no move is ever half applied.
- **Test every pair.** The table test loops over all 12 and counts the 4 that succeed.
- Even an event called `toString` is just an unknown event. A plain object lookup without `hasOwn` would find `Object.prototype.toString` and crash.

In a typed language you can go further and make each state its own type, so a method that is illegal in that state does not exist.

## Observer: subscribe, unsubscribe, notify

Now the door has to tell others. A log wants every change, an alarm wants only locks, a lamp wants open or closed. If `send` calls each of them, `Door` knows about all three and grows with every new one. **Observer** turns that around: the door keeps a list of callbacks and calls whoever signed up.

<CodeTabs files={['snippets/emitter.js', 'snippets/emitter.test.js']} python={['snippets/python/emitter.py', 'snippets/python/test_emitter.py']} />

Three details carry most of the weight. `subscribe` **returns the way to unsubscribe**, so the caller cannot forget it. The listener collection ignores a duplicate subscription. And `emit` loops over a **copy**, and catches each listener's error, for reasons the pitfalls section explains.

## Let the door announce itself

Combine the table door with the emitter. The door changes state first, then announces, and only for legal moves.

<CodeTabs files={['snippets/observable-door.js', 'snippets/observable-door.test.js']} python={['snippets/python/observable_door.py', 'snippets/python/test_observable_door.py']} />

The event here is **pushed**: it carries `from`, `event` and `to`, so a listener needs no reference to the door. The alternative is **pull**: tell listeners only that something changed, and let them read the door. Pull gives them the newest state but loses what happened in between if several changes pile up. Push is the safer default.

## Where Observer bites

Play the sequence, then switch branches: one listener throws, or one unsubscribes itself while the emitter is looping.

<SequenceDiagram spec={notifyFlow} />

- **Unsubscribing during a notification.** Removing from a collection while looping over it skips or breaks entries. The loop runs over a copy. The price is a rule: a listener removed mid-notification still hears that one event. Node's `EventEmitter` behaves the same way.
- **A throwing listener.** Without a guard, one bad listener stops the rest and may leave the door locked while the alarm never heard. Catch per listener, and report the errors to the caller or a logger. The door has already changed, and it stays changed.
- **Ordering.** Listeners run in subscription order, but do not build on it. If the alarm must run after the log, they are one listener.
- **Memory leaks.** The door holds a reference to every listener. A short-lived listener on a long-lived door (a screen that opens and closes) leaks unless it calls the function `subscribe` returned. The `size` check in the tests is how you catch it.
- **Re-entrancy.** A listener that sends another event during a notification starts a nested one, and listeners can see the two out of order. The vending machine question solves this with an event queue.

<Callout kind="warning" title="Do not observe what you could just call">
If exactly one thing reacts and it always will, call it. Observer adds hidden control flow: a reader of `send` can no longer see what happens next. Use it where the set of reactions really varies, or the door must not depend on them.
</Callout>

## Observer or an event bus

An observer is attached to **one object**: you subscribe to this door, and you get its events. An **event bus** sits in the middle: publishers announce a topic such as `door.locked`, subscribers ask for topics or patterns, and neither knows the other.

| | Observer | Event bus |
|---|---|---|
| You subscribe to | One specific object | A topic or pattern |
| Publisher knows subscribers | Holds them, does not know them | Does not even hold them |
| Typical reach | One process, one object graph | Many objects, sometimes many processes |

Pick Observer for a few listeners on one object. Pick a bus when many parts of the system need the same events and you want to add or move them freely, and accept the cost: no direct call to follow, and questions about order and lost events. The [event bus exercise](/lld/exercises/event-bus) builds the topic router.

<Callout kind="interview" title="What interviewers listen for">
You draw the state table before the classes, name the rejected cells, and say that illegal transitions leave the state unchanged. For Observer, you volunteer the pitfalls (a throwing listener, unsubscribing mid-loop, leaks) before being asked, and you can say when a plain call is better.
</Callout>

## Follow-up questions

<FollowUps>
  <FollowUp q="How is State different from Strategy?">
    A strategy is picked from outside and rarely changes itself. A state replaces itself as events arrive, and each state decides what comes next. The class shapes look alike, so the difference is who chooses.
  </FollowUp>
  <FollowUp q="How would you make a state machine survive a restart?">
    Persist the state name (and any pending data) on every transition, before announcing it. On start, load it and rebuild the object. The table is code, so only the current state needs storing.
  </FollowUp>
  <FollowUp q="What if a listener must be able to veto a change?">
    That is not Observer. Observers hear about facts after the fact. A veto is a guard in the table, or a validator the door calls before it changes state.
  </FollowUp>
  <FollowUp q="How do you stop a slow listener from blocking the door?">
    Hand the event to a queue or a worker and return at once, so a slow listener only delays itself. The price is that delivery becomes asynchronous, so ordering and failure handling need explicit design.
  </FollowUp>
  <FollowUp q="Where would you put guards, such as a keypad code to unlock?">
    On the cell: the table entry holds a function that checks the condition, and the event is rejected when it returns false. The state diagram stays the same and the rule stays beside the move it protects.
  </FollowUp>
</FollowUps>
