<TLDR>
Put the rule that keeps changing behind a one-method interface (**Strategy**). Add optional rules like caps and discounts as wrappers with the same interface (**Decorator**). Wrapping order is part of the rule, so test it.
</TLDR>

## The ladder that grows

On Monday the garage charges by the hour. By Friday bikes are cheaper, nights are half price, the first ten minutes are free, and finance wants a cap. Each request is one more `if`.

<CodeTabs files={['snippets/fee-before.js', 'snippets/fee-before.test.js']} python={['snippets/python/fee_before.py', 'snippets/python/test_fee_before.py']} />

It works, and it hurts three ways:

- **Every rule edits one function.** A new discount can break the cap.
- **The order is hidden.** Discount runs before cap only because that `if` is higher up.
- **You cannot swap it.** An event-day flat price needs a copy of the whole function.

## Strategy: the rule behind an interface

Picture a game console with swappable cartridges. It only cares that the cartridge fits the slot. That is a **Strategy**.

Here the part that varies is **how a stay becomes a price**. Name it `fee(stay)`, and let `Garage` depend on the name, not on any one rule.

<CodeTabs files={['snippets/strategy.js', 'snippets/strategy.test.js']} python={['snippets/python/strategy.py', 'snippets/python/test_strategy.py']} />

`Garage` is handed its pricing (**injection**), so a test passes a `FlatRate`. A new scheme is a new class, and `Garage` stays untouched ([open/closed](/lld/foundations/solid)).

## Decorator: wrap, do not branch

<Doodle name="decorator" size={150} caption />

Think of a gift wrapped in layers: ribbon over paper over box. Each layer adds something, and you still hold one gift. That is a **Decorator**.

Grace periods, caps and discounts **adjust** hourly pricing. Each implements `fee(stay)` and holds another strategy, which it calls and changes.

<CodeTabs files={['snippets/rules.js', 'snippets/rules.test.js']} python={['snippets/python/rules.py', 'snippets/python/test_rules.py']} />

A wrapper looks like the thing it wraps, so wrappers stack:

```js
const pricing = new GracePeriod(new Cap(new NightDiscount(new HourlyRate(20), 50), 100), 10);
```

Read it inside out: 20 an hour, half off at night, never over 100, free for the first 10 minutes.

## The order of wrapping is part of the rule

An 8-hour night stay at 20 an hour is 160 before any rule. Try a 50% night discount and a cap of 100, in each order:

<CodeTabs files={['snippets/order.js', 'snippets/order.test.js']} python={['snippets/python/order.py', 'snippets/python/test_order.py']} />

| Wrapping | Night, 8 hours | Day, 8 hours |
|---|---|---|
| `Cap(NightDiscount(base))` | 160, then 80, cap leaves 80 | 160, cap makes 100 |
| `NightDiscount(Cap(base))` | 160, cap makes 100, then 50 | 160, cap makes 100 |

Neither is a bug. They are different policies: "never pay over 100" or "half off the capped price". Decide on purpose and let a test hold it. Put a grace period outermost, so a free stay skips every other rule.

## Strategy, decorator, or just a function

In JavaScript and Python you often do not need a class. A function is a strategy with one method, and a function that takes a function is a decorator.

<CodeTabs files={['snippets/as-functions.js', 'snippets/as-functions.test.js']} python={['snippets/python/as_functions.py', 'snippets/python/test_as_functions.py']} />

The three versions give the same numbers. Use a class when the rule has **configuration to inspect**, **several methods**, **state**, or a name for logs.

<DecisionTree spec={chooseShape} />

<Callout kind="interview" title="What interviewers listen for">
You name what varies before drawing a class. Strategy for alternatives, Decorator for adjustments, a function when the rule is tiny. You say wrapping order changes the answer. A pattern name with no pain behind it scores worse than a plain `if`.
</Callout>

## The over-engineering trap

<Callout kind="warning" title="Three rules is not a framework">
Two stable cases belong in an `if`. Extract the interface when the third arrives, or when you must swap or test a rule alone.
</Callout>

Habits that keep it cheap:

- One interface, one method.
- Readable wrapper names, and log the chain at startup.
- No registry or factory until rules really come from configuration.
- Keep wrappers **pure**: same stay, same fee, clock passed in.

## Follow-up questions

<FollowUps>
  <FollowUp q="Strategy and State look the same in code. What is the difference?">
    A strategy is chosen from outside and usually stays put. A state changes itself as events arrive.
  </FollowUp>
  <FollowUp q="How do you test a stack of decorators?">
    Test each wrapper alone with a constant inner strategy like `FlatRate(160)`. Then test real stacks, both orders of any pair that interact.
  </FollowUp>
  <FollowUp q="Why inject the strategy instead of creating it inside Garage?">
    Creating it inside ties the class to one rule. Injection lets tests pass a stub.
  </FollowUp>
</FollowUps>
