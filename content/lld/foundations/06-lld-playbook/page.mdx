<TLDR>
Run every round the same way: clarify, use cases, entities, interface, diagram, code the core, then stress the design, in about 45 minutes. Add a pattern only when a requirement hurts, and name the race before you are asked.
</TLDR>

## What interviewers score

An LLD round is not a pattern quiz. The rubric is about how you work.

| What they score | What it looks like | What loses points |
|---|---|---|
| Scope | Questions first | Coding from sentence one |
| Modelling | One job per class | A god class, or a class per noun |
| Working code | One use case end to end | Half of everything, nothing runs |
| Extensibility | A new requirement adds a class | Editing a switch in four files |

<Callout kind="interview" title="What interviewers listen for">
The **reason** behind each choice: "I made pricing a strategy because it will change", not "I used Strategy".
</Callout>

## A 45-minute plan

The split is **5, 12, 16 and 12 minutes**. The longest block is code, because only working code proves anything.

<Timeline spec={lldPlan} />

Behind schedule? Cut scope out loud: "I will code only `book` and `cancel`."

## The repeatable template

<Steps>
  <Step title="Clarify">
    Three to five questions: scope, size, failures.
  </Step>
  <Step title="Use cases">
    The user's verbs, as method names.
  </Step>
  <Step title="Entities">
    Nouns become classes, one job each. See the [first lesson](/lld/foundations/thinking-in-objects).
  </Step>
  <Step title="Public interface">
    Four to six signatures, and what each returns on failure.
  </Step>
  <Step title="Class diagram">
    Boxes and arrows. Five minutes.
  </Step>
  <Step title="Code the core">
    One use case, end to end.
  </Step>
  <Step title="Extensibility check">
    Aim to **add a class, change none**.
  </Step>
  <Step title="Concurrency">
    Find the check-then-act and make it one step.
  </Step>
  <Step title="Tests">
    Happy path, boundary, failure, injected clock.
  </Step>
</Steps>

## The extensibility check

The interviewer will add a requirement, so do it to yourself first: **if they add a new X, how many existing classes do I edit?**

- A new vehicle type, payment method or pricing rule should be one new class and one registration line.
- A new `if` in four files means a missing seam. See the [SOLID lesson](/lld/foundations/solid).
- Say it as a sentence: "To add reservations I add a `ReservationPolicy`, and `ParkingLot` does not change."

Practise on the [parking lot](/lld/exercises/parking-lot) exercise: after each step, name a new requirement and the class you would add.

## The concurrency checklist

Every round ends with "what if two people do this at once?"

<Steps>
  <Step title="Find the check-then-act">
    "If it is free, take it" is a race once two callers interleave.
  </Step>
  <Step title="Make the pair one step">
    A lock, claim-first, or one atomic operation.
  </Step>
  <Step title="Lock the invariant, not the world">
    One lock per room, held briefly.
  </Step>
  <Step title="Make retries safe">
    Give each request an id, so a repeat returns the first result. That is **idempotency**.
  </Step>
  <Step title="Say what changes across servers">
    A memory lock covers one process. Across servers the database arbitrates.
  </Step>
</Steps>

## Worked example: a meeting-room booker

The prompt: "Design a system to book meeting rooms." The whole round, without the full code.

<Steps>
  <Step title="Clarify">
    Fixed rooms, one process, whole minutes. Out of scope: recurring meetings and calendar sync, named as follow-ups.
  </Step>
  <Step title="Use cases">
    `book(room, start, end, who)`, `cancel(bookingId)`, `freeRooms(start, end)`.
  </Step>
  <Step title="Entities">
    `Room`, `Booking`, and `RoomBooker` as the one class that owns the rules.
  </Step>
  <Step title="Public interface">
    A clash returns `false`. A backwards slot or unknown room throws. Say that aloud: it is the contract.
  </Step>
  <Step title="Class diagram">
    `RoomBooker` owns rooms, and each room owns its bookings.
  </Step>
  <Step title="Code the core">
    The subtle part is the overlap test. Use **half-open intervals** (start in, end out), so a meeting ending at 10 does not clash with one starting at 10.
  </Step>
  <Step title="Extensibility">
    Recurring: a rule that expands into bookings. Notify: an [observer](/lld/foundations/state-observer). Best room: a [strategy](/lld/foundations/strategy-decorator). Undo: a [command](/lld/foundations/creation-and-commands).
  </Step>
  <Step title="Concurrency and tests">
    Two people booking one slot is the check-then-act again: check and claim in one step, with a lock per room. Across servers, a database constraint arbitrates. Test the boundary, a clash, a backwards slot, and inject the clock.
  </Step>
</Steps>

The core is `book` and `freeRooms`, short enough for a whiteboard.

## When you are stuck

<Callout kind="warning" title="The mistakes that cost the most">
- Coding before the use cases are agreed.
- A class per noun and a pattern per class.
- A beautiful diagram and no code that runs.
- Waiting for the interviewer to raise concurrency.
- Skipping tests. Describe three even if you cannot write them.
</Callout>

Everyone stalls. The recovery is mechanical:

- **Say what you are stuck on.** Silence reads as lost.
- **Go back to the use cases.** Which verb am I implementing?
- **Write the simplest version**: one class, a list, a loop.
- **Cut scope on purpose**, and say where it would plug in.
- **Offer a choice, not a blank**: "a lock per room or one global lock?"

## Practise in this order

Work on a timer, out loud.

1. [Tic-tac-toe](/lld/exercises/tic-tac-toe): entities and responsibilities.
2. [Parking lot exercise](/lld/exercises/parking-lot), then the [question](/questions/parking-lot): SOLID in practice.
3. [Rate limiter](/lld/exercises/rate-limiter) and [pricing rules](/lld/exercises/pricing-rules): swappable, stackable behaviour.
4. [Vending machine](/lld/exercises/vending-machine) and [elevator](/questions/elevator): state machines.
5. [Event bus](/lld/exercises/event-bus) and [text editor](/lld/exercises/text-editor): observers, commands.

## Follow-up questions

<FollowUps>
  <FollowUp q="You are 20 minutes in and the design has grown too big. What do you do?">
    Stop adding. Finish the one use case that matters, and list the rest as extensions.
  </FollowUp>
  <FollowUp q="Your in-memory design must now run on several servers. What changes?">
    Memory locks protect nothing. Use a unique constraint or conditional update, and request ids for retries.
  </FollowUp>
</FollowUps>
