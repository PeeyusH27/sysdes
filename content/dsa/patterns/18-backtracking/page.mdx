<TLDR>
Backtracking builds an answer **one choice at a time**: choose, explore everything that follows, then **un-choose** and try the next option. It is exponential by nature, so the craft is producing each answer **exactly once** and **pruning** hopeless branches early.
</TLDR>

## When to reach for it

<Callout kind="tip" title="Spot it in the problem statement">

- "Return **all** subsets, combinations, permutations or partitions."
- "Generate **every valid** string, board or arrangement."
- **Place** items under constraints: queens, sudoku digits, a word in a grid.
- **Small limits** like `n <= 10` or a 6 × 6 board: exponential is expected.
- "Does **any** assignment exist?" with no greedy or DP shortcut.

</Callout>

| Variant | Repeats avoided by | Classic problems |
|---|---|---|
| Subsets and combinations | a start index (`i + 1`, or `i` for reuse) | subsets, combination sum |
| Permutations | a `used[]` array | permutations |
| Constraint placement | filling slots in a fixed order | n-queens, sudoku, parentheses |
| Grid search | marking the cell, then restoring it | word search, maze paths |

## The core idea: one path, walked forward and back

Every sequence of choices forms a tree: the root is "nothing chosen", each edge is a choice, each node a partial answer. Backtracking walks it depth-first with **one shared `path`**:

1. **Choose**: push an option (and mark it).
2. **Explore**: recurse through the whole subtree below.
3. **Un-choose**: pop it (and unmark it), so `path` is exactly as it was.

Each call undoes its own change, so one array serves the whole search. `path` always matches the highlighted route from the root:

<AlgoViz trace={combinationsTree} />

Correctness is two questions. **Does every answer appear?** Some sequence of choices must reach it. **Does each appear once?** No two paths may build the same answer. Everything else is speed, which means pruning.

## Step by step

<Steps>
  <Step title="Define the partial solution and when it is complete">
    A `path` array or string. Complete means length k, target hit, row n reached or every letter matched. Subsets record **every** node.
  </Step>
  <Step title="List the choices at one step">
    The next number, column, bracket or cell: the loop inside the recursive function.
  </Step>
  <Step title="Rule out duplicates by construction">
    Order doesn't matter: a `start` index. Order matters: `used[]`. Deduping afterwards with a Set is slow, and a sign the choice rule is wrong.
  </Step>
  <Step title="Write choose, explore, un-choose">
    Undo every change right after the recursive call.
  </Step>
  <Step title="Record copies">
    `result.push([...path])`, or `path.join("")` for strings. Pushing `path` itself stores the live array, which is empty by the end.
  </Step>
  <Step title="Prune">
    Ask "can this branch still succeed?" **before** recursing, not on finished answers. Return early if you only need **any** answer.
  </Step>
</Steps>

## Template 2: permutations with used[]

Now order matters: `[a, b]` and `[b, a]` are different answers, so a start index would lose half of them. Each call loops over **every** item and skips those already in the path, tracked in a boolean `used`.

## Template 3: pruning

A branch is worth exploring only if it can still succeed, so check **before** recursing. Sorting often makes one failed check final: once a number exceeds what's still missing, every later number does too, so `break` instead of `continue`. The red nodes are calls that never happen.

On a grid the choices are the four neighbours, and "used" means "on the current path". Let the grid be the visited set: overwrite the cell with a marker, explore, then write the original back, so a cell on a failed path is free for the next one.

## Complexity

Backtracking is exponential. Estimate **(nodes in the tree) × (work per node)**, plus copying each recorded answer.

| Problem shape | Time | Extra space (besides the output) |
|---|---|---|
| All subsets of n items | O(n · 2^n): 2^n subsets, O(n) copy each | O(n) |
| Combinations of k items from n | O(k · C(n, k)) | O(k) |
| All permutations of n items | O(n · n!) | O(n) for `path` and `used` |
| A word of length L in an m × n grid | O(m · n · 3^L): at most 3 new directions per step | O(L) recursion |
| N-Queens | O(n!) at most, far less after pruning | O(n) |

## JavaScript you'll use

<JsRef to={["recursion", "arrays", "destructuring-spread"]} />

```js
result.push([...path]);                    // record a COPY of the current path
path.push(x); backtrack(i + 1); path.pop(); // choose, explore, un-choose
const used = new Array(n).fill(false);     // flags for permutations
const word = path.join("");                // character path -> string answer
const board = Array.from({ length: n }, () => Array(n).fill(".")); // n independent rows
```

Recursion depth is rarely a worry: it equals one answer's length, far below JavaScript's limit of roughly ten thousand nested calls.

<Callout kind="warning">

- Forgetting to undo **every** change: the `pop()`, `used[i] = false`, the Set `delete`, the restored cell.
- Recursing with `start + 1` instead of `i + 1`: an earlier item can follow a later one, creating duplicates.
- Pruning with `break` on **unsorted** input, which skips smaller options further on.

</Callout>

## Interview questions

<FollowUps>
  <FollowUp q="The input has duplicate values. How do you avoid duplicate subsets or permutations?">
    Sort, then skip `nums[i]` when it equals `nums[i - 1]` and `i > start` (subsets) or `nums[i - 1]` isn't in use (permutations). Either way, that value was already tried at this level of the tree.
  </FollowUp>
  <FollowUp q="What is the difference between backtracking, DFS and dynamic programming?">
    Backtracking **is** DFS over a tree of partial solutions, with an explicit undo; DP applies when paths reach the **same** subproblem, so answers can be cached. Counting subsets with a given sum is DP; listing them is backtracking.
  </FollowUp>
  <FollowUp q="How do you estimate the running time of a backtracking solution?">
    Branching factor to the power of the depth, times the work per node including copies, as in the complexity table. Add that pruning cuts the real cost but not the worst-case bound.
  </FollowUp>
  <FollowUp q="How would you search a grid for many words at once?">
    Put every word in a **trie** and run one search per cell, following trie children instead of one word's letters, removing words once found.
  </FollowUp>
</FollowUps>
