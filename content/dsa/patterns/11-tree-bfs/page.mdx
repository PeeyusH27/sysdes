<TLDR>
Breadth-first search visits a tree **level by level** with a first-in, first-out queue. The **level-size loop** (snapshot the queue length when a level starts, then process exactly that many nodes) tells you where each level ends, which turns level averages, side views and zigzags into one-line changes. Because BFS reaches shallow nodes first, it can **stop at the first match**, as in minimum depth. O(n) time and O(w) space, where w is the widest level.
</TLDR>

## When to reach for it

<Callout kind="tip" title="Spot it in the problem statement">

- The answer is **per level** or **per row**: averages, maximums, counts, the values of each level.
- You need what is visible **from one side**: the first or last node on every level.
- The question asks for the **nearest** or **shallowest** something: minimum depth, the closest leaf, the first node with a property.
- The output must be ordered **top to bottom, left to right**, as in level-order listings and tree serialization.
- Nodes on the **same level** must be linked or compared with their neighbours.

</Callout>

| Variant | Per-level work | Classic problems |
|---|---|---|
| Level aggregate | sum, count or max while dequeuing | average of levels, largest value in each row |
| Collect each level | push values into one array per level | level order, bottom-up level order |
| First or last per level | keep the node at `i === 0` or `i === size - 1` | right side view, left side view |
| Alternating direction | write at index `i` or `size - 1 - i` | zigzag level order |
| Early exit | return at the first node that matches | minimum depth, nearest leaf |

## The core idea: a queue keeps the levels in order

A queue hands nodes out in the order they went in. Start with the root; every time you take a node out, put its children in at the back. The children of a level-d node are on level d + 1, and they join the queue **behind** every level-d node still waiting. So nodes come out in order of depth, left to right within a level.

That gives one invariant worth memorising:

> When a level starts, the queue holds exactly the nodes of that level, and nothing else.

So read `size` at that moment and dequeue exactly `size` nodes. Everything they add meanwhile is the next level. Watch the shaded band (this level) and the new nodes (next level) in the queue:

## Step by step

<Steps>
  <Step title="Handle the empty tree">
    Start the queue empty when `root` is `null` (or return early). Most problems want `[]` or `0` here, never `[[]]`.
  </Step>
  <Step title="Seed the queue">
    Put the root in an array and keep a `head` index for the front. Reading `queue[head++]` is an O(1) dequeue; `shift()` is not.
  </Step>
  <Step title="Snapshot the level size">
    At the top of the outer loop, `size = queue.length - head`. Those are exactly this level's nodes.
  </Step>
  <Step title="Process the level">
    Dequeue `size` nodes. Do the per-level work (add to a sum, write into the level array, check `i === size - 1`) and enqueue each node's left child, then its right child.
  </Step>
  <Step title="Record or stop">
    After the inner loop, push the level's answer. For "nearest" questions, return as soon as a dequeued node matches: nothing later can be shallower.
  </Step>
</Steps>

## Template 2: stop at the first match

DFS dives down one branch before looking at the next, so to find the shallowest leaf it must explore the whole tree: a leaf at depth 2 on the right is only seen after the entire left side. BFS meets every node at depth d before any node at depth d + 1. So **the first matching node it dequeues is a shallowest one**, and the rest of the tree is never touched.

## Template 3: a queue that never shifts

`Array.prototype.shift()` removes the first element and moves every remaining element down one index. Engines optimise it for small arrays, but on large queues each call copies the whole queue, so a BFS that uses it can become O(n²). On Node, draining a 50,000-item array with `shift()` takes around 100 ms, and doubling the size roughly quadruples that; a head index drains it in a couple of milliseconds.

Three ways to avoid it, from simplest to most general:

- **Head index**: `queue[head++]`. The array keeps the dequeued slots, which is fine for one BFS over a tree (every node is enqueued once anyway).
- **Swap arrays per level**: build `next` while walking `level`, then `level = next`. No dequeue at all.
- **A small Queue class**: a head index that occasionally slices off the used prefix, for long-running queues.

## Complexity

| Variant | Time | Extra space |
|---|---|---|
| Level-size BFS | O(n): each node enqueued and dequeued once | O(w): the widest level, up to about n / 2 |
| Early exit (first match) | O(n) worst case, often far less | O(w) for the levels it reaches |
| BFS with `shift()` | O(n²) worst case on large queues | O(w) |
| DFS passing the depth down | O(n) | O(h) for the recursion |

## JavaScript you'll use

<JsRef to={["stack-queue-deque", "linked-list-tree-nodes", "arrays"]} />

```js
const queue = root ? [root] : [];       // a queue: push at the back, read at head
let head = 0;
const size = queue.length - head;       // snapshot: the nodes of the current level
const node = queue[head++];             // O(1) dequeue, nothing moves
if (node.left) queue.push(node.left);   // never enqueue null children
level[size - 1 - i] = node.val;         // fill from the back for a right-to-left level
const avg = sum / size;                 // / is always floating-point division in JS
```

The two traps are `queue.shift()` on large inputs, and a loop condition that reads the live `queue.length`, which keeps growing while you enqueue children and merges every level into one.

<Callout kind="warning">

- Looping `while (i < queue.length)` inside a level instead of using the size snapshot: the levels run together.
- Enqueuing `null` children, then reading `.val` from them.
- In minimum depth, stopping at a node with one child: it is not a leaf.
- Calling `shift()` in a loop over tens of thousands of nodes.
- Returning `[[]]` or `[0]` for an empty tree instead of `[]`.
- For zigzag order, reversing the order children are **enqueued**, which scrambles the levels below.

</Callout>

## Interview questions

<FollowUps>
  <FollowUp q="BFS or DFS for a level-based question?">
    Both work: DFS can pass the depth down and write into `levels[depth]`. The difference is memory and early exit. BFS holds one level at a time, O(w), which is about n / 2 for a complete tree; DFS holds one path, O(h), which is n for a skewed tree. BFS also stops at the first match for "nearest" questions, which DFS cannot do. Mention both and pick by the tree's likely shape.
  </FollowUp>
  <FollowUp q="How do you return the levels bottom-up?">
    Run the normal level-order BFS and reverse the list of levels once at the end, O(n). Calling `unshift` for every level also works but moves the whole result array each time.
  </FollowUp>
  <FollowUp q="How do you link every node to its right neighbour on the same level?">
    With the level-size loop, link each dequeued node to the next one in the queue unless it is the last of its level. The O(1)-space follow-up walks each level using the next pointers already built on the level above, wiring up the children as it goes, so no queue is needed.
  </FollowUp>
  <FollowUp q="How would you find the maximum width of a level, counting the gaps between nodes?">
    Number positions like a heap: the root is 0, a node at position p has children at 2p + 1 and 2p + 2. Each level's width is last position minus first position plus one. On deep, skewed trees the positions double every level and exceed 2^53, so subtract the level's first position from every position as you go (or use BigInt).
  </FollowUp>
</FollowUps>
