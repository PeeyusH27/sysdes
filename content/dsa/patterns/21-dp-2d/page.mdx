<TLDR>
When one index can't describe a subproblem, use two: a grid cell, a prefix of **each** of two strings, or "the first `i` items, capacity `c`". Same recipe as [1D DP](/dsa/patterns/dp-1d), O(m × n) time, often O(n) space with one row.
</TLDR>

## When to reach for it

<Callout kind="tip" title="Spot it in the problem statement">

- **Two strings** are compared: common subsequence, edit distance, interleaving, wildcard matching.
- **A grid** you cross only right and down, counting paths or minimising cost.
- **Items under a budget**: a subset that fits a capacity or hits an exact sum.
- `dp[i]` needs a second number to be well defined (remaining capacity, a position in the other string).

</Callout>

| Variant | `dp[i][j]` means | Classic problems |
|---|---|---|
| Grid paths | the answer for reaching `(i, j)` | Unique Paths, Minimum Path Sum, Dungeon Game |
| Two strings | the answer for `a.slice(0, i)` and `b.slice(0, j)` | Longest Common Subsequence, Edit Distance |
| 0/1 knapsack | the best from the first `i` items, capacity `j` | Partition Equal Subset Sum, Target Sum |
| Unbounded knapsack | the same, but items may repeat | Coin Change II, Rod Cutting |
| Intervals | the answer for the slice `a[i..j]`, from shorter slices | Longest Palindromic Subsequence, Burst Balloons |

## The core idea: a cell, its neighbours, and a fill order

Every 2D DP is three things: what a cell means, which neighbours it reads, and an order that has them ready.

How many right-and-down paths reach cell `(r, c)`? The last move came from above or from the left, and those two groups don't overlap:

```js
paths[r][c] = paths[r - 1][c] + paths[r][c - 1];   // the first row and first column are all 1
```

Fill **row by row, left to right** and both neighbours are always finished. A 3 × 4 grid:

| | col 0 | col 1 | col 2 | col 3 |
|---|---|---|---|---|
| **row 0** | 1 | 1 | 1 | 1 |
| **row 1** | 1 | 2 | 3 | 4 |
| **row 2** | 1 | 3 | 6 | **10** |

### Two strings: prefixes and the empty row

The state is a **pair of prefixes**: `dp[i][j]` covers the first `i` letters of `a` and the first `j` of `b`, in an `(m + 1) × (n + 1)` table whose letters are `a[i - 1]` and `b[j - 1]`. Row 0 and column 0 are the **empty prefix**: LCS 0, or `i` deletions to reach the empty string.

Then compare the **last letters**. For the longest common subsequence, equal letters use both (diagonal + 1); otherwise keep the larger of above (drop `a`'s letter) and left (drop `b`'s). Watch the fill, then the walk back:

## Step by step: the recipe in two dimensions

The same six steps as 1D, with one more index to get wrong.

<Steps>
  <Step title="Name both indices and the cell in words">
    "`dp[i][j]` = the fewest edits turning the first `i` letters of `a` into the first `j` of `b`." A **length** index (prefixes, capacities) needs an extra 0 row; a **position** (grid cells) doesn't.
  </Step>
  <Step title="Size the table and avoid the shared-row trap">
    `Array.from({ length: m + 1 }, () => new Array(n + 1).fill(0))`. Never `fill(new Array(n + 1))`: that repeats one row object, so one write changes a whole column.
  </Step>
  <Step title="Seed row 0 and column 0">
    An empty prefix, no items, a grid's first row. Most wrong edit distances seed row 0 with zeros instead of `0, 1, 2, …`.
  </Step>
  <Step title="Write the recurrence from the last decision">
    The last grid move, the last letters (match or not), the last item (take or skip): each option points at one neighbour.
  </Step>
  <Step title="Fill in dependency order">
    Above, left and diagonal: row by row. Interval DPs read shorter intervals, so loop by length.
  </Step>
  <Step title="Read the answer, rebuild it, then compress">
    Usually the far corner `dp[m][n]`. Walk back if you need the choices; only then drop to one row.
  </Step>
</Steps>

| left `dp[i][j - 1]` | **insert** `b`'s last letter |

## Template 3: knapsack, 0/1 and unbounded

Rows are items, columns are capacities 0 to `W`. Each cell either **skips** the item (the cell above) or **takes** it (the cell above, `w` columns back, plus its value). Taking reads the **previous** row, so each item is used at most once.

<AlgoViz trace={knapsackTable} />

One row is enough, but then the **direction** of the capacity loop decides the problem:

- **0/1, high to low:** `dp[c - w]` isn't updated for this item yet, so it still means "without this item".
- **Unbounded, low to high:** `dp[c - w]` already includes this item, so it can be taken again, like reading `(i, j - w)`.

## Reconstructing the answer

The table stores values, not choices, but every value came from a neighbour you can find again:

- **LCS:** matching letters mean the diagonal (record the letter); otherwise move to the larger of above and left.
- **Knapsack:** if `dp[i][c] !== dp[i - 1][c]`, item `i` was taken: record it and move to `c - w`. Otherwise move up.
- **Grid minimum path:** step to the smaller of above and left.

The walk is O(m + n) but needs the **full** table, since one row has lost the history. Want the path? Keep the 2D table or a parent pointer per cell.

## Complexity

| Variant | Time | Extra space |
|---|---|---|
| Grid `m × n` | O(m × n) | O(m × n) table, O(n) with one row |
| Two strings, lengths `m` and `n` | O(m × n) | O(m × n), O(min(m, n)) with one row |
| 0/1 or unbounded knapsack, `n` items, capacity `W` | O(n × W) | O(n × W), O(W) with one row |
| Reconstruction walk | O(m + n) | needs the full table |
| Interval DP over length `n` | O(n²) states, often O(n³) total | O(n²) |

O(n × W) depends on the **value** of `W`, not its digits: fast up to about 10^5, hopeless at `W = 10^12`.

## JavaScript you'll use

<JsRef to={["arrays", "gotchas", "recursion"]} />

```js
const dp = Array.from({ length: m + 1 }, () => new Array(n + 1).fill(0)); // m + 1 independent rows
const bad = new Array(m + 1).fill(new Array(n + 1).fill(0));             // ONE row, shared m + 1 times
const grid2 = grid.map((row) => row.slice());                             // copy before writing into the input
let prev = new Array(n + 1).fill(0), cur = new Array(n + 1).fill(0);
[prev, cur] = [cur, prev];                                                // two rows, swapped each iteration
```

The shared-row trap fails silently: `fill(x)` evaluates `x` once and puts the **same** array in every slot, so `dp[1][2] = 5` also sets `dp[0][2]` and the rest. `Array(n).fill([])` has the same bug; `Array.from` builds a fresh row each time.

<Callout kind="warning">

- No extra row and column for prefixes: at `i = 0`, `dp[i - 1]` is `undefined` and `dp[i - 1][j]` throws a TypeError.
- In a prefix table, the letter for row `i` is `a[i - 1]`, not `a[i]`.
- Compressing 0/1 knapsack with the capacity loop going **up**: items get reused.

</Callout>

## Interview questions

<FollowUps>
  <FollowUp q="Can you bring LCS or edit distance down to O(min(m, n)) space?">
    Yes: keep two rows (or one plus a variable for the old diagonal), with the shorter string as the columns. You get the length or distance but not the subsequence or edit script; Hirschberg's divide and conquer recovers those in linear space, but it's rarely expected.
  </FollowUp>
  <FollowUp q="Why must the 0/1 knapsack loop run from high capacity to low with one row?">
    The 2D recurrence reads `dp[i - 1][c - w]`, the previous item's row. Going down, cells left of `c` still hold that row; going up, they may already include this item, which is exactly unbounded knapsack.
  </FollowUp>
  <FollowUp q="Coin Change II and Combination Sum IV look the same. Why do they give different answers?">
    Coin Change II counts multisets: coins in the outer loop build each in one fixed order. Combination Sum IV counts ordered sequences, so amounts go outside and any coin can be last; for amount 3 with coins 1 and 2 they give 2 and 3.
  </FollowUp>
  <FollowUp q="How would you print the actual edits that turn one word into another?">
    Walk back from `dp[m][n]` in the full table. Matching letters with an equal diagonal mean no edit; otherwise the neighbour plus 1 that equals the cell names it (diagonal: replace, above: delete `a[i - 1]`, left: insert `b[j - 1]`). Reverse the list.
  </FollowUp>
  <FollowUp q="What if the robot in the grid can move in all four directions?">
    Cells can then depend on each other in a cycle, so no fill order works and the DP breaks. Use Dijkstra for non-negative costs or BFS for unit costs; counting paths needs a no-revisit rule and becomes exponential backtracking.
  </FollowUp>
</FollowUps>
