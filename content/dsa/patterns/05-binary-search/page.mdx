<TLDR>
Binary search keeps a range that **must contain the answer** and halves it with every check, so a million candidates need about 20 checks. It works on anything **monotonic**, and one template, **first true** (`lo < hi`, `hi = mid`), prevents most off-by-one bugs.
</TLDR>

## When to reach for it

<Callout kind="tip" title="Spot it in the problem statement">

- The input is **sorted**, or sorted and then **rotated**.
- "Find the **first** / **last** position", "smallest index such that…", "where would it be inserted?"
- "**Minimum** speed / capacity / time such that…", "**minimize the maximum**": a yes/no check gets easier as the answer grows.
- **O(log n)** is required, or the answer can reach 10^9, so trying every value is out.

</Callout>

| Variant | Search range | Classic problems |
|---|---|---|
| Exact match | indices `[0, n - 1]` | binary search |
| First true (lower bound) | indices `[0, n]` | insert position, first and last position |
| Rotated array | indices `[0, n - 1]` | search rotated, find the minimum |
| On the answer | smallest to largest possible answer | Koko, ship capacity, split array |

## The core idea: a range that must contain the answer

One sentence holds every binary search together, the **invariant**: *if the answer exists, it is inside `[lo, hi]`.* Each check proves that one half **can't** hold it, so that half goes and the sentence stays true.

On a sorted array the proof is one comparison. If `nums[mid]` is smaller than the target, everything left of `mid` is smaller still, so the whole left half, `mid` included, is out.

Halving is the speed: after about log₂(n) checks one candidate is left, so 10 for a thousand, 20 for a million, 30 for a billion. `mid` rounds **down**, so `lo <= mid < hi` whenever `lo < hi`; the templates rely on it. Watch the ruled-out half fade, or try your own array with **Edit input**:

## Step by step

<Steps>
  <Step title="Name the search space">
    Indices (up to `n` when "insert at the end" is a valid answer), or answer values from the smallest that could work to the largest you'd need.
  </Step>
  <Step title="Write the yes/no question and check it is monotonic">
    You need a test `ok(x)` that is false for a prefix and true after it, like `nums[i] >= target`. Say why `ok(x)` implies `ok(x + 1)`; if you can't, binary search is the wrong tool.
  </Step>
  <Step title="Pick the template and state the invariant">
    Exact match: "if the target exists, it is in `[lo, hi]`". First true: "everything before `lo` is false, everything from `hi` on is true".
  </Step>
  <Step title="Update so the invariant holds and the range shrinks">
    Never `lo = mid` with a rounded-down `mid`: with two candidates left it loops forever.
  </Step>
  <Step title="Run the tiny cases by hand">
    Trace 0, 1 and 2 candidates. Every off-by-one bug lives there.
  </Step>
</Steps>

## Template 1: exact match

You want one specific value and can stop the moment you see it. The range is **inclusive**, so the loop runs while it holds at least one element (`lo <= hi`), and both updates skip the already-checked `mid`.

## Template 2: first true (lower bound)

Most questions aren't "is it here?" but "**where does it start?**": the first copy, the insert position, the first bad version, the slowest speed that works. Picture a yes/no test over the candidates:

```text
index:          0  1  2  3  4  5  6     (7 = "none")
nums:           1  3  3  3  5  8  9
nums[i] >= 3?   F  T  T  T  T  T  T
                   ^ first true = 1
```

`hi` starts at `n`, one past the end, because "nothing passes" is a legal answer. When `lo` and `hi` meet, they sit on the boundary.

`lowerBound` answers <ProblemLink slug="search-insert-position" />. Add an upper bound for <ProblemLink slug="find-first-and-last-position" />: the first copy is at `lowerBound(x)`, the last at `upperBound(x) - 1`.

**Off-by-one, settled.** The templates come in matched sets:

| Template | Loop | Updates | Ends with |
|---|---|---|---|
| Exact match | `lo <= hi` | `lo = mid + 1`, `hi = mid - 1` | `lo === hi + 1` (empty) |
| First true | `lo < hi` | `lo = mid + 1`, `hi = mid` | `lo === hi` (the answer) |

Mix the parts and you get a bug: `lo <= hi` with `hi = mid` loops forever, `lo < hi` with `hi = mid - 1` can skip the answer. For the **last** true, find the first false and subtract one.

## Template 3: rotated sorted arrays

Rotate `[1, 2, 4, 5, 7, 9]` into `[5, 7, 9, 1, 2, 4]` and "smaller middle means go right" breaks. What survives: cut anywhere and **at least one half is still sorted** (the left one if `nums[lo] <= nums[mid]`). Its two ends tell you whether the target is inside, so you know which half to keep.

To find the minimum, compare `nums[mid]` with `nums[hi]`: if `nums[mid] > nums[hi]`, the drop is right of `mid`. That's first true in disguise.

## Template 4: binary search on the answer

Nothing is sorted, but the **answer** is a number in a known range, and checking a candidate is cheap: can every package ship in `days` days with capacity `cap`? Does speed `k` finish the bananas in `h` hours?

If a candidate works, every bigger one does too. So "does `x` work?" goes no, no, …, yes, yes, and first true finds the smallest `x` that works. Ranges of a billion are fine.

## Complexity

| Variant | Time | Extra space |
|---|---|---|
| Exact match, bounds, first and last position | O(log n) | O(1) |
| Rotated array | O(log n) | O(1) |
| On the answer: range R, each check O(n) | O(n log R) | O(1) |
| Recursive version of any of these | same time | O(log n) call stack |

## JavaScript you'll use

<JsRef to={["numbers-math", "arrays"]} />

```js
const mid = Math.floor((lo + hi) / 2);     // exact for any integers up to 2^53
const mid2 = lo + ((hi - lo) >> 1);        // also fine while hi - lo < 2^31
(1500000000 + 1600000000) >> 1;           // -597483648: >> works on 32-bit integers
Math.ceil(pile / speed);                   // hours for a pile: a partial hour counts as one
Math.max(...weights);                      // largest value (spreads every element as an argument)
nums.reduce((a, b) => a + b, 0);           // total, a common upper bound for answer searches
```

`Math.max(...arr)` throws a `RangeError` somewhere above about 100,000 elements: use a loop or `reduce` for huge inputs.

<Callout kind="warning">

- Starting `hi` at `n - 1` when "past the end" is a valid answer.
- Trusting a lower bound blindly: it returns a position even when the target is missing, so check `nums[i] === target`.
- Rounding down in checks: hours for a pile are `Math.ceil(p / k)`.

</Callout>

## Interview questions

<FollowUps>
  <FollowUp q="Why do some people write lo + (hi - lo) / 2? Do you need it in JavaScript?">
    With 32-bit `int`s, `lo + hi` can overflow. JavaScript integers are exact up to 2^53, so `Math.floor((lo + hi) / 2)` is safe; the JavaScript bug is `(lo + hi) >> 1`, which goes negative once the sum passes about 2.1 billion.
  </FollowUp>
  <FollowUp q="What changes in a rotated sorted array if values can repeat?">
    When `nums[lo] === nums[mid] === nums[hi]` (as in `[1, 1, 1, 0, 1]`), you can't tell which half is sorted, so shrink with `lo++` and `hi--`. The worst case becomes O(n), and nothing does better.
  </FollowUp>
  <FollowUp q="How do you binary search for a real-valued answer, like a square root to six decimal places?">
    Set `lo = mid` or `hi = mid` (no plus or minus one) and stop after a fixed number of rounds, say 60, or once `hi - lo` is below the tolerance. For an integer square root, find the first `x` with `x * x > n` and subtract one.
  </FollowUp>
  <FollowUp q="The sorted array is too large to know its length (a stream or an API). How do you search it?">
    Exponential search: probe indices 1, 2, 4, 8, … until the value is at least the target, then binary search between the last two probes. O(log p) for a target at position p.
  </FollowUp>
  <FollowUp q="How do you search a matrix whose rows are sorted and each row starts after the previous one ends?">
    Treat it as one sorted array: index `i` is row `Math.floor(i / cols)`, column `i % cols`, so Template 1 runs in O(log(rows · cols)). If only rows and columns are sorted separately, walk from the top-right corner instead: O(rows + cols).
  </FollowUp>
</FollowUps>
