<TLDR>
A **binary heap** keeps the best item at its root: **peek** in O(1), **push** and **pop** in O(log n), and nothing ever gets fully sorted. Most heap problems are **top k** (O(n log k)), **k-way merge** (O(N log k)) or **two heaps** for a running median.
</TLDR>

## When to reach for it

<Callout kind="tip" title="Spot it in the problem statement">

- "The **k** largest, smallest, most frequent or closest", or "the **kth** largest".
- **Merge k sorted** lists, arrays or streams.
- A **running** answer over a stream: the median so far, the kth largest so far.

</Callout>

| Variant | The heap holds | Classic problems |
|---|---|---|
| Top k | the best k so far | kth largest, top k frequent, k closest points |
| K-way merge | one head per sorted input | merge k sorted lists, kth smallest in a sorted matrix |
| Two heaps | the lower and upper halves | running median, sliding window median |
| Best first | every pending item, **cheapest** first | task scheduling, meeting rooms, Dijkstra |

## The core idea: a tree that is only half sorted

A heap is lazy on purpose. It is a **complete binary tree** (every level full except the last, which fills from the left) with one rule: **every parent comes before its children**. The minimum sits at the root of a min-heap; siblings sit in any order, and that laziness makes updates cheap.

No gaps means the tree fits in a plain array: the children of index `i` are `2i + 1` and `2i + 2`, its parent is `(i - 1) >> 1`. A million items is only 20 levels deep.

- **push**: append as the last leaf, then **sift up**, swapping with the parent while smaller.
- **pop**: take the root, move the last leaf into its place, then **sift down**, swapping with the **smaller** child while that child is smaller.

Each is at most one swap per level. Watch both on the tree and the array underneath:

Pop everything and you have heap sort, but the real job is answering "what is the best item **right now**?" while items keep arriving.

## Play with it

Values stream into a heap capped at k, and every swap plays on the tree and the array at once. Step through one swap at a time, then set **Who sifts** to You and make the swaps yourself. Flip to the k smallest and the heap turns upside down.

## Step by step

<Steps>
  <Step title="Ask what you need the best of, repeatedly">
    The min or max **many times** while the data changes: heap. Just once: scan or sort.
  </Step>
  <Step title="Decide what goes into the heap">
    Whatever you need when it comes out: numbers, `[value, count]` pairs, list nodes, `{ value, list, index }` records.
  </Step>
  <Step title="Write the comparator and check its direction">
    `compare(a, b)` is negative when `a` leaves first. The k largest need a **min**-heap: you evict the smallest you keep.
  </Step>
  <Step title="Bound the size">
    Pop at k + 1 for top k; one item per input for a merge. O(n log n) becomes O(n log k).
  </Step>
  <Step title="Read the answer">
    `peek()` for the kth best, pop all for the top k (reversed), two tops for a median.
  </Step>
</Steps>

## Template 1: a binary heap with a comparator

One class, one comparator: a min-heap, a max-heap, or pairs ordered by any key.

<CodeTabs files={['snippets/heap.js']} />

```js
new Heap((a, b) => a - b);          // min-heap of numbers
new Heap((a, b) => b - a);          // max-heap of numbers
new Heap((a, b) => a[1] - b[1]);    // pairs, smallest second element first
new Heap((a, b) => a.val - b.val);  // linked list nodes by value
```

Practise until `siftUp` and `siftDown` come out right first time: interviews expect your own heap.

## Template 3: k-way merge

With k **sorted** inputs, the next output is always one of the k current heads. Keep the heads in a min-heap: pop the smallest, output it, push its successor. The heap never holds more than k.

<AlgoViz trace={kWayMerge} />

<CodeTabs files={['snippets/k-way-merge.js']} />

Each entry must know its successor: an index into its array, or for linked lists the node itself (`node.next`). Practice: <ProblemLink slug="merge-k-sorted-lists" />.

## Template 4: two heaps for a running median

Keep the **lower half** in a max-heap and the **upper half** in a min-heap, under two rules:

1. Every value in the lower half is at most every value in the upper half.
2. The lower half holds as many values as the upper half, or one more.

The median is the lower top (odd count) or the average of both tops (even). To add a number, push it low and move the lower top up (rule 1); if the upper half is now bigger, move its top back (rule 2). That's O(log n) per number and O(1) per median.

## Complexity

| Operation or variant | Time | Extra space |
|---|---|---|
| `peek` | O(1) | O(1) |
| `push`, `pop` on n items | O(log n): one swap per level | O(1) |
| Build a heap from n items | O(n log n) by pushing, O(n) bottom-up | O(n) |
| Top k of n items | O(n log k) | O(k) |
| K-way merge of N items from k inputs | O(N log k) | O(k) |
| Running median | O(log n) per number, O(1) per median | O(n) |

## JavaScript you'll use

<JsRef to={["heap", "classes", "sorting"]} />

```js
const parent = (i - 1) >> 1;                 // index of the parent: halve and round down
const left = 2 * i + 1, right = 2 * i + 2;   // indices of the children
[a[i], a[j]] = [a[j], a[i]];                 // swap two slots
const byCount = (a, b) => a[1] - b[1];       // comparators return numbers, never booleans
for (const entry of counts) heap.push(entry); // Map entries are [key, value] pairs
```

Don't fake a heap: `arr.sort()` after every insert is O(n log n) per operation, and `arr.shift()` is O(n). Both pass the examples and time out on the hidden tests.

<Callout kind="warning">

- A comparator that returns a **boolean**, like `(a, b) => a > b`. Return a negative, zero or positive number.
- siftDown that swaps with the first smaller child instead of the **smaller of the two**.
- pop on a one-item heap that writes the last item back into index 0, leaving a **ghost value**.

</Callout>

## Interview questions

<FollowUps>
  <FollowUp q="Kth largest element: heap, sort or quickselect?">
    Sorting is O(n log n); a size-k min-heap is O(n log k) with O(k) memory and works on a **stream**. Quickselect is O(n) on average but O(n²) worst case without a random pivot, and it reorders the input: name all three, then code the heap.
  </FollowUp>
  <FollowUp q="Why can a heap be built in O(n) instead of O(n log n)?">
    Bottom-up heapify sifts down every non-leaf, last to first. Half the nodes are leaves, a quarter sink at most one level, an eighth at most two, so n/4 · 1 + n/8 · 2 + n/16 · 3 + … stays below n.
  </FollowUp>
  <FollowUp q="How would you change the priority of an item already in the heap, or delete it?">
    Keep a Map from item to index (updated on every swap) and sift from there. Or use **lazy deletion**: push the new version and discard stale ones when they reach the top, as Dijkstra in JavaScript usually does.
  </FollowUp>
  <FollowUp q="Running median: what if every number is between 0 and 100? And over a sliding window?">
    For 0 to 100, a count array of 101 buckets gives O(1) inserts and a median in at most 101 steps. For a **sliding window**, delete lazily (a Map of values waiting to leave) and balance the halves by live counts.
  </FollowUp>
  <FollowUp q="When is a heap the wrong tool?">
    Sorting once, arbitrary lookups or ranges (use a sorted array or balanced tree), or k close to n. A heap only promises fast access to one end.
  </FollowUp>
</FollowUps>
