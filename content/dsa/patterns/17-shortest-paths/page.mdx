<TLDR>
Every shortest-path algorithm repeats one move, **relaxation**: if going through `u` reaches `v` more cheaply, lower `dist[v]`. Only the order differs: **BFS** for equal edges, O(V + E); **Dijkstra** for non-negative weights, O(E log V); **Bellman-Ford** for negative weights or an edge limit, O(V · E).
</TLDR>

## When to reach for it

<Callout kind="tip" title="Spot it in the problem statement">

- **Minimum** cost, time or effort from a start to a target.
- **Weighted** edges: road lengths, flight prices, delays, heights.
- **Fewest moves** in a grid or puzzle: every move costs 1, so BFS.
- "At most **k stops**": count rounds with Bellman-Ford.
- A route costs its **largest** step: Dijkstra with `max` instead of `+`.

</Callout>

| Algorithm | Edge weights | Classic problems |
|---|---|---|
| BFS (queue) | all equal | binary-matrix path, word ladder |
| Dijkstra (min-heap) | non-negative | network delay, minimum effort |
| Bellman-Ford (rounds) | any; finds negative cycles | cheapest flights within k stops |
| Floyd–Warshall | any | all pairs on a small graph |

## The core idea: relax, closest first

Picture a road trip where every town shows a sign: "best known cost to get here". That sign is `dist[v]`, `Infinity` everywhere but the source. Relaxing `u → v` with weight `w` asks: is `dist[u] + w < dist[v]`? If so, a better route runs through `u`.

Dijkstra adds one greedy rule: **always expand the unsettled node with the smallest `dist`**. When `u` leaves the heap at distance `d`, that's final: any other route leaves the settled region through a node at least `d` away, and non-negative edges can't make it cheaper.

JavaScript has no decrease-key heap, so use **lazy deletion**: on an improvement, push a fresh `[dist, v]` and leave the old entry. When an outdated one surfaces (`d > dist[u]`), skip it. Watch B, D, E and F get stale entries:

### Why negative edges break Dijkstra

Take `A → B` costing 4, `A → C` 5 and `C → B` -3. Dijkstra settles B at 4, but `A → C → B` costs 2. The proof assumed edges never make a route cheaper, so a version that marks nodes done returns 4.

The lazy version recovers by pushing B again, but nodes can then be re-processed so often that the running time blows up exponentially. Use Bellman-Ford. With a **negative cycle**, no shortest path exists: one more lap is always cheaper.

## Step by step

<Steps>
  <Step title="Model the graph">
    A node is a city, a cell or a state like `(city, flights used)`. Build `adj[u]` as `[v, w]` pairs.
  </Step>
  <Step title="Pick the algorithm from the weights">
    Equal: BFS. Non-negative: Dijkstra. Negative, or an edge limit: Bellman-Ford.
  </Step>
  <Step title="Define how a route's cost combines">
    Usually `dist[u] + w`; for effort, `Math.max(dist[u], step)`. Dijkstra needs it never to decrease.
  </Step>
  <Step title="Initialise">
    `dist` full of `Infinity`, `dist[source] = 0`, source pushed.
  </Step>
  <Step title="Relax until nothing changes">
    Pop, skip stale, relax, push improvements. Dijkstra stops when the target is **popped**, not pushed; BFS may stop when it's first reached.
  </Step>
  <Step title="Read the answer">
    `dist[target]`, the largest `dist`, or `-1` where it's still `Infinity`.
  </Step>
</Steps>

## Template 3: Bellman-Ford, round by round

No clever order here: each round relaxes **every** edge. Read last round's distances, write into a copy, and after round `r`, `dist[v]` is the cheapest path with **at most `r` edges**. No shortest path needs more than `n - 1` edges, so `n - 1` rounds always suffice.

## Complexity

| Algorithm | Time | Extra space |
|---|---|---|
| BFS | O(V + E) | O(V) |
| Dijkstra, heap, lazy deletion | O(E log E) = O(E log V), as E ≤ V² | O(V + E) |
| Dijkstra, array scan for the minimum | O(V²): better when dense | O(V) |
| Bellman-Ford | O(V · E) | O(V) |
| Bellman-Ford, k + 1 rounds | O(k · E) | O(V): two arrays |
| Floyd–Warshall (all pairs) | O(V³) | O(V²) |

## JavaScript you'll use

<JsRef to={["heap", "graphs-in-js", "stack-queue-deque"]} />

```js
const adj = Array.from({ length: n }, () => []);   // one fresh list per node
for (const [u, v, w] of edges) adj[u].push([v, w]);
const dist = new Array(n).fill(Infinity);           // Infinity + w is still Infinity
const [d, u] = heap.pop();                          // entries are [distance, node]
const next = dist.slice();                          // Bellman-Ford: read old, write new
const DIRS = [[1, 0], [-1, 0], [0, 1], [0, -1]];    // grid neighbours
```

The real trap is the missing priority queue. Re-sorting costs O(n log n) per push and `queue.shift()` O(n) per pop: both quietly wreck the complexity. Bring a heap, and a head index for queues.

<Callout kind="warning">

- Freezing a node early: visited on **push**, or returning when the target is pushed. Only a pop is final.
- `new Array(n).fill([])`: every node shares one adjacency array.
- 1-based labels in size-n arrays, or `Math.max(...dist)` over an unused `Infinity` slot.

</Callout>

## Interview questions

<FollowUps>
  <FollowUp q="How do you return the path itself, not just its cost?">
    Set `prev[v] = u` on every improvement; those pointers form the shortest-path tree. Walk `prev` back from the target and reverse, in O(path length).
  </FollowUp>
  <FollowUp q="Edges cost either 0 or 1. Can you beat Dijkstra?">
    Yes: 0-1 BFS pushes 0-edges to the **front** of a deque and 1-edges to the **back**, so it stays sorted without a heap, O(V + E). Think "minimum walls to remove".
  </FollowUp>
  <FollowUp q="How would you detect a negative cycle?">
    After n - 1 Bellman-Ford rounds, make one more pass: any edge that still relaxes means a reachable negative cycle. Currency arbitrage is the classic case, with weights `-log(rate)`.
  </FollowUp>
  <FollowUp q="You need shortest paths between every pair of nodes. What would you do?">
    Small and dense: Floyd–Warshall, trying `dist[i][k] + dist[k][j]` for every middle `k`, O(V³), negative edges fine. Large, sparse and non-negative: Dijkstra from every node, O(V · E log V).
  </FollowUp>
  <FollowUp q="Dijkstra is too slow on a huge road map for a single A-to-B query. How can it be sped up?">
    Stop when B is popped, run bidirectional Dijkstra that stops when the two searches meet, or use A*. A* orders the heap by `dist[v] + h(v)`, with `h` a lower bound like straight-line distance, so the search heads for B.
  </FollowUp>
</FollowUps>
