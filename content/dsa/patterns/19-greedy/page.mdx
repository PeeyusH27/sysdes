<TLDR>
Greedy takes whatever looks best **right now** and never takes it back: usually a sort plus one pass, O(n log n) or O(n). It is correct only when you can **prove** the choice safe, with an **exchange argument** or by showing greedy **stays ahead**; a small counterexample means DP.
</TLDR>

## When to reach for it

<Callout kind="tip" title="Spot it in the problem statement">

- "Maximum or minimum number of…" with a natural **rule of thumb**: earliest deadline, cheapest so far, furthest reach.
- "Can you reach the end?": one quantity (reach, fuel, balance) sums up the past.
- Scheduling and assignment, where **sorting** puts the obvious candidate in front.
- n up to 10^5 or more: O(n log n), not every combination.

</Callout>

| Variant | The greedy rule | Classic problems |
|---|---|---|
| Running best | keep the best so far (cheapest price, furthest reach) | buy and sell stock, jump game |
| Sort, then match | smallest item with the smallest slot it fits | assign cookies, boats |
| Earliest end first | sort by end, keep whatever still fits | non-overlapping intervals, minimum arrows |
| Restart on failure | when a running total goes negative, restart after it | gas station, Kadane |

## The core idea: a choice you never regret

Greedy code is easy; knowing the local choice can't hurt is the hard part. Name the proof in an interview.

**Exchange argument.** Take *any* optimal solution. If it skips the greedy choice, swap it in and show the result is still valid and no worse. Cookies are the textbook case: the **smallest** cookie that works goes to the **least greedy** child, and swapping cookies in any other best pairing keeps every child happy.

<AlgoViz trace={assignCookies} />

**Greedy stays ahead.** Show greedy is never behind on some measure. In interval scheduling, greedy's k-th interval (by earliest end) ends no later than any other schedule's k-th, so it always has as much room left.

Can't make either argument? Hunt for a counterexample; if one exists, reach for [dynamic programming](/dsa/patterns/dp-1d).

## Step by step

<Steps>
  <Step title="Write the brute force in one sentence">
    "Try every subset of intervals" names the choices and the goal.
  </Step>
  <Step title="Propose a rule, usually after sorting">
    Earliest end, smallest that fits, cheapest so far, furthest reach. Sorting puts the rule's favourite first.
  </Step>
  <Step title="Attack your own rule">
    Spend a minute breaking it on 2–4 items: a long interval blocking short ones, a big but awkward coin. Interviewers expect this.
  </Step>
  <Step title="Prove it, or drop it">
    Make the exchange or stays-ahead argument out loud. If a counterexample survives, switch to DP or search.
  </Step>
  <Step title="Implement the one pass">
    A sort plus a loop. Watch ties (`>=` versus `>`): that's where hidden tests bite.
  </Step>
</Steps>

## Template 1: sort, then match

Pairing items with slots (cookies with children, people with boats, tasks with workers)? Sort both and walk them together. A cookie too small for the least greedy child is too small for everyone left, so throw it away; one that fits goes to that child.

The same shape answers "boats to save people" (pair the heaviest with the lightest if they fit) and "assign tasks to workers", each justified by an exchange argument.

## Template 2: earliest end first

To keep the most non-overlapping activities, always keep the one that **ends first** among those that still fit. Earliest start and shortest length both fail on small examples; earliest end stays ahead.

## Template 3: one pass with a running best

Many greedy solutions never sort: one scan, one number that sums up the past.

```js
let reach = 0;                                   // Jump Game: furthest index reachable so far
for (let i = 0; i < nums.length; i++) {
  if (i > reach) return false;                   // a gap nothing can cross
  reach = Math.max(reach, i + nums[i]);
}
return true;
```

- <ProblemLink slug="best-time-to-buy-and-sell-stock" />: the cheapest price so far.
- <ProblemLink slug="jump-game" />: the furthest reachable index; reachable indices always form a prefix.
- <ProblemLink slug="jump-game-ii" />: count frontier extensions, BFS by levels without a queue.
- <ProblemLink slug="gas-station" />: fuel since the start; running dry at station `i` rules out every start before it.
- <ProblemLink slug="partition-labels" />: the furthest last occurrence in the piece; cut when the scan reaches it.

Need both directions? **Two passes**: in <ProblemLink slug="candy" />, left to right then right to left, taking the max so the first pass survives.

## When greedy fails

"Make change with the fewest coins: take the largest coin that fits." US-style coins, fine. Coins `4, 3, 1` and amount 6: greedy pays 4 + 1 + 1, while 3 + 3 needs two. The 4 felt like progress but left a remainder only small coins could fill.

<AlgoViz trace={greedyCoins} />

The fix is to stop committing. Dynamic programming finds the best answer for **every** smaller amount, trying each coin as the last one, so no early choice can trap it.

<CodeTabs files={['snippets/coins.js']} />

The split shows up elsewhere. Fractional knapsack is greedy by value per kilo; 0/1 knapsack needs DP. Shortest paths with non-negative weights are greedy (Dijkstra); with negative weights they are not.

## Complexity

| Variant | Time | Extra space |
|---|---|---|
| Sort, then one pass (matching, earliest end) | O(n log n) | O(1) to O(n) for the sort or a copy |
| One pass with a running best | O(n) | O(1) |
| Two passes (candy) | O(n) | O(n) for the per-item array |
| Coin change by DP, for comparison | O(amount × coins) | O(amount) |

## JavaScript you'll use

<JsRef to={["sorting", "numbers-math"]} />

```js
const sorted = [...items].sort((a, b) => a - b);   // copy first if the caller's order matters
intervals.sort((a, b) => a[1] - b[1]);             // by end time
let best = -Infinity, cheapest = Infinity;         // sentinels: any real value beats them
best = Math.max(best, price - cheapest);           // Infinity arithmetic is safe: 5 - Infinity is -Infinity
const total = nums.reduce((sum, x) => sum + x, 0); // feasibility totals (gas station)
```

`sort` works **in place**, so `const sorted = arr.sort(…)` also reorders `arr`. Copy with `[...arr]` or use `toSorted` when the order matters later.

<Callout kind="warning">

- Ties: `start > lastEnd` instead of `>=` rejects intervals that only touch.
- Skipping a global feasibility check, like total fuel in Gas Station, before trusting the local answer.
- Overwriting instead of taking a max in a second pass, which undoes the first.

</Callout>

## Interview questions

<FollowUps>
  <FollowUp q="How do you convince an interviewer your greedy algorithm is correct?">
    Name the argument (exchange, or stays ahead) and walk it through their example. Then show the small counterexample you tried, and offer the DP if you can't argue it.
  </FollowUp>
  <FollowUp q="For which coin systems does greedy change-making work?">
    "Canonical" ones like 1, 5, 10, 25 or 1, 2, 5, 10, 20, 50; 1, 3, 4 fails at 6. If greedy ever fails, it fails below the sum of the two largest coins, so compare it with DP up to there (or, with arbitrary coins, just use DP).
  </FollowUp>
  <FollowUp q="Greedy or dynamic programming: how do you decide quickly?">
    Ask whether an early choice can be regretted, as in 0/1 knapsack or arbitrary coins: then you need DP. A few tiny inputs against a brute force settle it fast.
  </FollowUp>
  <FollowUp q="Jump Game II is greedy, but people also call it BFS. Which is it?">
    Both: the indices reachable in k jumps form a contiguous block, BFS level k. The greedy scan walks each level once, computing BFS distances in O(n) without a queue.
  </FollowUp>
</FollowUps>
