<TLDR>
Union-find (also called disjoint set union) keeps items in separate groups, each stored as a tree whose **root names the group**. `find(x)` climbs to the root and `union(a, b)` hangs one root under the other, so "are these two connected?" becomes "do they have the same root?". With **path compression** and **union by rank**, both operations are effectively O(1), so adding m edges to n items costs about O(n + m) instead of re-running a graph search after every edge.
</TLDR>

## When to reach for it

<Callout kind="tip" title="Spot it in the problem statement">

- The answer is a number of **groups**: connected components, provinces, friend circles, networks.
- Links **arrive one at a time** and you need connectivity after each one.
- "Does this edge **create a cycle**?" or "is this a valid tree?" in an **undirected** graph.
- Items are **equivalent** through a chain of links: accounts that share an email, variables constrained by `a == b`, similar strings.
- You need a minimum spanning tree (Kruskal's algorithm).

</Callout>

| Variant | Items | What you watch | Classic problems |
|---|---|---|---|
| Count groups | indices `0 … n - 1` | `count`, lowered by every union that merges | number of provinces, connected components |
| Cycle detection | the edges of an undirected graph | `union` returning `false` (both ends share a root) | redundant connection, graph valid tree |
| Keyed groups | strings, emails, `"r,c"` cells in a `Map` | each item's root, and the size of each group | accounts merge, largest group, islands added one by one |
| Kruskal's MST | edges sorted by weight | take an edge only if it joins two groups | min cost to connect all points |

## The core idea: one root per group

Every item has a `parent`. A root is an item that is its own parent, and following parent pointers from any item always ends at its group's root. So:

- **same group?** Compare `find(a)` with `find(b)`.
- **merge two groups?** Find both roots and point one at the other. Every item below the old root now reaches the new root too.

Linking roots is O(1); the only real cost is the climb inside `find`, which is as long as the tree is tall. Two tricks keep trees almost flat:

- **Union by rank.** Each root stores a rank, an upper bound on its tree's height. Always hang the shorter tree under the taller one. Height only grows when two equally tall trees merge, so no tree is taller than log₂ n.
- **Path compression.** After `find(x)` has found the root, point every node it passed straight at the root. The next `find` from any of them is a single hop.

Watch the badges (each node's root) change as edges arrive. The edge 3-0 is rejected because both ends already share root 0, and finding 3 flattens its path on the way:

<AlgoViz trace={unionByRank} />

With both tricks, any sequence of m operations on n items costs O(m α(n)), where α is the inverse Ackermann function: at most 4 for any input that fits in the universe. Treat it as constant.

## Step by step

<Steps>
  <Step title="Decide what the items are">
    Number them `0 … n - 1` when you can: cities, nodes, account indices, grid cells as `r * cols + c`. If the items are strings you can't easily number, use the keyed version with a `Map`.
  </Step>
  <Step title="Decide what links two items">
    An edge, a shared email, an equation `a == b`, two adjacent land cells. Each link is one `union` call.
  </Step>
  <Step title="Initialise">
    `parent[i] = i`, `rank[i] = 0`, and `count = n` if you need the number of groups.
  </Step>
  <Step title="Union every link and use the return value">
    `true` means two groups merged (lower the count). `false` means the two items were already connected: in a graph, that edge closes a cycle.
  </Step>
  <Step title="Read the answer through find">
    The answer is `count`, a comparison `find(a) === find(b)`, or the items bucketed by `find(i)`. Never read `parent[i]` directly: a parent is not always a root.
  </Step>
</Steps>

## Complexity

| Version | find / union | Extra space |
|---|---|---|
| Path compression + union by rank (or size) | O(α(n)) amortised, effectively O(1) | O(n) for parent and rank |
| Union by rank only | O(log n) worst case | O(n) |
| Path compression only | O(log n) amortised | O(n) |
| Neither (always link a under b) | O(n) worst case: the trees become chains | O(n) |
| n items, m unions and finds, both tricks | O(n + m α(n)) total | O(n) |

Kruskal's MST is dominated by sorting the edges: O(E log E).

## JavaScript you'll use

<JsRef to={["classes", "arrays", "map-set"]} />

```js
const parent = Array.from({ length: n }, (_, i) => i); // [0, 1, 2, …, n - 1]
const rank = new Array(n).fill(0);
[ra, rb] = [rb, ra];                                    // swap so ra is the taller root
const id = (r, c) => r * cols + c;                      // grid cell → item number
const uf = new UnionFind(n + 1);                        // labels 1 … n: one extra slot
```

The main JavaScript trap is recursion depth: a recursive `find` on a long chain throws `RangeError: Maximum call stack size exceeded`. Union by rank prevents long chains; the loop version never recurses at all.

<Callout kind="warning">

- Comparing `parent[a] === parent[b]` instead of `find(a) === find(b)`. Two items can share a root while their direct parents differ.
- Linking the items instead of their roots: `parent[a] = b` cuts `a` out of its old tree and leaves the rest of that tree behind.
- Lowering `count` on every union call, including the ones that return `false`.
- Labels that start at 1 with arrays of size n: node `n` has no slot. Allocate `n + 1`.
- Grouping items by `parent[i]` at the end. Call `find(i)` for each item first.

</Callout>

## Interview questions

<FollowUps>
  <FollowUp q="Union-find or BFS/DFS for connected components: which would you pick?">
    For a fixed graph both are linear in practice: BFS/DFS is O(V + E) and also gives you paths and distances. Union-find needs no adjacency list and shines when edges **arrive over time**: after each new edge you can answer "how many groups?" or "are x and y connected?" in near-constant time, where BFS would have to start again.
  </FollowUp>
  <FollowUp q="Can union-find remove an edge?">
    Not directly: merges can't be undone once paths are compressed. If all queries are known in advance, process them **offline in reverse**: start from the final graph and turn deletions into additions. If you must undo in last-in-first-out order (backtracking), use union by rank **without** path compression and keep a stack of the links you made, so each undo just restores one parent and one rank.
  </FollowUp>
  <FollowUp q="How would you find the size of the largest group?">
    Use union by size: keep `size[root]`, add the smaller group's size to the larger root on every merge, and update a running maximum. The same trick answers "how many items are connected to x?" with `size[find(x)]`.
  </FollowUp>
  <FollowUp q="How does Kruskal's algorithm use union-find?">
    Sort the edges by weight and walk through them. Take an edge only if `union(a, b)` returns `true` (it joins two different trees); skip it otherwise, because it would close a cycle. Stop after n - 1 edges. Sorting is O(E log E) and the unions are almost free.
  </FollowUp>
  <FollowUp q="How do you use union-find on a grid, for example islands appearing one cell at a time?">
    Number each cell `r * cols + c`. When a cell becomes land, add it as a new group (count + 1) and union it with each neighbouring land cell (count - 1 for every union that merges). Each new cell costs O(α(n)), so k additions cost about O(k) instead of a fresh flood fill each time.
  </FollowUp>
</FollowUps>
