<TLDR>
Union-find (disjoint set union) stores each group as a tree whose **root names the group**, so "are these connected?" becomes "same root?". With **path compression** and **union by rank**, `find` and `union` are effectively O(1): m edges on n items cost about O(n + m).
</TLDR>

## When to reach for it

<Callout kind="tip" title="Spot it in the problem statement">

- The answer is a number of **groups**: components, provinces, friend circles.
- Links **arrive one at a time** and you need connectivity after each.
- "Does this edge **create a cycle**?" in an **undirected** graph.
- Items **equivalent** through chains of links: shared emails, `a == b` constraints.

</Callout>

| Variant | What you watch | Classic problems |
|---|---|---|
| Count groups | `count`, down one per merge | number of provinces, connected components |
| Cycle detection | `union` returning `false` | redundant connection, graph valid tree |
| Keyed groups | roots and group sizes in a `Map` | accounts merge, islands added one by one |
| Kruskal's MST | edges that join two groups | min cost to connect all points |

## The core idea: one root per group

A group is a chain of command: everyone has a `parent`, and following parents ends at the **root**, the one item that is its own parent. Same group? Compare `find(a)` with `find(b)`. Merge? Point one root at the other.

Linking is O(1); the cost is the climb inside `find`, which is as long as the tree is tall. Two tricks keep trees flat:

- **Union by rank**: hang the shorter tree (by rank, an upper bound on height) under the taller. Height grows only when equals merge, so no tree passes log₂ n.
- **Path compression**: after `find(x)` reaches the root, point every node it passed straight at it. The next `find` from any of them is one hop.

Watch the badges (each node's root). The edge 3-0 is rejected because both ends already share root 0, and finding 3 flattens its path. Try your own edges with Edit input.

<AlgoViz trace={unionByRank} />

With both, m operations on n items cost O(m α(n)), where α, the inverse Ackermann function, is at most 4 for any input that fits in the universe. Treat it as constant.

## Step by step

<Steps>
  <Step title="Decide what the items are">
    Number them `0 … n - 1` (grid cells as `r * cols + c`), or use the keyed version with a `Map`.
  </Step>
  <Step title="Decide what links two items">
    An edge, a shared email, `a == b`, two adjacent land cells: one `union` each.
  </Step>
  <Step title="Initialise">
    `parent[i] = i`, `rank[i] = 0`, and `count = n` if you need the number of groups.
  </Step>
  <Step title="Union every link and use the return value">
    `true`: merged, lower the count. `false`: already connected, so that edge closes a cycle.
  </Step>
  <Step title="Read the answer through find">
    `count`, `find(a) === find(b)`, or items bucketed by `find(i)`. Never `parent[i]`: a parent is not always a root.
  </Step>
</Steps>

## Complexity

| Version | find / union | Extra space |
|---|---|---|
| Path compression + union by rank (or size) | O(α(n)) amortised, effectively O(1) | O(n) |
| Union by rank only | O(log n) worst case | O(n) |
| Path compression only | O(log n) amortised | O(n) |
| Neither (always link a under b) | O(n) worst case: trees become chains | O(n) |
| n items, m unions and finds, both tricks | O(n + m α(n)) total | O(n) |

Kruskal's MST is dominated by sorting the edges: O(E log E).

```js
const parent = Array.from({ length: n }, (_, i) => i); // [0, 1, 2, …, n - 1]

[ra, rb] = [rb, ra];                                    // swap so ra is the taller root

const uf = new UnionFind(n + 1);                        // labels 1 … n: one extra slot
```

The JavaScript trap is recursion depth: a recursive `find` on a long chain throws `RangeError: Maximum call stack size exceeded`.

<Callout kind="warning">

- Linking the items instead of their roots: `parent[a] = b` cuts `a` out of its tree and leaves the rest behind.
- Lowering `count` on every union call, including the ones that return `false`.
- Labels that start at 1 with arrays of size n: node `n` has no slot. Allocate `n + 1`.

</Callout>

## Interview questions

<FollowUps>
  <FollowUp q="Union-find or BFS/DFS for connected components: which would you pick?">
    On a fixed graph both are linear, and BFS/DFS also gives paths. Union-find wins when edges **arrive over time**: each answer is near-constant, where BFS would start again.
  </FollowUp>
  <FollowUp q="Can union-find remove an edge?">
    Not directly. With all queries known, run them **offline in reverse** so deletions become additions; for last-in-first-out undo, skip compression and keep a stack of links to restore.
  </FollowUp>
  <FollowUp q="How would you find the size of the largest group?">
    Union by size: add the smaller `size` to the larger root on each merge and track the maximum. `size[find(x)]` counts x's group.
  </FollowUp>
  <FollowUp q="How does Kruskal's algorithm use union-find?">
    Sort edges by weight and take one only if `union(a, b)` returns `true` (otherwise it closes a cycle), stopping at n - 1 edges. Sorting is O(E log E); the unions are almost free.
  </FollowUp>
  <FollowUp q="How do you use union-find on a grid, for example islands appearing one cell at a time?">
    Number cells `r * cols + c`. New land adds a group (count + 1) and unions with each land neighbour (count - 1 per merge): about O(k) for k additions, not a flood fill each time.
  </FollowUp>
</FollowUps>
