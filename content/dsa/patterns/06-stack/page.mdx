<TLDR>
A stack hands back the **most recent** unfinished item first, which is exactly the order in which nested things close: brackets, function calls, undo steps. A **monotonic stack** keeps the items that are still waiting in sorted order, so each new element **resolves** every waiting item it beats. That finds every "next greater" or "next smaller" answer in one O(n) pass instead of O(n²).
</TLDR>

## When to reach for it

<Callout kind="tip" title="Spot it in the problem statement">

- Things **open and close** in a nested way: brackets, tags, function calls, `..` in a path.
- You must **undo** or cancel the most recent action: backspaces, collisions, removing adjacent pairs.
- An operator applies to the **latest** operands: postfix notation, calculators.
- For each element, find the **next (or previous) greater or smaller** element, or how far away it is.
- A width, span or area is bounded by the nearest **taller or shorter** neighbour: stock span, histograms.

</Callout>

| Variant | The stack holds | Pop when | Classic problems |
|---|---|---|---|
| Matching and nesting | openers (or partial results) still waiting to close | a closer arrives: it must match the top | valid parentheses, simplify path, decode string |
| Expression evaluation | operands waiting for an operator | an operator arrives: pop two, push the result | reverse Polish notation, basic calculator |
| Monotonic decreasing | indices still waiting for a **greater** value | the new value is greater than the top | next greater element, daily temperatures, stock span |
| Monotonic increasing | indices still waiting for a **smaller** value | the new value is smaller than the top | largest rectangle in histogram, sum of subarray minimums |
| Stack with extra state | each value plus a summary of everything below it | an ordinary pop | min stack, max stack |

## The core idea: the most recent open item closes first

In `{ [ ( ) ] }` the last bracket opened is the first one closed. Whenever the rule is "the newest unfinished thing is the next one to finish", a stack keeps the unfinished things in exactly the right order, with O(1) `push` and `pop`. A closer never needs to search: it only looks at the top.

That is also why counting is not enough. `([)]` has one of each bracket, but when `)` arrives, the newest open bracket is `[`. The stack catches the crossing at the moment it happens:

The same shape covers more than brackets. In reverse Polish notation each operator consumes the two newest values, so the stack holds operands. In a file path, `..` cancels the newest directory, so the stack holds directory names. The question to ask is always: **what is still open, and does the newest one get resolved first?**

## Step by step

<Steps>
  <Step title="Name what is waiting">
    Say in one sentence what sits on the stack: "opening brackets not yet closed", "operands not yet used", "indices that haven't found a greater value yet". That sentence is your invariant.
  </Step>
  <Step title="Decide what resolves the top">
    A closer, an operator, a `..`, or a value that beats the top. Write the pop condition as a `while` when one new element can resolve several waiting ones, as in the monotonic stack.
  </Step>
  <Step title="Do the work at pop time">
    The answer for an item is known at the moment it is popped: a match, a computed value, a next greater index, a rectangle width. Record it there.
  </Step>
  <Step title="Push the new element">
    After popping, the new element becomes the newest unfinished item. Push an **index** when you will later need a position or a distance, a value otherwise.
  </Step>
  <Step title="Handle what is left at the end">
    Items still on the stack never got resolved: unclosed brackets (invalid), elements with no greater value (answer -1), bars that extend to the end (flush them with a sentinel).
  </Step>
</Steps>

## Template 2: monotonic decreasing stack (next greater)

For "the next greater element to the right", a brute force scans right from every index: O(n²) on a decreasing array. Flip it around: walk left to right and keep the indices that **haven't found their answer yet** on a stack.

Values on the stack never go up from bottom to top, because each push first pops everything smaller. So when a new value arrives, every waiting value **smaller** than it sits at the top, and each of them has just found its answer. Popping index `j` because `nums[i] > nums[j]` resolves exactly one question: **i is j's next greater element**. It must be the first one, because any bigger value in between would have popped `j` earlier.

## Template 3: monotonic increasing stack (next smaller, both sides)

Flip the comparison and the stack keeps values **increasing** from bottom to top. Now each pop answers "next **smaller**", and a second answer comes for free:

- Popping `j` because `nums[i] < nums[j]` means **i is the first smaller value to the right of j**.
- After the pops, the index left on top is the **nearest value to the left of i that is not larger**. Everything between them was larger and has already been popped.

<AlgoViz trace={smallerNeighbours} />

That pair of neighbours is everything <ProblemLink slug="largest-rectangle-in-histogram" /> needs: the widest rectangle of height `heights[j]` stretches from just after its left neighbour to just before its right neighbour, so its width is `right - left - 1`. The histogram solution measures that width at the moment `j` is popped, and a final bar of height 0 flushes whatever is still waiting.

| You want, for each element | Stack order (bottom → top) | Pop while | Popping j tells you | The top after popping is |
|---|---|---|---|---|
| next greater | decreasing | `nums[top] < nums[i]` | i is j's next greater | i's previous value that is at least as large |
| next smaller | increasing | `nums[top] > nums[i]` | i is j's next smaller | i's previous value that is at most as large |

The strictness of the comparison decides how **ties** behave. With `<` in the decreasing stack, equal values wait together and are popped by the same larger value, which is right for "strictly greater". Read the problem for the words "strictly" and "or equal" before choosing `<` or `<=`.

## Complexity

| Variant | Time | Extra space |
|---|---|---|
| Matching / expression evaluation | O(n): each item pushed and popped once | O(n) in the worst case (everything nested) |
| Monotonic stack | O(n) amortised: n pushes and at most n pops in total | O(n) for the stack and the answers |
| Stack with extra state (min stack) | O(1) per operation | O(n): one summary per element |
| Brute-force next greater, for comparison | O(n²) | O(1) |

The `while` inside the `for` looks quadratic, but it can't pop more items than were pushed, and every index is pushed exactly once.

## JavaScript you'll use

<JsRef to={["stack-queue-deque", "arrays"]} />

```js
const stack = [];
stack.push(x);                 // O(1): add on top
const top = stack.pop();       // O(1): remove the top (undefined when the stack is empty)
stack.at(-1);                  // peek at the top without removing it
stack.length === 0;            // empty check
new Array(n).fill(-1);         // default answers for "never resolved"
```

The top of a JavaScript stack is the **end** of the array. `shift` and `unshift` work on the front and move every other element, so they are O(n): never use them for a stack.

<Callout kind="warning">

- Peeking at an empty stack: `stack.at(-1)` is `undefined`, and `nums[undefined] < x` is silently `false`. Check `stack.length` first.
- Pushing values when you need indices, then having no way to compute a distance or a width.
- Using `<=` where the problem says "strictly greater" (or the reverse): equal values then resolve each other.
- Forgetting the items left on the stack at the end. They keep the default answer, or, as in the histogram, still need a final flush.
- Popping operands in the wrong order for `-` and `/`: the first pop is the right operand.

</Callout>

## Interview questions

<FollowUps>
  <FollowUp q="Why is the monotonic stack O(n) when there is a while loop inside the for loop?">
    Count pops instead of loop iterations. Every index is pushed exactly once, and an index can be popped at most once, so all the `while` iterations together pop at most n items. Each `for` iteration does O(1) work besides those pops, so the total is O(n) amortised, even though a single iteration may pop many items.
  </FollowUp>
  <FollowUp q="How do you find the next greater element in a circular array?">
    Walk the array twice: `i` from 0 to `2n - 1`, reading `nums[i % n]`. Push indices only during the first lap, but keep popping during both, so elements near the end can be resolved by values near the start. Anything still on the stack after two laps has no greater value anywhere and keeps -1. Still O(n).
  </FollowUp>
  <FollowUp q="You only need the next greater element for a few query values, not every index. What changes?">
    Run the monotonic stack once over the whole array and store the answers in a `Map` from value to next greater value (this needs distinct values), then answer each query with one lookup. Total O(n + q) instead of O(n) per query.
  </FollowUp>
  <FollowUp q="How do you build a queue from two stacks?">
    Push new items onto an `in` stack. To dequeue, pop from an `out` stack; when `out` is empty, pop everything from `in` and push it onto `out`, which reverses the order so the oldest item is on top. Each item moves between the stacks at most once, so every operation is O(1) amortised.
  </FollowUp>
  <FollowUp q="When would you use an explicit stack instead of recursion?">
    Recursion is a stack that the engine manages for you, and it is limited: deep nesting (say 10^5 levels of brackets or a long linked list) can throw "Maximum call stack size exceeded" in JavaScript. An explicit array stack has no such limit and makes the state you keep visible. Recursion is fine, and often clearer, when the depth is small, such as a balanced tree.
  </FollowUp>
</FollowUps>
