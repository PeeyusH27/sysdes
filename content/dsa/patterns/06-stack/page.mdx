</TLDR>

## The core idea: the most recent open item closes first

In `{ [ ( ) ] }` the last bracket opened is the first one closed. A stack keeps the newest on top and takes from the top, with O(1) `push` and `pop`. A closer never searches: it looks at the top.

Counting isn't enough. `([)]` has one of each bracket, but when `)` arrives the newest open bracket is `[`. The stack catches the crossing at once:

<AlgoViz trace={bracketMatch} />

Always ask: **what is still open, and does the newest one resolve first?**

## Step by step

<Steps>
  <Step title="Name what is waiting">
    "Openers not yet closed", "indices without a greater value yet". That is your invariant.
  </Step>
  <Step title="Decide what resolves the top">
    A closer, an operator, or a value that beats the top. Use a `while` when one element can resolve several.
  </Step>
  <Step title="Do the work at pop time">
    An item's answer is known the moment it is popped.
  </Step>
  <Step title="Push the new element">
    Push an **index** if you need a position or distance later.
  </Step>
  <Step title="Handle what is left">
    Leftovers never resolved: unclosed brackets (invalid), no greater value (-1).
  </Step>
</Steps>

## Template 2: monotonic decreasing stack (next greater)

Brute force scans right from every index: O(n²). Instead, walk left to right and keep on a stack the indices that **have not found their answer yet**.

Each new value pops everything smaller. A popped index `j` just found its answer: `i` is its next greater element, and the first, since any bigger value in between would have popped it earlier. Try your own numbers with **Edit input**:

## Template 3: monotonic increasing stack (next smaller, both sides)

Flip the comparison and each pop answers "next **smaller**". A second answer comes free: after the pops, the top is the nearest value left of `i` that is not larger.

<AlgoViz trace={smallerNeighbours} />

Those two neighbours are all <ProblemLink slug="largest-rectangle-in-histogram" /> needs: the widest rectangle of height `heights[j]` has width `right - left - 1`.

Strictness decides **ties**. Read for "strictly" or "or equal" before choosing `<` or `<=`.

## Complexity

| Variant | Time | Extra space |
|---|---|---|
| Matching / expression evaluation | O(n) | O(n) worst case |
| Monotonic stack | O(n) amortised | O(n) |
| Brute-force next greater | O(n²) | O(1) |

## JavaScript you'll use

<JsRef to={["stack-queue-deque", "arrays"]} />

```js
const stack = [];
stack.push(x);                 // O(1): add on top
const top = stack.pop();       // O(1): remove the top (undefined when the stack is empty)
stack.at(-1);                  // peek at the top without removing it
stack.length === 0;            // empty check
new Array(n).fill(-1);         // default answers for "never resolved"
```

The top of a JavaScript stack is the **end** of the array; `shift` and `unshift` are O(n).

<Callout kind="warning">

- Peeking at an empty stack: `stack.at(-1)` is `undefined`. Check `stack.length` first.
- Pushing values when you need indices.

</Callout>

## Interview questions

<FollowUps>
  <FollowUp q="Why is the monotonic stack O(n) with a while loop inside a for loop?">
    Each index is pushed once and popped at most once, so all the `while` iterations together pop at most n items.
  </FollowUp>
  <FollowUp q="How do you find the next greater element in a circular array?">
    Walk it twice, reading `nums[i % n]`. Still O(n).
  </FollowUp>
  <FollowUp q="You only need the answer for a few query values. What changes?">
    Run the stack once, store answers in a `Map`, then each query is one lookup.
  </FollowUp>
  <FollowUp q="How do you build a queue from two stacks?">
    Push onto `in`; pop from `out`, refilling it from `in` only when empty. O(1) amortised.
  </FollowUp>
  <FollowUp q="When would you use a stack instead of recursion?">
    When nesting can be very deep: 10^5 levels can overflow the call stack.
  </FollowUp>
</FollowUps>
