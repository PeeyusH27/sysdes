<TLDR>
Clients hold a **WebSocket** to any gateway, and **Redis pub/sub** routes each message to the gateway holding the recipient. Every message gets a **per-conversation seq**, is **stored before it's acked**, and carries a client id that dedupes retries; offline users **sync from their last seq**.
</TLDR>

  functional={["1:1 and group messaging (groups up to 500 members)", "Delivery and read receipts", "Offline delivery with push notifications", "Paginated message history", "Typing indicators and presence", "Media attachments"]}

## Clarifying questions to ask

- **Groups?** 50, 500 or 100K members? Size decides fan-out on write or on read.
- **Receipts and devices?** Delivery and read receipts, per member or a count? Does my phone's message appear on my laptop?
- **History and encryption?** Forever or 90 days, searchable on the server? End-to-end encryption moves search, previews and moderation to the client.
- **Scale?** DAU, messages per user per day, peak **concurrent** connections.
- **Media?** Which types, how large?

## Capacity estimate

| Quantity | Calculation | Result |
|---|---|---|
| Messages | 50M DAU × 40 messages/day = 2B/day | ≈ **23K/s** (≈ 70K/s peak) |
| Storage | 2B × ~200 B | ≈ 400 GB/day, ≈ 146 TB/year before replication |
| Connections | 10M concurrent ÷ ~50K per gateway | ≈ **200 gateway nodes** |

The write rate is modest: one sharded database handles it. **Concurrent connections** shape the design. They're long-lived and stateful, so you scale by adding gateways and routing between them.

## API

WebSocket events: one socket per device, JSON frames with a `type` field.

| Direction | Event | Payload |
|---|---|---|
| Client → server | `send` | `{ clientId, conversationId, text }` |
| Client → server | `sync` | `{ conversationId, after }` (the last seq the client has) |
| Client → server | `read` | `{ conversationId, seq }` |
| Client → server | `typing` | `{ conversationId }` (throttled) |
| Server → client | `ack` | `{ clientId, seq }` |
| Server → client | `message` | The stored message, including `seq` |
| Server → client | `receipt` | `{ conversationId, userId, readUpTo }` |
| Server → client | `typing`, `presence` | Ephemeral, never stored |

REST for the rest:

| Method | Path | Notes |
|---|---|---|
| GET | `/conversations` | Mine, with unread counts (`lastSeq − lastReadSeq`) |
| GET | `/conversations/:id/messages?before=SEQ&limit=50` | History page, newest first, by seq cursor |
| POST | `/uploads` | A presigned upload URL and the object key |

Authenticate **during the HTTP upgrade** (session cookie or short-lived token), so no frame is ever processed for an unknown user.

## Data model

MongoDB at moderate scale: messages are append-only and always read by conversation and seq.

```js
// messages: one document per message
{ conversationId: 'c42', seq: 1043, from: 'u_alice', clientId: '7f3c…', text: 'see you at 7', ts: 1760000000000 }
// members: one document per (conversation, user), holding the receipt watermarks
{ conversationId: 'c42', userId: 'u_bob', lastDeliveredSeq: 1043, lastReadSeq: 1040, muted: false }
// conversations
{ _id: 'c42', type: 'group', title: 'Goa trip', memberCount: 12, lastSeq: 1043 }
```

At very large scale, Cassandra (or ScyllaDB) fits exactly, as in the CQL table: one partition per conversation, rows clustered by seq. For years-long conversations, add a time bucket to the partition key so no partition grows without bound.

```sql
CREATE TABLE messages (
  conversation_id uuid,
  seq             bigint,
  sender_id       uuid,
  client_id       uuid,
  body            text,
  created_at      timestamp,
  PRIMARY KEY ((conversation_id), seq)
) WITH CLUSTERING ORDER BY (seq DESC);
```

Ephemeral state lives in Redis:

| Key | Type | Purpose |
|---|---|---|
| `seq:CONVERSATION_ID` | counter | `INCR` gives the conversation's next seq |
| `user:USER_ID` | pub/sub channel | Every gateway holding a socket for that user subscribes |
| `presence:USER_ID` | string, `EX 70` | Exists while the user's heartbeats keep arriving |

## Architecture

Gateways are dumb socket-holders that don't know each other. Each subscribes to `user:ID` for the users it holds, and the chat service publishes every stored message to each member's channel. Pub/sub is fire-and-forget, which is fine: the **database is the source of truth** and sync repairs misses. Play **Bob offline** and **Ack lost → retry** to see both repairs.

## Step-by-step answer

<Steps>
<Step title="Clarify">

Ask the questions, then write down the number that drives everything: 10M concurrent sockets.

</Step>
<Step title="Choose the transport">

**WebSocket** online, **push** (APNs/FCM) offline, **REST** for history and uploads. Reject unauthenticated upgrades with 401. A layer-4 load balancer spreads connections with no sticky sessions, since pub/sub does the routing.

</Step>
<Step title="Keep a connection registry on each gateway">

`userId → Set<socket>`, because one user has several devices. Subscribe to `user:ID` while the set is non-empty; unsubscribe on the last close, or Redis keeps sending traffic for users the gateway no longer holds.

```js
let mine = local.get(userId);
if (!mine) { local.set(userId, (mine = new Set())); sub.subscribe(`user:${userId}`); }
mine.add(ws);
```

</Step>
<Step title="Send path: store, then ack, then fan out">

Membership check → dedupe by `(from, clientId)` → `seq = INCR seq:CONVERSATION` → store → **ack the sender** → publish to each member. Store-then-ack means an acked message is never lost; the unique index turns a retry into a re-ack.

```js
const existing = await db.messages.findOne({ from: userId, clientId });
if (existing) return ack(existing.seq);                         // a retry: just ack again
const seq = await pub.incr(`seq:${conversationId}`);
await db.messages.insertOne({ conversationId, seq, from: userId, clientId, text, ts: Date.now() });
ack(seq);                                                       // durable first, then ack
await broadcast(conversationId, { type: 'message', /* … */ });
```

</Step>
<Step title="Ordering">

**Per conversation**, by seq. Clients sort and tolerate gaps (an insert failing after `INCR` burns a number); nobody compares order across chats, so there's no global bottleneck.

</Step>
<Step title="Offline delivery and sync">

On every (re)connect and conversation open, the client sends `sync` with its last seq, and the server replays the rest from the `(conversationId, seq)` index. That also **repairs any missed live message**. Members with no presence key get a push notification.

</Step>
<Step title="Receipts as watermarks">

A `lastReadSeq` and `lastDeliveredSeq` per member, not a row per message: reading seq 1042 implies everything before. Conditional updates (only if higher) keep watermarks moving forward, and receipts broadcast only on a change.

</Step>
<Step title="Presence and typing">

Presence: a Redis key with a 70 s TTL and a 30 s heartbeat, so a crashed client simply expires. Typing: at most one event per 3 s, never stored, sent only to people with the conversation open, hidden after 5 s of silence.

</Step>
<Step title="Groups and very large channels">

Small groups fan out on write. Channels of thousands fan out on read: members pull on open, notifications are batched or mention-only, and there are no per-member delivery receipts.

</Step>
<Step title="Client: optimistic, reconciled, resilient">

Show the bubble at once as `sending`, keyed by `clientId`, and merge the ack, your echo and any sync replay into it (sorted by seq, unsent last). After reconnect, resend pending messages with the same `clientId`. **Full-jitter** backoff stops 50K clients from a dead gateway returning in the same second.

</Step>
</Steps>

Classic bugs fixed: a **set** of sockets per user, unsubscribe on the last close, membership checks before send and sync, a per-conversation `seq`, and idempotent sends via the unique `(from, clientId)` index, even for two simultaneous retries (duplicate-key error `11000` becomes a re-ack).

## Failure modes

| What breaks | Effect | Mitigation |
|---|---|---|
| A gateway node dies | Its ~50K sockets drop | Jittered reconnect elsewhere; `sync` from the last seq |
| A pub/sub message is lost | A live message is missed | Sync on reconnect and on conversation open |
| Client retries after a lost ack | Duplicate message | Unique `(from, clientId)`; re-ack the stored seq |
| Out-of-order arrival | Wrong display order | Clients sort by seq |
| A huge group | Fan-out storm | Fan out on read; no per-member receipts |
| Redis is down | No cross-gateway routing, no new seqs | Replicated Redis with failover; stored messages safe; sync recovers |
| Mass reconnect after a deploy | Thundering herd on remaining gateways | Drain slowly (close sockets over minutes); client jitter |

## Trade-offs

| Choice | Pros | Cons | Choose when |
|---|---|---|---|
| WebSocket vs long polling | Low latency, two-way | Stateful connections to scale | Chat (always) |
| Redis pub/sub vs Kafka for routing | Simple and fast | No durability or replay | Routing only (durability is DB + sync) |
| Fan-out on write vs read for groups | Fast reads | Write amplification | Small groups vs large channels |
| MongoDB vs Cassandra | Flexible, simpler ops | Less write scale | Moderate vs very large scale |

<Callout kind="warning" title="Common mistakes">
Acking before storing, and a registry with one socket per user (goodbye, multi-device): the two classic chat-server bugs.
</Callout>

## Follow-up questions

<FollowUps>
  <FollowUp q="How do you guarantee message ordering?">
    Per conversation only, from an `INCR` counter that clients sort by. Gaps are fine, and no global sequencer means no global bottleneck.
  </FollowUp>
  <FollowUp q="How would you build presence and typing at scale?">
    Presence is a TTL'd key refreshed by heartbeats, with changes sent only to contacts who have the app open; typing is throttled and never stored.
  </FollowUp>
  <FollowUp q="How does end-to-end encryption change the design?">
    Per-device keys (the Signal protocol: X3DH or PQXDH, then the Double Ratchet) leave the server only ciphertext and public prekey bundles. Search, previews and moderation move to the client, and every message is encrypted for every device of every member.
  </FollowUp>
  <FollowUp q="What about very large channels (100K members)?">
    Fan out on read, as in the groups step, with a view count instead of per-member receipts.
  </FollowUp>
  <FollowUp q="How do media messages work?">
    Upload to object storage with a presigned URL and send the object key as a message. An async worker makes thumbnails; downloads go through a CDN with signed, expiring URLs.
  </FollowUp>
  <FollowUp q="How do you run 10M concurrent connections?">
    About 200 gateways at ~50K sockets each behind layer-4 load balancers, with raised file-descriptor limits, lean per-socket memory and 30 s pings for connections dead behind NATs. Deploy by draining sockets gradually.
  </FollowUp>
  <FollowUp q="How does multi-device sync work?">
    Every device's socket is in the user's set, so each gets every message; your own come back as echoes merged by `clientId`. Read state is per user, so reading on the laptop clears the phone's badge.
  </FollowUp>
</FollowUps>
