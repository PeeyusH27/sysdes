<TLDR>
Each phone keeps a **WebSocket** open to a gateway, and **pub/sub** passes each message to the gateway holding the recipient. Store the message first, then ack, then deliver. A client that was offline asks for what it missed.
</TLDR>

## Clarifying questions to ask

- **Groups?** 50, 500 or 100K members? Size decides how you fan out.
- **Receipts and devices?** Delivered and read ticks? Does my phone's message show on my laptop?
- **History and encryption?** Kept forever? End-to-end encryption moves search to the client.
- **Scale?** Daily users, and how many are connected at once.

## Capacity estimate

| Quantity | Calculation | Result |
|---|---|---|
| Messages | 50M DAU × 40 messages/day = 2B/day | ≈ **23K/s** (≈ 70K/s peak) |
| Storage | 2B × ~200 B | ≈ 400 GB/day |
| Connections | 10M concurrent ÷ ~50K per gateway | ≈ **200 gateway nodes** |

At roughly 10 KB per idle socket, 10M sockets need about 100 GB of memory across the gateways. The write rate is modest. **Open connections** shape the design: they last long and hold state, so you scale by adding gateways.

## API

WebSocket events: one socket per device, JSON frames with a `type` field.

| Direction | Event | Payload |
|---|---|---|
| Client → server | `send` | `{ clientId, conversationId, text }` |
| Client → server | `sync` | `{ conversationId, after }` (the last seq the client has) |
| Client → server | `read` | `{ conversationId, seq }` |
| Client → server | `typing` | `{ conversationId }` (throttled) |
| Server → client | `ack` | `{ clientId, seq }` |
| Server → client | `message` | The stored message, including `seq` |
| Server → client | `receipt` | `{ conversationId, userId, readUpTo }` |
| Server → client | `typing`, `presence` | Ephemeral, never stored |

REST for the rest:

| Method | Path | Notes |
|---|---|---|
| GET | `/conversations` | Mine, with unread counts |
| GET | `/conversations/:id/messages?before=SEQ&limit=50` | History, newest first |
| POST | `/uploads` | A presigned upload URL and the object key |

Check who the user is **during the HTTP upgrade**, so no frame is ever processed for a stranger.

## Data model

Messages are append-only and always read by conversation and seq.

```js
// messages: one document per message
{ conversationId: 'c42', seq: 1043, from: 'u_alice', clientId: '7f3c…', text: 'see you at 7', ts: 1760000000000 }
// members: one document per (conversation, user), holding the receipt watermarks
{ conversationId: 'c42', userId: 'u_bob', lastDeliveredSeq: 1043, lastReadSeq: 1040, muted: false }
// conversations
{ _id: 'c42', type: 'group', title: 'Goa trip', memberCount: 12, lastSeq: 1043 }
```

<CodeBlock src="snippets/indexes.js" title="indexes.js" />

At very large scale, Cassandra fits: one partition per conversation, rows clustered by seq.

```sql
CREATE TABLE messages (
  conversation_id uuid,
  seq             bigint,
  sender_id       uuid,
  client_id       uuid,
  body            text,
  created_at      timestamp,
  PRIMARY KEY ((conversation_id), seq)
) WITH CLUSTERING ORDER BY (seq DESC);
```

Short-lived state lives in Redis:

| Key | Type | Purpose |
|---|---|---|
| `seq:CONVERSATION_ID` | counter | `INCR` gives the next seq |
| `user:USER_ID` | pub/sub channel | Every gateway holding that user's socket subscribes |
| `presence:USER_ID` | string, `EX 70` | Exists while heartbeats keep arriving |

## Architecture

<Doodle name="pubsub" size={150} caption />

Why sockets, not polling? Ask every 5 seconds and a message waits 2.5 seconds on average, and most answers are empty.

| Users | Polling every 5 s | Verdict |
|---|---|---|
| 1,000 | 200 requests/s | Polling is fine |
| 100,000 | 20,000/s, mostly empty | Long polling, or sockets |
| 10M | 2M requests/s | WebSockets |

Gateways just hold sockets and don't know each other. Each listens on a channel per connected user, and the chat service publishes every stored message there. Pub/sub can drop a message, and that is fine: the **database is the truth**, and sync repairs misses. Play **Bob offline** and **Ack lost → retry**.

## Step-by-step answer

<Steps>
<Step title="Clarify">

Ask, then name the number that drives everything: 10M open sockets.

</Step>
<Step title="Choose the transport">

**WebSocket** online, **push** offline, **REST** for history and uploads. Pub/sub does the routing, so no sticky sessions.

</Step>
<Step title="Keep a connection registry on each gateway">

`userId → Set<socket>`, because one user has several devices. Subscribe to `user:ID` while the set is non-empty, and unsubscribe on the last close.

```js
let mine = local.get(userId);
if (!mine) { local.set(userId, (mine = new Set())); sub.subscribe(`user:${userId}`); }
mine.add(ws);
```

</Step>
<Step title="Send path: store, then ack, then fan out">

Check membership, dedupe by `(from, clientId)`, get a `seq`, store, **ack the sender**, then publish. An acked message is never lost, and the unique index turns a retry into a re-ack.

```js
const existing = await db.messages.findOne({ from: userId, clientId });
if (existing) return ack(existing.seq);                         // a retry: just ack again
const seq = await pub.incr(`seq:${conversationId}`);
await db.messages.insertOne({ conversationId, seq, from: userId, clientId, text, ts: Date.now() });
ack(seq);                                                       // durable first, then ack
await broadcast(conversationId, { type: 'message', /* … */ });
```

</Step>
<Step title="Ordering">

**Per conversation**, by seq. Clients sort and tolerate gaps. Nobody compares order across chats, so there is no global bottleneck.

</Step>
<Step title="Offline delivery and sync">

On every reconnect, the client sends `sync` with its last seq, and the server replays the rest. That also **repairs any missed live message**. Members who are offline get a push notification.

</Step>
<Step title="Receipts as watermarks">

Keep a `lastReadSeq` and `lastDeliveredSeq` per member, not a row per message. Reading 1042 implies everything before it.

</Step>
<Step title="Presence and typing">

Presence: a Redis key with a 70 s TTL and a 30 s heartbeat, so a crashed client expires. Typing: one event per 3 s at most, never stored.

</Step>
<Step title="Groups and very large channels">

Small groups fan out on write. Big channels fan out on read: members pull on open.

</Step>
<Step title="Client: optimistic and resilient">

Show the bubble at once as `sending`. After reconnect, resend pending messages with the same `clientId`. Random (**jittered**) backoff stops 50K clients returning together.

</Step>
</Steps>

## Failure modes

| What breaks | Effect | Mitigation |
|---|---|---|
| A gateway dies | Its ~50K sockets drop | Jittered reconnect; `sync` from the last seq |
| A pub/sub message is lost | A live message is missed | Sync on reconnect and on open |
| Retry after a lost ack | Duplicate message | Unique `(from, clientId)`; re-ack |
| Out-of-order arrival | Wrong display order | Clients sort by seq |
| A huge group | Fan-out storm | Fan out on read |
| Redis is down | No routing, no new seqs | Replicated Redis; sync recovers |
| Mass reconnect after a deploy | Thundering herd | Drain slowly; client jitter |

## Trade-offs

| Choice | Gain | Cost |
|---|---|---|
| WebSocket, not long polling | Fast, two-way | Stateful connections |
| Redis pub/sub, not Kafka | Simple and fast | No replay |
| Fan-out on write | Fast reads | Heavy writes for big groups |
| MongoDB, not Cassandra | Simpler | Less write scale |

<Callout kind="warning" title="Common mistakes">
Acking before storing, and one socket per user (goodbye, multi-device).
</Callout>

## Follow-up questions

<FollowUps>
  <FollowUp q="How do you guarantee message ordering?">
    Per conversation only, from a counter that clients sort by. Gaps are fine, and there is no global bottleneck.
  </FollowUp>
  <FollowUp q="How would you build presence and typing at scale?">
    Presence is a key with a TTL, refreshed by heartbeats. Typing is throttled and never stored.
  </FollowUp>
  <FollowUp q="How does end-to-end encryption change the design?">
    The server sees only ciphertext. Search, previews and moderation move to the client, and each message is encrypted for every device of every member.
  </FollowUp>
  <FollowUp q="What about very large channels (100K members)?">
    Fan out on read, with a view count instead of per-member receipts.
  </FollowUp>
  <FollowUp q="How do media messages work?">
    Upload to object storage with a presigned URL, then send the object key as a message.
  </FollowUp>
  <FollowUp q="How do you run 10M concurrent connections?">
    About 200 gateways at ~50K sockets each, behind layer-4 load balancers. Deploy by draining sockets gradually.
  </FollowUp>
  <FollowUp q="How does multi-device sync work?">
    Every device's socket is in the user's set, so each gets every message.
  </FollowUp>
</FollowUps>
