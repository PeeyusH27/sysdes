<TLDR>
**Hybrid fan-out**: copy a normal user's post into each follower's ready-made feed, so reading is one lookup. For **celebrities** (over ~100K followers), skip the copy and merge their posts in when the feed opens.
</TLDR>

<Requirements
  functional={["Follow and unfollow", "Post text and media", "A home feed, ranked or reverse-chronological", "Like and comment", "New posts appear without a manual refresh"]}
  nonFunctional={["Feed p99 under 200 ms", "Followers see new posts within seconds", "Celebrities with millions of followers", "300M daily active users", "Available over consistent: a feed a few seconds stale is fine"]}

## Clarifying questions to ask

- **Ranked or chronological?** Ranking adds a scoring step.
- **Follow graph?** Average follows, biggest follower count, a follow limit?
- **Freshness?** Seconds, or is a minute fine?
- **Celebrities?** Millions of followers? Yes: this is the crux.
- **Scale?** Daily users, feed opens, posts per day.

## Capacity estimate

| Quantity | Calculation | Result |
|---|---|---|
| Feed reads | 300M × 10/day | ≈ **35K/s** (~100K/s peak) |
| New posts | 50M/day | ≈ 580/s |
| Fan-out writes | 50M posts × 200 average followers | ≈ **116K/s** |
| Cached feed memory | 300M × 800 ids × ~40 B | ≈ 9.6 TB |

Reads outnumber posts 60 to 1, so do the work at write time. The bill: 580 posts/s become 116K writes/s, and 9.6 TB of RAM. So cache only active users' feeds.

## API

| Method | Path | Notes |
|---|---|---|
| POST | `/posts` | Creates a post; fan-out runs asynchronously |
| GET | `/feed?cursor=&limit=20` | `{ posts, nextCursor }` |
| POST/DELETE | `/users/:id/follow` | Follow or unfollow |
| POST | `/posts/:id/like` | Optimistic on the client |
| GET | `/feed/new-count?after=TS` | For the "new posts" banner |

`nextCursor` is the last post's timestamp; `null` means nothing older exists.

```json
{
  "posts": [
    { "id": "p_981", "author": { "id": "u_7", "name": "Maya" }, "text": "Sunset", "media": ["img/981.jpg"], "likes": 12, "liked": false, "createdAt": 1760000000000 }
  ],
  "nextCursor": 1759998000000
}
```

## Data model

Posts and follows live in a durable store. Ids are time-ordered.

```sql
CREATE TABLE posts (
  id         bigint PRIMARY KEY,
  author_id  bigint NOT NULL,
  body       text,
  media      jsonb,
  created_at timestamptz NOT NULL DEFAULT now(),
  deleted    boolean NOT NULL DEFAULT false
);
CREATE INDEX posts_by_author ON posts (author_id, created_at DESC);

CREATE TABLE follows (
  follower_id bigint NOT NULL,
  followee_id bigint NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (follower_id, followee_id)
);
CREATE INDEX follows_by_followee ON follows (followee_id, follower_id);  -- "who follows X?" for fan-out
```

Feeds are derived data in Redis:

| Key | Type | Contents |
|---|---|---|
| `feed:USER_ID` | sorted set | score = `createdAt` ms, member = post id; newest 800 |
| `posts:AUTHOR_ID` | sorted set | The author's own timeline, for the celebrity merge |
| `post:ID` | string (JSON) | Post body cache, 1 h TTL |

A time-scored sorted set makes the **score cursor** work: "20 posts older than T" stays correct as new posts arrive.

## Push, pull or hybrid

The whole question turns on this. Compare the two pure strategies first.

<FlowDiagram spec={pushVsPull} />

**Push** copies each post into every follower's feed, so reads are one lookup. **Pull** stores a post once, but every feed open merges many timelines. The **hybrid** pushes for most authors and pulls only the few celebrities each user follows.

<FanoutCalc />

Do the sum first. Say the workers manage about 100K feed writes a second:

| Author | Followers | Push takes |
|---|---|---|
| Typical user | 200 | Instant |
| Popular account | 100K | About 1 second |
| Celebrity | 30M | About 5 minutes |

Push the first two. Pull the third: fans see the post when they next open the feed. A user who follows 5 celebrities merges only 5 extra timelines. An app where nobody has many followers can skip fan-out and just pull.

## Step-by-step answer

<Steps>
<Step title="Clarify">

About 60 reads per post justifies work at write time.

</Step>
<Step title="Push: fan-out on write">

Write each post id into every follower's feed. Reads are one lookup, but 10M followers means 10M writes.

</Step>
<Step title="Pull: fan-out on read">

Merge timelines at read time. Writes are cheap, but reads are too slow at 35K/s.

</Step>
<Step title="Hybrid: push for most, pull for celebrities">

Tune the ~100K threshold on write cost versus read cost. Users follow few celebrities, so the merge stays small.

</Step>
<Step title="Feed storage">

A sorted set per user, scored by time, capped at 800. Skip users inactive for 30 days.

```js
redis.zadd(`feed:${userId}`, ts, postId);
redis.zremrangebyrank(`feed:${userId}`, 0, -801);             // keep the newest 800
```

</Step>
<Step title="Read path: score cursor, merge, hydrate">

Read a page by score cursor, plus the same window from each followed celebrity. Merge, dedupe, sort, then fetch post bodies and drop deleted ones.

```js
const max = cursor ? `(${cursor}` : '+inf';                     // "(" = strictly older than the cursor
redis.zrevrangebyscore(`feed:${userId}`, max, '-inf', 'WITHSCORES', 'LIMIT', 0, limit);
```

</Step>
<Step title="Ranking">

Start chronological, then score candidates: `affinity × (likes + 2·comments + 3·shares + 1) / (ageHours + 2)^1.5`. A learned model can replace the formula later.

</Step>
<Step title="Freshness">

Poll `/feed/new-count` every 30 to 60 s and show a banner. Never insert above the reader.

</Step>
<Step title="Unfollow and delete">

Filter at read time, then clean up asynchronously. Never block the user on cleanup.

</Step>
<Step title="Client">

A virtualized list (see [Build an Infinite Scroll Feed](/questions/infinite-feed)) and optimistic likes that roll back on error.

</Step>
</Steps>

## Failure modes

| What breaks | Effect | Mitigation |
|---|---|---|
| Fan-out queue backlog | Posts arrive late | Autoscale workers; authors see their own post at once |
| A worker dies mid-batch | Some followers miss the post | Redeliver; `ZADD` is idempotent |
| A Redis feed is lost | Empty feed | Rebuild by pulling |
| A celebrity's timeline is hammered | A hot key | Short in-process cache; replicate the key |
| A post is deleted after fan-out | A ghost post | Filter at read time |
| Unfollow | Old posts linger | Follow check at read time |

## Trade-offs

| Choice | Gain | Cost |
|---|---|---|
| Ranked, not chronological | Better engagement | Ranking compute |
| Lower celebrity threshold | Less write cost | More read-time merging |
| Cache every feed | No rebuilds | Terabytes of RAM for idle users |
| SSE, not polling, for banners | Instant | A connection per user |

<Callout kind="warning" title="Common mistakes">
- Whole posts in every follower's feed instead of ids.
- Invalidating the whole infinite query after every like.
</Callout>

## Follow-up questions

<FollowUps>
  <FollowUp q="How would you rank posts?">
    Score pushed and pulled candidates, then mix so one author doesn't fill the page.
  </FollowUp>
  <FollowUp q="How do you handle unfollows and deleted posts?">
    Filter at read time, then clean the sorted sets later, never blocking the user.
  </FollowUp>
  <FollowUp q="How do you cache viral posts?">
    Cache post bodies in Redis and in-process. Spread like counters across sub-keys.
  </FollowUp>
  <FollowUp q="What does a new user see?">
    Follow suggestions and a "popular" feed, until their own graph fills a feed.
  </FollowUp>
  <FollowUp q="How do you handle inactive users?">
    Skip them in fan-out. On login, rebuild their feed once by pulling, then switch back to push.
  </FollowUp>
  <FollowUp q="How do you shard the feed cache?">
    By user id, so one read touches one shard. Workers batch writes per node.
  </FollowUp>
  <FollowUp q="An author goes from 90K to 110K followers. What changes?">
    New posts are pulled, not pushed. Old pushed posts stay in feeds, so the merge dedupes by post id.
  </FollowUp>
</FollowUps>
