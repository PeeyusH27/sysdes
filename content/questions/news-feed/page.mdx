<TLDR>
**Hybrid fan-out**: a normal user's post is pushed into each active follower's capped Redis feed, so a read is one lookup, while **celebrities** (over ~100K followers) are merged in at read time. Reads hydrate ids through a post cache and page with a **score cursor**.
</TLDR>

  functional={["Follow and unfollow", "Post text and media", "A home feed, ranked or reverse-chronological", "Like and comment", "New posts appear without a manual refresh"]}
  nonFunctional={["Feed p99 under 200 ms", "Followers see new posts within seconds", "Celebrities with millions of followers", "300M daily active users", "Available over consistent: a feed a few seconds stale is fine"]}

## Clarifying questions to ask

- **Ranked or chronological?** Ranking adds a scoring step; chronological is simpler and more transparent.
- **Follow graph?** Average follows, largest follower count, a follow limit (say 5,000)?
- **Freshness?** Seconds, or is a minute fine?
- **Celebrities?** Millions of followers? (Yes: this is the crux.)
- **Media and scale?** Video changes storage and CDN cost, not the feed design. DAU, feed opens per user, posts per day.

## Capacity estimate

| Quantity | Calculation | Result |
|---|---|---|
| Feed reads | 300M × 10/day | ≈ **35K/s** (~100K/s peak) |
| New posts | 50M/day | ≈ 580/s |
| Fan-out writes | 50M posts × 200 average followers | ≈ **116K/s** |
| Cached feed memory | 300M × 800 ids × ~40 B | ≈ 9.6 TB |

Reads outnumber posts 60 to 1, so pay at write time to make reads cheap. The bill: 580 posts/s become 116K writes/s, and 9.6 TB of RAM is about 100 Redis nodes at ~100 GB, before replicas. So cache only recently active users' feeds, capped, and rebuild cold ones on demand.

## API

| Method | Path | Notes |
|---|---|---|
| POST | `/posts` | Creates a post; fan-out runs asynchronously |
| GET | `/feed?cursor=&limit=20` | `{ posts, nextCursor }` |
| POST/DELETE | `/users/:id/follow` | Follow or unfollow |
| POST | `/posts/:id/like` | Optimistic on the client |
| GET | `/feed/new-count?after=TS` | For the "new posts" banner |

In a feed page, `nextCursor` is the last post's timestamp; `null` means nothing older exists.

```json
{
  "posts": [
    { "id": "p_981", "author": { "id": "u_7", "name": "Maya" }, "text": "Sunset", "media": ["img/981.jpg"], "likes": 12, "liked": false, "createdAt": 1760000000000 }
  ],
  "nextCursor": 1759998000000
}
```

## Data model

Posts and the follow graph live in a durable store (SQL here; wide-column works too). Ids are time-ordered (Snowflake-style), so sorting by id sorts by time.

```sql
CREATE TABLE posts (
  id         bigint PRIMARY KEY,
  author_id  bigint NOT NULL,
  body       text,
  media      jsonb,
  created_at timestamptz NOT NULL DEFAULT now(),
  deleted    boolean NOT NULL DEFAULT false
);
CREATE INDEX posts_by_author ON posts (author_id, created_at DESC);

CREATE TABLE follows (
  follower_id bigint NOT NULL,
  followee_id bigint NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (follower_id, followee_id)
);
CREATE INDEX follows_by_followee ON follows (followee_id, follower_id);  -- "who follows X?" for fan-out
```

Feeds are derived data in Redis:

| Key | Type | Contents |
|---|---|---|
| `feed:USER_ID` | sorted set | score = `createdAt` ms, member = post id; newest 800 |
| `posts:AUTHOR_ID` | sorted set | The author's own timeline; used for the celebrity merge |
| `post:ID` | string (JSON) | Post body cache, 1 h TTL |

A time-scored sorted set, not a list, makes the **score cursor** possible: "20 posts strictly older than T" stays correct however many posts arrive at the top.

## Architecture

<FlowDiagram spec={feedArchitecture} />

Play **Normal user posts**, **Celebrity posts** and **User opens feed**. Writes store, enqueue fan-out and return, so the author never waits; reads usually touch only caches: one sorted-set read, one per followed celebrity, one batched post-cache lookup.

## Push, pull or hybrid

The decision the whole question turns on. Compare the two pure strategies in the flow diagram first.

<FlowDiagram spec={pushVsPull} />

Push makes every read one lookup, but write cost grows with followers: at 100K fan-out writes per second, a post by a 30M-follower account takes 5 minutes to reach everyone. Pull writes once, but every feed open merges hundreds of timelines. The hybrid pushes for the vast majority of authors and pulls only the few celebrities each user follows. Try the numbers in the fan-out calculator.

<FanoutCalc />

Push and hybrid deliver in seconds; pull is instant.

| Strategy | Write cost | Read cost | Choose when |
|---|---|---|---|
| Fan-out on write (push) | High (× followers) | Very low | Most users |
| Fan-out on read (pull) | Low | High (merge many timelines) | Celebrities, inactive users |
| **Hybrid** | Bounded | Low + a small merge | Real systems |

## Step-by-step answer

<Steps>
<Step title="Clarify">

Note the read/write ratio, about 60 feed reads per post: it justifies doing work at write time.

</Step>
<Step title="Push: fan-out on write">

Write each post id into every follower's feed: one-lookup reads, but 10M followers means 10M writes, mostly for people who never look.

</Step>
<Step title="Pull: fan-out on read">

Merge followed authors' timelines at read time: cheap writes, always fresh, but too slow for a 200 ms p99 at 35K reads/s.

</Step>
<Step title="Hybrid: push for most, pull for celebrities">

Push for normal authors, pull celebrities. Tune the ~100K-follower threshold on write amplification versus read cost; users follow few celebrities, so the merge stays small.

</Step>
<Step title="Feed storage">

A sorted set per user, scored by time, capped at 800. Workers skip users inactive for 30 days (rebuilt on login); each queue message carries 1,000 followers to spread the work.

```js
redis.zadd(`feed:${userId}`, ts, postId);
redis.zremrangebyrank(`feed:${userId}`, 0, -801);             // keep the newest 800
```

</Step>
<Step title="Read path: score cursor, merge, hydrate">

Read a page of your sorted set by score cursor, plus the same window from each followed celebrity; merge, dedupe, sort, cut. Hydrate ids through the post cache (database on a miss) and drop deleted posts.

```js
const max = cursor ? `(${cursor}` : '+inf';                     // "(" = strictly older than the cursor
redis.zrevrangebyscore(`feed:${userId}`, max, '-inf', 'WITHSCORES', 'LIMIT', 0, limit);
```

</Step>
<Step title="Ranking">

Start chronological, then score a few hundred candidates with an explainable formula: `affinity × (likes + 2·comments + 3·shares + 1) / (ageHours + 2)^1.5`. Engagement decays with age; authors you interact with get up to 3×. A learned model later replaces the formula, not the pipeline.

</Step>
<Step title="Freshness">

Poll `GET /feed/new-count?after=TS` every 30 to 60 s (or listen on SSE) and show a "New posts" banner. Never insert above the reader; a tap scrolls up and refetches page one.

</Step>
<Step title="Unfollow and delete">

Filter at read time (hydration drops `deleted` posts; a follow check drops unfollowed authors), then remove that author's ids from the follower's set asynchronously. Never block the user's action on cleanup.

</Step>
<Step title="Client">

A cursor-paginated, virtualized infinite list (see [Build an Infinite Scroll Feed](/questions/infinite-feed)), a server-rendered first page, fixed-size image placeholders, and optimistic likes that roll back on error.

</Step>
</Steps>

## Failure modes

| What breaks | Effect | Mitigation |
|---|---|---|
| Fan-out queue backlog | Followers see posts late | Autoscale workers on queue age; authors see their own post at once |
| A worker dies mid-batch | Some followers miss the post | Redeliver; `ZADD` is idempotent, so a retry can't duplicate |
| A Redis feed is lost or evicted | Empty feed | Rebuild from follows + author timelines (fan-out on read) |
| A celebrity's timeline gets hammered | A hot key | In-process L1 cache with a few seconds' TTL; replicate the key |
| A post is deleted after fan-out | A ghost post | Filter at hydrate time (deleted flag); clean up async |
| Unfollow | Old posts linger | Follow check at read time; remove async |

## Trade-offs

| Choice | Pros | Cons | Choose when |
|---|---|---|---|
| Ranked vs chronological | Better engagement | Ranking compute; less transparent | Engagement goals vs transparency |
| Sorted set vs list for feeds | Score cursor, ordered inserts | A little more memory | Always for feeds that page |
| Lower vs higher celebrity threshold | Less write amplification | More read-time merging | Tune on measured read vs write cost |
| Cache every feed vs active users only | No rebuilds | Terabytes of RAM for people who never look | Active-only, rebuild on login |
| SSE vs polling for "new posts" | Instant | An open connection per user | Polling is usually enough here |

<Callout kind="warning" title="Common mistakes">
- Whole posts in every follower's feed instead of ids.
- Invalidating the whole infinite query after every like.
</Callout>

## Follow-up questions

<FollowUps>
  <FollowUp q="How would you rank posts?">
    Gather pushed and pulled candidates, compute features (engagement, recency, affinity, content type), score them (formula first, learned model later), re-rank for diversity (no five in a row from one author), and cache the page briefly.
  </FollowUp>
  <FollowUp q="How do you handle unfollows and deleted posts?">
    Filter both at read time (cheap, always correct), then clean the sorted sets asynchronously, never blocking the user.
  </FollowUp>
  <FollowUp q="How do you cache viral posts?">
    Post bodies sit in Redis behind an in-process L1 cache; like counters are salted across sub-keys or batched (write-behind) and shown approximately ("12.3K").
  </FollowUp>
  <FollowUp q="What does a new user see?">
    Onboarding follow suggestions plus a "popular" feed pulled from trending timelines, until their graph can fill a feed on its own.
  </FollowUp>
  <FollowUp q="How do you handle inactive users?">
    Skip them in fan-out. On their next login, rebuild the feed once by fan-out on read, then switch back to push.
  </FollowUp>
  <FollowUp q="How do you shard the feed cache?">
    By user id across a Redis Cluster's hash slots, so a read touches one shard. Workers pipeline writes per node, so a batch of 1,000 followers costs a few round trips, not 1,000.
  </FollowUp>
  <FollowUp q="An author goes from 90K to 110K followers. What changes?">
    Their new posts are pulled instead of pushed. Already-pushed posts stay in followers' feeds, so for a while one post can come from both sources; the read-time merge dedupes by post id.
  </FollowUp>
</FollowUps>
