<TLDR>
A **logger tree** keyed by dotted names lets a child inherit its level, and each logger fans one record out to a list of **appenders**, each with its own threshold and **formatter**. Check the level before building anything, and put slow I/O behind a bounded queue.
</TLDR>

A **low-level design** (LLD) question where the patterns are easy to name and the real test is judgement: what to build, and what to leave out.

New to this? Read [Swap behaviour](/lld/foundations/strategy-decorator) and [State machines and observers](/lld/foundations/state-observer) first.

## Clarifying questions

- Do loggers form a hierarchy, or is there one global logger?
- Can levels and appenders change while the program runs?
- Must a log call ever block, or may it lose lines under load?
- Plain text only, or JSON for a log shipper too?
- Many threads? Does the order of lines matter?

## Public interface

| Call | Returns | Notes |
|---|---|---|
| `manager.getLogger(name)` | A logger | Same name, same logger; parents are created on demand |
| `logger.log(level, message)` | How many appenders wrote it | The message may be a function, called only if the level is on |
| `logger.level = ...` | | Unset means inherit from the parent |
| `logger.addAppender(a)` | | Copy-on-write, safe while others log |
| `appender.append(record)` | `true` if it wrote | Applies its own threshold and formatter |

## What it remembers

- `LogManager.loggers`: name → logger, plus the `root`, which always has a level.
- Per logger: an optional level, its parent, and a list of appenders.
- Per appender: a threshold, a formatter, and a sink. An async appender also holds a bounded queue and a drop count.

A record is built once per call and shared, never copied per appender.

## Async logging

A slow disk must not slow the request. The **async appender** is a **decorator**: it puts records on a bounded queue, and one worker thread writes them in order.

<SequenceDiagram spec={asyncFlow} />

The bound is the real decision. **Drop** keeps the app fast and counts what it lost. **Block** keeps every line but can stall callers. Choose drop for debug noise, block for audit lines, and always flush the queue on shutdown.

## Patterns, and when to skip them

**Strategy** for the formatter, **Decorator** for the async wrapper, and **Observer** in spirit for the appender list: the logger never knows who is listening. These three earn their place because real changes land on them.

**Skip the rest.** A `LoggerFactoryBuilder`, an abstract `LogHandlerChain`, or a level class per level add nothing. Levels are four ordered values.

**Singleton is a smell.** A global logger cannot be reset between tests. Inject the manager, and offer a module-level default as a convenience only.

## Thread safety

- **Appenders list**: copy-on-write. Adds are rare and log calls constant, so each call iterates a snapshot with no lock.
- **Line order**: each sink call holds a lock, so two threads never interleave half-lines.
- **Level**: one reference read, safe if it is volatile (Java) and read once per call.
- **Listener failures**: catch per appender, so one broken disk does not silence the console.

## Step-by-step answer

<Steps>
  <Step title="The level check comes first">

A disabled call must cost almost nothing. Check before building the record, and take the message as a function so the string is built only when needed.

```js
log(level, message) {
  if (!this.isEnabled(level)) return 0;
  const text = typeof message === 'function' ? message() : message;
  /* build the record, walk up the tree */
}
```

  </Step>
  <Step title="Inheritance is a walk up the tree">
    A null level means ask the parent. The root always has one, so the loop ends. Changing `app` changes every descendant that inherits from it.
  </Step>
  <Step title="Parents come from the name">
    `getLogger("app.db")` cuts at the last dot and gets `app` first. No registry of parents to keep in step.
  </Step>
  <Step title="Appenders are independent">
    Each has its own threshold and formatter. Return how many wrote, so callers and tests can see the effect.
  </Step>
  <Step title="Tests">
    Inherit, override, thresholds, a lazy message that is not built, an appender added mid-call, one that throws, and an async queue that drops.
  </Step>
</Steps>

## Failure modes

| What breaks | Effect | Mitigation |
|---|---|---|
| Disk full or slow | Every request stalls | Async appender with a bounded queue |
| Queue grows without a limit | Out of memory | Bound it, drop and count |
| Process exits with a full queue | Lost last lines | Flush on shutdown |
| An appender throws | Other appenders silent | Catch per appender |
| Log call builds a big string | CPU cost even when off | Lazy message, level check first |

## Trade-offs

| Choice | Pros | Cons |
|---|---|---|
| Drop vs block | Drop: fast. Block: complete | Drop loses lines. Block can stall |
| Hierarchy vs one logger | Per-area levels | Inheritance rules to explain |
| Copy-on-write vs lock | No lock on the hot path | A copy on each add |
| Lazy message vs string | No cost when off | Slightly clumsier calls |

## Follow-up questions

<FollowUps>
  <FollowUp q="How would you add structured fields like request id?">
    Give the record a map of fields, filled from a per-thread or per-request context. Formatters decide how to print them. The call sites do not change.
  </FollowUp>
  <FollowUp q="How would you rotate log files?">
    Make rotation part of the file sink: when the size or day changes, close the file and open the next. The logger and the formatter do not know.
  </FollowUp>
  <FollowUp q="How do you stop sensitive data from leaking?">
    Add a filter or a decorating formatter that masks known fields, so every appender is covered by one change.
  </FollowUp>
  <FollowUp q="How do logs from 1,000 servers reach one place?">
    Each server writes JSON lines to local disk, and an agent ships them to a queue and a search index. That is the HLD version of this appender.
  </FollowUp>
  <FollowUp q="How would you test it?">
    Inject the clock and a memory sink, then assert whole lines. Add a slow sink to test drop and block, and a throwing appender to test isolation.
  </FollowUp>
</FollowUps>
