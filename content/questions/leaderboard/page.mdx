It all hinges on one question: **what is my rank?** Answer it fast, then cover ties, time windows and sharding.

## Clarifying questions

- How many players and matches a day?
- Total points, or best single score?
- Ties: shared rank, or first to get there?
- Which windows (daily, weekly)? How fresh?
- Who computes the score: the game server, or the client?

## Capacity estimate

| Quantity | Estimate |
|---|---|
| Players | 50M registered, 10M daily active |
| Score events | 10M × 20 matches = 200M a day ≈ **2.3K per second** |
| Peak | About 5× average ≈ **12K events per second** |
| Redis work per event | One Lua script: an offset check, 3 `ZINCRBY`, 2 `EXPIRE` |
| Rank reads | ≈ 12K per second at peak, O(log n) each |
| Top-100 reads | Cached 1 s: a few Redis calls per second |
| Memory per member | ~100 bytes |
| All-time board | 50M × 100 B ≈ **5 GB** |
| Daily boards | 10M × 100 B ≈ 1 GB each; 8 days kept ≈ 8 GB |
| Weekly boards | ~20M weekly actives ≈ 2 GB each; 2 kept ≈ 4 GB |

About 17 GB and 12K scripts a second: one primary plus a replica. **Don't shard yet.**

## Why a sorted set

An index on `points` serves the top 100 fine. But "my rank" has to count everyone above you: millions of entries, 12K times a second. Caching ranks fails too, since one score change shifts everyone it passes.

```sql
SELECT COUNT(*) + 1 FROM player_totals
WHERE game_id = 1 AND period = 'all' AND points > 900;
```

Do the sum first. The count walks every higher-scoring row, so the cost grows with players times reads:

| Players | Rank reads | Verdict |
|---|---|---|
| 10K | 1 a second | SQL is fine |
| 1M | 100 a second | Borderline; cache or add replicas |
| 50M | 12K a second | Sorted set; SQL would scan millions each time |

Try SQL first for a small game. When a tournament final ends and a million players open "my rank" together, only the sorted set keeps up.

A Redis **sorted set** keeps a count on every link of a **skip list**. Adding the counts on the way down gives your rank in a few dozen hops, even for 50M players.

| Command | What it does | Cost |
|---|---|---|
| `ZINCRBY lb 50 maya` | Add points (creates the member if new) | O(log n) |
| `ZADD lb GT CH 950 maya` | Raise a best score, never lower it | O(log n) |
| `ZREVRANGE lb 0 99 WITHSCORES` | Top 100, highest first | O(log n + 100) |
| `ZREVRANK lb maya` | 0-based position, highest first | O(log n) |
| `ZCOUNT lb (1250 +inf` | Players with strictly more points | O(log n) |
| `ZSCORE lb maya` | One player's points | O(1) |
| `ZUNIONSTORE w 7 d1 … d7` | Sum several boards into one | O(N) + O(M log M) |

## API

| Method | Path | Result |
|---|---|---|
| POST | `/matches/:id/result` | From the match server, signed: `{ playerId, points, playedAt }` → `202` |
| GET | `/boards/:board/top?n=100` | Top N with ranks; cached for 1 s |
| GET | `/boards/:board/players/:id` | `{ score, rank }`, or `404` with no score this period |
| GET | `/boards/:board/players/:id/around?r=5` | The 2r + 1 players around this one |
| GET | `/boards/:board/stream` | SSE: top-10 changes, at most once per second |

`:board` is `all`, `daily` or `weekly`. Only match servers may submit, never the player's app.

## Data model

The database is the durable copy. Redis holds an index of it.

```sql
CREATE TABLE score_events (
  match_id  uuid        PRIMARY KEY,           -- a redelivered event inserts nothing
  game_id   int         NOT NULL,
  player_id bigint      NOT NULL,
  points    int         NOT NULL CHECK (points BETWEEN 0 AND 10000),
  played_at timestamptz NOT NULL,              -- decides the daily and weekly period
  status    text        NOT NULL DEFAULT 'ok'  -- 'voided' after an anti-cheat review
);

CREATE TABLE player_totals (                   -- what a Redis rebuild loads
  game_id    int    NOT NULL,
  period     text   NOT NULL,                  -- 'all', 'd:2026-10-13', 'w:2026-W42'
  player_id  bigint NOT NULL,
  points     bigint NOT NULL,
  reached_at timestamptz NOT NULL,             -- when the total last changed: the tie-break
  PRIMARY KEY (game_id, period, player_id)
);

CREATE TABLE consumer_offsets (                -- written in the same transaction as the totals
  partition   int    PRIMARY KEY,
  next_offset bigint NOT NULL
);
```

| Redis key | Holds | Expiry |
|---|---|---|
| `lb:{g1}:all` | Sorted set: player id → season points | None; a new key per season |
| `lb:{g1}:daily:2026-10-13` | Sorted set: points that UTC day | 8 days |
| `lb:{g1}:weekly:2026-W42` | Sorted set: points that ISO week | 14 days |
| `lb:{g1}:best` | Sorted set: best single match, composite score | None |
| `off:{g1}:<partition>` | String: last Kafka offset applied | None |

The `{g1}` tag keeps a game's keys together, so one Lua script can update them all.

## Step-by-step answer

<Steps>
  <Step title="Name the queries">
    Top K, my rank, and the players around me. Top K is shared, so cache it.
  </Step>
  <Step title="One sorted set per board">
    `ZINCRBY` adds points, `ZREVRANGE 0 99` is the top 100, `1 + ZCOUNT key (myScore +inf` is my rank. All O(log n).
  </Step>
  <Step title="Pick a tie rule and say it">

**Shared** ranks ("1224") are plain `ZCOUNT`. **Dense** ranks ("1223") need a second set. **First to reach wins** ("1234") puts the time inside the score:

```js
export const TIME_BITS = 28;                          // 2^28 s ≈ 8.5 years of season
export const MAX_POINTS = 2 ** (53 - TIME_BITS) - 1;  // 33,554,431
// earlier time → larger remainder → higher among equal points
const encode = (points, tsSec) => points * 2 ** TIME_BITS + (2 ** TIME_BITS - 1 - tsSec);
```

Scores are doubles, exact only to 2^53, so both parts must fit in 53 bits. Adding to a composite runs in the Lua script.

  </Step>
  <Step title="Time windows are separate keys">
    Keys come from when the match was **played**, so a 23:59:59 result arriving after midnight counts for its day. One script bumps the daily, weekly and all-time keys.
  </Step>
  <Step title="Write path: validate, log, apply">
    The Score API checks the signed result, appends it to Kafka and returns `202`. Kafka can redeliver and `ZINCRBY` isn't idempotent, so the script stores the last applied offset and skips anything at or below it.
  </Step>
  <Step title="Read path: cache what everyone shares">
    The top 100 is cached for one second ([caching](/learn/caching)). "My rank" is two or three O(log n) calls on a replica, well inside 50 ms.
  </Step>
  <Step title="Durability: Redis is an index">
    A DB writer saves each event, the totals and the Kafka offsets in one transaction. If the primary dies, the replica takes over and Kafka replays. If both die, reload the totals into a fresh instance, then replay.
  </Step>
  <Step title="Past one node: shard by player">

Split a board by player hash ([sharding strategies](/deep-dives/sharding-strategies)). Writes touch one shard. Reads fan out:

- **Top K:** each shard returns its full top K and the API merges them.
- **My rank:** 1 plus the sum of each shard's `ZCOUNT`.

Line the Kafka partitions up with the shards.

  </Step>
  <Step title="Or shard by score range">
    Top K comes from one shard, but the top shard runs hot and players move. Hash sharding is safer.
  </Step>
  <Step title="Approximate the tail, push the head">
    Nobody cares about #18,402,118 versus #18,402,090. Keep exact ranks for the top 10K and show a percentile ("top 37%") below. Push top-10 changes over SSE ([polling, SSE and WebSockets](/deep-dives/polling-sse-websockets)).
  </Step>
</Steps>

## Failure modes

| What breaks | Effect | Mitigation |
|---|---|---|
| Redis primary crashes | A few ms of scripts lost | Promote the replica; replay Kafka |
| Kafka redelivers | Points counted twice | Offset check in the script |
| Both Redis copies lost | No leaderboard | Rebuild from the database; serve the cached top 100 |
| Result arrives after midnight | Wrong day | Period from `played_at` |
| Evening peak | Updater lag | Kafka absorbs it; alert on lag |
| Cheater found later | Fake scores | Void events, recompute totals |
| `ZUNIONSTORE` per request | Redis blocks | Rebuild jobs only |

## Trade-offs

| Choice | Pros | Cons |
|---|---|---|
| Sorted set vs SQL index | O(log n) rank | Memory-bound; a copy to sync |
| Kafka first vs Redis directly | Durable, replayable | ~100 ms lag, more parts |
| Write every period vs `ZUNIONSTORE` | Every board live | Three writes per event |
| Shard by player hash | Even writes | Reads fan out |
| Shard by score range | Top K from one shard | Hot top shard |
| Percentile for the tail | Tiny memory | No exact rank down there |
| Composite tie score | Fixed order for ties | Fewer bits for points |
