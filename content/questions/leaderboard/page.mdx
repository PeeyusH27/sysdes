It all hinges on one query: **what is my rank?** Say how you answer it fast, then spend your time on ties, time windows, durability and sharding.

## Clarifying questions

- How many players, daily actives and matches per day?
- Season points, a best single score, or both?
- Ties: shared rank, or first to get there? Do prizes depend on it?
- Which windows, and in which time zone does a day end? How fresh?
- Who computes the score: a trusted game server, or the client?

## Capacity estimate

| Quantity | Estimate |
|---|---|
| Players | 50M registered, 10M daily active |
| Score events | 10M × 20 matches = 200M a day ≈ **2.3K per second** |
| Peak | About 5× average ≈ **12K events per second** |
| Redis work per event | One Lua script: an offset check, 3 `ZINCRBY`, 2 `EXPIRE` |
| Rank reads | One per match ≈ 12K per second at peak, O(log n) each |
| Top-100 reads | Cached 1 s per API instance: a few Redis calls per second |
| Memory per member | ~100 bytes (skip-list node, hash entry, id); check with `MEMORY USAGE` |
| All-time board | 50M × 100 B ≈ **5 GB** |
| Daily boards | 10M × 100 B ≈ 1 GB each; 8 days kept ≈ 8 GB |
| Weekly boards | ~20M weekly actives ≈ 2 GB each; 2 kept ≈ 4 GB |

About 17 GB and 12K scripts per second: one primary plus a replica, so **don't shard yet**. A billion players, or ten times the writes, would force it.

## Why a sorted set

An index on `points` serves the top 100 fine (`ORDER BY points DESC LIMIT 100`). But a B-tree stores no counts, so the rank query reads every entry above you: millions, up to 12K times a second. Caching ranks fails too: one score change shifts everyone it passes.

```sql
SELECT COUNT(*) + 1 FROM player_totals
WHERE game_id = 1 AND period = 'all' AND points > 900;
```

A Redis sorted set is a **skip list** with a span count on every link, plus a **hash** from member to score. Summing spans on the way down makes a rank O(log n): a few dozen hops for 50M members.

| Command | What it does | Cost |
|---|---|---|
| `ZINCRBY lb 50 maya` | Add points (creates the member if new) | O(log n) |
| `ZADD lb GT CH 950 maya` | Raise a best score, never lower it | O(log n) |
| `ZREVRANGE lb 0 99 WITHSCORES` | Top 100, highest first | O(log n + 100) |
| `ZREVRANK lb maya` | 0-based position, highest first | O(log n) |
| `ZCOUNT lb (1250 +inf` | Players with strictly more points | O(log n) |
| `ZSCORE lb maya` | One player's points | O(1) |
| `ZUNIONSTORE w 7 d1 … d7` | Sum several boards into one | O(N) + O(M log M) |

Small sets (up to 128 short members by default) are one compact listpack instead: O(n), but tiny.

## API

| Method | Path | Result |
|---|---|---|
| POST | `/matches/:id/result` | From the match server, signed: `{ playerId, points, playedAt }` → `202` |
| GET | `/boards/:board/top?n=100` | Top N with ranks; cached for 1 s |
| GET | `/boards/:board/players/:id` | `{ score, rank }`, or `404` with no score this period |
| GET | `/boards/:board/players/:id/around?r=5` | The 2r + 1 players around this one |
| GET | `/boards/:board/stream` | SSE: top-10 changes, at most once per second |

`:board` is `all`, `daily` or `weekly`, plus an optional `?period=2026-10-13`. Only match servers may submit (mutual TLS or a signed service token), never the player's app.

## Data model

The schema is the durable copy; Redis holds an index of it.

```sql
CREATE TABLE score_events (
  match_id  uuid        PRIMARY KEY,           -- a redelivered event inserts nothing
  game_id   int         NOT NULL,
  player_id bigint      NOT NULL,
  points    int         NOT NULL CHECK (points BETWEEN 0 AND 10000),
  played_at timestamptz NOT NULL,              -- decides the daily and weekly period
  status    text        NOT NULL DEFAULT 'ok'  -- 'voided' after an anti-cheat review
);

CREATE TABLE player_totals (                   -- what a Redis rebuild loads
  game_id    int    NOT NULL,
  period     text   NOT NULL,                  -- 'all', 'd:2026-10-13', 'w:2026-W42'
  player_id  bigint NOT NULL,
  points     bigint NOT NULL,
  reached_at timestamptz NOT NULL,             -- when the total last changed: the tie-break
  PRIMARY KEY (game_id, period, player_id)
);

CREATE TABLE consumer_offsets (                -- written in the same transaction as the totals
  partition   int    PRIMARY KEY,
  next_offset bigint NOT NULL
);
```

| Redis key | Holds | Expiry |
|---|---|---|
| `lb:{g1}:all` | Sorted set: player id → season points | None; a new key per season |
| `lb:{g1}:daily:2026-10-13` | Sorted set: points that UTC day | 8 days |
| `lb:{g1}:weekly:2026-W42` | Sorted set: points that ISO week | 14 days |
| `lb:{g1}:best` | Sorted set: best single match, composite score | None |
| `off:{g1}:<partition>` | String: last Kafka offset applied | None |

The `{g1}` hash tag puts every key of a game in one Redis Cluster slot, so one Lua script can update them all atomically.

## Step-by-step answer

<Steps>
  <Step title="Name the queries">
    Top K, my rank and score, and the players around me, per board. Top K is shared, so cache it; "my rank" is personal and must be cheap on demand.
  </Step>
  <Step title="One sorted set per board">
    `ZINCRBY` adds points, `ZREVRANGE 0 99` is the top 100, `1 + ZCOUNT key (myScore +inf` is my rank, and `ZREVRANK` then `ZREVRANGE p-5 p+5` is the window around me. All O(log n).
  </Step>
  <Step title="Pick a tie rule and say it">

**Shared** ranks ("1224") are plain `ZCOUNT`. **Dense** ranks ("1223") need a second set of distinct scores. **First to reach wins** ("1234") puts the tie-break inside the score:

```js
export const TIME_BITS = 28;                          // 2^28 s ≈ 8.5 years of season
export const MAX_POINTS = 2 ** (53 - TIME_BITS) - 1;  // 33,554,431
// earlier time → larger remainder → higher among equal points
const encode = (points, tsSec) => points * 2 ** TIME_BITS + (2 ** TIME_BITS - 1 - tsSec);
```

Scores are doubles, exact only to 2^53, so both parts must fit in 53 bits; time as a fraction collapses at a million points. Adding to a composite is read-modify-write, so it runs in the Lua script. A best-score board just uses `ZADD GT`: an equal score reached later encodes smaller, so it never wins.

  </Step>
  <Step title="Time windows are separate keys">
    Keys come from when the match was **played**, so a 23:59:59 result arriving after midnight counts for its day. One script bumps daily, weekly and all-time keys and sets expiry once (`EXPIRE … NX`). `ZUNIONSTORE` of seven days is O(N): rebuilds only. After a grace period, snapshot yesterday's standings for prizes.
  </Step>
  <Step title="Write path: validate, log, apply">
    The match server signs the result; the Score API checks it, appends to Kafka with `acks=all` and returns `202`. Kafka delivers at least once and `ZINCRBY` isn't idempotent, so the updater's script stores each partition's last applied offset and skips anything at or below it, atomically with the board changes.
  </Step>
  <Step title="Read path: cache what everyone shares">
    The top 100 is cached for one second per API instance (see [caching](/learn/caching)); "my rank" and "around me" are two or three O(log n) calls on a replica, well inside 50 ms. Names come from a profile cache.
  </Step>
  <Step title="Durability: Redis is an index">
    The DB writer inserts each event (keyed by `match_id`), bumps `player_totals` and records Kafka offsets in one transaction. If the primary dies, Sentinel promotes the replica and the updater replays Kafka from the offsets it holds; if both die, batch-`ZADD` the totals into a fresh instance (50M members in minutes), then replay.
  </Step>
  <Step title="Past one node: shard by player">

Split a board into N keys by player hash ([sharding strategies](/deep-dives/sharding-strategies)). Writes touch one shard; reads fan out:

- **Top K:** each shard returns its full top K and the API merges. Not K / N: the top K could all sit on one shard.
- **My rank:** 1 + the sum of `ZCOUNT shard (myScore +inf` over shards. Dense ranks don't add up across shards.

Align Kafka partitions with shards, so each offset key lives beside its boards.

  </Step>
  <Step title="Or shard by score range">
    Shard 0 holds scores above 10,000, shard 1 from 1,000 to 9,999: top K comes from one shard, and rank is the higher shards' `ZCARD` plus your rank in yours. But the top shard runs hot, players move between shards and boundaries drift, so hash sharding is safer.
  </Step>
  <Step title="Approximate the tail, push the head">
    Nobody cares whether they're #18,402,118 or #18,402,090: keep exact ranks for the top 10K and give everyone else a percentile ("top 37%") from a histogram of a few hundred counters. Push top-10 changes over SSE at most once per second ([polling, SSE and WebSockets](/deep-dives/polling-sse-websockets)).
  </Step>
</Steps>

- `encode` refuses more than 33,554,431 points; its test shows the refused composite decoding one point too high.
- `aroundMe` slides its window at the board's ends, so it shows 11 rows whenever there are 11 players.
- `mergeTopK` needs each shard's full top K; the test shows K / N dropping a player.
- `periods.js` gets ISO weeks right at the year boundary: 2027-01-01 belongs to 2026-W53.

## Failure modes

| What breaks | Effect | Mitigation |
|---|---|---|
| Redis primary crashes | Last few ms of scripts lost | Promote the replica; replay Kafka from the offsets in Redis |
| Kafka redelivers | Points counted twice | Offset check in the script; DB insert keyed by `match_id` |
| Both Redis copies lost | No leaderboard | Rebuild from `player_totals`; serve the cached top 100 meanwhile |
| Match ends 23:59:59, arrives after midnight | Wrong day | Period from `played_at`; daily keys live 8 days |
| Evening peak | Updater lag | Kafka absorbs it; pipeline scripts; alert on consumer lag |
| Cheater found days later | Fake scores everywhere | Void events, recompute totals, fix each board |
| `ZUNIONSTORE` per request | Redis blocks for seconds | Rebuild jobs only, off-peak or on a spare |

## Trade-offs

| Choice | Pros | Cons |
|---|---|---|
| Sorted set vs SQL index | O(log n) rank over millions | Memory-bound; a derived copy to sync |
| Kafka first vs writing Redis directly | Durable before `202`; absorbs spikes; replayable | ~100 ms lag, more moving parts |
| Write every period vs `ZUNIONSTORE` | Every board live | Three writes per event |
| Shard by player hash | Even writes | Every rank and top-K query fans out |
| Shard by score range | Top K from one shard | Hot top shard; players move |
| Percentile for the tail | Tiny memory below the top 10K | No exact rank down there |
| Composite tie score | Deterministic order when prizes depend on rank | Fewer bits for points; increments need a script |

Why rank is the hard query and how a sorted set makes it O(log n); a definite tie rule (and the 2^53 limit); period keys from play time; Redis as a rebuildable, idempotently fed index; and sharding that gets top K and rank right.

## Follow-up questions

<FollowUps>
  <FollowUp q="How would you build a friends leaderboard?">
    Fetch a few hundred friends' scores with one `ZMSCORE`, sort in the API and cache per user for a few seconds: O(friends), with no per-user sorted sets to update.
  </FollowUp>
  <FollowUp q="How would you add country boards?">
    One more key per country and period, written by the same script, so country rank is O(log n) too.
  </FollowUp>
  <FollowUp q="How do you stop cheating?">
    Signed, server-computed scores, plausibility rules at ingest (points per minute, match length, matches per hour), anomaly detection, and prizes held until review.
  </FollowUp>
  <FollowUp q="What changes at a billion players?">
    About 100 GB for the all-time board, so hash-shard into, say, 8 keys on 8 primaries; or keep exact ranks for the top million (`ZREMRANGEBYRANK`) and percentiles below.
  </FollowUp>
  <FollowUp q="How do you show rank changes live?">
    SSE with "top 10 changed" at most once per second per board; notify "you were overtaken" only across lines that matter, such as the top 100.
  </FollowUp>
</FollowUps>
