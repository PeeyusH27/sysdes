## Clarifying questions

- **Who pays whom?** A marketplace: customers pay, the platform keeps a cut, merchants get paid later.
- **Which methods?** Cards answer in a second. Bank debits confirm hours later, by webhook.
- **Charge now, or hold first and capture on shipment?**
- **Refunds, currencies, peak load?**

## Capacity estimate

| Quantity | Calculation | Result |
|---|---|---|
| Payments | 10M/day ÷ 86,400 s | ≈ **116/s** average |
| Peak | ~10× on Black Friday | ≈ **1,160/s** |
| PSP calls in flight | 1,160/s × ~1 s latency | ≈ **1,160 concurrent** |
| Ledger entries | 4 per payment × 10M | **40M rows/day** |
| Storage | payments + ledger | ≈ 11 GB/day, **4 TB/year** |
| Money moved | 10M × $50 average | **$500M/day** |

One Postgres primary copes. Two numbers matter:

- **1,160 calls** are always waiting on the PSP, so never hold a lock across one.
- At $500M a day, a 0.01% error rate is **1,000 wrong payments daily**. Constraints and reconciliation beat luck.

## API

| Method | Path | Body | Result |
|---|---|---|---|
| POST | `/payments` | `Idempotency-Key` header; `orderId`, `amount`, `currency`, `paymentMethod` (PSP token) | `201` done, `202` still unknown, `402` declined |
| GET | `/payments/:id` | | `id`, `status`, `amount`, `refunded` |
| POST | `/refunds` | `Idempotency-Key`; `paymentId`, `amount` | `201`, or `409` above the refundable amount |
| POST | `/webhooks/psp` | The PSP's signed event | `200` once stored, duplicates included |

The client makes the key once per checkout and reuses it on retries. The server keeps keys 24 hours. Same key and body: replay the stored response. Still running: `409`. Different body: `422`.

## Data model

<CodeBlock src="snippets/schema.sql" title="schema.sql" />

The payment is a **state machine**:

- `created → processing`, committed before the PSP call.
- `processing → succeeded | failed | requires_action`, or `unknown` on timeout.
- `unknown → succeeded | failed`, settled by a webhook or status query, never a guess.
- `succeeded → partially_refunded → refunded`.

Money lives in the **ledger**, not a balance column. A balance is the sum of entries.

## Step-by-step answer

<Steps>
  <Step title="Keep card data out">
    The PSP's SDK swaps the card for a token in the browser.
  </Step>
  <Step title="Claim the idempotency key in the same transaction">

One transaction claims the key and creates the payment. The unique key lets only one request win:

```sql
BEGIN;
INSERT INTO idempotency_keys (customer_id, key, request_hash)
VALUES ($1, $2, $3)
ON CONFLICT (customer_id, key) DO NOTHING;      -- 0 rows: someone owns the key
-- if 0 rows: SELECT request_hash, status, response_code, response_body ...
--   hash differs     → ROLLBACK, 422
--   status 'done'    → ROLLBACK, replay the stored response
--   status 'started' → ROLLBACK, 409
INSERT INTO payments (id, ..., status) VALUES ($4, ..., 'processing');
COMMIT;
```

  </Step>
  <Step title="Never hold a transaction across the PSP call">
    Commit the claim, call the PSP, then record the outcome in a second transaction. After a crash, the recovery job asks the PSP.
  </Step>
  <Step title="A timeout means unknown">
    Mark it `unknown` and return `202`. Retry with your own key, never a new one. The webhook or a status query decides. Why not retry with a fresh key? If the first call did charge, the customer pays twice. Why not mark it failed? The customer taps Pay again, with the same result.
  </Step>
  <Step title="Webhooks: verify, dedupe, move forward">
    Check the signature. `ON CONFLICT DO NOTHING` on the event id drops repeats. Ignore late events that go backward. Answer `200` fast.
  </Step>
  <Step title="One writer for each move">
    The reply, the webhook and the recovery job share one function: lock the row, check the move is legal, then update everything in one transaction. The first signal wins.
  </Step>
  <Step title="Double-entry ledger">

Each transaction's entries sum to zero, in integer cents. $50.00 with a PSP fee and a 10% commission:

| Account | Type | Debit | Credit |
|---|---|---|---|
| Cash at PSP | asset | $48.25 | |
| PSP fees | expense | $1.75 | |
| Merchant payable (m_42) | liability | | $45.00 |
| Platform revenue | revenue | | $5.00 |
| **Total** | | **$50.00** | **$50.00** |

Append-only: fixes are new entries. One leg is the remainder, so rounding loses no cent.

  </Step>
  <Step title="Outbox for events">
    Write `payment.succeeded` to an `outbox` table in the same transaction. A relay publishes it, maybe twice, so consumers dedupe. See [the dual-write problem](/learn/async-messaging#the-dual-write-problem-and-the-transactional-outbox).
  </Step>
  <Step title="Reconcile every day">
    Match the PSP's settlement report to the ledger, then payouts to the bank statement. Fix mismatches with new entries, never by editing history.
  </Step>
  <Step title="Refunds">

One conditional UPDATE reserves a refund, so concurrent refunds can't exceed the charge:

```sql
UPDATE payments
SET refunded = refunded + $2,
    status = CASE WHEN refunded + $2 = amount THEN 'refunded' ELSE 'partially_refunded' END
WHERE id = $1 AND status IN ('succeeded', 'partially_refunded') AND refunded + $2 <= amount;
```

Zero rows means `409`. Multi-step flows (authorize, reserve stock, capture) run as a **saga**: every step has an undo.

  </Step>
</Steps>

## Failure modes

| What breaks | Effect | Mitigation |
|---|---|---|
| PSP times out | Charged or not: unknown | `unknown`; same-key retry; webhook, then status query |
| DB down after the PSP charged | Money moved, no record | Intent committed first; webhook retries; reconciliation |
| Webhook storm | Slow handler, more retries | Store, answer `200`, process from a queue |
| Double submit | Two charges | Unique key; `409` while running |
| Two refunds at once | Too much refunded | `refunded + $2 <= amount` in the UPDATE |
| Currency rounding | Cents vanish | Integer minor units; remainder leg |
| Outbox relay down | Orders not marked paid | Rows wait; alert on the oldest |

## Trade-offs

| Choice | Gain | Cost |
|---|---|---|
| Ledger, not a balance column | Full history, auditable | More rows to sum |
| Key in the DB, not Redis | Atomic with the payment | More load on the primary |
| Charge now, not async | Instant, simple | Tied to the PSP's speed |
| Hold then capture | Free voids | Holds expire in about 7 days |

## Follow-up questions

<FollowUps>
  <FollowUp q="How do you handle multiple currencies?">
    Tag every entry with its currency. Never mix two in one transaction. Convert through an FX account and store the rate.
  </FollowUp>
  <FollowUp q="How do payouts to merchants work?">
    A daily job pays each merchant's balance minus a refund reserve. Failed payouts reverse with new entries.
  </FollowUp>
  <FollowUp q="Where do fraud checks go?">
    Before the PSP call. Low risk passes, medium asks for extra checks, high is blocked. If the risk service is down, allow small amounts only.
  </FollowUp>
  <FollowUp q="Can you fail over to a second PSP?">
    Only if the first certainly never charged. After a timeout, a second charge can mean two. Settle the first through its webhooks.
  </FollowUp>
  <FollowUp q="Reconciliation found a mismatch. Now what?">
    Fix forward, never by editing entries. Replay a missed webhook or reverse a bad posting. Send the unexplained to a human.
  </FollowUp>
</FollowUps>
