<TLDR>
Seats go `available → held → booked`, and one **conditional UPDATE** holds all requested seats or none: Postgres row locks pick exactly one winner per seat. Payment carries an idempotency key; the webhook confirms only if the hold is still yours, and refunds otherwise.
</TLDR>

The core test is **concurrency**: two people must never buy the same seat.

## Capacity estimate

The average is tiny; the **spike** is the design problem.

| Quantity | Estimate |
|---|---|
| Bookings | 10M per month ≈ **4 per second** on average |
| Launch spike | 500K people in the first minutes of a blockbuster |
| Seat-map reads, no CDN | 500K viewers refreshing every 5 s ≈ **100K requests/s** |
| Seat-map reads, 1 s CDN cache | About 1 origin request per show per second, per edge |
| Admitted shoppers | 200 per second per hot show, via the waiting room |
| Hold writes | A few hundred conditional UPDATEs per second: easy for one primary |

Seat maps are read far more than written, so cache the snapshot and push changes.

## API

| Method | Path | Result |
|---|---|---|
| GET | `/shows/:id/seats` | Seat-map snapshot (CDN-cached for 1–2 s) |
| GET | `/shows/:id/seats/stream` | SSE stream of seat changes |
| POST | `/shows/:id/holds` | `{ seats }` → `201 { holdId, expiresAt }`, or `409` if taken |
| POST | `/payments` | `{ holdId }` + `Idempotency-Key` → payment intent |
| POST | `/webhooks/payments` | Provider confirms → booking confirmed or refunded |
| DELETE | `/holds/:id` | Release early |

During a launch, holds also need a waiting-room admission token.

## Data model

<CodeBlock src="snippets/schema.sql" title="schema.sql" />

Beside it sits `shows(id, movie, screen, starts_at)`. Each seat is a state machine:

- `available → held`: a hold sets `held_by` and `held_until`.
- `held → booked`: payment confirmed; sets `booking_id`, clears `held_until`.
- `held → available`: expired, released, or payment failed.
- `booked` is final unless cancelled.

The primary key `(show_id, seat_no)` is one row per seat per show: exactly the unit Postgres locks.

## Step-by-step answer

<Steps>
  <Step title="State the invariant aloud">
    "A seat is booked at most once." Say it before you draw a single box.
  </Step>
  <Step title="Seat state machine">
    `available → held → booked`, or back to `available` (the data model lists each transition).
  </Step>
  <Step title="Hold atomically">

One statement for every requested seat; if `rowCount` falls short, roll back.

```sql
UPDATE seats SET status = 'held', held_by = $1, held_until = now() + interval '5 minutes'
WHERE show_id = $2 AND seat_no = ANY($3)
  AND (status = 'available' OR (status = 'held' AND held_until < now()))
```

Mind the brackets: without them, `status = 'available' OR held_until < now()` also matches **booked** seats with an old `held_until`.

</Step>
  <Step title="Why it's safe">
    Under READ COMMITTED, Bob's UPDATE waits on Alice's row lock, then **re-evaluates the WHERE clause** against her committed row and matches 0 rows. No application lock, no `SELECT … FOR UPDATE` round trip.
  </Step>
  <Step title="Payment">
    `Idempotency-Key = holdId` stops double charges. The verified webhook (maybe retried, maybe late) confirms, not the browser redirect.
  </Step>
  <Step title="Confirm">
    Insert the booking `ON CONFLICT (payment_id) DO NOTHING`, then `UPDATE seats … WHERE status = 'held' AND held_by = me`. Hold lost? Roll back and refund, idempotently. A failed payment frees seats under the same guard.
  </Step>
  <Step title="Expiry">
    Lazy: expired holds already count as free, so correctness never waits on a timer. A sweeper frees them every 30 s anyway, for honest seat maps.
  </Step>
  <Step title="Live seat map">
    A 1–2 s CDN snapshot plus changes pushed over SSE via Redis, with **one** Redis subscription per API instance fanning out locally ([why SSE](/deep-dives/polling-sse-websockets)).
  </Step>
  <Step title="Launch spikes">

- A FIFO waiting room admits N users per second with admission tokens; holds without one are rejected.
- CDN-cached seat maps, per-account [rate limits](/questions/rate-limiter), a CAPTCHA to join, pre-scaled API and database.

</Step>
  <Step title="Redis holds?">
    `SET NX PX` per seat (Lua for several) is fast, but bookings need the database as truth: Redis is only a front-line filter for mega-launches.
  </Step>
</Steps>

- `confirmBooking` checks `held_by` but not `held_until`: a just-expired hold nobody reclaimed still books.

## Failure modes

| What breaks | Effect | Mitigation |
|---|---|---|
| Webhook after the hold expired | Seat may be someone else's | Book if still held by me; else roll back and refund |
| Webhook retried | Duplicate booking | `UNIQUE (payment_id)` + `ON CONFLICT DO NOTHING` |
| Double-clicking Pay | Two charges | Idempotency key = holdId |
| DB failover mid-hold | Transaction errors | Client retries: held again, or taken |
| Launch-day herd | DB overwhelmed | Waiting room, cached seat map, limits, CAPTCHA |
| Sweeper stops | Stale holds on seat maps | Harmless (expired holds count as free); alert on lag |

## Trade-offs

| Choice | Pros | Cons |
|---|---|---|
| Conditional UPDATE vs `SELECT … FOR UPDATE` | One round trip, short locks (the default) | Less flexible logic |
| DB holds vs Redis holds | One source of truth | More DB writes |
| Countdown vs silently extending holds | Fair, predictable; extend only while payment is in flight | Some lost sales |
| SSE vs polling seat maps | Fresh within a second for popular shows | A connection per viewer; poll the CDN for quiet ones |

## Follow-up questions

<FollowUps>
  <FollowUp q="What if payment succeeds after the hold expires?">
    Still yours? Book it. Taken? Roll back and refund automatically. A visible countdown keeps it rare.
  </FollowUp>
  <FollowUp q="Seat-level or show-level locking?">
    Seat-level: row locks let thousands book at once, while a show-level lock serialises every booking.
  </FollowUp>
  <FollowUp q="How do you survive a launch-day thundering herd?">
    Waiting-room admission tokens, seat maps from the CDN and SSE, per-account limits and pre-scaling, with admission tuned from database metrics.
  </FollowUp>
  <FollowUp q="How do you stop bots from grabbing all the seats?">
    A CAPTCHA or device attestation at the queue, per-account and per-card limits, velocity checks, delayed release of suspicious holds.
  </FollowUp>
  <FollowUp q="How would you suggest the best available seats?">
    Score seats by centre distance and row, find contiguous runs of N free seats in the cached map, and hold the best with the same conditional UPDATE.
  </FollowUp>
</FollowUps>
