<TLDR>
Seats go `available → held → booked`. One **conditional UPDATE** holds every seat or none, so row locks pick one winner. A late payment is refunded.
</TLDR>

## Capacity estimate

The average is tiny. The **spike** is the problem.

| Quantity | Estimate |
|---|---|
| Bookings | 10M a month ≈ **4 per second** |
| Launch spike | 500K people in minutes |
| Seat-map reads, no CDN | ≈ **100K requests/s** |
| Seat-map reads, 1 s CDN cache | About 1 origin request per show per second |
| Admitted shoppers | 200 per second per hot show |
| Hold writes | A few hundred per second: easy |

Seat maps are mostly read, so cache them.

## API

| Method | Path | Result |
|---|---|---|
| GET | `/shows/:id/seats` | Seat-map snapshot (CDN-cached for 1–2 s) |
| GET | `/shows/:id/seats/stream` | SSE stream of seat changes |
| POST | `/shows/:id/holds` | `{ seats }` → `201 { holdId, expiresAt }`, or `409` if taken |
| POST | `/payments` | `{ holdId }` + `Idempotency-Key` → payment intent |
| POST | `/webhooks/payments` | Provider confirms → booking confirmed or refunded |
| DELETE | `/holds/:id` | Release early |

During a launch, holds also need a waiting-room token.

## Data model

<CodeBlock src="snippets/schema.sql" title="schema.sql" />

Each seat is a small state machine:

- `available → held`: sets `held_by` and `held_until`.
- `held → booked`: payment confirmed.
- `held → available`: expired, released, or payment failed.

The key `(show_id, seat_no)` is one row per seat: exactly what Postgres locks.

## Step-by-step answer

<Doodle name="idempotency" size={150} caption />

<Steps>
  <Step title="State the invariant aloud">
    "A seat is booked at most once." Say it before you draw.
  </Step>
  <Step title="Seat state machine">
    `available → held → booked`, or back to `available`.
  </Step>
  <Step title="Hold atomically">

One statement for all seats. If `rowCount` falls short, roll back.

```sql
UPDATE seats SET status = 'held', held_by = $1, held_until = now() + interval '5 minutes'
WHERE show_id = $2 AND seat_no = ANY($3)
  AND (status = 'available' OR (status = 'held' AND held_until < now()))
```

Mind the brackets, or **booked** seats with an old `held_until` match too.

</Step>
  <Step title="Why it's safe">
    Bob's UPDATE waits on Alice's row lock, **re-checks the WHERE clause** and matches 0 rows.
  </Step>
  <Step title="Payment">
    `Idempotency-Key = holdId` stops double charges. The webhook confirms, not the browser.
  </Step>
  <Step title="Confirm">
    Insert the booking once, then update seats only `WHERE held_by = me`. Hold lost? Refund.
  </Step>
  <Step title="Expiry">
    Expired holds already count as free. A sweeper tidies up every 30 s.
  </Step>
  <Step title="Live seat map">
    A CDN snapshot plus changes pushed over SSE ([why SSE](/deep-dives/polling-sse-websockets)).
  </Step>
  <Step title="Launch spikes">

- A waiting room admits N users a second. Holds without a token are rejected.
- Cached seat maps, [rate limits](/questions/rate-limiter), a CAPTCHA.

</Step>
  <Step title="Redis holds?">
    Only as a front filter. The database stays the truth.
  </Step>
</Steps>

## Failure modes

| What breaks | Effect | Mitigation |
|---|---|---|
| Late webhook | Seat may be taken | Book if still mine; else refund |
| Webhook retried | Duplicate booking | `UNIQUE (payment_id)` |
| Double-click on Pay | Two charges | Idempotency key |
| Launch-day herd | DB overwhelmed | Waiting room, cache, limits |

## Trade-offs

| Choice | Pros | Cons |
|---|---|---|
| Conditional UPDATE vs `SELECT … FOR UPDATE` | One round trip, short locks | Less flexible |
| DB holds vs Redis holds | One source of truth | More DB writes |
| Countdown vs extending holds | Fair and predictable | Some lost sales |
| SSE vs polling | Fresh within a second | A connection per viewer |

## Follow-up questions

<FollowUps>
  <FollowUp q="What if payment succeeds after the hold expires?">
    Still yours? Book it. Taken? Refund automatically. A countdown keeps it rare.
  </FollowUp>
  <FollowUp q="Seat-level or show-level locking?">
    Seat-level. A show-level lock would make every booking wait in line.
  </FollowUp>
  <FollowUp q="How do you survive a launch-day thundering herd?">
    A waiting room, CDN seat maps, per-account limits and pre-scaling.
  </FollowUp>
  <FollowUp q="How do you stop bots from grabbing all the seats?">
    A CAPTCHA at the queue, per-account limits, and checks for suspiciously fast buyers.
  </FollowUp>
  <FollowUp q="How would you suggest the best available seats?">
    Score seats by distance from the centre, find N free in a row, and hold them with the same UPDATE.
  </FollowUp>
</FollowUps>
