<TLDR>
Model **ParkingLot → Floor → Spot**, put spot choice and pricing behind small swappable rules, and keep a **free list per spot type** so nothing scans. Across gate servers, the database locks the spot with `FOR UPDATE SKIP LOCKED`.
</TLDR>

## Scale check

Five floors of 200 spots is **1,000 spots** and about 500 cars an hour. One small process can run it. The hard part is two gates never giving out the same spot.

A scan of 1,000 spots takes microseconds, so speed alone does not justify free sets. They keep the smallest-first rule simple and the cost flat as lots grow past hundreds of spots.

## Public interface

| Call | Returns | Errors |
|---|---|---|
| `park(vehicle)` | `Ticket` with id, spot and entry time | `Lot full for car` |
| `quote(ticketId)` | Fee owed right now | `Unknown ticket` |
| `exit(ticketId, payment)` | `{ fee, change }`, and the spot is freed | `Payment of 40 required`, `Unknown ticket` |
| `floor.available(type)` | Free spots of that type on the floor | |
| event `changed(floor)` | Fired after every park and exit | |

Not every rule needs a class. Do the sum on pricing, at 20 an hour for a car:

| Rules today | Code |
|---|---|
| Hourly only | One function |
| Plus a 150 daily cap | Borderline, one `if` reads fine |
| Plus weekend rates, EV charging, monthly changes | Strategies, cap as a decorator |

A car parked 8 hours owes 160 hourly, so the cap bites. The second rule is the tipping point. Until it exists, a function is enough.

## Step-by-step answer

<Steps>
  <Step title="Use cases first">
    Park, pay, exit, show free spots.
  </Step>
  <Step title="Nouns become classes, verbs become methods">
    `Spot`, `Vehicle` and `Ticket` hold data. `ParkingLot`, `Floor` and the rules hold behaviour.
  </Step>
  <Step title="Relationships">
    The lot owns floors, floors own spots. A ticket only points at a spot.
  </Step>
  <Step title="Allocation without a scan">

`FITS` lists the spots each vehicle may use, **smallest first**:

```js
export const FITS = {
  bike: ['bike', 'compact', 'large'],
  car: ['compact', 'large'],
  truck: ['large'],
};
```

`take(types, accept)` pops the first free spot that passes `accept`.

  </Step>
  <Step title="Pricing as a strategy">
    `fee(durationMs, vehicle)` is the whole interface. A daily cap wraps it as a **decorator**. Pass in the clock.
  </Step>
  <Step title="Payment flow">
    Quote, pay, then `exit` re-checks the amount and frees the spot. A failed payment changes nothing.
  </Step>
  <Step title="Concurrency">

One Node process is atomic for free. Several servers need one statement that picks **and** locks a row:

```sql
UPDATE spots SET ticket_id = $1, taken_at = now()
WHERE id = (SELECT id FROM spots WHERE ... AND ticket_id IS NULL
            LIMIT 1 FOR UPDATE SKIP LOCKED)
RETURNING id, floor;
```

Insert the ticket in the same transaction, or a crash loses the spot.

  </Step>
  <Step title="Display boards">
    The lot announces `changed(floor)`. Boards listen (an **observer**).
  </Step>
  <Step title="Extensibility check">
    A new vehicle is one `FITS` row.
  </Step>
  <Step title="Tests">
    Lot full, bad ticket, grace period, daily cap, all with a fake clock.
  </Step>
</Steps>

## Persistence across gate servers

Only if asked. The database is the truth: a spot is free while `ticket_id` is NULL.

```sql
CREATE TABLE spots (
  id        text   PRIMARY KEY,                 -- '2-C14'
  lot_id    bigint NOT NULL,
  floor     int    NOT NULL,
  type      text   NOT NULL CHECK (type IN ('bike', 'compact', 'large')),
  features  text[] NOT NULL DEFAULT '{}',       -- 'ev', 'accessible'
  ticket_id uuid   UNIQUE,                      -- NULL means free
  taken_at  timestamptz
);
CREATE INDEX spots_free ON spots (lot_id, type, floor, id) WHERE ticket_id IS NULL;

CREATE TABLE tickets (
  id       uuid   PRIMARY KEY,
  lot_id   bigint NOT NULL,
  plate    text   NOT NULL,                     -- lets you find a lost ticket
  vehicle  text   NOT NULL,
  spot_id  text   NOT NULL REFERENCES spots (id),
  entry_at timestamptz NOT NULL DEFAULT now(),
  exit_at  timestamptz,
  fee      int
);
```

## Failure modes

| What breaks | Effect | Mitigation |
|---|---|---|
| Two gates allocate at once | Same spot twice | One process: atomic `take()`. Several: `SKIP LOCKED` |
| Gate crashes before the ticket prints | Spot lost | Spot and ticket in one transaction; a cleanup job frees orphans |
| Lost ticket | No fee | Find it by plate, or charge the daily maximum |
| Gate loses its network | No central DB | A local service works offline and syncs later |
| Payment declined | Driver stuck | Nothing changes until payment works; offer another method |

## Trade-offs

| Choice | Pros | Cons |
|---|---|---|
| Free lists vs a scan | Fast, even with many spots | More state to keep right |
| Strategy classes vs `if/else` | Rules swap and test easily | More files |
| Memory vs database | Simple and fast | One process only |
| Decorators vs one class | Rules combine freely | Wrapping order matters |

Strategy, decorator and observer, and why. A clear answer to "two gates, one spot". Tests with an injected clock. Too many classes costs points.

## Follow-up questions

<FollowUps>
  <FollowUp q="How would you scale to 500 lots?">
    Run a local service per lot, offline-safe, syncing to a central one split by `lot_id`.
  </FollowUp>
  <FollowUp q="How do you handle a lost ticket?">
    Find the open ticket by plate and charge from the real entry time. No match: charge the daily maximum.
  </FollowUp>
  <FollowUp q="How would you add reservations?">
    Reserve a spot **type** for a time window, not one spot. Release no-shows after a grace period.
  </FollowUp>
  <FollowUp q="How would you add EV charging?">
    Add an `ev` spot feature, a `needsCharger` filter and an `EnergyFee` decorator. No existing class changes.
  </FollowUp>
  <FollowUp q="Is take() really atomic in Node?">
    In one process, yes. Across processes, allocate in the database (`SKIP LOCKED`) or Redis (`SET NX`).
  </FollowUp>
</FollowUps>
