<TLDR>
Model **ParkingLot → Floor → Spot**, plus thin **Vehicle** and **Ticket** classes. Put what changes (spot selection, pricing, payment) behind small strategy interfaces, and keep a **free set per spot type on each floor** so allocation never scans every spot. In one Node process the event loop makes allocation atomic; across several gate servers, let the database pick and lock a spot with `FOR UPDATE SKIP LOCKED`.
</TLDR>

This is a **low-level design** (LLD) question: the interviewer wants classes, responsibilities and clean seams, then a check that you know where concurrency bites. Say that out loud before you draw anything.

## Clarifying questions

- How many floors and spots? (It decides whether a linear scan is acceptable.)
- Which vehicles fit which spots? May a bike use a compact spot, or a car a large one?
- What's the pricing model: hourly, flat, peak hours, a daily cap, a grace period?
- Is payment at the exit gate or at pay stations? Which methods: card, cash, wallet?
- One lot (classes in one process) or a chain of lots (a distributed system)?

## Capacity estimate

The numbers are small, which tells you the hard part is **correctness**, not scale.

| Quantity | Estimate |
|---|---|
| Spots | 5 floors × 200 spots = **1,000** |
| Average stay | 2 hours, so about 500 cars enter per hour (0.14 per second) |
| Peak entries | ~3× average, so under 0.5 per second across 4 gates |
| Tickets per day | 1,000 spots × 12 busy hours ÷ 2 h = **6,000** |
| Ticket storage | 6,000 × ~200 bytes ≈ 1.2 MB per day |

One small process could serve the whole lot. The real risk is two gates handing out the same spot at the same moment.

## API

The interface is the public methods of `ParkingLot`, plus one event.

| Call | Returns | Errors |
|---|---|---|
| `park(vehicle)` | `Ticket` with id, spot and entry time | `Lot full for car` |
| `quote(ticketId)` | Fee owed right now | `Unknown ticket` |
| `exit(ticketId, payment)` | `{ fee, change }`, and the spot is freed | `Payment of 40 required`, `Unknown ticket` |
| `floor.available(type)` | Free spots of that type on the floor | |
| event `changed(floor)` | Fired after every park and exit | |

## Data model

In memory, everything hangs off the lot:

- `ParkingLot.floors`: an array indexed by level.
- `Floor.free`: a `Map` from spot type to a `Set` of free spots. A spot is free exactly when it is in its set.
- `ParkingLot.tickets`: `Map<ticketId, Ticket>` of **open** tickets. Exit deletes the entry, so a ticket can't be used twice.

With several gate servers the source of truth moves to the database:

```sql
CREATE TABLE spots (
  id        text   PRIMARY KEY,                 -- '2-C14'
  lot_id    bigint NOT NULL,
  floor     int    NOT NULL,
  type      text   NOT NULL CHECK (type IN ('bike', 'compact', 'large')),
  features  text[] NOT NULL DEFAULT '{}',       -- 'ev', 'accessible'
  ticket_id uuid   UNIQUE,                      -- NULL means free
  taken_at  timestamptz
);
CREATE INDEX spots_free ON spots (lot_id, type, floor, id) WHERE ticket_id IS NULL;

CREATE TABLE tickets (
  id       uuid   PRIMARY KEY,
  lot_id   bigint NOT NULL,
  plate    text   NOT NULL,                     -- lets you find a lost ticket
  vehicle  text   NOT NULL,
  spot_id  text   NOT NULL REFERENCES spots (id),
  entry_at timestamptz NOT NULL DEFAULT now(),
  exit_at  timestamptz,
  fee      int
);
```

## Step-by-step answer

<Steps>
  <Step title="Use cases first">
    Park, quote, pay and exit, show availability. Say them aloud before drawing anything; every class you add should serve one of them.
  </Step>
  <Step title="Nouns become classes, verbs become methods">
    `Spot`, `Vehicle` and `Ticket` are thin data classes. Behaviour lives in `ParkingLot`, `Floor` and the strategies. Resist a `ParkingSpotManagerFactory`: interviewers reward fewer, sharper classes.
  </Step>
  <Step title="Relationships">
    The lot owns its floors and the floors own their spots (composition: they live and die together). A ticket only **references** a spot and a vehicle (association).
  </Step>
  <Step title="Allocation without a scan">

Each floor keeps a `Map` from spot type to a `Set` of free spots. `FITS` lists the spot types each vehicle may use, **smallest first**, so a truck never blocks a bike spot:

```js
export const FITS = {
  bike: ['bike', 'compact', 'large'],
  car: ['compact', 'large'],
  truck: ['large'],
};
```

`take(types, accept)` walks those types and pops the first free spot that passes `accept`. EV charging is a spot **feature** the selector filters on, not a new subclass.

  </Step>
  <Step title="Pricing as a strategy">
    `fee(durationMs, vehicle)` is the whole interface. A daily cap, peak hours or a discount is a **decorator** that wraps another strategy, so rules combine without editing classes (open/closed). Inject the clock so tests can hit exact hour boundaries.
  </Step>
  <Step title="Payment flow">
    `quote(ticket)` → pay with any `PaymentMethod` → `exit(ticket, payment)`. Exit re-checks the amount, frees the spot and deletes the ticket, so the same ticket can't exit twice. A failed payment changes nothing.
  </Step>
  <Step title="Concurrency">

In one Node process, `take()` runs to completion without interleaving, so it's atomic for free. With several gate servers, the source of truth moves to the database: one statement picks **and** locks a free row.

```sql
UPDATE spots SET ticket_id = $1, taken_at = now()
WHERE id = (SELECT id FROM spots WHERE ... AND ticket_id IS NULL
            LIMIT 1 FOR UPDATE SKIP LOCKED)
RETURNING id, floor;
```

Insert the ticket in the same transaction, so a crash can't leave a taken spot with no ticket.

  </Step>
  <Step title="Display boards">
    Observer pattern: the lot emits `changed(floor)` after every park and exit, and each board re-reads `available(type)` for that floor. The lot doesn't know boards exist.
  </Step>
  <Step title="Extensibility check">

- A new vehicle type is a new enum value plus its row in `FITS`.
- Reservations are a hold with a TTL on a spot **type**.
- EV charging is a feature on spots, a selector filter, and a decorator for energy fees.

</Step>
  <Step title="Tests">
    Cover lot full, an unknown ticket, the grace period, exact hour boundaries, the daily cap, and the observer firing. The injected clock makes all of them deterministic.
  </Step>
</Steps>

A few details worth pointing out:

- `HourlyPricing` charges every **started** hour: 61 minutes is 2 hours. The grace period is inclusive, so exactly 10 minutes is free.
- `DailyCap` charges whole days at the cap, then caps the remainder: 26 hours for a car is 150 + 40 = 190.
- `LowestFloorFirst` prefers a lower floor over a smaller spot type. `allocate.sql` orders by type first, then floor. Both are valid; pick one policy and make the SQL match the selector.

## Failure modes

| What breaks | Effect | Mitigation |
|---|---|---|
| Two gates allocate at the same moment | The same spot is assigned twice | One process: the event loop serialises it. Several servers: `SKIP LOCKED` in a transaction |
| Gate crashes after taking a spot, before printing the ticket | Spot leaked | Spot update and ticket insert in one transaction; a reconciliation job frees orphaned spots |
| Lost ticket | Can't compute the fee | Look up the open ticket by plate, or charge the daily maximum |
| Gate loses its network | Can't reach the central DB | A local lot service keeps working offline and syncs later |
| Payment declined | Driver stuck at the barrier | Nothing changes until payment succeeds; offer another method |

## Trade-offs

| Choice | Pros | Cons | Choose when |
|---|---|---|---|
| Free sets per type vs a linear scan | O(types) allocation | More state to keep consistent | Hundreds of spots or more |
| Strategy classes vs `if/else` | Swappable, testable rules | More files | Rules change often (they do) |
| In-memory vs DB as source of truth | Simple and fast | One process only | One gate controller; switch to the DB for several servers |
| Decorators vs one big pricing class | Rules compose freely | Order of wrapping matters | Several independent pricing rules |

<Callout kind="interview" title="What interviewers listen for">
Naming the patterns (strategy, decorator, observer) **and** why you used them; a concrete answer to "two gates, one spot"; and tests with an injected clock. Over-modelling (a class per spot size, a manager for every noun) costs more points than it earns.
</Callout>

## Follow-up questions

<FollowUps>
  <FollowUp q="How would you scale to 500 lots?">
    Each lot runs a local service, so the gates keep working if the WAN drops. It syncs tickets and payments to a central service whose database is sharded by `lot_id`. The availability API for apps reads aggregated counts that each lot pushes every few seconds.
  </FollowUp>
  <FollowUp q="How do you handle a lost ticket?">
    Tickets store the plate. The attendant looks up the open ticket by plate (automatically, with plate recognition, if available) and charges from the real entry time. Without a match, charge the posted maximum daily fee.
  </FollowUp>
  <FollowUp q="How would you add reservations?">
    Reserve a spot **type** for a time window rather than a specific spot, with a count per type and window. On arrival, convert the reservation into a normal allocation. Release no-shows after a grace TTL, and define an over-booking policy.
  </FollowUp>
  <FollowUp q="How would you add EV charging?">
    Add an `ev` feature to some spots, a selector filter (`needsCharger`), and an `EnergyFee` pricing decorator. No existing class changes, which is open/closed in practice.
  </FollowUp>
  <FollowUp q="Is take() really atomic in Node?">
    Yes, within one process: synchronous code isn't interleaved. With worker threads or several processes it isn't, so move allocation to the database (`SKIP LOCKED`) or to Redis (`SET NX` per spot).
  </FollowUp>
</FollowUps>
