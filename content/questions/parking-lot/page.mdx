<TLDR>
Model **ParkingLot → Floor → Spot**, hide spot choice, pricing and payment behind small strategies, and keep a **free set per spot type on each floor** so nothing scans. One Node process allocates atomically for free; across gate servers, the database locks a spot with `FOR UPDATE SKIP LOCKED`.
</TLDR>

New to low-level design? Start with [From requirements to classes](/lld/foundations/thinking-in-objects) and [SOLID](/lld/foundations/solid); the strategy and decorator in this answer are taught in [Swap behaviour](/lld/foundations/strategy-decorator).

## Clarifying questions

- How many floors and spots? (Decides whether a scan is fine.)
- Which vehicles fit which spots: may a bike take a compact spot?
- Pricing: hourly, flat, peak, a daily cap, a grace period?
- Pay at the exit gate or a pay station; card, cash or wallet?
- One lot (one process) or a chain (a distributed system)?

## Scale check

Five floors of 200 spots is **1,000 spots** and about 500 entries an hour, under one per second even at peak. One small process could run the lot, so the hard part is **correctness**: two gates must never hand out the same spot.

## Step-by-step answer

<Steps>
  <Step title="Use cases first">
    Park, quote, pay and exit, show availability. Every class must serve one.
  </Step>
  <Step title="Nouns become classes, verbs become methods">
    `Spot`, `Vehicle` and `Ticket` are thin data; behaviour lives in `ParkingLot`, `Floor` and the strategies. Fewer, sharper classes win: no `ParkingSpotManagerFactory`.
  </Step>
  <Step title="Relationships">
    Lot owns floors, floors own spots (composition); a ticket only **references** a spot and a vehicle.
  </Step>
  <Step title="Allocation without a scan">

`FITS` lists the spot types each vehicle may use, **smallest first**, so a bike never takes the large spot a truck needs:

```js
export const FITS = {
  bike: ['bike', 'compact', 'large'],
  car: ['compact', 'large'],
  truck: ['large'],
};
```

`take(types, accept)` pops the first free spot that passes `accept`. EV charging is a spot **feature** the selector filters on, not a subclass.

  </Step>
  <Step title="Pricing as a strategy">
    `fee(durationMs, vehicle)` is the whole interface. A daily cap, peak hours or a discount is a **decorator** around it, so rules combine without edits (open/closed). Inject the clock.
  </Step>
  <Step title="Payment flow">
    `quote(ticket)` → pay with any `PaymentMethod` → `exit(ticket, payment)`, which re-checks the amount, frees the spot and deletes the ticket. A failed payment changes nothing.
  </Step>
  <Step title="Concurrency">

One Node process runs `take()` without interleaving: atomic for free. Several gate servers need one statement that picks **and** locks a free row:

```sql
UPDATE spots SET ticket_id = $1, taken_at = now()
WHERE id = (SELECT id FROM spots WHERE ... AND ticket_id IS NULL
            LIMIT 1 FOR UPDATE SKIP LOCKED)
RETURNING id, floor;
```

Insert the ticket in the same transaction, or a crash leaks the spot.

  </Step>
  <Step title="Display boards">
    Observer: the lot emits `changed(floor)` after every park and exit, and boards re-read `available(type)`. The lot never knows boards exist.
  </Step>
  <Step title="Extensibility check">
    A new vehicle type is an enum value plus its `FITS` row. Reservations and EV charging are in the follow-ups.
  </Step>
  <Step title="Tests">
    Lot full, unknown ticket, grace period, exact hour boundaries, daily cap, observer firing: all deterministic with the injected clock.
  </Step>
</Steps>

## Persistence across gate servers

Only if the interviewer asks. Across gate servers the database is the truth: a spot is free while its `ticket_id` is NULL.

```sql
CREATE TABLE spots (
  id        text   PRIMARY KEY,                 -- '2-C14'
  lot_id    bigint NOT NULL,
  floor     int    NOT NULL,
  type      text   NOT NULL CHECK (type IN ('bike', 'compact', 'large')),
  features  text[] NOT NULL DEFAULT '{}',       -- 'ev', 'accessible'
  ticket_id uuid   UNIQUE,                      -- NULL means free
  taken_at  timestamptz
);
CREATE INDEX spots_free ON spots (lot_id, type, floor, id) WHERE ticket_id IS NULL;

CREATE TABLE tickets (
  id       uuid   PRIMARY KEY,
  lot_id   bigint NOT NULL,
  plate    text   NOT NULL,                     -- lets you find a lost ticket
  vehicle  text   NOT NULL,
  spot_id  text   NOT NULL REFERENCES spots (id),
  entry_at timestamptz NOT NULL DEFAULT now(),
  exit_at  timestamptz,
  fee      int
);
```

## Failure modes

| What breaks | Effect | Mitigation |
|---|---|---|
| Two gates allocate at once | Same spot twice | Event loop (one process); `SKIP LOCKED` in a transaction (several) |
| Gate crashes before printing the ticket | Spot leaked | Spot and ticket in one transaction; a reconciliation job frees orphans |
| Lost ticket | Can't compute the fee | Find the open ticket by plate, or charge the daily maximum |
| Gate loses its network | Can't reach the central DB | A local lot service works offline and syncs later |
| Payment declined | Driver stuck at the barrier | Nothing changes until payment succeeds; offer another method |

## Trade-offs

| Choice | Pros | Cons |
|---|---|---|
| Free sets per type vs a scan | O(types) allocation; pays off past hundreds of spots | More state to keep consistent |
| Strategy classes vs `if/else` | Swappable, testable rules (and rules change) | More files |
| In-memory vs DB as source of truth | Simple and fast for one gate controller | One process only |
| Decorators vs one pricing class | Independent rules compose freely | Wrapping order matters |

<Callout kind="interview" title="What interviewers listen for">
Strategy, decorator and observer **and** why; a concrete answer to "two gates, one spot"; tests with an injected clock. Over-modelling (a class per spot size, a manager per noun) costs points.
</Callout>

## Follow-up questions

<FollowUps>
  <FollowUp q="How would you scale to 500 lots?">
    A local service per lot keeps gates running offline and syncs to a central service sharded by `lot_id`.
  </FollowUp>
  <FollowUp q="How do you handle a lost ticket?">
    Find the open ticket by plate and charge from the real entry time; with no match, charge the daily maximum.
  </FollowUp>
  <FollowUp q="How would you add reservations?">
    Reserve a spot **type** per time window, not a specific spot, and release no-shows after a grace TTL (which needs an over-booking policy).
  </FollowUp>
  <FollowUp q="How would you add EV charging?">
    An `ev` spot feature, a `needsCharger` filter and an `EnergyFee` decorator: no existing class changes.
  </FollowUp>
  <FollowUp q="Is take() really atomic in Node?">
    Within one process, yes; across threads or processes, allocate in the database (`SKIP LOCKED`) or Redis (`SET NX` per spot).
  </FollowUp>
</FollowUps>
