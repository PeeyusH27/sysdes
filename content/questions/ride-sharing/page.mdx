<TLDR>
Drivers report a position every 4 seconds, 1.25M a second. **Overwrite** the latest one in memory, never in a database row. To match, search the rider's map cell and its 8 neighbours, rank by arrival time, and offer to **one driver at a time**.
</TLDR>

## Clarifying questions

- **Scale?** Drivers online at peak, rides a day, cities.
- **Freshness?** How old may a position be? Here, 4 s.
- **Matching?** Nearest car or shortest arrival time? One request at a time, or batches?
- **Offers?** How long to answer? One driver at a time, so nobody races.

## Capacity estimate

| Quantity | Calculation | Result |
|---|---|---|
| Location updates | 5M online drivers ÷ a fix every 4 s | **1.25M/s** |
| Ingest bandwidth | 1.25M/s × ~100 B | ≈ 125 MB/s |
| Latest positions in memory | 5M × ~200 B | ≈ **1 GB** |
| A database row per update | 1.25M/s × 100 B × 86,400 s | ≈ 10.8 TB/day |
| Rides | 20M/day ÷ 86,400 s | ≈ 230/s (~700/s at peak) |
| Matching searches | ~3 per ride | ≈ 2K/s at peak |
| Riders browsing the map | 2M open apps ÷ a refresh every 5 s | ≈ 400K/s reads |

For the cell numbers, take a city of roughly 1,000 km² with 100,000 drivers: about 70 per 1.2 km × 0.6 km cell, so 9 cells hold roughly 600. Matching is cheap. The **location write rate** drives the design. Only the latest fix matters and it fits in 1 GB, so overwrite it in memory. For map browsing, serve a per-cell snapshot cached for a few seconds.

## API

WebSocket messages: one socket per app, JSON frames with a `type` field.

| Direction | Message | Payload |
|---|---|---|
| Driver → server | `location` | `{ lat, lon, heading, speed, accuracy, ts }` every ~4 s |
| Driver → server | `status` | `{ online: true }` or `{ online: false }` |
| Server → driver | `offer` | `{ rideId, pickup, fare, etaS, expiresAt }` |
| Driver → server | `offer_reply` | `{ rideId, accept }` |
| Server → rider | `ride_update` | `{ rideId, state, driver, etaS }` |
| Server → rider | `driver_location` | `{ lat, lon, heading, ts }` while matched |

REST for the rest:

| Method | Path | Notes |
|---|---|---|
| GET | `/drivers/nearby?lat=&lon=` | Car markers for the map, from the per-cell cache |
| POST | `/fares/estimate` | `{ pickup, dropoff }` → `{ quoteId, fare, surge, expiresAt }` |
| POST | `/rides` | `{ quoteId, pickup, dropoff }` + `Idempotency-Key` → `201 { rideId, state: 'REQUESTED' }` |
| GET | `/rides/:id` | State, driver and ETA; called after every reconnect |
| POST | `/rides/:id/cancel` | Until the trip starts |

The idempotency key turns a double-tap into one ride. Check who the user is during the HTTP upgrade, as in the [chat design](/questions/chat).

## Data model

Rides are durable and low-volume: Postgres, sharded by city.

```sql
CREATE TABLE rides (
  id            uuid PRIMARY KEY,
  city          text   NOT NULL,
  rider_id      bigint NOT NULL,
  driver_id     bigint,
  state         text   NOT NULL CHECK (state IN ('REQUESTED', 'MATCHED', 'ARRIVING', 'IN_TRIP', 'COMPLETED', 'CANCELLED')),
  pickup        point  NOT NULL,                 -- (lon, lat)
  dropoff       point  NOT NULL,
  quote_id      uuid   NOT NULL,
  surge         numeric(3, 2) NOT NULL DEFAULT 1.00,
  fare_cents    int,
  idem_key      text   NOT NULL UNIQUE,          -- a double tap finds the first ride
  requested_at  timestamptz NOT NULL DEFAULT now(),
  matched_at    timestamptz,
  completed_at  timestamptz
);
-- A backstop for the matcher: at most one active ride per driver, whatever happens upstream.
CREATE UNIQUE INDEX one_active_ride_per_driver ON rides (driver_id)
  WHERE state IN ('MATCHED', 'ARRIVING', 'IN_TRIP');
```

Live driver state is soft and fast, so it lives in Redis, one key set per city.

| Key | Type | Purpose |
|---|---|---|
| `geo:{city}` | GEO (a sorted set) | Online drivers by position: `GEOADD` per fix, `GEOSEARCH` to match |
| `loc:DRIVER` | hash, `EX 15` | Latest fix; expires when the app goes quiet |
| `drv:DRIVER` | hash | `state` (AVAILABLE, OFFERED, ON_TRIP); compare-and-set only |
| `ride:RIDE` | pub/sub channel | The matched driver's fixes, for the rider's gateway |
| `cell:{city}:GEOHASH` | string, `EX 3` | Nearby-car snapshot for the map |

History goes to Kafka, keyed by driver id, then to object storage for analytics.

## Architecture

<Doodle name="cache" size={150} caption />

A driver's position is a sticky note: write the new one over the old one, in fast memory. Nothing waits on a database. Do the sum on finding drivers within 2 km:

|---|---|---|
| 500 (small town) | 500 checks | About 500 |
| 100,000 (big city) | 100,000 checks | About 600 |
| 5M (one pile) | 5M checks | About 600 |

## Step-by-step answer

<Steps>
<Step title="State the two hard parts">

"Locations are a firehose of overwrites. Assignments must happen exactly once." The first rules out a database write per update. The second rules out check-then-write while matchers race.

</Step>
<Step title="Ingest locations into memory">

A fix every 4 s over a WebSocket. Drop out-of-order fixes. One pipelined round trip updates Redis:

```js
await redis.multi()
  .geoAdd(`geo:{${city}}`, { longitude: lon, latitude: lat, member: id })
  .hSet(`loc:${id}`, { lat, lon, heading, ts })
  .expire(`loc:${id}`, 15)
  .exec();
```

`GEOADD` overwrites the old position, so a driver leaves the old cell automatically. History is batched to Kafka and nothing waits on it.

</Step>
<Step title="Index space with cells">

A geohash cuts the map into grid cells; a shared prefix means a shared cell.

| Precision | Cell size at the equator |
|---|---|
| 5 | 4.9 km × 4.9 km |
| 6 | 1.2 km × 0.6 km |
| 7 | 153 m × 153 m |
| 8 | 38 m × 19 m |

Cells have **edges**: a rider near one is closer to the next cell than to most of their own. So read the 8 neighbours too. Redis does:

```bash
GEOSEARCH geo:{sf} FROMLONLAT -122.41 37.7749 BYRADIUS 2 km ASC COUNT 20 WITHDIST
```

</Step>
<Step title="Partition by city">

Rides never cross cities, so the city is the shard. Huge cities split by zone.

</Step>
<Step title="Find and rank candidates">

Search ring by ring: the rider's cell, then the 8 around it, then the 16 around those. Stop once the best are nearer than the next ring. Skip busy drivers and expired records, then rank the best 10 by ETA. Across a river, the closest car is often not the quickest.

</Step>
<Step title="Offer behind a compare-and-set">

Driver state runs `AVAILABLE → OFFERED → ON_TRIP`. Reserve **before** offering, so two matchers can't both send an offer:

```lua
-- KEYS[1] = drv:<id>; ARGV: expected state, expected ride ('' = any), new state, new ride, reservation ms ('' = none)
local cur = redis.call('HMGET', KEYS[1], 'state', 'rideId', 'offerUntil')
local t = redis.call('TIME')
local now = t[1] * 1000 + math.floor(t[2] / 1000)
local state = cur[1]
if state == 'OFFERED' and tonumber(cur[3] or 0) < now then state = 'AVAILABLE' end  -- an expired reservation is free
if state ~= ARGV[1] or (ARGV[2] ~= '' and cur[2] ~= ARGV[2]) then return 0 end
redis.call('HSET', KEYS[1], 'state', ARGV[3], 'rideId', ARGV[4], 'offerUntil', ARGV[5] == '' and 0 or now + tonumber(ARGV[5]))
return 1
```

The loser gets 0 and tries its next candidate.

</Step>
<Step title="Declines, timeouts and crashes">

The driver has 10–15 s to answer, and silence is a decline. The next candidate gets the offer. If none is left, widen the search. A crashed matcher's reservation simply expires.

</Step>
<Step title="Ride lifecycle in the database">

`REQUESTED → MATCHED → ARRIVING → IN_TRIP → COMPLETED`, or `CANCELLED`. A conditional update means a ride can't get two drivers:

```sql
UPDATE rides SET state = 'MATCHED', driver_id = $2, matched_at = now()
WHERE id = $1 AND state = 'REQUESTED';
```

The unique index on active rides is the last backstop.

</Step>
<Step title="Real time to the rider">

Once matched, the rider's gateway listens to `ride:RIDE` for that driver's fixes. The client glides the marker to each new fix, and calls `GET /rides/:id` first after a reconnect. See [polling, SSE and WebSockets](/deep-dives/polling-sse-websockets).

</Step>
<Step title="Fare estimate and surge">

Every minute, per cell: demand over supply becomes a capped, smoothed multiplier. The `quoteId` locks the fare for a few minutes.

</Step>
</Steps>

## Failure modes

| What breaks | Effect | Mitigation |
|---|---|---|
| A stadium empties (hot cell) | One shard and matcher overload | Smaller cells; batch matching; surge |
| A driver's app goes quiet | Offers to a ghost | `loc:` expires in 15 s |
| Matcher crashes mid-offer | Driver stuck in `OFFERED` | Reservation TTL; another matcher takes over |
| Accept after the offer expired | Driver thinks the ride is theirs | Confirm is a compare-and-set; "offer expired" |
| A region goes down | Its cities stop matching | Geo DNS failover; rebuild the index in ~4 s |
| GPS jitter | Car jumps streets | Drop bad fixes; snap to roads; glide |
| Update rate outgrows Redis | Positions go stale | Shard by city and zone; drop old fixes |

## Trade-offs

| Choice | Gain | Cost |
|---|---|---|
| Geohash cells | Plain strings; Redis GEO built in | Must read neighbours |
| H3 hexagons | Equidistant neighbours | Needs a library; no Redis GEO |
| One offer at a time | Simple; nearest first | Each decline costs up to 15 s |
| Push to riders, not poll | Fresh within a second | A socket per rider |

## Follow-up questions

<FollowUps>
  <FollowUp q="How does surge pricing work?">
    Demand over supply per cell, mapped to a capped multiplier and smoothed so it doesn't flap. It also tells drivers where to go.
  </FollowUp>
  <FollowUp q="How would pooled rides change matching?">
    Candidates are cars with free seats, scored by the detour a new rider adds. Batch requests for a few seconds to pair riders.
  </FollowUp>
  <FollowUp q="What does the ETA service do?">
    It holds the road map with live speeds and answers shortest-route questions in milliseconds. It takes one pickup and ten drivers in one call.
  </FollowUp>
  <FollowUp q="How do you scale to 100 cities?">
    Each city is a shard in a nearby region. Giant cities split into zones. Accounts and payments stay global, off the hot path ([sharding strategies](/deep-dives/sharding-strategies)).
  </FollowUp>
  <FollowUp q="How do you guarantee a driver is never offered two rides?">
    One authority per driver, changed only by compare-and-set, with expiring reservations. The unique index on active rides is the last defence.
  </FollowUp>
</FollowUps>
