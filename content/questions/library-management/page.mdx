<TLDR>

</TLDR>

## Public interface

| Call | Returns | Notes |
|---|---|---|
| `borrow(member, isbn, day)` | A loan, or a reason | `LIMIT_REACHED`, `NO_COPY`, `UNKNOWN` |
| `returnItem(loan, day)` | The fine in cents | Hands the copy to the queue first |
| `reserve(member, isbn)` | Place in the queue | Refused while a copy is free |
| `renew(loan, day)` | The new due day | Refused if overdue, waited for, or renewed twice |
| `search(text)` | ISBNs | Title or author contains it, or the ISBN matches |
| `sweep(day)` | | Overdue notices once, lapsed holds pass on |

## What it remembers

- `books`: ISBN → title, author, its copies and its queue of waiting members.
- Each copy: state, and who it is held for and until when.
- `loans`: copy, member, due day, renewals, open or closed.
- `members`: type, which gives the limit and the loan period.

## A copy's life

A copy is always in one state. Only the moves in the table are legal, and anything else is a bug that should fail loudly.

| From | Event | To |
|---|---|---|
| AVAILABLE | Member borrows it | LOANED |
| LOANED | Returned, nobody waiting | AVAILABLE |
| LOANED | Returned, someone waiting | HELD |
| HELD | Waiting member borrows it | LOANED |
| HELD | Hold lapses | AVAILABLE, or HELD for the next |
| LOANED | Reported lost | LOST |

A returned copy goes to the queue **before** it can become available. That one rule keeps the queue fair.

## Patterns, and when to skip them

**State** keeps the legal moves in one table. **Strategy** turns days late into cents, one policy per member type, and a **Decorator** wraps a policy in a cap or a grace period without editing it. **Observer** sends "ready" and "overdue" to email or SMS, so the library never knows who listens.

**Skip the rest.** A subclass per member type is data pretending to be code, so use a small record of limits. A `FineCalculatorFactory` for two policies, or a `LibraryManager` that does everything, loses points. Keep one `Library` as the entry point.

## The last copy

Two members borrow the last copy in the same instant. If the code checks "is it free?" and then sets "loaned" as two steps, both pass the check.

- **Make it one step.** One lock around the change is the honest first answer. In a database it is one conditional update, `SET state = 'LOANED' WHERE id = ? AND state = 'AVAILABLE'`, then checking that a row changed.
- **Check the member limit in the same step**, or two quick borrows slip past it.
- **Tell listeners after releasing the lock**, so a slow email never blocks a borrow.
- **Scale up later** with a lock per title, not one for the whole library.

## Failure modes

| What breaks | Effect | Mitigation |
|---|---|---|
| Check then write | One copy loaned twice | One atomic step |
| Returned copy goes to AVAILABLE first | A walk-in jumps the queue | Release to the queue first |
| Hold never expires | An absent member blocks others | Deadline, then pass on |
| Overdue notice every sweep | Members get spammed | A notified flag per loan |
| Fine as a float | Cents drift | Integer cents |

## Trade-offs

| Choice | Pros | Cons |
|---|---|---|
| One lock vs lock per title | Simple and correct | Contention at scale |
| Member type as data vs subclass | No hierarchy to grow | Odd rules need code |
| Hold with a deadline vs no hold | Fair to the queue | A sweep and a notice |
| Queue on the book vs Reservation class | Less code | No place for per-reservation data |

## Follow-up questions

<FollowUps>
  <FollowUp q="How would you add another fine rule?">
    Write a new `FinePolicy` and register it for a member type. A weekend discount wraps an existing policy as a decorator. The library does not change.
  </FollowUp>
  <FollowUp q="How would you support many branches?">
    A `Branch` owns copies, and the title and the queue stay global. A return at another branch is a transfer, and a hold names the branch to collect from.
  </FollowUp>
  <FollowUp q="How do you handle a lost book?">
    Move the copy to LOST, close the loan, and charge a replacement fee from a policy. LOST has no way out, so it can never be loaned again.
  </FollowUp>
  <FollowUp q="How would you make search fast?">
    Keep an inverted index from words in titles and authors to ISBNs, and a map for exact ISBNs. A search service takes over at scale.
  </FollowUp>
  <FollowUp q="How would you send reminders three days before the due date?">
    The daily sweep emits a `dueSoon` event for loans due within three days. Listeners decide to send email or SMS.
  </FollowUp>
</FollowUps>
