<TLDR>
A **state machine** in disguise: four states and a table that gives every (state, event) pair one outcome. Money stays in **integer cents** and in **escrow** until the drop sensor confirms; change comes from a **bounded DP** over the coins in the tubes, and no change means no sale.
</TLDR>

A **low-level design** (LLD) question with two tests: spot the state machine in the first minute, and handle money exactly. Most points are lost on change-making and on the gap between "motor on" and "item in the tray".

## Clarifying questions

- Coins only, or notes and cards? (Cards add authorize and capture.)
- Is change paid from the machine's own tubes? (Then change can fail.)
- After SOLD OUT, does the customer keep their credit?
- Does a drop sensor confirm the item fell? What if it sticks?
- One machine, or a monitored fleet (HLD)?

## Capacity estimate

| Quantity | Estimate |
|---|---|
| Slots | 6 rows × 5 = **30**, ~10 items each: 300 items when full |
| Sales | A busy office machine: about **300 a day** |
| Events per sale | About 5: three coins, a select, the drop sensor |
| Events per day | 300 × 5 = **1,500**, one every 36 s over 15 hours |
| Telemetry | 1,500 × ~100 bytes ≈ 150 KB per day |

A microcontroller copes easily, so the hard part is **correctness**: one wrong transition hands out a free cola or swallows a dollar.

## API

Every input is one event for `machine.send(event)`.

| Event | Accepted in | Outcome |
|---|---|---|
| `coin` (100, 25, 10, 5) | Idle, HasMoney | Into escrow; elsewhere it drops to the cup |
| `select(code)` | HasMoney | Dispense, SOLD OUT, "insert 15¢ more", or refund if no change |
| `cancel` | HasMoney | Refund the escrowed coins |
| `dropped`, `dropFailed` | Dispensing | Drop sensor: commit, or refund |
| `service` | Idle, HasMoney, OutOfService | Toggle out of service (refunds credit first) |
| `restock(code, n)`, `refill(coins)` | Idle, OutOfService | Admin: never mid-purchase |
| events `transition`, `sale`, `returned`, `rejected` | | For display, telemetry and persistence |

## Data model

- `Inventory.slots`: slot code → `Slot { code, product, price, count, capacity }`, prices in integer cents.
- `CoinBox.counts`: coins per denomination in the tubes, e.g. `{ 100: 2, 25: 40, 10: 50, 5: 50 }`.
- `escrow`: coins inserted for this purchase, still the customer's.
- `pending`: the sale between "motor on" and the drop sensor: `{ code, price, change }`.
- `state`: one of four names.

Persist `state`, `escrow` and `pending` on every transition, so a power cut can't forget credit. A fleet uploads events to the table shown.

```sql
CREATE TABLE vend_events (
  machine_id text        NOT NULL,
  seq        bigint      NOT NULL,          -- per machine: re-sent batches are idempotent
  at         timestamptz NOT NULL,
  type       text        NOT NULL,          -- 'sale', 'refund', 'rejected', 'jam', 'restock'
  slot       text,
  amount     int,                           -- cents, never a float
  PRIMARY KEY (machine_id, seq)
);
```

## State transition table

Thirty-two cells, one outcome each. ✕ means **rejected**: nothing changes, and a refused coin drops to the return cup.

| Event | Idle | HasMoney | Dispensing | OutOfService |
|---|---|---|---|---|
| **coin** | escrow → HasMoney | escrow, stay | ✕ | ✕ |
| **select** | ✕ insert money first | sale → Dispensing¹ | ✕ | ✕ |
| **cancel** | ✕ | refund → Idle | ✕ too late | ✕ |
| **dropped** | ✕ | ✕ | commit → Idle | ✕ |
| **dropFailed** | ✕ | ✕ | refund → Idle | ✕ |
| **service** | → OutOfService | refund → OutOfService | ✕ | → Idle |
| **restock** | apply | ✕ | ✕ | apply |
| **refill** | apply | ✕ | ✕ | apply |

¹ No possible change: refund, back to Idle. Sold out or short credit: stay in HasMoney.

**Sold out belongs to a slot, not the machine**: the other 29 slots still sell, so SOLD OUT is a message and the customer keeps their credit. A table beats nested `if/else` because a missing cell is a rejection by default, and a test can loop over all 32 pairs.

## Step-by-step answer

<Steps>
  <Step title="Events first">
    Coin, slot button, cancel, drop sensor (dropped or not), service key, restock, refill. Keypad, coin mech and sensor all feed **one queue**.
  </Step>
  <Step title="States">
    **Idle**, **HasMoney**, **Dispensing**, **OutOfService**. Dispensing is a real state, not a step inside `select()`: it waits for the sensor and refuses everything else.
  </Step>
  <Step title="The State pattern as a table">

Each state object maps the events it accepts to the next state; anything else is rejected and changes nothing.

```js
hasMoney: {
  select: (m, { code }) => {
    const slot = m.inventory.get(code);
    if (slot.soldOut) return no(`${code} is sold out`);
    const credit = sum(m.escrow);
    if (credit < slot.price) return no(`Insert ${slot.price - credit}¢ more`);
    const change = makeChange(credit - slot.price, m.box.with(m.escrow));
    if (!change) { m.refund('exact change only'); return 'idle'; }
    m.pending = { code, price: slot.price, change };
    return 'dispensing';
  },
```

Every rejection comes **before** any mutation, so nothing half-applies.

  </Step>
  <Step title="Money is integer cents">
    `0.1 + 0.2` is `0.30000000000000004` in floating point. A cola costs `65`, not `0.65`.
  </Step>
  <Step title="Escrow, then commit">
    Coins sit in `escrow`; select only reserves the change. `dropped` moves escrow into the tubes, pays the change and decrements the slot **exactly once**; cancel and `dropFailed` return the same coins. Invariant: escrow + tubes + coins paid out = opening float + coins inserted + refills.
  </Step>
  <Step title="Making change">

Greedy (largest coin first) is optimal only with unlimited coins of a canonical system like 100/25/10/5. Owe 30¢ from one 25¢ and three 10¢, and greedy takes the 25¢, then needs a missing 5¢. A bounded DP over the real counts finds 10¢ + 10¢ + 10¢:

```js
for (const d of denoms) {                     // best[a]: fewest coins for amount a
  for (let a = 0; a <= amount; a++)
    for (let j = 0; j <= counts[d] && j * d <= a; j++)
      if (best[a - j * d] + j < next[a]) { next[a] = best[a - j * d] + j; pick[a] = j; }
}
```

Microseconds per sale. Include the escrow: the customer's own quarter can be their change.

  </Step>
  <Step title="No change, no sale">
    DP returns `null`? Refuse, refund, back to Idle. **EXACT CHANGE ONLY** lights when tubes run low, but the DP check is the real guard.
  </Step>
  <Step title="One event at a time">
    `send()` queues events and drains them in order, so an event sent mid-transition (by the display, or an async card terminal) waits its turn and never sees half-updated state.
  </Step>
  <Step title="Payment methods as a strategy">
    `PaymentMethod` has `credit()`, `commit(price)` and `refund()`. Coins use the escrow; a card **authorizes** at select, **captures** on `dropped` and **voids** on `dropFailed` or cancel. The table doesn't change.
  </Step>
  <Step title="Tests">
    Loop over all 32 pairs asserting rejections change nothing; add the greedy counterexample, a brute-force DP check, the no-change refund, the failed drop, and thousands of random events with the money invariant checked after each.
  </Step>
</Steps>

## Failure modes

| What breaks | Effect | Mitigation |
|---|---|---|
| Item stuck in the spiral | Paid, got nothing | No beam break in 2 s: retry once, then `dropFailed` refunds and flags the slot |
| Power cut mid-purchase | Lost credit or a double vend | Persist every transition; booting in Dispensing refunds unless the sensor logged a drop |
| Coin jams in the acceptor | Coins swallowed | Credit only after the validator confirms; a jam sensor goes OutOfService |
| Counterfeit coin or washer | Free products | Validator checks size, weight and metal; unknown coins drop to the cup |
| Change tubes run low | Can't pay change | DP check, refuse and refund; EXACT CHANGE ONLY; low-coins alert |
| Button bounce, two buttons at once | Double vend | One event queue; Dispensing rejects select; keypad debounce |

## Trade-offs

| Choice | Pros | Cons |
|---|---|---|
| Table or state objects vs `switch` | Every cell visible; unlisted means rejected | More structure for two or three states |
| State classes vs a plain table | Per-state fields or timers | More boilerplate |
| Bounded DP vs greedy | Finds change whenever it exists, even with low tubes | A little more code |
| Escrow vs a credit number | Exact refunds; commit on a confirmed drop | Tracks coins, not a total |
| Return the same coins vs equal value | No change-making on refund | Needs an escrow tray (most have one) |

<Callout kind="interview" title="What interviewers listen for">
"This is a state machine" early; one outcome in **every** cell; rejections that change nothing; integer cents, escrow until the drop, and the greedy counterexample. A class per coin or a `SoldOutState` costs points.
</Callout>

## Follow-up questions

<FollowUps>
  <FollowUp q="How would you add card payments?">
    A `CardPayment` behind `PaymentMethod`: authorize on select, capture on `dropped`, void otherwise, with the terminal's reply as one more queued event.
  </FollowUp>
  <FollowUp q="How would you run a fleet of 10,000 machines?">
    Machines work offline and upload event logs keyed by a per-machine sequence number, so re-sends are idempotent; the centre plans restocks and pushes versioned prices, applied only when Idle.
  </FollowUp>
  <FollowUp q="How would you support dynamic pricing?">
    A `PricingStrategy` fed by pushed config, with the price locked into `pending` at select so a mid-purchase change can't alter it.
  </FollowUp>
  <FollowUp q="How would you add a buy-2 combo?">
    Make `pending` a **basket**: each select adds a slot, each `dropped` commits one item, and a failed item refunds its share of the combo price.
  </FollowUp>
  <FollowUp q="How do you test it?">
    Table tests over all 32 pairs plus long random runs asserting the money invariant and "stock drops once per sale"; nothing random in the core, so failures reproduce.
  </FollowUp>
</FollowUps>
