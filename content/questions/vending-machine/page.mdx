A **low-level design** (LLD) question with two tests: spot the state machine fast, and handle money exactly.

New to this? Read [State machines and observers](/lld/foundations/state-observer) first.

## Clarifying questions

- Coins only, or notes and cards?
- Is change paid from the machine's own tubes? (Then it can fail.)
- After SOLD OUT, does the customer keep their credit?
- Does a sensor confirm the item fell?
- One machine, or a fleet?

## Scale check

A busy machine sees one event every 36 seconds. A tiny chip copes. The hard part is **correctness**: one wrong transition hands out a free cola or swallows a dollar.

## Public interface

Every input is one event for `machine.send(event)`.

| Event | Accepted in | Outcome |
|---|---|---|
| `coin` (100, 25, 10, 5) | Idle, HasMoney | Into escrow; elsewhere it drops to the cup |
| `select(code)` | HasMoney | Dispense, SOLD OUT, "insert 15¢ more", or refund if no change |
| `cancel` | HasMoney | Refund the escrowed coins |
| `dropped`, `dropFailed` | Dispensing | Drop sensor: commit, or refund |
| `service` | Idle, HasMoney, OutOfService | Toggle out of service (refunds credit first) |
| `restock(code, n)`, `refill(coins)` | Idle, OutOfService | Admin: never mid-purchase |
| events `transition`, `sale`, `returned`, `rejected` | | For display, telemetry and persistence |

## What it remembers

- `Inventory.slots`: slot code → product, price (cents), count.
- `CoinBox.counts`: coins per denomination, e.g. `{ 100: 2, 25: 40, 10: 50, 5: 50 }`.
- `escrow`: coins for this purchase, still the customer's.
- `pending`: the sale between "motor on" and the drop sensor.
- `state`: one of four names.

Save `state`, `escrow` and `pending` on every transition, so a power cut can't forget credit.

## State transition table

Thirty-two cells, one outcome each. ✕ means **rejected**: nothing changes.

| Event | Idle | HasMoney | Dispensing | OutOfService |
|---|---|---|---|---|
| **coin** | escrow → HasMoney | escrow, stay | ✕ | ✕ |
| **select** | ✕ insert money first | sale → Dispensing¹ | ✕ | ✕ |
| **cancel** | ✕ | refund → Idle | ✕ too late | ✕ |
| **dropped** | ✕ | ✕ | commit → Idle | ✕ |
| **dropFailed** | ✕ | ✕ | refund → Idle | ✕ |
| **service** | → OutOfService | refund → OutOfService | ✕ | → Idle |
| **restock** | apply | ✕ | ✕ | apply |
| **refill** | apply | ✕ | ✕ | apply |

¹ No possible change: refund, back to Idle. Sold out or short credit: stay in HasMoney.

**Sold out belongs to a slot, not the machine.** The customer keeps their credit.

**Is a table worth it?** A toy with two states and two events is four cells, so one `if` is fine. Here, three flags (`hasMoney`, `dispensing`, `broken`) give 8 combinations and only 4 are legal. Miss one guard and a double press of `select` mid-drop hands out a second cola. A table shows every cell, a missing cell means rejected, and a test can loop over all 32 pairs.

## Step-by-step answer

<Steps>
  <Step title="Events first">
    Coin, select, cancel, drop sensor, service, restock, refill.
  </Step>
  <Step title="States">
    **Idle**, **HasMoney**, **Dispensing**, **OutOfService**. Dispensing waits for the sensor and refuses everything else.
  </Step>
  <Step title="The State pattern as a table">

Each state maps the events it accepts to the next state. Anything else is rejected.

```js
hasMoney: {
  select: (m, { code }) => {
    const slot = m.inventory.get(code);
    if (slot.soldOut) return no(`${code} is sold out`);
    const credit = sum(m.escrow);
    if (credit < slot.price) return no(`Insert ${slot.price - credit}¢ more`);
    const change = makeChange(credit - slot.price, m.box.with(m.escrow));
    if (!change) { m.refund('exact change only'); return 'idle'; }
    m.pending = { code, price: slot.price, change };
    return 'dispensing';
  },
```

Every rejection comes before any change, so nothing half-applies.

  </Step>
  <Step title="Money is integer cents">
    `0.1 + 0.2` is `0.30000000000000004`. A cola costs `65`, not `0.65`.
  </Step>
  <Step title="Escrow, then commit">
    Coins sit in `escrow`. `dropped` moves them into the tubes, pays the change and takes one item off the slot, **once**. Cancel and `dropFailed` return the same coins.
  </Step>
  <Step title="Making change">

Greedy (biggest coin first) fails when coins run low. Owe 30¢ from one 25¢ and three 10¢: greedy takes the 25¢, then needs a missing 5¢. A **bounded DP** over the real counts finds 10 + 10 + 10:

```js
for (const d of denoms) {                     // best[a]: fewest coins for amount a
  for (let a = 0; a <= amount; a++)
    for (let j = 0; j <= counts[d] && j * d <= a; j++)
      if (best[a - j * d] + j < next[a]) { next[a] = best[a - j * d] + j; pick[a] = j; }
}
```

Include the escrow: the customer's own quarter can be their change.

  </Step>
  <Step title="No change, no sale">
    DP returns `null`? Refuse, refund, back to Idle.
  </Step>
  <Step title="One event at a time">
    `send()` runs events in order, so none sees half-updated state.
  </Step>
  <Step title="Payment methods as a strategy">
    `PaymentMethod` has `credit()`, `commit(price)` and `refund()`. A card authorizes at select, captures on `dropped`, voids otherwise. The table doesn't change.
  </Step>
  <Step title="Tests">
    Loop over all 32 pairs. Add the greedy counterexample, the no-change refund and the failed drop.
  </Step>
</Steps>

## Telemetry for a fleet

Only if asked. Each machine uploads its events, and `seq` makes a re-sent batch safe.

```sql
CREATE TABLE vend_events (
  machine_id text        NOT NULL,
  seq        bigint      NOT NULL,          -- per machine: re-sent batches are idempotent
  at         timestamptz NOT NULL,
  type       text        NOT NULL,          -- 'sale', 'refund', 'rejected', 'jam', 'restock'
  slot       text,
  amount     int,                           -- cents, never a float
  PRIMARY KEY (machine_id, seq)
);
```

## Failure modes

| What breaks | Effect | Mitigation |
|---|---|---|
| Item stuck | Paid, got nothing | No drop in 2 s: retry once, then refund and flag the slot |
| Power cut mid-purchase | Lost credit or double vend | Save every transition; refund on boot unless a drop was logged |
| Coin jams | Coins swallowed | Credit only after the validator confirms |
| Fake coin | Free products | Validator checks size and weight; unknown coins drop to the cup |
| Tubes run low | Can't pay change | DP check, refuse and refund; low-coins alert |
| Two buttons at once | Double vend | One event queue; Dispensing rejects select |

## Trade-offs

| Choice | Pros | Cons |
|---|---|---|
| Table vs `switch` | Every cell visible | More structure |
| Bounded DP vs greedy | Finds change when it exists | More code |
| Escrow vs a credit number | Exact refunds | Tracks coins |
| Same coins vs equal value | No change-making on refund | Needs an escrow tray |

## Follow-up questions

<FollowUps>
  <FollowUp q="How would you add card payments?">
    A `CardPayment` behind `PaymentMethod`: authorize on select, capture on `dropped`, void otherwise.
  </FollowUp>
  <FollowUp q="How would you run a fleet of 10,000 machines?">
    Machines work offline and upload event logs numbered per machine, so re-sends are safe. The centre plans restocks and pushes prices, applied only when Idle.
  </FollowUp>
  <FollowUp q="How would you support dynamic pricing?">
    A `PricingStrategy` fed by config. Lock the price into `pending` at select so it can't change mid-purchase.
  </FollowUp>
  <FollowUp q="How would you add a buy-2 combo?">
    Make `pending` a **basket**. Each `dropped` commits one item. A failed item refunds its share.
  </FollowUp>
  <FollowUp q="How do you test it?">
    Table tests over all 32 pairs, plus long random runs that check the money adds up. Nothing random in the core, so failures repeat.
  </FollowUp>
</FollowUps>
