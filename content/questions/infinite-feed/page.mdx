## Clarifying questions

- **Order and page size?** Newest first, or ranked. About 20 per page.
- **Item height?** Variable heights mean measuring each row.
- **Session length?** Thousands of posts means you need to limit what is on screen.
- **Back and new posts?** Back should land on the same post, with no refetch. New posts show as a banner.
- **SEO?** Server-render page one.

## Answer with RADIO

<Doodle name="index" size={150} caption />

Don't ask for "page 2". You read page 1, then 5 new posts arrive, and page 2 starts with 5 posts you already saw. Ask for "posts older than the last one I have", like a bookmark. That is a **cursor**. Offsets are fine for a small, static list where people jump to page 37. Structure a frontend answer as **R**equirements (done), **A**rchitecture, **D**ata model, **I**nterface and **O**ptimizations.

### Architecture

- **FeedPage** (server) fetches page one for first paint and crawlers.
- **Feed** (client) continues from `nextCursor`, and renders virtualized rows, a loader row and a **NewPostsBanner**.
- **Post** is an `article` with its image box reserved by `width` and `height`.
- **Data layer:** a TanStack Query infinite query, or the `useInfiniteFeed` hook.

### Data model

```js
// Query cache: one entry per page, in order
{ pages: [{ data: Post[], nextCursor: 'p_140' }, { data: Post[], nextCursor: null }] }

// Derived for rendering
items = pages.flatMap(p => p.data)
status: 'idle' | 'loading' | 'error' | 'done'

// Scroll anchor in sessionStorage: the first visible post and its offset
{ id: 'p_87', top: 120 }
```

### Interface

```http
GET /api/feed?cursor=p_160&limit=20
→ 200 { "data": [ …20 posts ], "nextCursor": "p_140" }      (nextCursor is null on the last page)

GET /api/feed/new-count?after=p_200
→ 200 { "count": 12 }
```

`useInfiniteFeed(url, limit)` returns `{ items, status, loadMore, sentinel }`. The [API lesson](/learn/api-load-balancing) builds the cursor endpoint.

### Optimizations

- **Prefetch:** `rootMargin: '600px 0px'` starts the next page a screen early.
- **No layout shift:** reserve every image's box.
- **Small DOM:** virtualize, and drop old pages in very long sessions.

## How to approach it

<Steps>
  <Step title="Clarify">
    Page size, ordering, item height, Back.
  </Step>
  <Step title="Choose the trigger">
    An IntersectionObserver on a sentinel, not scroll listeners.
  </Step>
  <Step title="Use cursors">
    They stay correct as new items arrive; page numbers don't.
  </Step>
  <Step title="Control the DOM">
    Virtualize, so rendering stays cheap.
  </Step>
  <Step title="Handle states">
    Skeletons, retry, end of list, restored scroll, accessibility.
  </Step>
</Steps>

## Step-by-step answer

<Steps>
  <Step title="Clarify">
    Then state the shape: a sentinel triggers cursor fetches, pages go in a cache, rows are virtualized.
  </Step>
  <Step title="Pick the trigger">
    Watch a 1 px sentinel after the last post. An IntersectionObserver costs nothing per frame. It reports only **changes**, so re-observe after each page in case a short page leaves the sentinel on screen.
  </Step>
  <Step title="Paginate with a cursor">
    With page numbers, 5 new posts at the top shift everything down 5, so the next page repeats 5. Deep offsets are slow too: `OFFSET 10000` reads and drops 10,000 rows to return 20. A cursor reads 20.

```sql
SELECT id, title, image, width, height
FROM posts
WHERE id < $1          -- the cursor: an index range scan, as fast on page 500 as on page 1
ORDER BY id DESC
LIMIT 21;              -- one extra row says whether another page exists
```
  </Step>
  <Step title="Guard the fetch">
    One request in flight, reset in `finally` so one failure can't freeze the feed. On error, show Retry rather than looping against a struggling server.
  </Step>
  <Step title="Virtualize">
    Render only the rows in view plus a few extra, in a container sized to the estimated total. 10,000 posts loaded, about 20 in the DOM.
  </Step>
  <Step title="Cache the pages">
    Back renders from memory with no request, and the saved anchor restores the same post.
  </Step>
  <Step title="Keep the layout stable">
    Reserve every image's box. Never insert posts above the reader: show "12 new posts ↑" instead.
  </Step>
  <Step title="Make it accessible">
    `role="feed"`, with each post a focusable `article` using `aria-posinset` and `aria-setsize` (-1 while the total is unknown). Let keyboard users reach the footer, or offer a "Load more" button.
  </Step>
</Steps>

<Callout kind="warning">
Don't virtualize a 50-item list: it breaks Ctrl+F and buys nothing.
</Callout>

## Failure modes

| What breaks | Effect | Mitigation |
|---|---|---|
| Fetch error | The feed stops | Reset `busy` in `finally`; a Retry button |
| Page shorter than the screen | Observer never fires again | Re-observe after each page |
| Fast scroll past the loader | Blank area | Extra rows, skeletons, bigger `rootMargin` |
| Images load late | Layout shift | Reserve the box |
| Very long session | Memory grows | Virtualize; `maxPages` |
| Unmount mid-request | Wasted work | Abort in cleanup |

## Trade-offs

| Choice | Gain | Cost |
|---|---|---|
| Virtualization, not a plain list | Constant DOM size | Breaks Ctrl+F; needs measuring |
| Infinite scroll, not "Load more" | Seamless | Footer unreachable |
| Cursor, not offset | Stable; fast deep pages | No jumping to page 37 |
| Bigger `rootMargin` | Next page ready sooner | Fetches unseen data |

## Follow-up questions

<FollowUps>
  <FollowUp q="How do you show new posts at the top?">
    Poll a cheap count endpoint every 30 s and show a banner. A tap scrolls up and refetches page one. Never shift content above the reader unasked.
  </FollowUp>
  <FollowUp q="How do you stop memory growing in a long session?">
    Virtualize (about 20 rows), and cap cached pages with `maxPages`.
  </FollowUp>
  <FollowUp q="What about SEO?">
    Server-render the first page and add real links to older pages. Infinite scroll sits on top as an enhancement.
  </FollowUp>
  <FollowUp q="What if items are deleted while the user is paginating?">
    A cursor by id stays stable: a deleted post isn't returned and nothing shifts.
  </FollowUp>
  <FollowUp q="What about bi-directional scrolling, like chat history?">
    Add a top sentinel. When adding older items above, add the change in height to `scrollTop`, or the content jumps.
  </FollowUp>
  <FollowUp q="How would you test the feed?">
    Mock `fetch` and fake the IntersectionObserver. Assert one request in flight, the right cursor, and Retry with no automatic loop.
  </FollowUp>
</FollowUps>
