<TLDR>
A **token bucket** per user, API key or IP, in Redis, updated by **one Lua script** on Redis's clock so the check is atomic across servers. The gateway answers `429` with `Retry-After`; if Redis dies, most endpoints fail open, login and OTP fail closed.
</TLDR>

## Choosing an algorithm

Five algorithms, one real question: how much burst do you allow?

| Algorithm | State per key | Behaviour |
|---|---|---|
| Fixed window | 1 counter | Simplest; bursts up to 2× the limit at window edges |
| Sliding log | Every timestamp | Exact, no bursts; memory grows with traffic |
| **Sliding window counter** | 2 counters | ~Exact, limited bursts; good for "N per minute" quotas |
| **Token bucket** | Tokens + timestamp | Exact average rate, bursts up to capacity; the API default |
| Leaky bucket | Queue | Smooth output, no bursts; adds queueing latency |

A token bucket holds up to `capacity` tokens, refills at `rate` per second, and spends one per request: bursts pass, the average holds. Fire a burst at it.

A fixed window resets on the minute, so a client can send the full limit just before the edge and again just after: **2× in a couple of seconds**. A sliding window counter weights the previous window by its overlap; burst on both sides of the boundary in the fixed-vs-sliding widget.

## API

The contract is mostly headers, from the IETF RateLimit header fields draft; the example shows a `429`.

| Header | When | Meaning |
|---|---|---|
| `RateLimit-Limit` | Every response | Bucket capacity (the burst size) |
| `RateLimit-Remaining` | Every response | Whole tokens left right now |
| `RateLimit-Reset` | Optional | Seconds until the bucket is full again |
| `Retry-After` | On `429` (and `503`) | Seconds to wait, from the token deficit |

```http
HTTP/1.1 429 Too Many Requests
RateLimit-Limit: 20
RateLimit-Remaining: 0
Retry-After: 1
Content-Type: application/json

{"error":"Too many requests"}
```

Internally, the gateway calls `check(key, ratePerSec, capacity)` and gets `{ ok, remaining, retryAfterMs }`.

## Data model

| Key | Holds | Expiry |
|---|---|---|
| `rl:<rule>:<id>` | Hash: `tokens` (float), `ts` (ms, Redis time) | Time to refill completely |
| `sw:<key>:<window>` | String: request count in that window | Two windows |

Rules live in config (the JSON), cached in each process; `plans` multiplies rate and capacity per tier, so one rule serves every plan.

```json
{
  "api":   { "ratePerSec": 5,   "capacity": 20, "key": "user", "failClosed": false },
  "login": { "ratePerSec": 0.1, "capacity": 5,  "key": "ip",   "failClosed": true },
  "plans": { "free": 1, "pro": 10 }
}
```

## Step-by-step answer

<Steps>
  <Step title="Identity">
    The user or API key first; the IP only for anonymous traffic, and loosely, since one campus or carrier NAT can hide thousands of people.
  </Step>
  <Step title="Algorithm">
    A token bucket (rate `r`, capacity `b`) by default; a sliding window counter for strict "100 per minute" billing quotas.
  </Step>
  <Step title="Where to enforce">
    Global limits at the gateway, where rejecting is nearly free; expensive operations (search, exports) inside the service. Client-side throttling is UX, not security.
  </Step>
  <Step title="State">
    The `rl:<rule>:<id>` hash, expiring after the full-refill time (`capacity / rate`), when it's full anyway.
  </Step>
  <Step title="Atomicity">

One Lua script reads, refills, takes and writes. Separate `GET` and `SET` from 50 servers race: two read "1 token left" and both spend it.

```lua
tokens = math.min(cap, tokens + math.max(0, now - ts) * rate / 1000)
if tokens >= 1 then tokens = tokens - 1; allowed = 1 end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
```

</Step>
  <Step title="Clock">
    `redis.call('TIME')` in the script: a server clock running 2 seconds fast can't mint tokens.
  </Step>
  <Step title="Response">
    `429` with `Retry-After` = `(1 − tokens) / rate`, and quota headers on every response so polite clients slow down early.
  </Step>
  <Step title="Failure policy">

- Normal endpoints fail open, to a per-instance local bucket.
- Login, OTP and payments fail closed (`503`).
- ioredis must **fail fast** (no offline queue, no retries, a 50 ms timeout), or the limiter becomes the outage.

</Step>
  <Step title="Rules and regions">
    Rules per plan and endpoint come from config, cached in process; regions are a follow-up.
  </Step>
  <Step title="Observability">
    Count allowed and limited per rule, watch script latency, alert on sudden 429 spikes (a client bug or an attack).
  </Step>
</Steps>

## Implementation

- The in-memory `TokenBucket` is the single-server answer and the Redis fallback: 3 quick requests drain a capacity-3 bucket, and the 4th waits 500 ms at 2 tokens per second.
- The Lua script fixes three classic bugs: Redis's clock, not the app server's; `HSET`, not the deprecated `HMSET`; a retry delay from the deficit, not a hard-coded 1.
- `middleware.js` keeps fallback buckets in the bounded `LRU` from the [caching lesson](/learn/caching), so a flood of keys can't exhaust memory.

## Failure modes

| What breaks | Effect | Mitigation |
|---|---|---|
| Redis down | No shared state | Fail fast; local fallback (open) or 503 (closed), per rule |
| Redis slow | Latency on every request | 50 ms timeout, then treat it as down |
| One key sends huge traffic | A hot Redis shard | A local pre-limiter for keys already over |
| App servers' clocks skewed | Wrong refills | Redis `TIME` inside the script |
| Millions of idle keys | Memory growth | `PEXPIRE` at the full-refill time |

## Trade-offs

| Choice | Pros | Cons |
|---|---|---|
| Central Redis vs local only | Accurate global limits | A hop and a dependency |
| Token bucket vs sliding window | Bursts, tiny state | Looser "per minute" |
| Fail open vs closed | Availability | Abuse during outages |
| Gateway vs in-service | Rejects early, cheaply | Blind to operation cost |

## Follow-up questions

<FollowUps>
  <FollowUp q="Per-IP or per-user limits, and what about shared NATs?">
    By user or key; per-IP only for anonymous traffic, and generous. For login, combine both.
  </FollowUp>
  <FollowUp q="How do you handle 1M distinct keys?">
    TTLs drop idle buckets at about two fields each; Redis Cluster scales it, since each single-key script lives in one slot.
  </FollowUp>
  <FollowUp q="How do you avoid clock skew between servers?">
    Read the time from Redis (`TIME`) inside the script.
  </FollowUp>
  <FollowUp q="How do you rate-limit globally across regions?">
    Give each region a fraction of the limit, or sync counters asynchronously and accept brief overshoot; strict global limits cost a cross-region round trip.
  </FollowUp>
  <FollowUp q="Rate limiting or load shedding?">
    Both: rate limiting is fairness per client; load shedding drops low-priority work from anyone when saturated.
  </FollowUp>
</FollowUps>
