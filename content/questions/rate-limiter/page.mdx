<TLDR>
Give each user a **token bucket** in Redis, updated by **one Lua script** so the check is atomic. Over the limit, the gateway answers `429`. If Redis dies, most endpoints keep working and login does not.
</TLDR>

## Choosing an algorithm

<Doodle name="sliding-window" size={150} caption />

Five algorithms, one real question: how much burst do you allow?

| Algorithm | State per key | Behaviour |
|---|---|---|
| Fixed window | 1 counter | Simplest; 2× bursts at the edges |
| Sliding log | Every timestamp | Exact; memory grows |
| **Sliding window counter** | 2 counters | Nearly exact; good for quotas |
| **Token bucket** | Tokens + time | Allows bursts; the API default |
| Leaky bucket | Queue | Smooth; adds delay |

Match the traffic to the algorithm:

| Traffic | Pick | Why |
|---|---|---|
| A page fires 20 calls at once | Token bucket | The burst passes, the average stays 5 a second |
| Paid quota of 100 a minute | Sliding window counter | No edge doubling |
| Calls to a fragile partner | Leaky bucket | Steady rate out |

A bucket refills at a steady rate. Each request spends a token. Bursts pass, the average holds. Fire a burst at it.

## API

The contract is mostly headers. Here is a `429`.

| Header | When | Meaning |
|---|---|---|
| `RateLimit-Limit` | Every response | Bucket capacity (the burst size) |
| `RateLimit-Remaining` | Every response | Whole tokens left right now |
| `RateLimit-Reset` | Optional | Seconds until the bucket is full again |
| `Retry-After` | On `429` (and `503`) | Seconds to wait, from the token deficit |

```http
HTTP/1.1 429 Too Many Requests
RateLimit-Limit: 20
RateLimit-Remaining: 0
Retry-After: 1
Content-Type: application/json

{"error":"Too many requests"}
```

The gateway calls `check(key, rate, capacity)` and gets `{ ok, remaining, retryAfterMs }`.

## Data model

| Key | Holds | Expiry |
|---|---|---|
| `rl:<rule>:<id>` | Hash: `tokens` (float), `ts` (ms, Redis time) | Time to refill completely |
| `sw:<key>:<window>` | String: request count in that window | Two windows |

Rules are cached config. `plans` scales them per tier.

```json
{
  "api":   { "ratePerSec": 5,   "capacity": 20, "key": "user", "failClosed": false },
  "login": { "ratePerSec": 0.1, "capacity": 5,  "key": "ip",   "failClosed": true },
  "plans": { "free": 1, "pro": 10 }
}
```

## Step-by-step answer

<Steps>
  <Step title="Identity">
    The user or key first. The IP only for anonymous traffic.
  </Step>
  <Step title="Algorithm">
    A token bucket by default. A sliding window counter for strict "100 per minute" quotas.
  </Step>
  <Step title="Where to enforce">
    Global limits at the gateway, where rejecting is cheap.
  </Step>
  <Step title="State">
    One hash per key, expiring once it is full.
  </Step>
  <Step title="Atomicity">

One Lua script reads, refills, takes and writes. A separate `GET` and `SET` would race: two servers read "1 token left" and both spend it.

```lua
tokens = math.min(cap, tokens + math.max(0, now - ts) * rate / 1000)
if tokens >= 1 then tokens = tokens - 1; allowed = 1 end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
```

</Step>
  <Step title="Clock">
    Use Redis's own `TIME`, so a fast server clock can't mint tokens.
  </Step>
  <Step title="Response">
    `429` with `Retry-After`, plus quota headers on every response.
  </Step>
  <Step title="Failure policy">

- Normal endpoints **fail open**, to a local bucket.
- Login, OTP and payments **fail closed** (`503`).
- **Fail fast**: a 50 ms timeout, no retries, or the limiter becomes the outage.

</Step>
  <Step title="Rules and regions">
    Rules per plan come from cached config.
  </Step>
  <Step title="Observability">
    Count allowed and limited calls. Alert on 429 spikes.
  </Step>
</Steps>

## Failure modes

| What breaks | Effect | Mitigation |
|---|---|---|
| Redis down | No shared state | Fail fast; local bucket (open) or 503 (closed) |
| Redis slow | Every request slows | 50 ms timeout, then treat as down |
| One key floods | A hot Redis shard | A local pre-limiter |
| Skewed clocks | Wrong refills | Redis `TIME` in the script |
| Millions of idle keys | Memory growth | Expire them |

## Trade-offs

| Choice | Pros | Cons |
|---|---|---|
| Central Redis vs local | Accurate global limits | A hop and a dependency |
| Token bucket vs sliding window | Bursts, tiny state | Looser "per minute" |
| Fail open vs closed | Stays up | Abuse during outages |
| Gateway vs in-service | Rejects early | Blind to cost |

## Follow-up questions

<FollowUps>
  <FollowUp q="Per-IP or per-user limits, and what about shared NATs?">
    By user or key. Per-IP only for anonymous traffic, and generous. For login, use both.
  </FollowUp>
  <FollowUp q="How do you handle 1M distinct keys?">
    Expiry drops idle buckets. Redis Cluster scales it, since each script touches one key.
  </FollowUp>
  <FollowUp q="How do you avoid clock skew between servers?">
    Read the time from Redis inside the script.
  </FollowUp>
  <FollowUp q="How do you rate-limit globally across regions?">
    Give each region a share, or sync counters later and accept a brief overshoot.
  </FollowUp>
  <FollowUp q="Rate limiting or load shedding?">
    Both. Rate limiting is fair per client. Load shedding drops low-priority work when overloaded.
  </FollowUp>
</FollowUps>
