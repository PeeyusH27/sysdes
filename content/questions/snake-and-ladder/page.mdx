<TLDR>
A **board** holds one map of jumps (a snake and a ladder are the same thing pointing different ways), and a **game** rolls, applies the ending rule, then applies one jump per turn. Make the **dice** and the **ending rule** strategies, and the game becomes easy to test and easy to change.
</TLDR>

A **low-level design** (LLD) question that looks like a toy. The marks come from how you handle the rules people argue about, and from keeping the dice swappable.

New to this? Read [Swap behaviour](/lld/foundations/strategy-decorator) first.

## Clarifying questions

- What happens if the roll goes past the last square: stay, finish, or bounce?
- Do jumps chain, so a ladder can end on a snake?
- Does a six give another turn? Is there a limit?
- How many players, and how big is the board?
- Real dice only, or fixed rolls for tests and demos?

## Public interface

| Call | Returns | Notes |
|---|---|---|
| `new Board(size, jumps)` | A board | Refuses a bad layout |
| `new Game(board, players, dice, rule, sixAgain)` | A game | Everyone starts at 0 |
| `game.play()` | A move result, or nothing | One roll by whoever is next |
| `game.on(listener)` | | Called after every move |
| `game.winner` | Name or nothing | Set when someone reaches the end |

## What it remembers

- `board.size` and `board.jumps`: square → square. Never changes after setup.
- `position`: player → square, with 0 meaning off the board.
- `turn`: an index into the players. `winner`: set once, and never cleared.

A move result is `player, roll, from, to` and an event: move, ladder, snake, stay or win.

## Patterns, and when to skip them

**Strategy** twice. The **dice** decide where a roll comes from. The **ending rule** decides what happens at the last square. Both are small and both change in real life. **Observer** lets a UI watch without the game knowing.

**Skip the rest.** A `Snake` class and a `Ladder` class with a shared base add nothing: a jump from 17 to 7 is a snake because 7 is less than 17. No `GameFactory`, no `BoardBuilder` for two numbers, no `Cell` object for every square.

## Rules to settle out loud

- **Overshoot**: *exact* (must land on the last square, else stay), *finish* (any roll that reaches it wins), or *bounce* (extra steps walk back).
- **Chains**: allow them and you need a loop check. The simpler rule is to refuse any layout where a jump lands on another jump's start.
- **Last square**: no jump may start there, or the winner could slide away.
- **Six**: the same player rolls again. State whether a refused move still earns it.

## Concurrency

One game has one writer at a time. Make `play` a single critical section: a lock around the whole turn, so two threads calling at once take turns and the same player never moves twice by accident. Different games share nothing and never wait for each other. For a server, give each game an owner (one thread, or one queue), and tell listeners after the turn is complete.

## Failure modes

| What breaks | Effect | Mitigation |
|---|---|---|
| Jumps form a loop | A turn never ends | Refuse chains at construction |
| Jump from the last square | The winner slides back | Refuse it up front |
| Overshoot unspecified | Players argue, tests flake | Pick a rule and test it |
| Two threads call play | A player moves twice | One lock around the turn |
| Unseeded dice in tests | Failures that never repeat | Inject fixed or seeded dice |

## Trade-offs

| Choice | Pros | Cons |
|---|---|---|
| One jump type vs Snake and Ladder classes | Less code, no duplicates | A little less literal |
| Rule as a strategy vs an enum and switch | New rules need no edits | An extra interface |
| Refuse chains vs follow them | No loops possible | Rules out fun layouts |
| Lock per game vs a global lock | Games run in parallel | A lock object per game |

"A snake and a ladder are the same thing." The overshoot rule asked about before coding. Dice injected for tests. A loop check or a ban on chains. No class per square.

## Follow-up questions

<FollowUps>
  <FollowUp q="How would you add a loaded dice?">
    A new `Dice` class that skews its roll. The game is unchanged, which is the point of passing the dice in.
  </FollowUp>
  <FollowUp q="How would you let a jump chain safely?">
    Follow jumps in a loop and keep the squares you have visited. If you see one twice, the layout loops, so refuse it at construction.
  </FollowUp>
  <FollowUp q="How would you support undo or replay?">
    Keep the list of move results. Replay by feeding the same rolls to a fresh game. Undo means going back one result.
  </FollowUp>
  <FollowUp q="How would you run thousands of games on a server?">
    Give each game one owner, a single thread or queue, so no locks are needed. Store only the rolls and the setup, and rebuild a game from them.
  </FollowUp>
  <FollowUp q="How would you test it?">
    Fixed dice for every rule and event, a seeded random game that must finish, and a table of invalid boards that must all be refused.
  </FollowUp>
</FollowUps>
